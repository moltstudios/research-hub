EIP-6963 · Standards Track: Interface · Final · 2023-05-01

EIP-6963 Multi-Injected Provider Discovery

Replace the broken window.ethereum race condition with an event-based protocol that lets every installed wallet announce itself. Users see their real wallets with real icons, real brand names, and deterministic selection.

Status Final (2023) Adoption Universal (MetaMask · Coinbase · Phantom · Rabby · Brave · Trust · Frame) Library All modern (wagmi v2 · web3.js · ethers v6 · viem) Priority P1 (Critical · Remes)
Section 1

The race condition nobody talks about

Since MetaMask injected window.ethereum in 2016, every wallet extension has targeted the same single object. Extensions load in unpredictable order — the last one to load wins, even if the user prefers the loser. This breaks multi-wallet users silently.

❌ Today (window.ethereum)
Last wallet wins
  • Unpredictable loading order
  • User has no control over which wallet is "active"
  • Wallets hack around it by delaying injection ("unfair competition")
  • Only one wallet usable at a time — barrier to entry for new wallets
  • DBL screens show "MetaMask" when Coinbase was actually loaded
  • Mobile wallets (WalletConnect-style) have no discovery at all
  • Nothing to fall back to when a wallet removes the property
✓ EIP-6963 (announce / request)
All wallets always visible
  • Deterministic discovery via DOM events
  • User picks wallet in dApp UI — never silent
  • UUID v4 per provider — no collisions
  • Each wallet ships its own icon + name + RDNS
  • Banker-grade trust: brand, not raw object ref
  • WalletConnect coexists with injected wallets
  • Backwards compatible with existing window.ethereum
Section 2

How it works: two events + two payloads

EIP-6963 is intentionally minimal — a request/announce dance across two window events. There is no global registry, no static API, no library lock-in. Every wallet that ships the spec fires eip6963:announceProvider. Every dApp that wants wallets fires eip6963:requestProvider. That's it.

1
dApp
Fire request
eip6963:requestProvider
Asks every wallet extension to re-announce. Idempotent — safe to call any time.
→
2
Wallets
Announce
eip6963:announceProvider
Each extension responds with its info: UUID, name, icon (data URI), RDNS, and the EIP-1193 provider handle.
→
3
dApp
Render UI
n wallets → n rows
Listen to announce events, deduplicate by UUID, render branded wallet rows, let the user pick.
→
4
dApp ↔ Wallet
EIP-1193
provider.request(...)
After the user picks, switch to the chosen wallet's EIP-1193 provider. Talk to it like any other injected wallet.

The reference implementation (full DApp side, ~30 lines)

// 1. Type & event names (from the spec) const REQUEST_EVENT = "eip6963:requestProvider"; const ANNOUNCE_EVENT = "eip6963:announceProvider"; // 2. In-memory registry, dedup'd by UUID let announceEvent = {}; const providers = new Map(); // 3. Listen once on every announce window.addEventListener(ANNOUNCE_EVENT, (event) => { const { info, provider } = event.detail; providers.set(info.uuid, { info, provider }); announceEvent = event; // expose for late listeners }); // 4. Kick off discovery window.dispatchEvent(new Event(REQUEST_EVENT)); // 5. Render — for every UUID, build a picker row with icon + name + RDNS for (const { info } of providers.values()) { renderWalletRow(info); // <img src=info.icon> {info.name} } // 6. User clicks → talk EIP-1193 async function selectWallet(uuid) { const { provider } = providers.get(uuid); const accounts = await provider.request({ method: "eth_requestAccounts" }); return { provider, accounts }; }
Section 3

The ProviderInfo payload (what each wallet sends)

Each announce event carries a single EIP6963ProviderDetail object — composed of info (metadata) and provider (the EIP-1193 handle). The four info fields are the entire schema.

FieldTypeSpec requirementWhy it matters
uuidstringMUST be RFC 4122 UUIDv4De-duplicates announcements. Two tabs, two wallets, no collisions. Stays stable across the lifetime of the page.
namestringHuman-readable local alias"MetaMask", "Coinbase Wallet", "Phantom", "Rabby" — the brand name the user recognizes.
iconstringMUST be RFC 2397 data URI · ≥96×96px · PNG/WebP/SVG · render via <img> (no SVG JS execution)The wallet's own logo. Self-contained. No CORS round-trip to a CDN.
rdnsstringReverse-DNS, e.g. io.metamask · com.coinbase.walletStable identifier across rebrands. The user-agent string of wallets. DApps SHOULD be defensive about imitation here.

Anatomy of a real announce event

{ info: { uuid: "0x21dca50c-4d4c-3202-9a35-3a2a7e8c5f1a", name: "MetaMask", icon: "data:image/svg+xml;base64,PHN2ZyB4bWxucz0i...", // 96×96 SVG, no JS rdns: "io.metamask" }, provider: /* EIP-1193 compatible object with .request(), .on(), .removeListener() */ } // Detail.dispatchEvent fires as a CustomEvent: window.dispatchEvent(new CustomEvent("eip6963:announceProvider", { detail }));

Section 7

Drop-in library wrappers — most projects shouldn't write the protocol themselves

The two-event dance is short, but production wallets ship better wrappers. Pick by stack:

wagmi v2

React + viem. injected() connector auto-discovers all EIP-6963 wallets. Zero config.

import { injected } from "@wagmi/connectors"; connectors: [ injected({ shimDisconnect: true }), // And, if you want WalletConnect: walletConnect({ projectId, showQrModal: true }), ] // wagmi builds the picker UI automatically

web3.js v4 + EIP-6963

Vanilla JS. @web3modal/ethers uses EIP-6963 by default.

import { createWeb3Modal, defaultConfig } from "@web3modal/ethers"; const wagmiConfig = defaultConfig({ metadata: { name: "MyApp", description: "..." }, }); createWeb3Modal({ wagmiConfig, projectId });

viem (raw, no framework)

You write the protocol yourself with createWalletClient + custom transport. Lightweight.

import { createWalletClient, custom } from "viem"; import { mainnet } from "viem/chains"; const provider = providers.get(pickedUuid).provider; const client = createWalletClient({ chain: mainnet, transport: custom(provider), }); const [address] = await client.requestAddresses();

MIPD (Store)

@metamask/mipd — framework-agnostic reactive store. Same protocol, with subscription helpers.

import { createStore } from "@metamask/mipd"; const store = createStore(); store.subscribe((providerInfos) => { picker.renderAll(providerInfos); }); // Auto-listens to eip6963:announceProvider // Auto-dedupes by UUID
Section 8 — OpenDrones × Remes

Production patterns for crypto & adjacent UIs

EIP-6963 isn't just for ETH. The same protocol is being adapted (or is directly useful) for any single-object-on-window injection pattern — including auth providers, EVM L2 rollup endpoints, and even remote-device bridges.

Remes · wallet picker v10
Latam stablecoin swap · PWA
Replace v9's wallet-brand registry (manual UUID + EIP-6963 string sniffing) with the actual announce events. Each wallet self-describes — no map to maintain. Add Phantom, Rabby, Frame, Trust via a 4-line change instead of a 40-line registry edit. Calls eth_requestAccounts on the picked UUID's provider.
OpenDrones · proof-of-location
Pilot attestation · EVM L2
If/when OpenDrones issues a pilot NFT or pilot-license attestation via wallet, the same picker pattern applies. Pilots with three wallets (cold-storage Ledger + hot Rabby + backup Frame) pick whichever they want on the moment of attestation. No "wrong wallet" failures.
Molt Studios · auth providers pattern
Generalize beyond crypto
Several auth providers (Sign in with X, Passkey providers, OAuth identity brokers) suffer the same single-injector problem. Adopt the pattern (announce/request events, UUID-stamped providers, deduplication) even when the official auth is OAuth redirect. Defense-in-depth.
dApp · connected-but-then-changed-tab
Edge case made simple
User connects MetaMask, opens a new tab, installs Coinbase in that tab, opens Remes again. Old window.ethereum shows MetaMask only. EIP-6963 picks up Coinbase as soon as the extension load event fires — no extra code.
dApp · wallet reconnect on navigation
SPA / cross-document
Re-fire eip6963:requestProvider on every page load and after every view-transition. Wallets re-announce in <50ms. The picker automatically reflects any newly installed or uninstalled extensions. No polling, no setInterval.
dApp · "walletofchoice" semantic UI
Last-connected preference
If the user picked Coinbase yesterday, Remes remembers (localStorage) and pre-selects Coinbase today. The picker still appears with all wallets if user taps "switch wallet". Identity-layer UX for crypto, the same as Apple ID on iOS — switchable but stable.
Section 9 — Security

Security considerations from the spec

EIP-6963 makes two attacks harder and one attack still possible. The spec's Security Considerations section is worth reading in full.

✓ Mitigated: Prototype pollution

Unlike the old window.ethereum, EIP-6963 events carry provider objects in a CustomEvent.detail — not on the global. Attackers can't poison the namespace for subsequent wallets. Spec explicitly calls this out.

✓ Mitigated: Wallet race condition

No wallet can "win" by injecting last. Every wallet is equally discoverable. Wallets no longer need to delay injection to compete, removing a class of fingerprintable timing attacks.

⚠ Still possible: Wallet imitation

A malicious extension could announce with RDNS io.metamask and a copy of MetaMask's icon. The spec recommends dApps treat unknown / duplicate RDNS defensively (warn the user, show a fingerprint row) — but the protocol itself doesn't prevent this. Never sign without verifying the provider matches the wallet UI.

⚠ SVG icon execution

SVG data URIs CAN contain JavaScript. The spec mandates rendering wallet icons via <img src={info.icon}> — NOT inline SVG. Browsers honor this. Don't use .innerHTML = info.icon, ever.

Section 11 — Recap

The pattern in five sentences

  1. EIP-6963 replaces the broken window.ethereum singleton with a two-event announce/request protocol that runs entirely on CustomEvent.
  2. Every modern wallet self-describes with a UUID, name, icon (data URI), and reverse-DNS — the user sees real brands, the dApp gets stable identifiers.
  3. DApps that need picking listen once, dedupe by UUID, render a row per wallet, call provider.request({method: "eth_requestAccounts"}) on the picked one.
  4. Library support is universal: wagmi v2's injected(), viem transports, MIPD store, web3modal, RainbowKit, ConnectKit, Web3-Onboard — they all wrap the same spec.
  5. Pattern-wise, this is the right shape for any "many injectors, one subject" problem: auth providers, Passkey brokers, remote-device bridges. Adopt the protocol pattern even where the spec doesn't formally apply.
Why P1 for Remes
Today's v9 picker needed a 40-line wallet-brand registry + a 9-case error expander to handle the "MetaMask might be there, might not" problem. EIP-6963 turns this into a single dispatch + listen. Ship it as v10.
Pairs with
EIP-1193 (the provider interface itself), WalletConnect v2 (the 300+-wallet fallback), wagmi v2 (the React wrapper), Web Crypto for session key derivation.
Risks
Wallet imitation via spoofed RDNS — defense-in-depth: warn on duplicate RDNS, never sign without verifying the provider UI matches expectations. SVG icon XSS — always render via <img> tag.
Status · July 2026
All major wallets ship it. All major libraries support it. Final EIP, no breaking changes since 2023. The race condition is solved.
