The Device Input Tier: raw MIDI bytes in the browser

MIDI is not audio — it's a 40-year-old event protocol: note-ons, controller knobs, clock ticks, 3-byte messages at 31,250 baud. Web MIDI exposes the whole byte stream: enumerate ports, receive MIDIMessageEvents, schedule sends to hardware. The cheapest physical control surface a mission-control dashboard or an interactive site can ask for — $60 fader decks with 8 analog axes and a transport bar, no SDK, no driver. This page runs live engine probes (badged LIVE) plus spec-accurate simulated ports where real hardware can't exist headless (badged SIM).

§1

What MIDI actually is — the wire format

Every MIDI message starts with a status byte (high bit set, 0x80–0xFF) followed by 0–2 data bytes (high bit clear, 0x00–0x7F — 7 bits each). Channel messages carry a channel in the low nibble of the status byte (0–15, displayed 1–16). That's the whole grammar — learn it once, read any device.

StatusMessageData bytesNotes
0x8nNote Off2 — note, velocityRelease. Note On with velocity 0 is the common equivalent
0x9nNote On2 — note, velocityAttack. 60 = C4 (middle C, this page's convention)
0xAnPoly Aftertouch2 — note, pressurePer-key pressure
0xBnControl Change (CC)2 — controller #, value7-bit: knobs/faders/buttons. MSB/LSB pairs go 14-bit (§8)
0xCnProgram Change1 — programPatch switch
0xDnChannel Aftertouch1 — pressureWhole-keybed pressure
0xEnPitch Bend2 — LSB, MSBAlways 14-bit: (msb<<7)|lsb, center 8192
0xF0System Exclusivevariable, ends 0xF7Manufacturer blobs. Needs {sysex:true} (§5)
0xF1/0xF3MTC / Song Select1System Common
0xF2Song Position2 — LSB, MSB14-bit position in 16th notes
0xF6Tune Request0System Common
0xF8 0xFA 0xFB 0xFC 0xFE 0xFFClock/Start/Continue/Stop/ActiveSensing/Reset0System Real-Time — legal inside sysex (§5)
0xF4 0xF5 0xF7 0xF9 0xFDundefined—Invalid per spec — a parser must flag, not crash
The spec's own validity guide: high nibble 8/9/A/B/E → 3 bytes total; C/D → 2; F1/F3 → 2; F2 → 3; F6/F8/FA/FB/FC/FE/FF → 1; F0 → until F7. The first byte must have the high bit set and following bytes must not (except inside sysex).
§2

Getting access — the permission ladder

One call: navigator.requestMIDIAccess(options) → Promise<MIDIAccess>. It's a powerful feature: secure-context-only, gated by the midi Permissions Policy (default allowlist 'self'), queryable via the Permissions API, and — for System Exclusive — a stronger permission: {name:'midi', sysex:true} beats {name:'midi'} in the descriptor ordering spec.

const perm = await navigator.permissions.query({ name: 'midi' });          // 'granted' | 'prompt' | 'denied'
const permSysEx = await navigator.permissions.query({ name: 'midi', sysex: true }); // stronger descriptor
const access = await navigator.requestMIDIAccess({ sysex: true });  // may prompt; headless = denied
access.inputs   // MIDIInputMap  — maplike<id, MIDIInput>
access.outputs  // MIDIOutputMap
access.sysexEnabled  // did sysex survive the prompt?

Rejection taxonomy from the spec: NotAllowedError (user/policy denied — also what a headless browser with no way to prompt returns), AbortError (page navigating away), InvalidStateError (underlying system error), NotSupportedError (anything else). The software:true option is the forgotten sibling: it asks to expose installed software synths as virtual ports.

This engine returned NotAllowedError without showing a prompt — that's the documented behavior when no user gesture/permission decision is possible. On a real desktop Chrome, first visit triggers a permission prompt (non-sysex included; sysex re-prompts). Firefox is stricter: MIDI is gated behind a site-permission add-on the user must install (since FF 108), and Firefox Android never shipped it.
§3

The decoder — bytes → meaning

The API hands you event.data: a Uint8Array of one complete message. Nobody decodes it for you — this is the parse layer every Web MIDI app owns. Each chip constructs a real MIDIMessageEvent on this engine and runs it through a spec-accurate decoder (#dcd).


  

    
    
    
    
    
    
    
    
  







  
§4

  
Running status — the byte-stream state machine

  
MIDI 1.0's wire optimization: when consecutive messages share a status byte, transmitters omit it — a keyboard streaming 20 note-ons sends 0x90 once, then 40 data bytes. Rules that matter: a new status byte resets it; System Common (F1–F6) cancels it; System Real-Time (F8–FF) does NOT — clock bytes legally interleave mid-message. Browsers hand you complete messages on onmidimessage (the host stack already did this), but any code touching raw streams — file playback, a WebSocket MIDI relay, a BLE-MIDI bridge — needs this state machine. And per spec, send() data must not use running status ("underlying systems may not support it").

  

  

    
    
    
  







  
§5

  
Sysex — manufacturer blobs, framing, and the permission wall

  
F0 … F7 brackets an arbitrary manufacturer payload — firmware updates, patch dumps, device IDs, lighting protocols. Three rules from the spec: (1) send without sysexEnabled → NotAllowedError throws; (2) receive without sysex → messages are silently masked (no event, no error — your handler just never hears them); (3) real-time bytes may legally interleave inside a sysex transmission (pass them through, don't abort). First payload byte(s) identify the target: 0x7E Universal Non-Real-Time, 0x7F Universal Real-Time, 0x41 Roland (1-byte ID), 0x00 0x20 0x29 Elektron (3-byte IDs start with 0x00).

  
new Uint8Array([0xF0, 0x7E, 0x7F, 0x06, 0x01, 0xF7])
│    │    │    │    │    └ end of sysex (EOX)
│    │    │    │    └ sub-ID #2: 01 = Identity Request
│    │    │    └ sub-ID #1: 06 = General Information
│    │    └ device ID 0x7F = "all devices"
│    └ 0x7E = Universal Non-Real-Time manufacturer ID
└ sysex start

§6

  
Scheduling — timestamps, queues, and clear()

  
output.send(data, timestamp) enqueues to the device; timestamp is an absolute DOMHighResTimeStamp (same clock as performance.now()). 0 or any past time = send ASAP. Multiple sends with the same timestamp go out in call order. The event you receive on input carries its arrival in event.timeStamp — the one clock that matters is this shared time origin, never Date.now().

§7

  
Ports & hot-plug — two state machines

  
Every port has state (connected/disconnected — is the device physically there) and connection (closed/open/pending — has your app opened it). The transitions are the API's best part: implicit open — assigning onmidimessage or calling send() opens the port automatically, no ceremony. pending — an opened device that unplugs goes open → pending, not closed; on reconnect the system auto-reopens it before firing statechange, so the event you receive already reflects the final state. Events fire on the port AND on the MIDIAccess (hot-plug fan-out via MIDIConnectionEvent.port).

Spec GC note: an attached onstatechange handler prevents the MIDIAccess/port from being garbage-collected — detach handlers when a view that owns a port unmounts (the exact leak class for long-lived dashboards). And a Firefox truth worth pinning: onstatechange handlers are supported since FF 108 but the event never fires (bug 1802149) — don't build a FF-only flow on it.







  
§8

  
14-bit — pitch bend, CC pairs, RPN/NRPN

  
7-bit CC (0–127) feels steppy on a long fader. MIDI's precision ladder: pitch bend is natively 14-bit; CC MSB/LSB pairs (controller + controller+32) go 14-bit; and RPN/NRPN (CC 101/100 select a registered parameter, CC 99/98 a non-registered one, then CC 6/38 deliver the value) address device parameters like pitch-bend range. For a gimbal or throttle axis, 14-bit = 16,384 steps — the difference between "smooth" and "visibly quantized" at 8× zoom.

  
// RPN 0 (pitch bend sensitivity) ← ±12 semitones, via CC stream:
CC#101=0 CC#100=0   // select RPN 0
CC#6=12              // data entry MSB = 12 semitones
// NRPN example (99/98): select then 6/38 writes

Everything below was either probed live on this engine or quoted from the spec + BCD with version numbers. These are the things that bite production code.
