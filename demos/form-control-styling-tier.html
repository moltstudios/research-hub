Form-control styling — the ::picker-icon / appearance / accent-color tier

The UA-shadow styling surface of native controls: which pseudo-elements parse, which ones match, which ones actually take author paint — and the three engines' very different vocabularies. Probed live in your browser below — parse/computed/geometry verdicts are measured on this page load; paint rows render live for your own eyes.

§1The pseudo-element census — and the feature-detect that lies

CSS.supports('selector(…)') returns false for every -webkit- pseudo on Firefox and WebKit even though those selectors parse and (sometimes) match rules. insertRule is the honest feature-detect: it throws only on truly invalid selectors. §2::picker-icon is select-only — and a real layout box

The unprefixed picker pseudo parses on CfT + WebKit for every input type probed — date, color, file, range, even checkbox — but only ever matches the select chevron. Under appearance: base-select it becomes a real layout participant: give it width and the select grows; display:none it and the select shrinks (CfT: 75.7→57.1px measured). Firefox throws SyntaxError on sight.

§3The date indicator tier — ::-webkit-calendar-picker-indicator (CfT) vs nothing

On Chromium the date chevron is reachable only through the legacy -webkit- pseudo — and it's a geometry participant: display:none shrinks the input (125.3→108px measured). appearance:none does not remove it — the indicator survives with all its pixels. Firefox parses the -webkit- name (insertRule ok) but no author rule reaches its native glyph; WebKit paints no indicator glyph at all in headless lanes.

§4::checkmark — the parse-only vapor

::checkmark parses on CfT + WebKit (checkbox, radio, option:checked) and CSS.supports() says true — but no author color, background or display measurably reaches the checkbox/radio check glyph on any engine. The check paints in accent-color (or engine blue when auto). Firefox doesn't parse it at all. The one live use is inside the base-select popup (option:checked::checkmark) — a human-hand lane under automation.

§6The appearance ladder — three vocabularies, one silent fallback

Every engine accepts the legacy keyword list (menulist-button, checkbox, textfield…) even on the wrong control — a date input computes appearance:checkbox on all three. But the new keywords split: base-select computes on CfT + WebKit 26.5, and Firefox silently normalizes it to auto (the graceful degradation that makes base-select shippable). slider-horizontal survives only on WebKit. Invalid values fall to auto everywhere, silently.

§7The color input — ::-webkit-color-swatch / ::-moz-color-swatch

The unprefixed ::color-swatch is a SyntaxError on every engine — the prefixed names are the real API: -webkit- paints on CfT + WebKit, -moz- on Firefox (pixel-verified on all three). Warning: the swatch pseudo's background paints over the value color — styling it replaces what the user picked. The safe uses: border-radius and border (live below, second input).

§8The file input — the one universal pseudo

::file-selector-button is the only control pseudo that parses, computes, paints, and takes geometry on all three engines (styled red + display:none'd in the probes: geometry changed everywhere — and on WebKit the whole input collapsed to 0 height, the control is button-height-driven). It inherits font-size from the input but not color or font-weight; the filename label follows the input's color (red-text measured on all engines).

§9Spinners & search-cancel — parse, don't paint

The whole ::-webkit-inner-spin-button / ::-webkit-search-cancel-button family parses on every engine (SyntaxError nowhere) and CSS.supports() admits them only on CfT — but no author rule (background, opacity:0, display:none, even the canonical -webkit-appearance:none) measurably changed any pixel in the probe lanes. What actually works: appearance: textfield on the input removes Firefox's spin-gutter (pixel-verified: 276 gray pixels gone); macOS WebKit never paints spinners; headless CfT painted no spinner at all — a recorded lane limit (headed/human verification pending).

§11Molt audit — the client form-styling review (12 checks, half a day)

  • HIGH ::picker-icon styling shipped outside a base-select (matches nothing — the chevron stays native everywhere but CfT/WK selects)
  • HIGH base-select UI assumed cross-engine (Firefox computes it to auto — silent native fallback; verify the degraded layout)
  • HIGH accent-colored range sliders on Firefox/Safari (thumbs stay gray/white — rebuild with engine thumbs or accept gray)
  • HIGH ::checkmark rules in production CSS (parse-only vapor — the check never takes author paint on any engine)
  • HIGH feature-detects via CSS.supports('selector(::-webkit-…)') (returns false on FF/WK for selectors that parse and match)
  • MED ::-webkit-color-swatch backgrounds overriding the picked value color
  • MED date indicators expected to vanish under appearance:none (they survive on CfT — use the -webkit- pseudo or accept it)
  • MED file-button color/weight assumed inherited from the input (only font-size inherits)
  • MED meter controls styled via accent-color in dashboards (dead on every engine — semantic colors win)
  • MED spinner-hiding via pseudo rules only (the working lever is appearance:textfield on the input, FF)
  • LOW unprefixed ::color-swatch / ::slider-thumb in stylesheets (SyntaxError everywhere — dead rules that survive linters)
  • LOW e2e asserts on file-input height after button removal (WK collapses to 0; CfT/FF keep the label line)

§12Method, engine ledger, falsifications & lane limits

Method. 5 probe generations (~60 lanes × 3 engines) over plain-HTTP loopback, fresh document per lane. Parse truth: insertRule try/catch (throws only on invalid). Compute truth: getComputedStyle(el, pseudo) shape. Geometry truth: getBoundingClientRect before/after pseudo rules (a shrink/grow proves the rule reached the UA shadow). Paint truth: screenshot + pixel-classified strip/region scans with value-disambiguated fixtures. Contested paint lanes ×2 reps.
