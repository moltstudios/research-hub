bfcache + Page Lifecycle — the navigation-stability tier

1 in 10 desktop navigations and 1 in 5 mobile navigations are Back/Forward. The back/forward cache turns every one of them into an instant, network-free restore of the whole page — JavaScript heap included. This page is the tier's contract: how to observe restores (pageshow.persisted), how to read why a restore didn't happen (notRestoredReasons), how to survive freezing (freeze/resume), and the September 2026 endgame of the unload deprecation.

bfcache: all engines (Chrome 96+, FF 1.5, Safari ≈forever) pageshow/pagehide · persisted: universal notRestoredReasons: Chromium 125+ freeze/resume/wasDiscarded: Chromium-only (68+)

02The two caches — why a bfcache restore always wins

bfcache is not the HTTP cache. They hold different things and answer different navigations.

HTTP cachebfcache
Holdsresponse bytes per URLthe live page in memory — DOM, JS heap, scroll, timers (paused)
Cost to restorere-parse, re-execute, re-layout (fast path)make visible + unpause JS (~0ms of loading)
Revalidationno-cache/max-age=0 honorednone — memory snapshot shown as-is, headers ignored
Guaranteeuntil eviction by policybest-effort; can be refused or evicted at any time
Law: a bfcache restore beats even a perfectly HTTP-cached reload. A reload must at minimum re-parse and re-execute from cached bytes; a restore skips all loading — the page simply resumes. That's why browsers fight unload handlers for it: it is the single largest free navigation win left on the web.
While cached, the page is frozen, not destroyed. Timers, pending promises, and nearly all queued tasks pause. On restore they resume — which is both the magic (state survives) and the trap (a setTimeout that "was about to fire" fires late; Date.now() jumps forward across the freeze, and on engines that pause the page clock — Firefox, Safari — performance.now() lags behind it; Chromium keeps it running, §09).
SPAs don't get soft-navigation bfcache — but the shell does. bfcache keys on browser-managed (cross-document) navigations. In-app route changes can't be cached; going Back to the SPA tab from another site still restores the whole app without re-init.

04The persisted contract — four flags, two directions

Every bfcache observable hangs off PageTransitionEvent.persisted. The event order is fixed by spec; the flags mean different things entering vs leaving.

Measure hit-rate with pageshow, recover work with resume. resume also fires when a merely-frozen background tab is revisited (no bfcache involved), so it can't distinguish restore-from-bfcache from un-freeze. Only pageshow with persisted === true counts a bfcache hit.
pagehide.persisted = true does NOT promise a cache entry. It marks intent. Memory pressure, another tab claiming the slot, or a blocker discovered later can still evict — silently, with no event, because a frozen page can't run code. Never leave critical persistence to "persisted said true."

05notRestoredReasons — the post-mortem API

When Back doesn't restore, Chromium 125+ tells you why. The fresh document loaded by the back-navigation carries a PerformanceNavigationTiming.notRestoredReasons tree explaining what blocked the previous version of the page. Six reasons are spec-standard; the rest are UA-specific. Cross-origin iframes report "masked" — reasons hidden, blame still assigned.

reading this page's current navigation entry…
reason keyclasswhat it means
The shape. { children:[…per iframe…], id, name, src, url, reasons:[{reason}] }. children recurses same-origin iframes; cross-origin children get reasons: null + url: null and the parent gains "masked". id/name/src identify which iframe — your tool to blame third-party embeds precisely.
Spec reasons are stable vocabulary; UA reasons are volatile. The spec explicitly warns not to depend on exact wording — treat unknown future reasons as "blocked, investigate," not as errors. Monitor with a PerformanceObserver({type:'navigation', buffered:true}) and ship the strings to RUM.

07The unload endgame — deprecation, 100% as of Chrome 154

Chrome is deleting unload by rolling out "handlers stop firing" origin by origin. The completed ladder (rollout is by page-load share, held at each step for consistency):

What "deprecated" means here: the handler stops FIRING — the listener may still register. Rollout flips the default so unload callbacks don't run (unless the page re-enables via Permissions-Policy: unload=(self) or enterprise policy). A dead listener shouldn't keep blocking bfcache — but verify on your own 154 traffic: the §03 round B lab exists precisely because "should" is not a verdict.
The replacements, by job. Save state → visibilitychange to hidden (the last reliable moment on every platform). Cleanup on leave → pagehide (and restore-on-resume, because a pagehide page may come back). Warn unsaved changes → conditional beforeunload, removed once saved. End-of-session analytics → sendBeacon / fetch keepalive from pagehide.

// The canonical state reader — frozen/terminated only observable in their events
const getState = () =>
  document.visibilityState === 'hidden' ? 'hidden'
  : document.hasFocus() ? 'active' : 'passive';
hidden is your last reliable save point — not unload, not pagehide. Mobile browsers freeze and kill hidden tabs with no further events; desktops increasingly do the same. When visibilitychange reports hidden: flush state, release locks, stop cameras, send the beacon. Everything after hidden is best-effort.
Discarded pages run zero JS — recovery must happen on reload. The tab still shows title + favicon; the user's next click reloads the URL. That fresh document checks document.wasDiscarded === true and rebuilds the session instead of greeting the user with a login screen.

09freeze / resume — surviving the void

Chromium freezes hidden tabs (minutes later, or instantly under memory pressure) and every bfcache entry. While frozen: timers, rAF, microtask-draining tasks — all paused. The events are your only signal; there is no polling a frozen page.

document.addEventListener('freeze', () => {
  // LAST code before pause — sync, short, no promises of continuation
  saveToStorage(sessionState); stopRAF(); closeStreams();
});
document.addEventListener('resume', () => {
  // un-paused. Could be a background-tab un-freeze OR a bfcache restore —
  // check the NEXT pageshow.persisted to know which
  restartLoops(); reconnectSockets();
});
The clock split — only on engines that pause the page clock. Date.now() always jumps across a freeze. Whether performance.now() lags behind it is engine-specific: engines that pause the monotonic clock while frozen (Firefox, Safari) show Date.now() - then_date > performance.now() - then_perf by exactly the frozen duration — but Chromium 154 keeps the page clock running straight through (lab-measured: 1781ms frozen, page clock advanced 1781.3ms → pause ≈ 0ms; the §03 lab prints your engine's verdict live). Never compute durations across a freeze with Date.now(); and never assume the page clock paused — measure, then branch.
freeze-time limits: you get ~500ms, sync only. The freeze handler can finish, but long-running or async work may be killed. Anything that must survive has to be persisted synchronously (storage APIs), not promised.
freeze/resume listener armed. In a live browser: background this tab for ~5 min (Chrome desktop) and return — or run the §03 lab, which freezes this page en route to the child.

10wasDiscarded — the silent reload

reading…
if (document.wasDiscarded) {
  // this is NOT a fresh visit — the user never closed the tab.
  restoreSessionFrom(storage); skipOnboarding(); resumeWhereTheyLeftOff();
}
Discard ≠ crash, but your analytics can't tell the difference without this flag. A discard-reload is a normal navigation with a ghost session behind it. Mark it in RUM (wasDiscarded: true) or your "sessions" and "bounces" quietly rot on memory-constrained devices — which skew mobile, which is most of the traffic.

bfcache restores corrupt naive analytics. A restore re-fires pageshow but not load — so load-based PV counters undercount, while "page viewed" events bound to visibility overcount. Every RUM tag must carry the persisted flag:
window.addEventListener('pageshow', e => {
  rum('pageview', { bfcache: e.persisted });   // persisted=true → a restore, not a visit
  if (e.persisted) refreshTimeSensitiveData(); // prices, cart, auth — see §12
});
Core Web Vitals already count restores. Field INP/LCP include bfcache-restored pages — one more reason eligibility is a business metric, not a nicety. Chrome's own target: pages ineligible for bfcache are leaving measurable INP wins on the table for 10–20% of navigations.

🛒 Molt — checkout & funnels

Back is the #1 gesture in every funnel. Stale-cart and logged-out exposures are the two bfcache liabilities:

window.addEventListener('pageshow', e => {
  if (!e.persisted) return;
  // 1) a restore can show a cart the user just changed elsewhere
  refreshCartSummary();
  // 2) a restore can resurrect a page after logout on a shared device
  if (!document.cookie.includes('session')) location.reload();
});

And the server side: never blanket Cache-Control: no-store the document for freshness — it forfeits bfcache on 10–20% of navigations. Use no-cache (revalidates, still cacheable-in-memory) and refresh in-page on persisted restores.
