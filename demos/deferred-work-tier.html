Deferred Work — the Background Sync / Periodic Sync / Background Fetch tier

The three lanes that keep work alive after the click: one-shot retry (Background Sync), scheduled wake-ups (Periodic Background Sync), and resumable large downloads (Background Fetch). All three hang off ServiceWorkerRegistration — no service worker, no deferred work. This page runs the real APIs live (a service worker is registering right now) and documents the engine truths found by probing: the any-string tag law, the dup-fire law, the two-network-truths offline law, the periodic install wall, and the background-fetch eviction & silent-stall laws.

Chromium-family 42+ / 74+ / 74+ FF & Safari: never shipped any of the three Secure context only (via the SW container) LIVE lanes on this page Demo: dw-sw.js scope /demos/

01 · The three lanes

🔁 Background Sync

reg.sync.register(tag) — ask the browser to fire a sync event in the SW "when connectivity allows." One-shot per registration, browser-owned retry. The reconnect-work primitive: form sends, telemetry flushes, draft uploads.

⏰ Periodic Background Sync

reg.periodicSync.register(tag, {minInterval}) — the browser wakes your SW on a schedule only for installed, engaged PWAs. The strongest gate in the platform: NotAllowedError without install + engagement.

📦 Background Fetch

reg.backgroundFetch.fetch(id, requests) — OS-level resumable download with progress, its own UI, and SW lifecycle events. For payloads too big for a fetch(): firmware, media packs, map tiles.

All three: Chromium-only in practice (FF and Safari declined the whole family), reachable only through a service-worker registration, and — measured live below — far more permissive on identifiers and far weirder on offline than the docs imply.

03 · THE ANY-STRING TAG LAW — live

Tutorials describe sync tags as sanitized identifiers. 04 · THE DUP-FIRE LAW — live

getTags() dedupes the pending list — but the event queue does not. Registering the same tag twice (while still pending) fires the SW's sync handler twice, verified server-side in the probes (two POST beacons 2 ms apart). If your handler isn't idempotent, "register again to be safe" doubles your side effects. The mitigation is a done-set inside the handler (this demo's SW carries one; it reports seenBefore — honest label: an in-memory set only survives while this worker instance lives; production dedupe belongs in IndexedDB).

05 · THE TWO NETWORK TRUTHS — the offline-fire law

SIM / probe-transcript laneCDP emulation cannot be driven from a page — this section transcribes the measured probe runs verbatim (dw-probe2, CfT 154 headless, 2026-10-05).

The textbook model: register offline → the browser holds the event → connectivity returns → it fires. The probe tried to verify that with CDP Network.emulateNetworkConditions({offline:true}) and found something stranger — one browser, two network truths:

During emulated offlineResult
page navigator.onLinefalse
page fetch('/report')⛔ TypeError: Failed to fetch
sync.register('ofl-proof-2')✅ resolves — no throw
…1.5 s later, still "offline"sync event FIRED in the SW (t+2054 ms)
SW handler's fetch('/beacon')✅ HTTP 204 from the real server — the SW lane was never offline

Engine truth: CDP page-level network emulation does not gate the service-worker network lane, and the sync scheduler's connectivity check ignores it entirely — the event fired and its fetch reached the server while the page itself could not fetch. Practical consequences: (1) you cannot test "deferred until online" by emulating offline in Playwright/Puppeteer — the sync fires anyway; (2) the sync scheduler's notion of connectivity is a separate signal from navigator.onLine — never assume the two agree; (3) handlers must be idempotent because "it already fired once" is not observable from the page. Real-offline testing needs a real network kill (Wi-Fi off / interface down), not emulation.

06 · THE PERIODIC WALL — live

Periodic Background Sync is the most permission-gated surface in the family: no PWA install + engagement → NotAllowedError: Permission denied. And unlike Web Share's validation-first ladder, every argument shape — missing minInterval, bogus tag — hits the permission wall first. Nothing about your arguments is even looked at. The permission state itself reads denied on a fresh profile with name readback periodic_background_sync (underscores). Even installed-and-engaged, you don't choose the schedule — minInterval is a hint; the browser decides from engagement and battery. If you need dependable periodic work on the open web, this API is not it (see decision table §10).

08 · THE SILENT EXCEED STALL — live zombie

Declare downloadTotal: 1024, download 64 KB: spec says the fetch should fail with a total-exceeded reason. Measured (twice, 15+ s windows): zero bytes ever move — downloaded stays 0, no backgroundfetchfail, no failureReason, no cleanup. An invisible zombie registration that blocks its id forever. downloadTotal is a display hint, never a cap — but a wrong one can wedge the fetch entirely. Live:

09 · THE WORKER JAIL + the insecure door — live

Dedicated workers see all three manager constructors (they parse, they exist) — but self.registration, self.serviceWorker and self.clients are all undefined there: constructors present, door absent. Same law on insecure origins: the constructors exist on plain HTTP, but navigator.serviceWorker is undefined, so the entire tier is unreachable by construction — object-absence, never a rejection. 11 · Capstones

🛩️ OpenDrones — Mission Outbox

Flush-on-reconnect telemetryThe ground station writes each telemetry batch to IndexedDB with a monotonic batch id, then sync.register('flush-' + missionId). The SW handler reads pending batches, POSTs them with the batch id, and records the last-acked id in the same store — so the dup-fire law and the browser's opaque retries are both harmless (same batches re-POST, server dedupes on id). Firmware/artifact downloads go through Background Fetch with exact downloadTotal and an in-event progress audit; the exceed-stall law makes "estimate small, hope for the best" a wedged download.

🎨 Molt — Draft Send

Contact-form / draft uploads that never lose a clickClient sites where a submission must survive a flaky link: persist the draft locally → register a sync tag → optimistic UI ("will send when you're back online") → the SW sends and the confirmation flips. The any-string law means user-scoped tags like draft-1874 are safe as-is — but escape nothing and validate nothing: the tag round-trips verbatim, including on retry.

12 · Field checklist

  • No service worker → no deferred work. All three managers live on ServiceWorkerRegistration (page or SW scope — never a dedicated worker).
  • Treat sync tags as opaque cookies: any string legal, fires verbatim, objects coerce to "[object Object]". Don't parse, don't sanitize — just mirror.
  • Dedupe inside the sync handler (IndexedDB). getTags() lies about delivery; every register() is a future fire.
  • Never test offline deferral with emulated offline — the SW lane ignores it (two network truths). Kill the real network or don't claim it.
  • Failed sync handlers leave the tag pending with opaque retry timing. Idempotent handlers or bust.
  • Periodic Sync: expect NotAllowedError until installed + engaged; minInterval is a hint; don't build load-bearing schedules on it.
  • Background Fetch: exact downloadTotal or omit it. A low total doesn't cap — it wedges (silent stall, no events).
  • Persist audit data inside backgroundfetchsuccess — the registration evaporates on completion.
  • Cleanup on boot: getIds() → abort() your app's leftovers, or relaunches hit duplicate-id TypeErrors.
  • getIds() not getIDs() — modern name, lowercase s. Feature-detect both if you support old codepaths.
