Long Animation Frames API — find what actually broke your INP

The Long Tasks API told you that the main thread stalled. The Long Animation Frames API (LoAF) tells you which script, which function, which character position, how long the render took, and how much of the frame was actually blocking input — measured in the field, on real users, not in a lab trace.

Section 2

The problem: what Long Tasks couldn't tell you

The Long Tasks API (Chrome 58, 2017) reports any task over 50ms. It was the only field signal for a decade — and it has three structural blind spots that LoAF fixes:

1 · Attribution says "unknown"

A longtask entry names at best the container (window or iframe). Not the script, not the function. RUM tools could count long tasks but not explain them.

2 · Render work is invisible

Rendering often happens in separate tasks after your script. Long Tasks sees the script or the render — never the total "work until paint" that the user actually experiences.

3 · Death by a thousand cuts

Eight 40ms tasks chained back-to-back produce zero longtask entries — every task is under 50ms — while the frame they compose blocks input for ~320ms. Section 4 proves this live.

Section 4

Long-frame lab — four ways to break a frame

Each button does real main-thread damage; the observer in section 3 catches the resulting entry. Every result below also renders a full timeline bar in section 5.

A · One long task classic longtask

A single ~180ms synchronous busy loop in a click handler. Both APIs see it. Attribution names this exact function.

B · Eight 40ms tasks invisible to longtask

Chained setTimeout, each under 50ms, renders pending throughout. Long Tasks: 0 entries — ever. LoAF: catches every resulting long frame (~80ms each), attributes each 40ms chunk.

C · Layout thrash forced reflow

130 iterations of write-then-read DOM churn. Watch forcedStyleAndLayoutDuration appear in the script attribution (section 6).

D · The yield fix the remediation

The same kind of work (8 × 32ms), chunked with scheduler.yield(). Expect: blockingDuration ≈ 0 — input responsive throughout. Frame duration may still exceed 50ms (the browser batches high-priority yield continuations): yielding fixes responsiveness, only less work fixes smoothness.

Lab idle. Pick a scenario. 
// B — the invisible stall: every task is under 50ms, the frames are not
function chain(i) {
  if (i >= 8) { labDone('chain'); return; }
  busy(40);                       // under the 50ms longtask line
  counter.textContent = i;        // pending render keeps frames long
  setTimeout(() => chain(i + 1)); // task boundary, render may or may not squeeze in
}

// D — the fix: yield to the browser between chunks (Chrome 129+)
async function yielded() {
  for (let i = 0; i < 8; i++) {
    busy(40);
    counter.textContent = i;
    await scheduler.yield();  // task + frame boundary → browser paints + handles input
  }
}

scheduler.yield() (Chrome/Edge 129+) is the modern break-up-the-task primitive: unlike setTimeout, it inherits the caller's priority, so a user-initiated continuation can't be starved by background work. Fallback for other browsers: setTimeout(0) still ends the frame.

A frame that is mostly work is a JS problem (yield or shrink the work). A frame that is mostly style & layout is a DOM problem (smaller trees, less invalidation, content-visibility). That single glance is the triage step the Long Tasks API never gave you.

Section 6

Script attribution — down to the character

Every script contributing more than 5ms to a LoAF appears in entry.scripts[] with an invoker chain, a timing breakdown of its own, and — when source maps resolve — the file, function and character offset. The invokerType taxonomy has six values worth memorizing:

user-callback

Platform-scheduled callback: setTimeout, requestAnimationFrame, etc.

event-listener

Listener to a platform event: click, keyup, load…

resolve / reject-promise

Platform promise handlers (fetch().then); same-promise handlers merge into one entry.

classic-script

Top-level evaluation of a classic script or import().

module-script

Top-level evaluation of a module script.

windowAttribution

Not a type — the container field: self / ancestor / descendant iframe / unknown. The third-party smoke gun.

The per-script fields doing the heavy lifting: executionStart (post-compilation), duration (until the microtask queue drains), forcedStyleAndLayoutDuration (layout thrash inside this function — lab C will show it non-zero), and pauseDuration (synchronous stalls like alert() or sync XHR).

Section 7

Linking LoAFs to a slow interaction

There is no direct API joining an INP interaction to its LoAF entries (it's an open spec issue — w3c/long-animation-frames#5). The standard workaround is timestamp intersection, which is exactly what the web-vitals library does from v4: it ships every intersecting LoAF inside INPAttribution.longAnimationFramesEntries. Here it is live — the button below runs a deliberately slow (~140ms) click handler while both an Event Timing observer and the LoAF observer watch:

Waiting for your click…
// The WhyNp pattern (Noam Rosenthal's gist, simplified): intersect by time
const loafStart = l.startTime, loafEnd = l.startTime + l.duration;
const intersects = loafStart < entry.processingEnd && entry.startTime < loafEnd;

// Event Timing gives the interaction's own three slices:
inputDelay    = entry.processingStart - entry.startTime;   // queue time = what ELSE was blocking
processingDur = entry.processingEnd - entry.processingStart; // your handler
presentation = (entry.startTime + entry.duration) - entry.processingEnd; // paint after handler

The diagnostic gold is input delay: when it's large, your handler wasn't the problem — the intersecting LoAF's scripts[] shows which other code was hogging the frame when the user clicked. That's the field-debug workflow DevTools can't give you, because it depends on what real users happened to be doing.

Section 8

blockingDuration — the number INP actually feels

duration measures the whole frame; blockingDuration measures only the part that could delay input. The accounting: for each task in the frame, everything beyond its first 50ms counts as blocking (the final render rolls into the longest task). The spec's worked example:

Frame: task 1 (55ms) + task 2 (65ms) + render (20ms) → duration ≈ 140ms
blockingDuration = (55 − 50) + (65 + 20 − 50) = 40ms of the 140ms
grey = the free 50ms every task gets · hatched red = input-blocking

High blocking, high duration

The INP killer. Tasks too long to yield inside. Fix: break work up (scheduler.yield(), chunking) — blockingDuration drops even if total work doesn't.

Zero blocking, still-long duration

Frame stayed open over many small tasks (the browser chose to batch renders). Input still gets in — but smoothness/animation may suffer. Fix: reduce total work; you can't yield your way out of this one.

Section 9

The production pattern — field reporting

LoAF is designed for RUM, not labs. The pattern every vendor (Datadog RUM, Debugbearer, speedCurve…) converged on: observe continuously, report only on meaningful events (the INP interaction, or a slow LoAF above a threshold), and rank scripts by cumulative volume once samples accumulate. 

// Option 1 — web-vitals v4+: LoAFs arrive inside INP attribution, already linked
import { onINP } from 'web-vitals';
onINP(metric => {
  const loafs = metric.attribution.longAnimationFramesEntries ?? [];
  const offenders = loafs.flatMap(l => l.scripts)
    .map(s => ({ url: s.sourceURL || '(inline)', fn: s.sourceFunctionName,
                 ms: s.duration, forced: s.forcedStyleAndLayoutDuration }));
  navigator.sendBeacon('/api/rum', JSON.stringify(
    { inp: metric.value, offenders, route: location.pathname }));
});

// Option 2 — raw observer, report only exceptional frames (sample + threshold)
const REPORT_MS = 150;
new PerformanceObserver(list => {
  for (const l of list.getEntries())
    if (l.blockingDuration > REPORT_MS) report(l);   // e.g. 1-in-100 sampled users
}).observe({ type: 'long-animation-frame' });

Buffer discipline

The entry buffer is 200. Long sessions overflow it — observe with the callback (drains the buffer), and if you must query ad-hoc, be ready to call .clear().

Sampling

LoAF payloads are rich; beacon volume costs money. Report at a threshold (≥150ms blocking) and sample users (5–10%) — trends survive fine.

Rank by volume

One user's slow frame is an anecdote. Group scripts[].sourceURL origin across thousands of sessions — the widget with the most cumulative ms is your sprint ticket.

Section 11

Molt Studios — the CWV field-debug kit

Client complaint: "the site feels slow sometimes" — CrUX says INP fails, Lighthouse says it's fine. Lab tools can't see the chat widget fighting the analytics bundle on a mid-tier Android over hotel Wi-Fi. A ~1KB LoAF snippet on the client site turns that anecdote into a ranked list: 

// Group blocking time by origin — third parties can't hide
const byOrigin = {};
new PerformanceObserver(list => {
  for (const l of list.getEntries()) {
    for (const s of l.scripts) {
      const key = s.sourceURL
        ? new URL(s.sourceURL, location.href).origin
        : s.windowAttribution === 'self' ? '(first-party inline)' : '(iframe: ' + s.windowAttribution + ')';
      byOrigin[key] = (byOrigin[key] || 0) + (s.duration || 0);
    }
  }
}).observe({ type: 'long-animation-frame' });

Deliverable: field-debug kit

Ship the snippet, collect two weeks of origin-ranked LoAF data, present a fix list ordered by cumulative milliseconds. A repeatable $2–4k audit product.

Third-party leverage

When the top offender is a vendor script, the LoAF report is the evidence that moves the client meeting from "maybe redesign" to "swap the widget".

Regression alarm

Keep the observer in production at 1% sampling; alert when p75 blockingDuration for a route crosses a threshold. INP regressions get caught at deploy time, not at the next CrUX refresh.

Why it matters

INP became a Core Web Vital in March 2024 — the same month LoAF shipped. The metric that gates SEO and the instrument to debug it arrived together. Every Molt client site and the OpenDrones dashboard benefits.

Adoption cost

Near zero: one PerformanceObserver, feature-detected, no polyfill, no UX risk. The web-vitals v4 attribution build bundles the linkage logic for you.

The one-line pitch

Long Tasks said "something is slow." LoAF says which file, which function, which character, and whether it blocked input — from real users, in production.
