Houdini 2026 · Live-Falsified on Chromium 152

CSS Paint API + Typed OM — the tier where CSS hands you the pixels

Paint worklets run your code inside style resolution, Typed OM replaces string-slinging with typed values, and @property registration unlocks CSS-driven animation of painted content. On today's engines the usable surface is narrow and full of dead channels — this page maps exactly what ships, what lies, and what it costs. Every claim below is verified live or pixel-sampled by the harness.

§1 · Capability badges

What this browser actually has

Probed at page load. The badges are the adoption decision in miniature: Paint is Chromium-only, Typed OM is cross-engine-but-quiet, @property is Baseline 2024, and the argument channel of Paint is dead on Chromium 152 (§7).

§3 · Anatomy

The smallest honest paint: three moving parts

A worklet class, a module registration, and one CSS function. No build step, no separate file — the module is a Blob URL, which is exactly how this page loads its worklet.

/* 1 — the class (runs on a paint thread, NOT the main one) */
registerPaint('hello', class {
  static get inputProperties() { return ['--hue'] }      // repaint triggers: ONLY these
  paint(ctx, size, props) {                                    // ctx = PaintRenderingContext2D
    ctx.fillStyle = 'teal';
    ctx.fillRect(0, 0, size.width/2, size.height);
  }
});
/* 2 — the wiring (main thread) */
await CSS.paintWorklet.addModule(blobUrl);                     // Blob URL: single-file demo ✓
/* 3 — the paint function (CSS) */
.hello { background-image: paint(hello); }
harness · pixel-verified
The anatomy demo, actually painting: left half teal, right half left to the element's background (here, white). Sampled by the headless harness: pixel at x≈50 = teal, pixel at x≈180 = white.
Lifecycle truth (verified): the constructor runs once per class per worklet instance, not per element — two elements painted by one instance share this. And the worklet module is instantiated per thread (this page's module evaluated twice on this machine — top-level code ran on two paint threads). Module state is per-thread, instance state is shared across elements: neither is a per-element store. All per-element data must arrive through inputProperties.

§5 · Typed OM

CSSStyleValue: strings out, objects in

el.style.map.set('width', CSS.px(42)) writes typed values; el.attributeStyleMap.get() reads them back typed; el.computedStyleMap() gives computed values as typed objects. No parsing, no regex, no string concatenation bugs. Probes run on this page:

// the two worlds, side by side
el.style.width = '120px';                                  // string in, string out, pray
el.attributeStyleMap.set('width', CSS.px(120));            // typed in
el.attributeStyleMap.get('width');                         // CSSUnitValue {value:120, unit:'px'}
el.computedStyleMap().get('width');                        // computed, still typed
CSS.px(2).add(CSS.px(3)).toString();                       // '5px' — engine collapses same-unit math
CSS.px(1).add(CSS.percent(5)).toString();                  // 'calc(1px + 5%)' — mixed units deferred
§6 · The data plane

How values cross into the worklet — and the trap in the middle

inputProperties is the only config channel that works. Inside paint(), props.get(name) returns typed objects for registered properties and CSSUnparsedValue for unregistered ones. Both bars below are painted by one worklet reading one number each way:

Top: --u-num: 7 unregistered → CSSUnparsedValue → parseFloat(uv[0]) → 70% width. Bottom: --r-num: 3 registered <number> → CSSUnitValue → uv.value → 30% width. Same worklet, two type systems.
harness · pixel-verified
fillStyle coercion: ① magenta control (string) · ② ctx.fillStyle = props.get('--u-col') — the object, unregistered, String() would be '', yet it paints red: Blink's canvas setters natively accept CSSStyleValue · ③ registered <color> via String() → 'rgb(0,128,128)' · ④ black control. The MDN pattern works — the setter coerces the object. (String() of an unparsed value is only reliably non-empty page-side; in the worklet it reads empty — read fragments.)
Write it down: String(unparsedValue) is ''. If you need the scalar in JS, index the fragments: parseFloat(uv[0]). If you need a color on a canvas, hand the object straight to fillStyle. Never JSON.stringify CSSUnparsedValue and expect the tokens.

§8 · The animation engine

@property + transition = CSS-driven paint animation, zero rAF

Register --anim as <number>, put it in transition, and the engine interpolates the value — every intermediate frame re-resolves paint() with an interpolated input. The animation loop is the style engine; your JS touches nothing per frame.

harness · pixel-verified mid-flight
Harness flips --anim 0→100 via attributeStyleMap, samples at ~80 ms (bar mid-flight) and after settle (full). The partial bar is the whole point: repaints run per interpolated frame.
idle
.bar {
  background-image: paint(chargebar);
  --anim: 0;                            /* registered <number> */
  transition: --anim 600ms linear;      /* interpolated → repaint per frame */
}
el.attributeStyleMap.set('--anim', '100');     // one line of JS, zero per-frame JS
Why this is the crown jewel: hover states, scroll-driven flips (add animation-timeline: scroll() — same prop-interpolation pipeline), load progress — all off the main thread's rAF budget. The page JS writes one value; the compositor does the rest. This exact mechanism animates §9's capstones.

§10 · Capstone — OpenDrones

HUD chrome: one registered prop per telemetry tick

Battery, RSSI, scanline, grid — one worklet, four registered properties. The telemetry loop writes props; the paint thread renders. The main thread never builds DOM for the HUD again.

harness · pixel-verified
stopped
Scanline = --hud-tick advancing · battery arc = --hud-chg · grid from PaintSize. Every visual state is one prop write away.

Why not canvas?

A <canvas> HUD needs a resize observer, DPR bookkeeping, a rAF loop and manual dirty flags. The paint version is one CSS hook: the engine owns sizing, DPR scaling and invalidation. The catch — Chromium-only, so the HUD degrades to flat CSS panels on Firefox/Safari. Same ladder as §11.

Telemetry rate reality: ticks here are 300 ms — human-paced. For 60 fps sensor streams, prop writes are still the right interface (they batch into style resolution), but measure your own worst case; props resolve per style pass, not per rAF.

RuleWhy (verified this run)
Detect with 'paintWorklet' in CSS, not @supports@supports (background: paint(x)) returns true even when nothing will ever paint — the parser accepts the syntax, the pipeline is the feature. Bad names also parse + persist in computed style while painting nothing.
Static fallback BELOW, never insteadPaint is ~⅔-of-traffic Chromium enhancement (BCD Aug 2026: FF ✗, SF ✗). The gradient/SVG beneath is the product; the worklet is the upgrade.
Config via custom props onlyThe argument channel is dead (§7.1). Every knob = one registered @property, animated with transition where continuous (§8).
Keep paint() pure and allocation-lightShared instance + per-thread module (§7.5); exceptions vanish (§7.3); the engine may call paint at any time with any prop change. Derive everything from inputs.
