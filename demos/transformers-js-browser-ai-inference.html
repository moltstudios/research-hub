04 The Inference Ladder — 5 Tiers From Embedded to Cloud

Browser AI runs on a continuous spectrum. The honest rule: keep models small (under 2B params) for cross-device shipping, escalate to server GPU only when you need RAG, long-context, or 7B+ reasoning.

🪶 Tier 1 · Tiny <10M

MobileNetV4, DistilBERT, embedding models. ~10MB downloads. Runs on phones, smart TVs, low-end Chromebooks.

Best: classification · embeddings · on-device NER

📱 Tier 2 · Small 10M–500M

Whisper-tiny (39M), BERT-base, all-MiniLM. ~100-500MB. Modern phones and laptops handle these fine via WebGPU.

Best: speech-to-text · sentiment · semantic search

💻 Tier 3 · Medium 500M–2B

Phi-3-mini (3.8B q4), Gemma-2-2B, Llama-3.2-1B. ~1-3GB. M-series Macs and discrete GPU laptops fly.

Best: chat assistants · structured extraction · Q&A

🎮 Tier 4 · Large 2B–7B

Llama-3-8B q4, Mistral-7B q4. ~4-8GB. Needs WebGPU on desktop with discrete GPU. Mobile drops to slow.

Best: complex reasoning · code generation · long-form

☁️ Tier 5 · XL 7B+

70B+ models, GPT-4-class. Server GPU only. Use when client-side hardware can't fit the weights.

Best: RAG · multi-step reasoning · vision-language

🔀 Hybrid · Server fallback

Detect device tier, route small models client-side and large models to your API. Best of both.

Best: production chat · variable hardware fleet

05 Browser Support & The WASM Fallback

Transformers.js v4 runs the SAME model code on WASM and WebGPU. The fallback is automatic — your app degrades to ~3-5× slower CPU inference on browsers without WebGPU.

BackendStatusBrowser coverageNotes
WebGPUPrimary path~82% (Chrome 113+, Edge 113+, Safari 18+, Firefox 141+)5-15× faster than WASM. Compute shaders via ONNX Runtime Web C++ rewrite.
WASM (SIMD + threads)Universal fallback~99% (every browser since 2019)~3-5× slower than WebGPU but reliable. Same model file, same API.
WebNNExperimental (2026)Chrome 137+ behind flag, Edge 137+Direct NPU/GPU access. Future native-OS acceleration. Not production-ready.
Server GPUAlways-available100% (depends on your backend)When model >2B params, when RAG/long-context is needed, or mobile WebGPU is unreliable.

The device-selection one-liner

// Transformers.js v4: ask for WebGPU, accept whatever is offered
import { env } from "@huggingface/transformers";

// Prefer WebGPU when available, fall back to WASM silently
env.backends.onnx.wasm.proxy = false;          // use the Web Worker proxy for large models
env.useWasmCache = true;                  // survive offline reloads after first download

const pipe = await pipeline("text-generation", "onnx-community/Llama-3.2-1B-Instruct", {
  device: "webgpu",                       // tries WebGPU first
  dtype: "q4f16"                          // 4-bit weights, 16-bit activations — ~800MB on disk
});

06 Server GPU vs Client GPU — When to Pick Each

The honest economic split. Most teams dramatically over-build their AI backend. The browser can do more than you think.

DimensionClient-side (Transformers.js)Server-side (OpenAI / vLLM)
Per-query cost$0 (user's GPU does the work)~$0.0001–$0.01 per request
Latency~50–200ms after model loads (no network)~300–1500ms (network + queue + inference)
Privacy100% on-device — input never leavesData sent to third party; SOC2/HIPAA concerns
Offline supportYes after first cache (env.useWasmCache)No — requires internet
Model size limit~2B params for cross-device (8B+ on desktops)Unlimited (server GPU scales)
Setup complexity3 lines (pipeline + run)API key, rate limits, billing, vendor lock-in
MaintenanceZero (model + runtime pinned in npm)Vendor deprecations, pricing changes, outages
Best forEmbeddings, classification, sentiment, NER, short Q&A, semantic search, on-device triageRAG, 70B+ reasoning, long-context, multi-modal agents, code generation

💡 The hybrid pattern most teams miss

Route small/fast inference client-side (classification, embeddings, NER) and large/slow inference server-side (long-context RAG, complex reasoning). The result: 5-10× cheaper inference bills at better latency for 80% of queries. Most teams pay server GPU for what the browser could have done in 100ms.

07 Direct Applications — OpenDrones Mission Control

Five production patterns where the browser does the inference that used to require a server. All ship-today with Transformers.js v4 + WebGPU.

🚁 Aerial Footage Triage

MobileNetV4 runs on each captured frame in a Web Worker. Pilot uploads 4K flight video → client classifies every 5th frame → only anomaly frames go to human review. 95% reduction in human-review time for tower / solar / pipeline inspections.

⚡ Telemetry Anomaly Detection

MiniLM or DistilBERT reads streaming telemetry as embedded tokens (battery, GPS, altitude, attitude). Local anomaly score lights up red before the drone even hits a problem. Pairs with the WebGPU airspace view (P2).

🎙️ Pilot Voice Commands

Whisper-tiny (~40MB) runs in the browser tab. Pilot says "Return to home" or "Pause mission". No server round-trip, works in low-connectivity areas (rural inspections, search-and-rescue).

🔍 Semantic Flight Log Search

mxbai-embed-xsmall computes vectors for every flight log entry. Local cosine similarity search. Pilot types "inspections near tower farm" → instantly returns the 3 most semantically similar flights. Zero API cost, works offline.

🤖 Compliance Report Drafting

Phi-3-mini (3.8B q4) runs locally on desktop. Pilot hits "Draft Part 107 report" → model reads flight telemetry + captured frames + weather data → outputs a structured compliance summary. Pilot edits, doesn't write from scratch.

📡 Offline-First Mission Planning

PWA installs with the model cached. Pilot plans mission in airplane mode, syncs when online. The same `env.useWasmCache = true` flag that runs ASR offline also runs flight planning offline.

11 Why P2 — And When To Promote To P1

This entry slots in at P2 alongside WebGPU (the foundation it depends on). Three triggers would move it to P1.

Why P2 (not P1)

  • Depends on WebGPU (P2) and the modern CSS toolkit stack — ships through composition, not in isolation
  • Model downloads (~10-500MB) are still a UX barrier; teams need caching strategy
  • Most Molt clients don't ask for AI features yet — but every Molt client will ask in the next 12 months
  • Production deployment patterns are still emerging; Hugging Face v4 shipped March 2026, follow-ups ongoing

Triggers to promote to P1

  • A Molt client asks for AI features on a production site (timing-driven)
  • OpenDrones adopts in-browser telemetry anomaly detection as the v2 default (planned for Q3 2026 sprint)
  • WebGPU exceeds 90% global coverage AND bundle size drops below 500KB for the smallest useful models
