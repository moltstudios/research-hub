Media Capabilities: the mediaCapabilities capability tier

One object, two methods, three booleans. navigator.mediaCapabilities.decodingInfo() answers the question every media site gets wrong: can this visitor's device actually decode this file, at this size, without dropping frames and without flattening their battery?

Our catalog had the whole media stack — WebCodecs, MediaRecorder, MSE, WebRTC, the Image Decode tier — and zero coverage of the capability oracle that sits above all of them. The reason is a trap: half the API does not work in shipping Chrome, and the error message it throws is a lie about the spec.

Everything below is measured in your browser, in this page, right now. Nothing is quoted from documentation.

Chromium 155 / 148 · Brave 154 · WebKit 26.5 · 10 probe suites · measured 2026-10-28 · all lanes re-run in this visitor's browser on load

1 · The specimen — ask the oracle three questions

Three questions, one API. supported (can it at all), smooth (at the framerate you asked for), powerEfficient (without burning the battery). All three are booleans and they are not the same question — the page below proves it.

—

THE THREE-BOOLEAN LAW. supported is a codec+container question. smooth is a codec+size+framerate question. powerEfficient is a hardware question that the codec only partly controls. The same codec can be supported + smooth and still be not powerEfficient — and on a phone that third boolean is the one your users feel.

2 · The dead lane — encodingInfo({type:'record'}) is in the spec and is NOT in Chrome

The Media Capabilities spec lists two encoding types: "record" (MediaRecorder) and "webrtc" (RTCPeerConnection). MDN documents both. The W3C web-platform-tests suite asserts both. Chrome ships the enum member in its IDL. And yet —

—
THE RECORD-IS-DEAD LAW (headline #1). In shipping Chromium 155, Chromium 148 and Brave 154, encodingInfo({type:'record', …}) rejects with:
TypeError: The provided value 'record' is not a valid enum value of type MediaEncodingType.
The error message is false. "record" is a valid MediaEncodingType — it is the first member of the enum in the spec, in MDN, in the WPT, and in Chromium's own media_encoding_configuration.idl.

Why: Blink gates the whole record path behind a runtime feature called MediaCapabilitiesEncodingInfo, declared in runtime_enabled_features.json5 with status: "experimental" — i.e. off by default. The source of media_capabilities.cc reads:

if (config->type() == V8MediaEncodingType::Enum::kRecord &&
    !RuntimeEnabledFeatures::MediaCapabilitiesEncodingInfoEnabled()) {
  exception_state.ThrowTypeError(
      "The provided value 'record' is not a valid enum value of type "
      "MediaEncodingType.");
  return EmptyPromise();
}

Proof, not inference: we re-ran the identical battery with the flag flipped — --enable-blink-features=MediaCapabilitiesEncodingInfo — and the record lane opens on all three Chromium-family engines, with real verdicts (H.264 supported+smooth+powerEfficient, Opus supported but not smooth, VP9 unsupported). No other change was made. The error string is a hard-coded lie that happens to be technically true of the enabled feature set, not of the enum.

THE WEBKIT SPLIT. WebKit 26.5 accepts type:'record' — the lane exists — but returns supported:false for every codec and audio format we tested (H.264, VP8, VP9, AV1, HEVC, MPEG-4 Part 2, Opus, AAC). So the practical situation is: one lane is dead-but-well-documented (Chromium), the other is alive-but-empty (WebKit). There is no engine where the record lane gives you a useful answer.

The production workaround — gate the recorder on MediaRecorder.isTypeSupported()

You do not need encodingInfo to choose a recording codec. MediaRecorder.isTypeSupported(mime) answers "can this engine record this" directly, it is a synchronous boolean, and it works in every engine. Reserve encodingInfo for the transmit lane.

3 · The 64-pixel floor — Chromium's hardware path has a minimum surface

Nobody expects powerEfficient to depend on resolution — the codec and the hardware do that. It does. Sweep the size and watch it flip at exactly one pixel. And note the engine row underneath the ladder: this floor is a Chromium-family property, not a web standard.

—

THE MIN-DIMENSION-64 LAW (headline #2) — CHROMIUM FAMILY ONLY. On Chromium 155 / 148 and Brave 154, for the hardware-accelerated decoders (H.264, VP9, AV1), powerEfficient is false below 64 px and true from 64 px — and the floor is on the smaller of the two dimensions, not the larger, not the area, not the diagonal:
63×64 pe=false · 64×63 pe=false · 64×64 pe=true · 65×64 pe=true · 16×16 pe=false · 1×1 pe=false
The rule that fits every Chromium-family measurement: powerEfficient === (min(width, height) >= 64) for H.264 / VP9 / AV1.
THE ENGINE SPLIT — WEBKIT HAS NO FLOOR. WebKit 26.5 reports powerEfficient:true for H.264 / VP9 / AV1 at every size, including 1×1. The ladder above is live: if you are reading this in Safari, the 63 px rung will say P=true and that is the correct WebKit answer, not a broken measurement. The floor is a property of the Chromium hardware path, not of the API.
THE HEVC EXEMPTION. In Chromium, HEVC is exempt from the floor — it reports powerEfficient:true at 16×16 and 32×32. It is also the one codec that reports supported:false at 1×1 while still reporting smooth:true — a genuinely odd combination (a decoder that cannot decode a frame, smoothly). Do not build a ladder on smooth alone.
THE VP8 LAW — the codec with no hardware behind it. VP8 is supported:true and smooth:true at every size from 16×16 to 7680×4320 — and powerEfficient:false at every one of them, in every engine. VP8 is the one codec in the matrix with a software-only decoder on this platform. A VP8 stream decodes fine and burns the CPU doing it.
THE AUDIO LAW — MDN IS WRONG IN WEBKIT. MDN states: "All supported audio codecs report powerEfficient as true." In the Chromium family that is exactly right — AAC-LC, HE-AAC, Opus, Vorbis, FLAC, MP3 and PCM all report supported:true, smooth:true, powerEfficient:true. In WebKit 26.5 it is false: AAC-LC and Opus report supported:true but smooth:false and powerEfficient:false, and MP3 and FLAC are unsupported outright. A docs rule that holds in three engines and fails in the fourth is a platform rule, not an API rule — branch on the boolean, never on the documentation.

4 · The MIME law — the same codec, two lanes, two different verdicts

The webrtc lane does not accept the same MIME strings the file lane does. It wants RTP-style names, and it answers supported:false — with no error, no warning, no rejection — when you hand it a file-style MIME string.

—

THE WEBRTC-MIME LAW (headline #3). For the webrtc lane, contentType must be an RTP MIME type — video/VP8, video/H264, video/VP9, video/AV1, video/H265, audio/opus — matching what RTCRtpSender.getCapabilities() reports. Write 'video/webm; codecs="vp8"' and you get a clean supported:false. The codec is fine. The container is not the one that goes on the wire.

This matters because the file-lane spelling is what almost every tutorial shows, and the webrtc-lane spelling is what a real peer connection needs. Copying a config between the two lanes produces a silent false.

5 · The DRM lane — a single object, not an array

The encrypted-media path takes a keySystemConfiguration. The spec, MDN and the WPT all use a single object. A large share of blog posts show an array — and an array is not a crash, it is a confusing TypeError about a property that does not exist on an array.

—
THE SINGLE-OBJECT LAW (headline #4). keySystemConfiguration: { keySystem: 'org.w3.clearkey' } works. keySystemConfiguration: [ { keySystem: 'org.w3.clearkey' } ] rejects with "Failed to read the 'keySystem' property … Required member is undefined" — because an array has no keySystem property, and keySystem is a required member of MediaCapabilitiesKeySystemConfiguration.

The rest of the DRM grammar, measured

THE WORKER-AND-WEBRTC WALLS. keySystemConfiguration on the webrtc lane → TypeError: The keySystemConfiguration object cannot be set for webrtc MediaDecodingType. The same query inside a Worker → InvalidStateError: Encrypted Media decoding info not available in Worker context. (Chromium-family). WebKit has neither wall: it answers from a worker and simply omits keySystemAccess from the result.
THE RESULT-SHAPE SPLIT. Chromium's decodingInfo() resolves { keySystemAccess, powerEfficient, smooth, supported }. WebKit resolves { configuration, powerEfficient, smooth, supported } — no keySystemAccess at all. Code that reads result.keySystemAccess and calls .createMediaKeys() on it will find undefined in Safari, not null. Branch on the property's presence, never on its truthiness.

6 · The two-tier validation grammar — reject vs resolve-false

"This codec is unsupported" and "you wrote the config wrong" are two different outcomes, and they have two different shapes. A malformed MIME string rejects the promise. A well-formed MIME string with an unknown codec resolves with all three booleans false and prints a console warning.

—

THE REJECT/RESOLVE LAW (headline #5). Shape errors — unparseable MIME, wrong media family, a stray MIME parameter, a trailing semicolon, an out-of-range enum — reject the promise with a TypeError. Codec errors — an unknown codec string, an unknown media type, several codecs in one string, an unsupported profile — resolve with supported:false and emit console.warn("Failed to parse video contentType: …"). The second tier is easy to miss if you only look at the return value: you get a perfectly well-formed result object full of false.
THE REQUIRED-MEMBER LAW. A video configuration needs all five of contentType, width, height, bitrate, framerate. Omit bitrate and you get TypeError: … Failed to read the 'bitrate' property … Required member is undefined. The same for framerate, width and height. Audio needs only contentType; channels, bitrate and samplerate are optional. This is the single most common copy-paste failure — every MDN example includes bitrate and half the blog posts drop it.

7 · The cross-check — four oracles, one answer

The temptation with a new API is to trust it blindly. It does not need to be trusted: decodingInfo(), MediaSource.isTypeSupported(), MediaRecorder.isTypeSupported() and VideoDecoder.isConfigSupported() are four independent oracles and they agree. Here is the agreement, measured.

—

THE FOUR-WAY AGREEMENT LAW. Across H.264, VP8, VP9, AV1, HEVC, MPEG-4 Part 2 and VP9 profile 2, the four oracles returned identical verdicts in every engine: MPEG-4 Part 2 and VP9 profile 2 are unsupported everywhere; the other five are supported everywhere (Chromium's WebKit difference on AV1/HEVC is the hardware question, not the codec question — see the engine table).

8 · The cost law — the first call is the expensive one

The oracle is not free on the first question. It has to spin up a decoder probe, ask the platform what it can do, and cache the answer.

—

—

THE COLD-CALL LAW (headline #6). The first decodingInfo() for a given codec costs 7–75 ms in Chromium (we measured 73.4 ms for the first H.264 file query, 75.3 ms for the first VP8 webrtc query, 7.2 ms for VP9). Every subsequent call for the same lane is 0–0.7 ms. If your capability ladder asks eight codecs on page load, budget for one cold call and seven free ones — and do not put the ladder on the critical rendering path.

10 · OpenDrones — the cockpit codec ladder

The pilot cockpit receives H.264 over WebRTC from the aircraft. Choosing the codec by hand at build time is wrong: the right codec depends on the operator's laptop, which is the one machine we do not control.

—
// The transmit ladder — RTP MIME types, best-first, stop at the first good answer.
const LADDER = [
  { mime: 'video/VP9',  label: 'VP9',  note: 'best quality per bit' },
  { mime: 'video/AV1',  label: 'AV1',  note: 'best efficiency' },
  { mime: 'video/H264', label: 'H264', note: 'universal fallback' },
  { mime: 'video/H265', label: 'H265', note: 'hardware-only on some laptops' },
];
for (const c of LADDER) {
  const r = await navigator.mediaCapabilities.decodingInfo({
    type: 'webrtc',
    video: { contentType: c.mime, width: 1280, height: 720, bitrate: 2_500_000, framerate: 30 },
  });
  if (r.supported && r.smooth) { sendVia(c.mime); break; }
}
THE RECORDER FALLBACK. For the flight DVR the answer is not in this API at all in Chromium: encodingInfo({type:'record'}) is dead there (law #1). Gate the recorder on MediaRecorder.isTypeSupported(mime) instead — a synchronous boolean that works in every engine — and use encodingInfo only for the transmit side.
THE BATTERY LAW FOR THE GROUND STATION. A cockpit running on battery all day should ask for powerEfficient, not supported. On this platform VP8 is supported and smooth but never powerEfficient — so a VP8 downlink on an ungrounded laptop is a hot lap, not a smooth one.

11 · Molt — the client-site media preflight

Client sites are full of video: showreels, product loops, case-study reels. The preflight question is not "is this codec popular" but "can this visitor play this file without the page getting hot".

—
// Client preflight — pick a rendition the visitor can actually decode.
async function pickRendition(sources) {           // sources: [{url, mime, w, h, bitrate}]
  for (const s of sources) {
    const r = await navigator.mediaCapabilities.decodingInfo({
      type: 'file',
      video: { contentType: s.mime, width: s.w, height: s.h, bitrate: s.bitrate, framerate: 30 },
    });
    if (r.supported && r.smooth) {
      return { url: s.url, hw: r.powerEfficient };
    }
  }
  return null;   // no rendition this device can play — ship a poster frame
}
THE 64-PIXEL LAW, APPLIED TO DESIGN — IN CHROMIUM. A 32×32 looping avatar video is supported but powerEfficient:false in the Chromium family — software decode. Below 64 px the correct answer for a brand site is an image, not a video. (In WebKit the same asset reports powerEfficient:true, so the preflight's own boolean decides — which is the point of running it.)
THE POSTER-FRAME LAW. When the ladder returns nothing, the fallback is a poster frame — not a second attempt with a bigger codec. The preflight runs before the player mounts, so the visitor never sees a spinner they cannot resolve.

13 · The ten-rule ship checklist

  1. Always pass all five video members: contentType, width, height, bitrate, framerate. A missing one is a TypeError, not a false.
  2. Branch on the promise, never on a synchronous throw — every validation failure in this API is a rejected promise.
  3. Treat supported:false and a rejected promise as different events: one is "this device cannot", the other is "your config is wrong".
  4. Never gate a recorder on encodingInfo({type:'record'}) in Chromium — use MediaRecorder.isTypeSupported().
  5. In the webrtc lane use RTP MIME types (video/VP9), not file MIME types (video/webm; codecs="vp09…").
  6. Ask for powerEfficient, not just supported, on any battery-powered surface.
  7. Below 64 px in either dimension, expect no hardware decode — ship an image.
  8. Read result.keySystemAccess by presence, not truthiness: WebKit omits the property entirely.
  9. Keep the capability ladder off the critical rendering path — the first call costs 7–75 ms.
  10. Cross-check one codec against MediaSource.isTypeSupported() before you ship the feature — four independent oracles, zero cost, and they agree.
