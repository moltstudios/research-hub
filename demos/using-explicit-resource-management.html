Cleanup becomes a language feature: using and await using

Explicit Resource Management ties a resource's cleanup to its block scope. The engine calls [Symbol.dispose]() on every exit path — return, throw, break — so the try/finally tax and the leak it guards against disappear. Finalized in ES2026; running natively in Chrome 134+, Firefox 134+, and Node; WebKit shipped it in Safari Technology Preview 250 on August 13, 2026 — the last engine to come online.

02

JavaScript's silent leak epidemic

JavaScript has garbage collection, but GC only reclaims memory. It knows nothing about the resources behind the memory: OS file handles, WebSocket connections, stream locks, GPU buffers, event listeners, timers, advisory locks. Every one of those needs an explicit release call — and the language has never had a standard way to guarantee it happens.

Leak pattern

The forgotten finally

Code acquires a resource, work throws before the cleanup line runs. Without try/finally, the cleanup is skipped entirely. Reviewers see the happy path; the error path leaks.

Leak pattern

The locked stream

response.body.getReader() takes a lock. If reading throws before releaseLock(), the stream is stuck locked — nobody else can ever read it again. A classic in fetch pipelines.

Leak pattern

Listener accumulation

SPAs that re-render panels add window listeners on every mount and remove them on a manual teardown path that one early return skips. Memory grows across navigation.

Leak pattern

Half-torn-down setups

Setup acquires A, B, C. C fails. Cleanup code that only knows how to tear down all three (or none) leaves A and B orphaned. Correct partial-rollback needs LIFO discipline — handwritten every time.

Leak pattern

The masked error

Body throws E1, then finally throws E2. E2 replaces E1 — you debug the cleanup failure while the real bug (E1) vanishes. The language had no way to carry both.

The fix

One protocol, every exit path

using makes cleanup a language guarantee instead of a code-review discipline. Every pattern above is one declaration away from impossible.

The prior art: C# using, Python with, Java try-with-resources, C++ RAII. JavaScript is the last major language to standardize scoped cleanup — and the design that landed is clean: two declarations, two symbols, two stack classes, one error type.

03

using in 60 seconds

Declare a resource with using instead of const. When the block exits — normal return, thrown exception, break, continue — the engine calls [Symbol.dispose]() on it. Multiple using declarations dispose in reverse order (LIFO), like nested scopes.

Before — 7 lines, 2 failure modes 
const conn = pool.acquire();
try {
  return conn.query(sql);
} finally {
  pool.release(conn); // forget this once = leak
}

Works — until someone refactors the function, adds an early return, or the release itself throws and masks the query error.

After — the scope owns the cleanup 
function getUser(id) {
  using conn = pool.acquire();  // disposable
  return conn.query(sql);
} // release runs here — always, LIFO, error-safe

Any object with a [Symbol.dispose]() method is a disposable. That's the entire contract.

The rules that matter

RuleDetail
using is block-scoped onlyMust appear inside a block, function body, loop body, or class static block. Top-level using is a syntax error — wrap it in a block or an IIFE.
Disposal is LIFOThree using in one block dispose in reverse declaration order — dependencies acquired first are released last, which is the correct teardown order.
null / undefined are legalusing x = maybeNull; is fine — disposal skips nullish values. Conditional resources need no wrapper dance.
Value must be disposableAnything else throws a TypeError at the declaration — loud, immediate, not at block exit.
Disposal is synchronoususing calls [Symbol.dispose]() and does not await it. For promises, use await using.
const-like bindingReassignment is a syntax error, exactly like const.

Making your own disposables

// Any object with the well-known symbol method qualifies
const timer = setInterval(tick, 1000);
const disposableTimer = {
  timer,
  [Symbol.dispose]() { clearInterval(this.timer); }
};

{
  using t = disposableTimer;
  // ... tick loop running ...
} // interval cleared, guaranteed

Until web APIs grow native [Symbol.dispose] methods (streams and readers are the leading candidates), a one-line wrapper object is the whole integration cost.

04

await using — async cleanup without lying

Most real resources clean up asynchronously: database connections release with a round-trip, sockets flush before close, file handles fsync. await using declares an async-disposable and awaits its [Symbol.asyncDispose]() at scope exit — the block's promise doesn't settle until cleanup finishes.

Before — silent, un-awaited release 
const conn = await pool.acquire();
try {
  return await conn.query(sql);
} finally {
  pool.release(conn); // floating promise —
  // server may not have it back yet
}
After — cleanup completes before the caller resumes 
class PooledConn {
  constructor(conn, pool) { this.conn = conn; this.pool = pool; }
  async [Symbol.asyncDispose]() {
    await this.pool.release(this.conn);
  }
}

async function getUser(id) {
  await using conn = new PooledConn(await pool.acquire(), pool);
  return conn.conn.query(sql);
}

Fine print

• await using prefers [Symbol.asyncDispose]() and falls back to [Symbol.dispose]() — sync disposables work in async scopes, not the reverse.
• Disposal errors in an async scope reject the block's promise (wrapped in SuppressedError if they mask an earlier error — see section 09).
• Needs an async context: async function, async arrow, module top level inside an async IIFE. await using in a plain function is a syntax error.

The V8 team's canonical example, simulated deterministically on this page. A reader takes a lock on a stream; a parse error strikes mid-read. Watch the lock state under manual cleanup vs using — this section runs real native syntax when your engine supports it.

Manual cleanup — the lock leaks 
const reader = stream.getReader();
let chunk = await reader.read();
parse(chunk);          // 💥 throws here
reader.releaseLock(); // never runs — stream stuck

DisposableStack — dynamic cleanup for messy reality

Real code doesn't acquire all resources in one neat declaration list — it acquires conditionally, in loops, across helper calls. DisposableStack aggregates arbitrary cleanups and disposes them LIFO. The stack is itself disposable, so it composes: using stack = new DisposableStack() is the master pattern.

The four methods + one property

stack.use(res)A disposable objectResource already has [Symbol.dispose](). Returns the resource, so it chains: const t = stack.use(timer).
stack.adopt(res, fn)Any value + cleanup fnResource is not disposable; you supply the cleanup. stack.adopt(map, m => m.remove()).
stack.defer(fn)Just a functionNo resource at all — "also do this at teardown." Python's contextlib.ExitStack.callback.
stack.move()—Transfer ownership: empties this stack into a new one (see section 08).
stack.disposed—Boolean — has this stack already been disposed?

Why reverse order? Because correct teardown mirrors setup: the thing you acquired last is the thing that depends on everything acquired before it. Disposing in reverse guarantees no dependency is yanked out from under a live consumer. Click through a Mission-Control-style boot sequence.

08

move() — ownership transfer between scopes

The sleeper feature. A splash screen acquires a live telemetry stream; the main app wants to keep it. You can't return out of a using scope without triggering disposal — that's the point. move() is the escape hatch: it transfers every cleanup into a fresh stack whose lifetime you control.

function withSplash(handoff) {
  using scope = new DisposableStack();
  const stream = scope.use(connectTelemetry());

  if (needsSplash) {
    runSplash(stream);
    handoff(scope.move()); // ← ownership OUT, no dispose
  } // scope exits empty — nothing disposed
}

async function main() {
  await using lifetime = new AsyncDisposableStack();
  withSplash(s => lifetime.use(s));
  // stream lives until `main`'s scope exits — app lifetime
}

Ownership-transfer used to be hand-rolled booleans and null-checks scattered through teardown code. It's now one method call with a type-checked contract.

09

SuppressedError — no more vanishing bugs

The subtlest win. Your code throws E1 (the real bug). During unwinding, a cleanup throws E2. Old JS: E2 replaces E1 and the real bug evaporates from the stack. With using, the engine throws a SuppressedError carrying both: .error is the most recent (E2), .suppressed is what it masked (E1).

OpenDrones Mission Control — the panel teardown pattern

Mission Control is a vanilla-JS dashboard, which makes it the perfect adopter: every panel (map view, telemetry, fleet list) acquires resources on mount and must release them on unmount. One DisposableStack per panel turns component lifecycle into a language-level guarantee — including the hard part: partial failures during setup.

map telemetry-stream gpu-buffers battery-sub listeners
Panel unmounted…

The pattern in production shape

function mountFleetPanel(host) {
  using setup = new DisposableStack(); // rollback scope

  const map = setup.adopt(new maplibre.Map(cfg), m => m.remove());
  const stream = setup.use(telemetry.subscribe());     // asyncDisposable
  const buffers = setup.adopt(gpu.allocatePool(), b => b.destroy());
  setup.defer(() => log('fleet panel torn down'));

  // Hand the live stack to the app-lifetime registry — panel stays alive.
  // If ANY step above threw, `using setup` rolls back the earlier ones (LIFO).
  return panelRegistry.register(setup.move(), host);
}

Setup-rollback is the underrated half: if GPU allocation (step 3) throws, the map and telemetry subscription from steps 1–2 are disposed automatically on scope exit. Handwritten versions almost always leak there.

11

React, Next.js & where using actually fits

Honest framing: using does not replace useEffect cleanup — a component's lifetime is not a block scope, and effects outlive the render function. But React apps are full of block-scoped resource work where it's a strict upgrade.

Great fit — block-scoped work

• Event handlers: per-gesture/per-click acquisitions (streams, pointers, audio sessions) cleaned when the handler's block exits.
• Route loaders / actions: with the Navigation API, event.intercept({ async handler() { await using … } }) guarantees stream readers release even when a navigation is superseded mid-flight.
• Server code (RSC, route handlers, scripts): Node 25+ runs it natively — DB handles, fs handles, advisory locks. Adopt today.
• Analysis pipelines: canvas/OffscreenCanvas contexts, AudioContexts, ImageBitmaps — the classic "create → process → close" utility function.

Not a fit — cross-scope lifetimes

• Component lifetime → keep useEffect return (or wrap a DisposableStack in a ref and dispose on unmount — a clean hybrid).
• Global singletons (one MapLibre style, one WebGPU device) → app-lifetime registry, not scope.
• Client Components on old targets → TypeScript downlevels it, but each using becomes a try/finally — fine, just know it's there.

TypeScript: you've been able to write this since 5.2

TS 5.2 shipped the syntax with downleveling — target: ES2022 compiles every using into the exact try/finally you'd write by hand, LIFO-correct, with Symbol.dispose polyfilled via helpers. What changed with ES2026 finalization: set "target": "ES2026" (or per-build for server bundles) and the syntax ships as-is to engines that run it natively. Zero-risk ladder: write it now → old targets get correct downlevel → raise targets as support lands → delete the helpers.

SurfaceDo this today
Node servers / scripts / RSCShip native — Node 25+/V8 13.8+, TS target ES2026 for server builds.
Browser bundles (Molt client sites)Write now, downlevel — TS target ≤ES2022 emits try/finally. No behavior change.

Libraries published to npmAdd [Symbol.dispose]/[Symbol.asyncDispose] methods to your handle-like exports — harmless where unknown, instantly useful where supported. This is the ecosystem unlock.

Why this matters to us

OpenDrones: Mission Control's vanilla-JS panel lifecycle (map + WebTransport + GPU + listeners) gets a language-guaranteed teardown; setup-rollback kills the partial-boot leak class; move() models splash→app stream handoff; Node-side mission scripts adopt today.

Molt Studios: every client app with streams, maps, media sessions, or canvas pipelines ships fewer leak bugs; published libs gain disposable handles; TS downleveling means zero-risk adoption in the current build stack — and a clean story for Safari when stable lands this fall.

Adoption verdict

P3 — adopt asymmetrically, now. Server/Node: native today, no reason to write another manual try/finally. Bundled browser code: write it, let TS downlevel, delete the helpers when Safari stable ships (projected fall 2026 → then Baseline ~2027). The defect class it kills — leaked handles, stuck stream locks, masked errors — is a real production cost, but it's code-quality, not user-facing capability, and Safari stable is the gate on the last mile.
