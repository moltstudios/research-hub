§01Capability surface — two worlds, one handle family

What the engine exposes on a secure origin, before any permission is asked.

The API is really two products sharing one interface family: the picker tier (showOpenFilePicker / showSaveFilePicker / showDirectoryPicker — user-visible disk, Chromium-only) and the OPFS tier (navigator.storage.getDirectory() — origin-private, cross-browser: Chrome 86+, Firefox 111+, Safari 15.2+). Every FileSystemFileHandle from either world exposes the same methods, but the engine truth splits hard below the surface — §03, §08, §09.

§02The activation-wall split — three pickers, two different rejections

No gesture, live calls, 4s timeout-wrapped.

MDN documents one wall: "SecurityError — not called via a user interaction". Live on CfT 154 there are three walls in fixed order: binding validation (TypeError, pre-gesture), the activation gate (SecurityError "Must be handling a user gesture" — the documented wall), then the dialog (AbortError — headless has no dialog, so it aborts instantly; a real user's Cancel is the same signal). The probe log also captured a fourth variant under automation-carried calls (NotAllowedError: User activation required for save/dir) — the rejection name depends on invocation context, which is why every generic "catch SecurityError" snippet misses.

§03The headless AbortError truth — a real click changes nothing

Trusted-click button; transient activation verified in-band.

Click the button — a genuine trusted gesture (navigator.userActivation.isActive === true inside the handler). Past the activation gate, a headless picker still aborts: AbortError: The user aborted a request. No dialog can render, and the engine's answer is abort — not the BLE/WebUSB family's eternal pend, and not Window Management's auto-NotAllowedError: a third headless-chooser shape, fastAbort. (The same call from page script with no gesture dies earlier at the §02 wall with SecurityError.) Production consequence: your CI can exercise every code path except the granted-picker path — and a headless abort looks exactly like a user pressing Cancel.

§04Validation walls — the binding layer outranks the gesture gate

Malformed options, no gesture: which wall fires first?

Live order on CfT 154: WebIDL dictionary validation → activation gate → dialog. A filter extension without a dot ('txt' instead of '.txt') throws TypeError: Extension 'txt' must start with '.' with no gesture at all — the same binding-boundary layering as BLE's manufacturerData:[{}], but here it's the documented norm, not the exception. An unknown MIME ('nope/nope') passes the binding layer and dies at the activation wall instead. types: [] is legal (it means "no filter") and goes all the way to the dialog — where it aborts like §03.

§05OPFS — the no-picker tier that ships everywhere

navigator.storage.getDirectory(): the origin-private filesystem, zero prompts.

OPFS is the tier you can build on unconditionally: no pickers, no gesture, no permission state to track — the root handle arrives pre-granted (queryPermission({mode:'readwrite'}) → 'granted', always). The root's name is the empty string — don't render it as a label. Storage Buckets (navigator.storage.buckets / openBucket) — the per-app partitioning layer above OPFS — are absent on flag-clean CfT 154 despite launch posts; capability-probe before promising them.

§06createWritable atomicity — invisible until close

Write, read mid-stream, read after close: the temp-swap contract.

Every createWritable() writes to a sibling temp file (your file name + .crswap) and atomically renames at close(). Live consequence: reads through getFile() return the old bytes until the stream closes — even in the same context, even after multiple await write() calls. Two writes can land on one stream (they append at the shared position); keepExistingData: true starts the swap as a copy of the current file; seek() and the {type:'write', position, data} form give random access; the stream has no .size — track offsets yourself.

§07The .crswap ghosts — orphaned streams never land, and you can see them

The abandoned-writable trap, and the directory lock it holds.

Forget close() and your data never lands — it stays in name.crswap forever (GC is not a close). Worse, the ghost is enumerable: async iteration of the parent directory lists it as a regular file. And while any stream to a file is open, removeEntry(dir, {recursive:true}) on its parent throws NoModificationAllowedError — the lock releases only at close(). §08Sync access handles — the worker-only speed lane

Window: the method is removed. Worker: numbers, not promises.

On the window thread createSyncAccessHandle doesn't reject — it doesn't exist (TypeError: not a function; the interface itself is undefined on window). In a worker it resolves — and on CfT 154 the methods are synchronous: write()/read() return byte counts (numbers), not Promises. getSize() after close() → InvalidStateError; close() a second time → no throw (idempotent). Reads and writes take {at: offset} — a fixed-record telemetry log is pure pointer math. Cross-browser: Chrome 102+, Firefox 111+, Safari 15.2+ — but OPFS-only; no sync lane exists for picker-granted files.

§09Handle transfer — cloneable, NOT transferable

postMessage with and without the transfer list.

FileSystemHandle is serializable, not transferable: worker.postMessage({handle}, [handle]) throws DataCloneError: Value at index 0 does not have a transferable type. Drop the transfer list and structured clone delivers the worker a live handle to the same file — the worker reads what main wrote, writes back, and main sees the new bytes after the worker's close(). Both contexts keep working handles; clone ≠ move. This is the whole architecture pattern: pick on main (the only place you can), hand to a worker for the heavy I/O.

§10move() & remove() — the maintenance pair

Relocate without copy; delete by handle, not by parent lookup.

fh.move(dirHandle, 'new-name') moves atomically inside the same filesystem (content verified byte-exact live). remove() lives on the base FileSystemHandle prototype — an alternative to dir.removeEntry(name) when you already hold the handle. Both are Chromium-only today (BCD: remove 110+, ✗ Firefox/Safari; move live on CfT 154, untracked by BCD) — capability-probe before relying on them.

§11The insecure-origin law — the whole storage surface vanishes

Measured live on plain http:// over LAN (192.168.68.61).

On insecure origins it's not just the pickers: navigator.storage itself is undefined — OPFS, estimate(), persist(), everything, gone as one object. Same object-absent law as Camera/Geolocation/BLE, but applied to the entire storage manager. A LAN kiosk page served over plain http can cache via Cache API but cannot read or write a single OPFS byte.

Live chip reflects this origin's secure state; the insecure row is the recorded engine truth from the probe host (CfT 154, plain http, no page errors).

§12CDP: no door for pickers — and the input fallback that has one

Protocol dump evidence + the automatable alternative.

CfT 154's protocol serves 661 commands; none intercepts an FS Access picker. DOM.setFileInterceptors — the command automation tooling cites for this — is not in the shipped protocol (direct send and post-DOM.enable both reject "wasn't found"; the master protocol typings grep clean). The file doors that exist — DOM.setFileInputFiles, Page.setInterceptFileChooserDialog — answer only <input type="file">. That's the test strategy: picker flows get input[type=file] stand-ins in CI, OPFS paths test directly, and the granted-picker path stays a manual lane.

File objects from either door interop cleanly: getFile() and input files both yield the same cloneable File — pass either to a worker for hashing/encoding.

§13Capstone — OpenDrones flight logger

40 Hz telemetry → batched async lane · 100 Hz fixed-record sync lane · eviction posture. Fully deterministic, offline.

A mission logger needs three things the tiers above provide exactly: an append-only session file (createWritable + offset math — no per-tick swap churn), a fixed-record binary lane for high-rate IMU frames (createSyncAccessHandle in a worker: 24-byte records, {at} writes, one flush() per batch), and an eviction posture (estimate() + persist() so a storage-pressure phone doesn't eat the flight history).
