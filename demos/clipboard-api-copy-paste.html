§1Live capability matrix — what THIS browser actually ships

Probed at load, no assumptions. Every badge above is checked against the engine below — including the three engine-divergent features (change event, custom formats, presentationStyle) that decide whether a copy/paste UX degrades or breaks cross-engine.

Why this section exists: the Async Clipboard API is four APIs wearing one name — writeText/readText (universal since 2020), write/read with ClipboardItem (Baseline June 2024, Firefox held it back), the web custom formats extension (Chromium-only), and the brand-new clipboardchange event (Chromium 144+). Feature-detect or your paste button works in Chrome and throws in Firefox.

§2Anatomy — writeText & readText, the universal tier

The 95% path. writeText() resolves after the OS clipboard is actually updated (unlike the old execCommand synchronous lie). readText() returns an empty string — not a rejection — when the clipboard holds no text. That asymmetry is a feature: your paste handler never crashes on an image-only clipboard.

await navigator.clipboard.writeText(payload);          // resolves when the OS has it
const text = await navigator.clipboard.readText();      // '' if clipboard is not text

  






  
§3The security model — permissions, gestures & the focus wall

  
The spec's rules: reads need transient user activation + a paste gesture; writes need the clipboard-write permission or transient activation. Reality per engine (MDN security notes): Chromium honors clipboard-read/clipboard-write permissions (granted once, gestures optional); Firefox & Safari refuse both permissions outright and instead show an ephemeral "Paste" context-menu prompt per read, and require a gesture for every write. One API, three enforcement regimes.

The production bug this section prevents: a copy button that fires writeText() from a setTimeout after an async job finishes. By then the user gesture has expired — Firefox/Safari reject; Chromium only survives if the permission was granted. Pattern that always works: keep the gesture, show pending state, copy when data is ready if still activated, otherwise fall back to a visible "Copy now" reveal. And after any programmatic copy, refocus your button — see §12.






  
§4Rich writes — PNG from a canvas, SVG gate, byte-exact round-trip

  
write() takes ClipboardItems: MIME-keyed Blobs. image/png is the universal image format (Safari 13.1+ accepts PNG writes); image/svg+xml is gated behind ClipboardItem.supports() (Chromium 124+, Safari preview). The round-trip below compares the bytes that come BACK — and finds the macOS pasteboard re-encodes the image: what you paste into Figma is pixel-identical but not byte-identical to what the canvas produced. §5One copy, many formats — the single-item multi-type contract

  
The killer detail everyone misses: a single ClipboardItem carries multiple MIME types of the same data. Copy once as text/plain + text/html — a plain editor receives the text, Google Docs receives the styled table. This is how professional "Copy as…" buttons work: not two writes (the second would clobber the first — the clipboard holds items, last write wins), but one item, several renderings.

  

  
FormatWhat lands
text/plainid,name,battery — paste into a terminal or CSV
text/html<table>… — paste into Docs/Notion/Sheets

  

  
Note the read side: readText() only ever sees the text/plain projection. To know what a target app will get, you must read() and inspect item.types — that's the next section's job.






  
§6Delayed rendering — the clipboard as an IOU

  
Chromium accepts a Promise as the ClipboardItem value: the bytes are not generated until the system actually requests them (user pastes, or another app reads). For heavy payloads — a 4K export, a large CSV — you hand the OS a deferred IOU instead of blocking the click. The probe below timestamps exactly when the promise body runs.

  
const item = new ClipboardItem({ 'text/plain': new Promise(res => {
  // this body may run NOW or LAZILY — the probe timestamps it
  res(heavyPayload);
})});
await navigator.clipboard.write([item]);

  






  
§7Web custom formats — app-to-app data on the clipboard

  
The custom-format extension (Chromium 104+): any MIME type prefixed with web  can ride the clipboard — web application/x-open-drones-mission. Same-origin or cooperating apps read it back via getType(). Crucially, Chromium filters on read: unrecognized non-web custom types don't survive — which is both an interop wall and an anti-exfiltration measure (a page can't sniff arbitrary app-private clipboard formats).

  

    
    
  

  






  
§8clipboardchange — the clipboard becomes observable (Ch 144+)

  
Landmark change hidden in a minor number: from Chromium 144, navigator.clipboard is an EventTarget firing clipboardchange whenever the system clipboard changes — from any app. Sync-your-clipboard UIs no longer need focus or polling. Gated on sticky activation or the clipboard-read permission. Firefox/Safari: not shipped, not signaled.

  

  

  






  
§9The other half: copy/cut/paste events & pastejacking defense

  
Before the async API there was (and remains) the Clipboard Event API: copy/cut/paste events with a synchronous clipboardData, cancellable defaults — still the right tool for editors and intercepting pastes into contenteditable. And its dark twin: pastejacking, where a page's copy handler swaps in terminal escape sequences that execute on paste into a shell.

  
el.addEventListener('paste', e => {
  const plain = e.clipboardData.getData('text/plain');
  const html  = e.clipboardData.getData('text/html');   // '' if absent
  e.preventDefault();                                    // own the default action
  insert(mySanitizer(plain));
});
// pastejacking sentry — strip C0/C1 control chars before anything touches a shell:
const EVIL = /[\u0000-\u0008\u000B\u000C\u000E-\u001F\u007F-\u009F]/;
