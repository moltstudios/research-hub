§2The autocomplete IDL three-way split

The attribute keeps whatever you write, everywhere. The IDL getter (input.autocomplete) lies differently on every engine: Chromium normalizes (lowercases a valid token list, returns "" for an unparseable one), Firefox returns "" for every multi-token list (only bare on/off survive), WebKit validates + lowercases like Chromium. getAttribute() is the only honest read.

§3enterKeyHint — the enum grammar, two truths per element

The IDL is an enumerated reflection (3/3 engines): valid tokens read back lowercased, invalid tokens vanish to "" in the IDL while the attribute keeps the literal, whitespace is fatal, and the setter writes verbatim. It exists on HTMLElement — a plain <div> carries it. Seven valid tokens: enter · done · go · next · previous · search · send.

§4The attribute-selector case wall

Tokens fold in the IDL but never in selectors: [autocomplete="off"] does not match autocomplete="OFF", and [enterkeyhint="go"] does not match "GO" — case-sensitive value matching on all three engines, in CSS rules and in querySelector alike. The hidden=until-found uppercase trap, generalized: author in lowercase or match in lowercase, but never mix.

§5The autofill pseudo pair — and the instrument split

:autofill parses on all three engines, and so does :-webkit-autofill — Firefox ships the prefixed selector for compat. But only Chromium exposes an automation path to a real fill state: the CDP Autofill domain (setAddresses + trigger) performs genuine fills headless and reports per-field fillingStrategy (autocompleteAttribute vs autofillInferred — heuristics). Firefox/WebKit have no such path: their fill-state behavior is a human-hand lane, recorded as an instrument limit, not measured.

§7The anchor-scope law

One fill covers only the anchor's scope. shipping, billing and unprefixed fields are three separate worlds: anchor a shipping field → shipping fills, billing and unprefixed stay empty (×2 reps, stable); anchor billing → billing only. Explicit section-* tokens partition the same way. And the addressFormFilled event overspeaks — it lists every classified field on the form, filled or not: read field values, never the event, to know what happened.

autocomplete="postal-code"filled when an unprefixed field anchors
autocomplete="shipping postal-code"filled when a shipping field anchors
autocomplete="billing postal-code"filled when a billing field anchors

In unscoped mixed forms the fill group is anchor-relative and classifier-segmented — measured: forward bias (anchoring the ZIP filled ZIP + tel but not the email field after them), control-type boundaries and dead (readonly/disabled/hidden) neighbors influence grouping, while a simple text–select–text form fills whole from any anchor. The deterministic lever is the scope token: give every logical group a section-…, shipping or billing prefix and stop depending on adjacency.

The two-anchor checkout: a shipping+billing form needs the user (or your UI) to trigger each scope separately — one fill never crosses. That's not a bug; it's the partition working. Label the second button "Use for billing" and let it re-anchor.

§8The off grammar — and the submission folklore

autocomplete="off" on a field blocks its fill — but a field-level explicit token beats a form-level off (anchored directly, it fills inside an autocomplete="off" form). autocomplete="on" ≡ default. And the big folklore kill: off does not remove the field from submission — FormData carries its value exactly as before.

§9The heuristic fallback — absent ≠ anonymous

Remove every autocomplete token and Chromium's classifier still fills fields whose name hits its dictionary — reported as fillingStrategy: autofillInferred. Measured dictionary hits: email, zip, phone, city, firstname. Measured misses: fname, first_name, postal_code, zipcode, phonenumber, mobile, type=email alone, placeholder text alone. The dictionary is token-exact, not fuzzy.

The format split: the same profile's phone filled as "+14155550100" through autocomplete="tel" but as "4155550100" (national digits) through the name="phone" heuristic — ×2 stable across anchor lanes. If your validation regex demands E.164, the heuristic path fails it. Another reason tokens beat names: the token route is the deterministic format.

Privacy face: adding autocomplete="off" is the only opt-out — an unnamed-looking field with a dictionary name still fills.

§11The state walls

Readonly, disabled, display:none and visibility:hidden fields are classified (the event lists them) but never written. Fields outside any <form> don't fill from a form-anchored trigger. The walls are absolute in the measured lanes — multi-step checkouts that keep later fields readonly until "step 2" are invisible to autofill for the whole first pass.

§12The commit law — autofill meets React

Every filled field fires a real input followed immediately by a real change — isTrusted: true on both, change not waiting for blur. Focus stays on the anchor; filled fields never receive focus events. Consequences: React/Vue controlled inputs see autofill through the same native input event as typing (no synthetic wall), and a change-only listener fires too — but only after the input, so cross-field validation reading "the other field" mid-input reads stale values for one event.

// recorded CfT 149 — anchor at #n-email, two fields in scope:
focusin : n-email  : isTrusted=true   ← your focus() / the user's click
input   : n-email  : isTrusted=true   ← fill writes field 1
change  : n-email  : isTrusted=true   ← immediately, no blur wait
input   : n-zip    : isTrusted=true   ← fill writes field 2
change  : n-zip    : isTrusted=true
// (no focusin for n-zip — filled fields are never focused)

This is also why "clear the form" UIs miss autofilled values: reading el.value in a change handler is correct, but a snapshot taken before the fill (state hydrated at mount) won't see it — listen, don't snapshot.

§13The styling lock

After a real fill, inputs match :autofill and :-webkit-autofill simultaneously, and the UA's tint wins: computed background-color reads rgb(232,240,254) over every author strategy tried — a plain background on the element, a :autofill rule, a :-webkit-autofill rule — and authored background-image is stripped to none. The two measured escape hatches: the inset box-shadow trick and -webkit-text-fill-color.

/* measured on CfT 149 with a REAL CDP-driven fill: */
input            { background: #fff }        /* computed after fill: rgb(232,240,254) — LOSES */
input:autofill        { background: #00aa00 }  /* computed: rgb(232,240,254) — LOSES */
input:-webkit-autofill{ background: #00aaaa }  /* computed: rgb(232,240,254) — LOSES */
input { background-image: linear-gradient(...) } /* computed after fill: none — STRIPPED */

/* escape hatches that survive (computed, verified): */
input:-webkit-autofill {
  -webkit-box-shadow: 0 0 0 1000px #002642 inset;  /* survives — paints over the tint */
  -webkit-text-fill-color: #7fd1ff;                 /* survives — recolors the glyphs */
}

The computed background-color is a lie for what's visible: the surviving inset shadow renders over it. Dark-mode forms must use the shadow hatch or their autofilled fields flash blue-on-blue. Firefox/WebKit tint behavior: human-hand lanes (no automation fill path) — test with a real saved profile before shipping dark themes there.

§15Molt audit — the client form-fill checklist (half a day)

  • 1. Country selects with ISO-code option values — the fill writes "United States"; the select stays blank. Option values (not just labels) must carry plain names.
  • 2. Single-line street inputs that re-parse on "\n" — the fill comma-joins multi-line streets; the parser breaks silently.
  • 3. e2e/React reading el.autocomplete — Firefox returns "" for every token list; asserts pass vacuously. getAttribute only.
  • 4. tel validation demanding E.164 on heuristic-routed fields — the name-based path fills national digits; only the token route is international.
  • 5. Dark themes without the box-shadow hatch — autofilled fields flash the UA blue with light text; background-image hero fields lose their gradient entirely.
  • 6. Multi-step checkouts with readonly later steps — the walls: readonly/disabled/hidden fields never receive the first-pass fill.
  • 7. Forms relying on form-level autocomplete="off" for sensitive fields — field tokens beat it; the off must be on the field.
  • 8. addressFormFilled-style telemetry assumptions — the event overspeaks (lists unfilled fields); assert on values.
  • 9. "Anonymous" fields with dictionary names (email/zip/phone/city/firstname) — they still fill; off is the only opt-out.
  • 10. Uppercase attribute values with lowercase selectors (or vice versa) — the case wall: [autocomplete="off"] never matches "OFF".
  • 11. Snapshot-hydrated forms that never listen — fills arrive as trusted input+change; mount-time state never sees them.
  • 12. enterKeyHint values with typos or spaces — silently "" in the IDL, default key label on mobile; no console warning anywhere.

§16Method, ledger & falsifications

Method. Grammar lanes (reflection, selectors, IDL setters) live-probed on CfT 149 + Firefox 151 + WebKit 26.5 over a plain-HTTP loopback, fresh document per lane. Fill lanes driven headless on Chromium via CDP Autofill.enable → setAddresses/trigger with backendNodeIds from DOM.describeNode; verdicts read from field values (never the fill event — see the overspeak law); contested partition lanes ×2 reps. The CDP field-name vocabulary (19 accepted ServerFieldType names, e.g. NAME_FIRST not GIVEN_NAME) discovered empirically; PHONE_HOME_CITY_CODE/…_CITY_AND_NUMBER accept but hang the trigger — avoided. FF/WK fill-state behavior: no automation path exists, recorded as lane limits.

Falsified this session (3, all mine). (1) "type=number and type=tel block autofill" — my anchor-scope artifact: both fill fine inside the anchor's group (direct-anchor lanes). (2) "selects section the form / don't co-fill with inputs" — the simple text–select–text form fills whole from any anchor; the earlier split was the same artifact family. (3) "form-level off blocks a field-level token" — field beats form when the field carries an explicit token.

Instrument lessons (3). (1) A first-generation harness threw uniform Invalid parameters on every address lane while an isomorphic rebuild with identical payloads ran clean end-to-end — in CDP-trigger land, rebuild the harness before debugging the protocol; laws were measured only on the rebuilt harness. (2) The fill event overspeaks: Chromium's addressFormFilled lists all classified fields including never-written ones — value reads are the only truth. (3) Buffered-stdout + no per-call timeout swallowed a hung trigger for minutes — every CDP send gets a 4–5 s race and streaming progress now.
