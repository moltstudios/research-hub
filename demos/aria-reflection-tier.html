ARIA reflection: the accessibility-state tier

Our catalog had Forced Colors (the one accessibility row), <dialog>, Constraint Validation and CSS :user-invalid — and zero coverage of the ARIA reflection surface itself. Across the 251-entry MC catalog, ariaChecked scored 0 hits, ariaLabelledBy 0, ariaLabelledByElements 0, ariaChecked 0, ElementInternals 2 (both passing mentions), aria-valuenow 0.

ARIA is the tier every team reaches for the moment they build a custom widget — and its JavaScript surface is not what the documentation says. Every rule below is measured across Chrome-for-Testing 148, Brave 156 and WebKit 26.5. Five of them are false in MDN's own examples.

The live lab in §1 re-runs the headline laws in your browser, right now.

2 · The seven MDN-documented names that do not exist

MDN's Element reference documents a set of aria* IDL properties. Seven of them are not real — el.ariaLabelledBy is undefined, so el.ariaLabelledBy.split(' ') throws a TypeError. They were renamed to a *Elements family, and MDN's pages for the old names are 404s.

THE HEADLINE — ariaLabelledBy, ariaDescribedBy, ariaOwns, ariaControls, ariaDetails, ariaErrorMessage and ariaMultiSelect are all undefined on Element.prototype in all three engines. Measured by key-set diff, not by value eyeballing. MDN's own /Web/API/Element/ariaLabelledBy page returns 404 (fetched 2026-10-31); the ariaLabelledByElements page is the live one.
MDN-documented nameOn Element.prototype?What you actually getThe real replacementType
THE MDN EXAMPLE THAT CRASHES. The ariaChecked page's own example is fine — but the same documentation family teaches the string form for the idref attributes. MDN's shape for aria-labelledby is a space-separated id list; the IDL that matches it is ariaLabelledByElements, which returns an Array of Elements. el.ariaLabelledBy.length throws TypeError: Cannot read properties of undefined (reading 'length') in Chromium and Brave, and TypeError: undefined is not an object (evaluating 'el.ariaLabelledBy.length') in WebKit 26.5.

Chromium 148 / Brave 156 51 / 52 PROPS

Brave ships one more than Chromium: ariaActionsElements (Brave-only). Chromium's extra is the ariaNotify() method, not a property.

WebKit 26.5 51 PROPS

WebKit is the only engine with ariaOwnsElements. It has no ariaNotify.

3 · The attribute map is not kebab-case

Every other reflected DOM property in the platform converts camelCase to kebab-case. The ARIA reflection does not. The attribute names are all-lowercase with no hyphens — aria-colcount, not aria-col-count.

THE HEADLINE — the naive conversion 'aria-' + name.replace(/[A-Z]/g, m => '-'+m.toLowerCase()) produces the WRONG attribute name for 6 of the 43 reflected states. The real map is bijective and all-lowercase. Measured: write the property, then list which aria-* attribute actually appeared.
IDL propertyNaive kebab guessThe REAL attributeNaive guess correct?
THE READ SIDE IS SYMMETRIC — the attribute side is the all-lowercase one too. Setting aria-colcount and reading el.ariaColCount works. Setting aria-col-count (the naive spelling) is a different, inert attribute: it is accepted by the DOM as a generic attribute, it is not in the ARIA attribute list, and the property never sees it.

4 · The role does not gate the state

The ARIA spec defines which states are applicable to which role. The JavaScript reflection surface applies none of it — the IDL is a plain attribute mirror with no role validation.

THE HEADLINE — role="img" aria-checked="true" reads back "true". role="heading" aria-checked="true" reads back "true". role="presentation" aria-checked="true" reads back "true". Measured on 6 role/attribute pairs in all three engines — identical results. The role does not even remove the state when you switch to presentation or none.
roleattributeProperty reads backAttribute survived?Role-appropriate?
WHY THIS MATTERS MORE THAN IT LOOKS. The IDL will happily echo back a state the accessibility tree ignores. A test that asserts el.ariaChecked === 'true' after setting it proves that the attribute was written — not that the state is exposed, not that the widget announces correctly, and not that the role permits it. The IDL is an attribute mirror, not an accessibility oracle.

5 · The ARIA / native fork

A native <input type="checkbox"> already has a checked state. The ARIA reflection is a second, independent channel onto the same element — and the two do not talk to each other in either direction.

THE HEADLINE — writing checkbox.ariaChecked = 'true' sets the attribute, not the state. The checkbox stays unchecked. Measured: ariaChecked === 'true', checked === false. And in the other direction, toggling the real checked property does not update ariaChecked — it stays null.
OperationariaCheckedthe real stateThe attributeConsequence
THE SAME FORK ON EVERY NATIVE CONTROL. A native <option selected> reads option.selected === true and option.ariaSelected === null. A native <input type="range" value="30"> reads value === '30' and ariaValueNow === null. A native <button> reads ariaPressed === null. A <details>/<summary> reads summary.ariaExpanded === null — even after you open the details. The browser never fills the ARIA attributes in for you.
Native controlThe real state propertyThe ARIA reflectionForked?
AND THE INHERITED-DISABLED CASE IS WORSE. An input inside a <fieldset disabled> matches :disabled — so it is genuinely disabled in the platform's own model — yet input.disabled === false (the IDL property does not inherit) and input.ariaDisabled === null. Three different answers to "is this disabled?", none of them equal to the other two.

6 · Nothing is validated — not one value

Every enumerated ARIA state is a plain string attribute. The reflection accepts any string, writes it verbatim to the attribute, and reads it back verbatim. There is no enum check, no range check, no throw.

THE HEADLINE — el.ariaChecked = 'maybe' succeeds, writes aria-checked="maybe", and reads back "maybe". el.ariaValueNow = 'abc' on a slider writes aria-valuenow="abc". And ariaValueNow = '9999' on a slider whose aria-valuemax is 100 is not clamped — it writes 9999. Measured across 15 invalid writes × 3 engines, identical.
PropertyWroteRead backAttributeThrew?
THE THREE-VALUE SHAPE OF A MISSING VALUE. A missing attribute reads back null. An empty attribute reads back "". A whitespace-only attribute reads back " " — spaces intact. And case is never normalised: aria-checked="TRUE" reads back "TRUE", "True" reads back "True". The IDL is a byte-level mirror of the attribute, not a parsed value.
Attribute stateProperty readsType
THE COERCION TABLE — the setter accepts anything a string accepts. A number, a boolean, an object and an array are all stringified. null and undefined both remove the attribute. A Symbol throws a TypeError (it cannot be converted to a string).

7 · The *Elements family — five real replacements

The five idref attributes that do have a live twin expose it as ariaLabelledByElements, ariaDescribedByElements, ariaControlsElements, ariaDetailsElements and ariaErrorMessageElements. Each returns an Array of Elements.

THE HEADLINE — the getter returns null when the attribute is absent, and an empty array when the attribute is present but unresolvable. A truthiness check therefore behaves in the opposite way in the two cases you care about: if (el.ariaLabelledByElements) is false for "no label at all" and true for "the label points at an id that does not exist". Measured, identical in all three engines.
SituationGetter returns!!valueSafe read
THE SETTER CLEARS THE ATTRIBUTE — to the empty string, not to null. el.ariaLabelledByElements = [span] leaves aria-labelledby="" on the element: the attribute is still present, just empty. A CSS selector like [aria-labelledby] now matches an element that has no label. And the setter accepts an element with no id at all — which the attribute form cannot express.
OperationGetterAttribute afterwardsNote
THE GETTER ARRAY IS FROZEN — but its ELEMENTS are not. el.ariaLabelledByElements.push(el) throws a TypeError (the array is read-only), while el.ariaLabelledByElements[0].id = 'X' succeeds — the array holds live element references, not copies. Remove the target from the DOM and the getter returns a shorter array (measured 1 → 0) while the attribute is still "e1 e2".

8 · ElementInternals — the custom-element twin

A custom element that wants to expose ARIA state calls attachInternals() and gets an ElementInternals with a parallel ARIA surface. It is not the same surface as Element.

THE HEADLINE — internals.states.add('checked') does not set aria-checked, and internals.role = 'switch' does not write a role attribute. Measured: after states.add('checked'), internals.ariaChecked === null, host.ariaChecked === null and host.getAttribute('aria-checked') === null. After role = 'switch', host.getAttribute('role') === null. The two channels are independent: states feeds the platform's own state model, the aria* properties feed the attribute model.

THE SURFACE PARITY IS NOT EXACT — WebKit drops three properties. ElementInternals carries 50 ARIA properties in Chromium 148 and Brave 156, but only 48 in WebKit 26.5: WebKit's internals object has no ariaDescription, no ariaColIndexText and no ariaRowIndexText. Chromium and Brave's internals object also carries ariaNotify, which WebKit's Element lacks entirely.

9 · The shadow-DOM boundary holds

One thing that behaves as you would hope: the ARIA reflection does not leak across a shadow boundary in either direction.

THE GOOD LAW — a shadow child's aria* state stays in the shadow tree. Writing inner.ariaPressed = 'true' inside a shadow root sets aria-pressed="true" on the inner element; the host's aria-pressed stays null and the host gains no attribute. Measured, identical in all three engines.

10 · The two capstones

OpenDrones THE COCKPIT STATE MIRROR

The cockpit's mission panel is a custom element: a toggle switch, a battery slider, an armed/disarmed button, a live telemetry feed. Each widget is a custom element, which means its ARIA state is two channels — internals.states for the platform's state model and the aria* properties for the attribute model — and the two do not sync.

The shipped guard (aria-state-guard, runnable in §10b) does three things: (1) it asserts that every widget's announced state matches its real state, because the ARIA reflection will happily report "true" for a switch that is off; (2) it never uses :dir()-style role gates, because the IDL does not gate and a test that passes on the IDL proves nothing about the a11y tree; (3) it reads the *Elements getters with an explicit ?? [], because null and [] mean different things and a truthiness check gets the empty-label case backwards.

Why it sells: a cockpit that says "ARMED" to a screen reader while the drone is disarmed is a safety bug, not a lint error — and the ARIA reflection is exactly the API a developer reaches for that will not catch it.

Molt THE CLIENT-SITE ARIA AUDIT

A half-day, sellable line item for any client site that ships custom widgets, a design system or an embedded booking flow. 12 checks, all mechanical:

(1) every ariaLabelledBy / ariaDescribedBy / ariaOwns / ariaControls / ariaDetails / ariaErrorMessage usage in the JS — all seven are undefined and will throw at runtime; (2) every *Elements getter read without an ?? []; (3) every if (el.ariaX) truthiness check; (4) every aria* write against a native control that has a real state property (checked, selected, value, open) — the fork; (5) every custom element whose internals.states and aria* are out of sync; (6) every element with an aria-* attribute whose name is not in the engine's reflected set (the all-lowercase law); (7) every state written on a role that does not permit it; (8) every aria-checked on a native checkbox where the checked property is the source of truth; (9) every aria-valuenow outside the aria-valuemin/aria-valuemax range (never clamped); (10) every aria-label on an element that also has an aria-labelledby (the precedence is invisible in the IDL); (11) every aria-hidden="true" on a focusable element (the focus is still reachable — measured); (12) every live region whose aria-atomic/aria-relevant/aria-busy is set without an aria-live (the trio is independent — measured).

Why it sells: the seven undefined names throw a TypeError in production and pass every linter, because no linter knows the names are wrong — they are real MDN property names.

12 · Method

5 probe suites · 3 engines · 31 assertion lanes. Chrome-for-Testing 148.0.7778.96 · Brave 156.1.98.60 · WebKit 26.5 (the Playwright WebKit build), all headless, driven through Playwright-core over CDP.

How it was measured

A plain-HTTP loopback origin served a widget zoo (native controls, role-based widgets, a custom element with ElementInternals, a shadow root). The battery was injected with page.addInitScript (CDP Page.addScriptToEvaluateOnNewDocument) so it ran after DOMContentLoaded and was never subject to page CSP. Every lane was captured individually, so one rejected promise cost one lane and not the suite. The assertion battery's own result was 31/31 pass on all three engines, with 0 page errors.

How the surface claims were proven

Every "does this property exist" claim is a key-set diff over the prototype chain — Object.getOwnPropertyNames walked from Element.prototype up — never a value eyeball. Every "which attribute did it write" claim is a write-then-list-attributes probe, not a string comparison against a guess. Every "is the value valid" claim is a write-then-read-back on the same element.

THE PROBE-HARNESS LESSON THAT MATTERED HERE. The first pass put the setup on the wrong node — it wrote aria-checked on a wrapper and read it on a child — and every result was meaningless until the setup was moved onto the element under test. The second pass asked el.ariaLabelledBy.length and crashed, because the getter is null when the attribute is absent; the fix was to read the property without assuming it is an array, which is itself the law the entry publishes. A probe helper that puts the setup on the wrong node measures nothing, and a probe that assumes a shape it is trying to measure cannot measure it.
