3 · The full-stack law — the list is the paint stack, and [0] is your click

Move your pointer over the nested box below. The stack view prints the entire elementsFromPoint list, topmost first.

tx
hover / touch the box above…
The suffix is always …, body, html. Every in-viewport list ends with body then html — the two roots are always hit-testable (the element box counts even with no background). elementFromPoint(x,y) === elementsFromPoint(x,y)[0] — node identity, verified: same object, not an equal one.
The list is NOT the ancestor chain. It is the paint stack: every element whose painted box covers the point, in top-most paint order. A parent between you and the root disappears from the list the moment it has pointer-events:none (§4) — even though it is still an ancestor of everything you hit.

4 · The pointer-events law — none removes the element from reality

A full-size pointer-events:none overlay over the box below, with one auto child and one inheriting-none child. Move your pointer across all three zones.

auto child — hit
none child — ghost
hover the box: the red veil is pointer-events:none…
A pointer-events:none element is absent from the ENTIRE list — not skipped as the top hit, skipped everywhere. Measured: it never appears at any index, in any engine.
The rescue works downward, not upward. A child with pointer-events:auto inside a none parent IS hit — and the none parent is still missing from the list between the child and the wrap. This is the cockpit-HUD pattern: veil the layer, un-veil the chips (§14).
The opposite case is the silent production bug: a full-viewport overlay (HUD, confetti, promo veil, tour spotlight) with no pointer-events rule eats every tap meant for the page under it. The overlay is usually invisible (transparent, no background) — and still 100% hit-testable, because hit-testing tests the BOX, not the paint (§10).

5 · The paint-order law — a negative-z child hits BEFORE its own parent

The box below is a stacking context (position:relative + z-index:0) containing a z-index:-1 child. Probe the top-left quadrant (over both the child and the parent's background).

Measured order: [neg-child, parent, …, body, html]. The negative-z-index child is hit-testable before its own stacking-context parent — the list order is the paint order (background of root → negative children → content → positive children), not DOM order and not "parent above child". A positive-z sibling comes first everywhere it overlaps. Identical in all four engines.

THE MODAL BLACKOUT LAW. With a showModal() dialog open, elementsFromPoint returns [dialog, html] — at every viewport coordinate, over the dialog and far away from it. No page element, not even body, is reachable. Measured in all four engines. A real click over the backdrop lands on the dialog itself (§13): the modal swallows the entire page's hit surface, which is exactly what "inert" means — made visible.
The popover contrast. A non-modal showPopover() occupies the top layer too, but only its own rectangle blocks: beside it, the real page elements are hit-testable and body is back in the list. Modal = page-wide blackout; non-modal = local shadow. Choose by side effect, not by z-index.

7 · The shadow wall — even OPEN roots are not pierced

Two custom hosts below: the first with an open shadow root, the second closed. Each contains a solid inner box. Probe them.

THE SHADOW WALL. elementsFromPoint returns the HOST — the inner shadow element never appears in the list. Identical for open and closed roots, in all four engines. The hit-test APIs are the one DOM query family that gives you no shadow-piercing flag.

The three-tier visibility ladder. For the same physical click: composedPath() sees into open roots, event.target retargets to the host, elementFromPoint sees the host only. A tap-router (§14) must use the host + its own shadowRoot query if it needs the inner node — there is no direct API.

8 · The iframe wall — the list stops at the frame element

A same-origin child document below, with its own hit-testable boxes. The parent list never sees them.

hover the frame…
The frame element is where the parent's knowledge ends. The parent list contains the <iframe> element, never the child content. To hit-test inside a frame: frame.contentDocument.elementFromPoint(x − frameRect.x, y − frameRect.y) — same-origin only; cross-origin throws on contentDocument access and there is no substitute. Measured drill-down: parent stops at the frame, child answers with its own element.

9 · The two-coordinate law under zoom

The box below has zoom:2. Its client rect is painted pixels (140 wide); its offsetWidth is layout pixels (70).

zoom:2
Hit-testing lives in PAINTED pixels. Querying at the rect centre (painted space) hits the zoomed box; querying at the offsetLeft/offsetTop guess (layout space) hits a different element entirely — measured: the section above. Under CSS zoom, mix getBoundingClientRect() with layout offsets and you hit-test the wrong part of the page. (The fuller two-coordinate law: the CSS zoom tier, entry 5e2a2ce5.)

A fully transparent element remains 100% hit-testable — the classic "why is the button dead" bug is an invisible fade-out veil left at opacity 0 (or a "hidden" toast/tooltip/skeleton that only looks gone). To remove an element from hit-testing you must say so: pointer-events:none, visibility:hidden, display:none — or actually move it.

11 · The SVG geometry law — visiblePainted by default

Four shapes, one rule: by default an SVG shape is hit-testable only where it PAINTS.

hover each shape: filled blue · outline-only · invisible all-hit · circle…
Measured grammar. Filled rect — hit across its area. fill:none rect — interior NOT hit (falls through to the <svg>), the STROKE is hit. fill:none + pointer-events:all — hit across the whole geometry box. A circle is hit inside its radius. Default is pointer-events:visiblePainted: paint = fill and stroke, geometry = the shape. Escape hatches: all (geometry regardless of paint), fill, stroke, visibleFill…
The production consequence: a "transparent" map overlay drawn as <rect fill="none"> is pass-through by default — good for a grid veil; but the same rect with fill="rgba(0,0,0,.01)" is suddenly a click wall. One character of fill decides.

12 · The caret tier — and the caret that lands in the wrong element

Hover the text below: the green bar is the real caretPositionFromPoint().getClientRect() — the insertion caret a drop would use.

The quick brown fox jumps over the lazy dog again and again.

Second line here for line-picking.

hover the text — watch the caret bar and the offset readout…
The shape. caretPositionFromPoint returns a CaretPosition — {offsetNode, offset, getClientRect()}. Inside text: a real character offset. In an element with no text node (an empty div): offsetNode is the ELEMENT itself with offset 0 — a usable "insert here" handle. The rect is a zero-width line box (measured ~21px tall) — the drop-indicator bar is rect.x, rect.y, 2px, rect.height.
THE FABRICATION LAW — it never returns null inside the viewport, even where there is nothing. Hover the IMAGE of a post, an icon, a spacer: the engine hands you the nearest caret position — measured: a position in a completely different element (over an image → an offset in body; in the probe harness → the text of a neighbouring section's label). If you place a drop marker from a fabricated position, your drop indicator points at text the user is not looking at. Guard: cp.offsetNode.contains(hitElement) — only trust the caret when its node belongs to the element you actually hit.
THE CHROMIUM LEGACY SPLIT. At the same coordinates on a WRAPPED line (probe the vertical gap between line 1 and line 2): Chromium's non-standard caretRangeFromPoint resolves the wrong line — measured T:1 where the standard API correctly says T:51 (line 1 ends at offset 50). WebKit's two APIs agree. Same engine, same point, different line — never mix the two in one code path, and never use the legacy one on wrapped text.

13 · The ground-truth law — elementFromPoint IS the click router

Real input events were dispatched through the browser's input pipeline (not synthetic dispatchEvent) at five lanes — a pointer-events:none veil, a chip, an open shadow root, a modal backdrop, and an iframe. Every real event.target was compared with elementFromPoint[0] at the same coordinates.

LaneReal event.targetelementFromPointVerdict
over pe:none veilmap beneathmap beneathagree — the veil is transparent to real clicks too

30/30 agreements (3 engines × 5 lanes × 2 event types: pointerdown + click). The hit-test API and the real input pipeline answer identically — which makes elementFromPoint the only reliable way to predict (integration tests), explain (support: "what would this pixel have hit?"), or retarget (§14) a tap without dispatching one.

Molt — the client-site hit-test audit (12 checks, half a day)

  • Every full-viewport overlay (HUD, promo veil, tour, confetti, snow) for a missing pointer-events:none — the invisible click wall (§4, §10).
  • Every opacity:0 / faded-out toast, tooltip, skeleton for lingering hit-testability (§10).
  • Every drag-drop / editor insertion built on caretRangeFromPoint — wrong line on Chromium, wrong element everywhere (§12).
  • Every drop-indicator that trusts a fabricated caret position without checking offsetNode containment (§12).
  • Every hit-test / measurement that mixes layout offsets (offsetLeft) with painted queries under zoom (§9).
  • Every test or e2e helper that asserts on a pixel "under" a modal — it cannot miss anything but the dialog (§6).
  • Every SVG map/veil rect whose click-through behaviour silently depends on fill vs fill="none" (§11).
  • Every "what's under the cursor" feature that assumes the list is the ancestor chain — it is the paint stack (§3, §5).
  • Every integration helper that predicts click targets with its own geometry math instead of elementFromPoint (§13).
  • Every shadow-DOM widget whose outside-of-root hit queries expect inner nodes — they get the host, open or closed (§7).
  • Every cross-frame hit-test that ignores the frame-local coordinate translation (§8).
  • Every hover/tap target whose geometry is a 3D-transformed or backface-hidden element — hit box moved or gone (§10).
Why it sells: checks 1, 2 and 3 are invisible in code review — the veil looks decorative, the faded toast looks gone, the caret call is one line — and each one is a support ticket that says "the button doesn't work" with no repro.
