Trusted Types + Sanitizer API — the DOM-XSS defense tier

Every client app renders strings it doesn't fully trust — CMS copy, lead forms, mission logs. The DOM-XSS layer decides what happens at the sink. Trusted Types gates every injection sink behind typed values + CSP enforcement; the Sanitizer API parses-and-filters in the engine. Both just went cross-engine — this page probes what actually ships (and where the docs have drifted).

Enforcement lab A — real CSP headers, the throw matrix

The iframe below is served with Content-Security-Policy: require-trusted-types-for 'script' — a genuine response header (Vercel config). Under enforcement every raw-string sink throws TypeError before the DOM is touched, a securitypolicyviolation event fires, and the engine logs a console error even when you catch the throw. This is the contract that turns XSS from a runtime exploit into a crash you can see in CI.

Enforcement lab B — the default policy & the name allowlist

Child B carries require-trusted-types-for 'script'; trusted-types tt-demo default. Two ideas at once: the default policy auto-wraps raw strings (the engine calls default.createHTML(s) for you — audit/redact without touching call sites), and the name allowlist makes unknown policy names themselves throw.

Danger documented in-spec: a default policy that echoes its input unescaped re-opens the hole while silencing the crashes — default policy = audit hook, not a sanitizer.

§06

Meta-CSP child C — the delivery wall that isn't

Conventional wisdom: require-trusted-types-for is header-only, like sandbox and frame-ancestors. Live-falsified: child C declares the directive via <meta http-equiv="Content-Security-Policy"> with no response header — and the raw sink still throws. Meta delivery works on this engine. (Flip side: if an injection can write a meta tag, it can also ship policy on your page — but it could equally strip it, so don't lean on meta as your only layer.)

meta-delivered require-trusted-types-for: raw innerHTML = → directive honored in meta on this engine
§07

Sanitizer API — the builder shape that actually shipped

MDN documents sanitize() / sanitizeFor() / constructor config objects. Chromium 146+ shipped none of that: the Sanitizer is a builder — new Sanitizer() starts from a safe baseline, then allowElement, removeElement, replaceElementWithChildren, allowAttribute, removeAttribute, setComments, setDataAttributes, get() — consumed via element.setHTML(html, { sanitizer }). Constructor config keys are silently ignored.

The interplay — Sanitizer for content, Trusted Types for sinks

MDN's pairing story — sanitize() returns TrustedHTML that sails through enforced sinks — cannot happen on this engine: there is no sanitize(). The real pairing: setHTML() is its own safe door (not a TT sink), and TT policies remain the only producers of TrustedHTML for classic sinks. Probed on child A (enforced).
