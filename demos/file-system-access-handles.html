File System Access API — real user files, handles, swap-file writes & FileSystemObserver

OPFS (cataloged Jul 18) gave the web a hidden high-speed sandbox. This is the other half of the files tier: FileSystemFileHandle / FileSystemDirectoryHandle — the handle layer every engine already ships — plus the Chromium-only picker layer (showOpenFilePicker · showSaveFilePicker · showDirectoryPicker · drag-drop getAsFileSystemHandle) that lets a web app open, edit-in-place and watch the user's real files. Swap-file write semantics, siloed vs exclusive locks, seek-past-EOF sparse writes, handles that survive reload via IndexedDB, and the new FileSystemObserver (Chrome 133+) that kills polling. Every handle-layer lab below runs on OPFS-backed handles — the same interface the pickers return — so it's all live-verifiable headless.

1. The two-tier map — one API, three support realities

The spec name says "File System Access" but support splits cleanly into layers. Design against the handle layer (universal), feature-detect the picker layer (Chromium ~70%), treat the observer as progressive rocket fuel.

Handle layer Ch 86 · FF 111 · SF 15.2 — universal

  • getFile() → real File (a Blob: .text(), .arrayBuffer(), .slice()) · createWritable() (SF write: 26 — read-only before) · createSyncAccessHandle() (workers, OPFS files)
  • FileSystemDirectoryHandle: getFileHandle/getDirectoryHandle {create:true}, values() async iteration, resolve(), removeEntry() — plus isSameEntry(), move()
  • Where you get them: OPFS (navigator.storage.getDirectory()), pickers, drag-drop, Web Share targets

Picker layer Ch/Edge 86+ · FF ✗ · SF ✗ — ~70%

  • showOpenFilePicker({types, multiple, startIn, id, excludeAcceptAllOption}) · showSaveFilePicker({suggestedName,…}) · showDirectoryPicker({mode}) — transient user activation required, secure context only
  • Drag-drop: dataTransferItem.getAsFileSystemHandle() · Permissions: queryPermission() / requestPermission({mode:'readwrite'}) (Chromium-only surface)

Observer layer Ch 133+ · experimental, non-standard (whatwg/fs PR #165)

  • new FileSystemObserver(cb) → .observe(fileOrDirHandle) — change records (appeared / modified / disappeared / moved) for user-visible files AND OPFS. No more polling loops.

2. Handle anatomy — names, kinds, snapshots & identity

A handle is a capability token, not a file object. Two getFileHandle('a.txt') calls give two different objects for the same file — identity is isSameEntry(), never ===. And getFile() snapshots: the File you hold reflects the file at call time.

const root = await navigator.storage.getDirectory();      // OPFS — same handle interface
const h1 = await root.getFileHandle('a.txt', {create:true});
const h2 = await root.getFileHandle('a.txt');
h1 === h2                        // false — different objects…
await h1.isSameEntry(h2)         // true  — …same entry. Always isSameEntry.
const file = await h1.getFile(); // File — snapshots at call time
file.name; file.lastModified; file.size; await file.text(); file.slice(0,4) // it's a Blob

3. createWritable — the swap-file model ★ the #1 data-loss gotcha

createWritable() does NOT open the file. It opens a swap file: everything you write lands in the temp file, and only close() atomically swaps it over the real one. Default keepExistingData:false means the swap starts empty — write a small patch, close, and the original bytes are gone. This lab destroys a file on purpose.

Data-loss lab

idle — seeds 120B "mission.log", writes 6B patch both ways

Verdicts

Compares file bytes before/after each write; proves close() is the commit point (file unchanged while stream open).

The rule: full-file rewrites (an editor's Save) → default is fine, write the whole buffer. Surgical patches → {keepExistingData:true} + seek (§4). "I opened it and wrote 6 bytes and the file became 6 bytes" is not a bug — it's the swap-file model working exactly as specified.
const w = await handle.createWritable();              // swap starts EMPTY
await w.write('PATCH!'); await w.close();             // file is now 6 bytes. Was 120.

const w2 = await handle.createWritable({keepExistingData:true}); // swap = copy of file
await w2.write('PATCH!'); await w2.close();           // first 6 bytes replaced, rest intact

4. write() payloads — seek, sparse writes, truncate-grow

write() takes data (string | BufferSource | Blob) or a WriteParams instruction: {type:'seek', position}, {type:'write', position, data}, {type:'truncate', size}. Two behaviors worth knowing cold: seeking past EOF then writing zero-fills the gap (sparse write), and truncating larger than the file grows it with zeros.

WriteParams lab

idle — hex dumps show the zero gaps

Verdicts

10-byte seed file; each lab hexdumps before/after.

const w = await h.createWritable({keepExistingData:true});
await w.write({type:'seek',  position: 40});   // cursor → 40 (file is 10B)
await w.write(new TextEncoder().encode('X'));  // bytes 10..39 zero-filled → sparse
await w.write({type:'truncate', size: 20});    // shrink
await w.write({type:'truncate', size: 30});    // GROW → padded with zeros
await w.write({type:'write', position: 4, data:'≈'}); // one-shot positional write

5. Writer locks — siloed (default) vs exclusive

Two modes: 'siloed' (default) lets multiple writers open — each gets its own swap file, and the last one to close wins (the classic two-tab lost-update). 'exclusive' throws NoModificationAllowedError for the second writer. The question the docs don't answer cleanly: is the exclusive lock per handle object or per entry? 6. Streams integration — FileSystemWritableFileStream IS a WritableStream

The write stream from §3–5 is literally a WritableStream subclass — which means the entire Streams tier plugs straight into files. blob.stream().pipeTo(writable) streams a big buffer to disk without holding two copies; a TransformStream can deframe/reformat mid-pipe. This is the OPFS↔Streams bridge the plumbing entry promised.

OpenDrones — the folder watch

User picks their ~/missions folder once (showDirectoryPicker({mode:'readwrite'})) → observer watches the active day's dir → GCS writes a new log segment ⇒ modified record ⇒ Mission Control tails it like tail -f, no 500ms stat-poll, no Service Worker hack. The record's changedHandle is already a handle — feed it straight into the §6 pipe.

const obs = new FileSystemObserver((records) => {
  for (const r of records)
    console.log(r.type, r.changedHandle.kind, r.changedHandle.name); // 'modified','file','fan.log'
});
await obs.observe(dirHandle);   // dir or file. OPFS works. disconnect() to stop.

9. createSyncAccessHandle — the mmap-feel escape hatch (Worker-only)

createSyncAccessHandle() gives synchronous read/write/seek/truncate/flush on a fixed window — but only inside a Worker, and in practice only for OPFS files (it's the high-throughput lane under WASM-SQLite). Live-falsified here: the method is not merely rejected on the main thread — it is absent from the main-thread prototype entirely (proto = constructor, createWritable, getFile, move); Chromium injects it only in Worker contexts. So typeof fh.createSyncAccessHandle on the main thread is always undefined — capability-detect from inside the worker.

10. Persistence — handles in IndexedDB & the permission clock

Handles are structured-cloneable: store one in IndexedDB, reload the page, read it back, and your "project" reopens — no picker. The catch: granted readwrite permission on user-picked files expires (≈1 week Chromium, tab-close dependent), and re-granting needs a user gesture. OPFS handles stay granted (it's the app's own sandbox).

Reopen-your-project lab

idle — tiny bare IndexedDB promise wrapper, no libraries

Verdicts

Plus: queryPermission on the OPFS root (expect 'granted' — chip).

await idbPut('handles', fileHandle, 'project');   // store the CAPABILITY
// …reload…
const h = await idbGet('handles', 'project');
await h.queryPermission({mode:'readwrite'});      // 'granted' or 'prompt'
await h.requestPermission({mode:'readwrite'});    // MUST be inside a click handler
