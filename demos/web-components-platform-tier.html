01Why the component tier, and why now

The catalog has systematically covered every platform tier — storage, media, transport, routing, animation, scheduling, crypto — but never the component model itself. Web Components are the only primitive that ships with the browser: no build step, no hydration, no dependency to audit, no version to pin. A component written today runs in a plain <script> tag, in React, in Astro, in a 2036 browser.

The three pillars, and what each buys you:
  • Custom elements — customElements.define('my-el', class extends HTMLElement {}): a real HTML element with lifecycle callbacks, attributes, and a registry. Extend the platform's vocabulary instead of div-soup.
  • Shadow DOM — attachShadow() or a declarative <template shadowrootmode>: a style-and-DM boundary. Your component's CSS and markup cannot leak out; page CSS cannot reach in.
  • Element Internals — attachInternals(): form participation (real <form> membership, FormData entries, validation) and CustomStateSet — without shadow DOM if you don't want it.
Where it earns its keep at Molt / OpenDrones: Molt ships a zero-dependency UI kit (<molt-card>, <molt-rating>) reused across client builds with no library churn — §12. OpenDrones gets framework-proof telemetry components (<mission-gauge>) that survive UI-framework migrations — §12. The streaming ground-station page renders SSR'd declarative shadow roots with zero flash of unstyled content — §4-§5.

05The fragment wall — where DSD silently does nothing

The classic fragment paths below accept the markup without error and attach nothing — the template stays inert in the light DOM and your component renders empty. Try each path:

Every tutorial showing "create a DSD element" via el.innerHTML = '<template shadowrootmode…>' ships code that silently no-ops on all three engines. Working paths: real navigation/streaming parse, Document.parseHTMLUnsafe() (document algorithm), el.setHTMLUnsafe() — or just attachShadow() in the constructor. setHTML() needs an explicit allowlist or it drops your tags.

Live-falsified on this engine: same-mode re-attachShadow() returns the same root object — MDN documents this as legal — but empties its children (verified: 2 children → 0). The DSD root survives as an object; its content does not. A mode mismatch throws NotSupportedError, and a closed declarative root is invisible (host.shadowRoot === null) and re-attach throws.

11Serialization — innerHTML lies, getHTML doesn't

innerHTML has never been able to see shadow roots. Its successor getHTML({serializableShadowRoots:true}) round-trips a shadow root only if it was created serializable (the shadowrootserializable attribute, or attachShadow({serializable:true})). Side by side, live:

serializing…

Clone truth, probed live: cloneNode(true) on a host with shadowrootclonable copies the full shadow tree to the clone; without it the clone gets no shadow root at all (null, not an empty one). And the §5 wall pays off here: the getHTML output re-parsed with Document.parseHTMLUnsafe() re-attaches the root — a real server-side round-trip.
