1 · The event grammar — canvas, not context

Context events fire on the canvas element, not the GL context. The context object isn't even an EventTarget — gl.addEventListener doesn't exist. Measured event shape:

canvas.addEventListener('webglcontextlost', e => {
  // e : WebGlContextEvent
  // e.cancelable     → true   (the ONLY handle that saves the context: e.preventDefault())
  // e.bubbles        → false
  // e.statusMessage  → ''     (empty on synthetic loss; driver text on real loss)
  // e.isTrusted      → true
});
canvas.addEventListener('webglcontextrestored', ...);  // fires only if you preventDefault'ed
canvas.addEventListener('webglcontextcreationerror', ...); // the never-fires-silent-null lane
lost: cancelable=true ✓probed lost: bubbles=false ✓probed statusMessage='' on synthetic loss ✓probed listener added AFTER loss never fires (no retro-dispatch) neighbors unaffected — each context dies alone

The timing truth: isContextLost() flips synchronously inside loseContext() — already true in the very next microtask. Restoration is the opposite: async, delivered via the restored event (~1 frame later).

2 · The silent no-op law — a lost context throws nothing

The most dangerous property of context loss: every method becomes a silent no-op or returns a degenerate value — nothing throws. Your render loop keeps "succeeding" on a dead GPU connection while the screen shows a frozen or blank canvas. Run the battery on a sacrificed context:

// measured on the lost context (Chromium 154, every lane):
createTexture()        → [object WebGLTexture]   // a REAL zombie object — dead on arrival
getParameter(VERSION)  → null                    // even the version string is gone
getError()             → 0x9242 CONTEXT_LOST_WEBGL  // ONCE. second call → 0. a one-shot token.
drawArrays()           → undefined (no throw)    // the render loop never crashes
readPixels()           → [0,0,0,0]               // zero pixels, no throw
shaderSource/compile   → "succeed"; COMPILE_STATUS → null
getExtension()         → null                    // even WEBGL_lose_context is unreachable
getContextAttributes() → null
finish() / clear() / bufferData() → no throw, no effect

The zombie-creation trap: createTexture() returning a live-looking object on a lost context means init code that "rebuilds resources" during loss fabricates handles that are invalid the moment the context returns. Gate all resource creation on !isContextLost().

3 · Permanent-handle death — restoration revives the context, not your objects

With preventDefault() + restoreContext(), the same context object comes back with factory-fresh engine state (viewport, clearColor reset to defaults) — but every program, shader, texture, buffer and uniform-location handle you created before the loss is permanently invalid. Measured census, live in your browser:

The re-init checklist (the only correct restored-handler): recreate programs and re-link, recompile shaders, re-create every texture/buffer/VAO/feedback, re-fetch uniform locations (old ones return null now), rebind everything, restore viewport/blend/depth state. Nothing survives. Cache the recipe (sources, uploads), never the handles.

4 · The 16-context ceiling — eviction, not failure

At the limit the engine never returns null from getContext — it evicts the oldest live context, firing a real webglcontextlost on an innocent canvas. Measured census, one context per step (deterministic, perfectly FIFO):

contexts created#14#15#16#17#18#20#25#30
alive after1415161616161616
evicted (indices)———[0][0,1][0–3][0–8][0–13]

The frame-tree sharing law: the budget is shared across the whole page, iframes included. Measured: a parent page holding 14 live contexts dropped to 11/14 the moment a same-origin iframe created 5 of its own — the iframe's births evicted the parent's oldest. After 23 total across both frames: parent 7/14, iframe 9/9 alive (younger wins). Embedded WebGL widgets don't get their own budget.

Watch the hero closely: it gets evicted too — but because its listener preventDefaults, the engine may auto-restore it seconds later (measured: lost at eviction, self-restored ~3s later with zero code calling restoreContext()). The rebuilt frame you see after is the §3 re-init handler doing its job. Idle contexts without the listener stay dead forever.

6 · The pixel truths — readback vs. the screen

Two lanes that look like one API and behave like two different ones:

lanesame taskafter presentation
preserve:false + presented canvas → readPixels cleared to [0,0,0,0] preserve:true → pixels survive presentation off-DOM canvas never "presents" → buffer survives even with preserve:false the SCREEN keeps the last composited frame after the buffer clears (screenshot-verified) premultipliedAlpha: cosmetic in compositing — legal AND out-of-gamut colors composite identically (measured: clearColor(1,0,0,0) → pure white over white in BOTH modes) alpha:false forces the alpha byte to 255 regardless of clearColor

The practical law: readPixels/toDataURL in the same task as the draw always work; anything after a presented frame needs preserveDrawingBuffer:true — or draw-and-read in one task. GL readback returns unpremultiplied values regardless of the premul hint.

7 · Capstones

OpenDrones Mission Control — the eviction guard

MapLibre map + 3D replay + telemetry sparkline canvases on one page = one shared 16-slot FIFO with every embedded widget. The production shape:

// one place owns every context birth
const CTX_BUDGET = 12; // headroom for embeds/ads/ifs
let live = new Set();
function acquire(canvas, attrs){
  if (live.size >= CTX_BUDGET)
    releaseOldestHidden();          // evict ours before the engine evicts the map
  const gl = canvas.getContext('webgl2', attrs);
  if (gl) live.add(gl);
  canvas.addEventListener('webglcontextlost', onLost);
  return gl;
}
function onLost(e){
  e.preventDefault();               // or we never get it back
  scheduleRebuild(canvas);          // §3: full re-init — handles are dead
}
// tab hidden → release its contexts (visibility, not survival, is the budget lever)

Molt — WebGL hero sections that don't eat clients' dashboards

Marketing sites with three.js heroes land on pages full of other people's WebGL (embeds, players, ads). Three rules:

  • The hero owns one context; renderer.dispose() + forceContextLoss() on route change — a SPA leak of 16 heroes is a time bomb for every other canvas on the site.
  • Never ship a WebGL hero without a webglcontextlost handler that degrades to the static poster — silent no-ops mean the failure mode without one is a frozen frame, not an error.
  • MapLibre/three on the same page as chart canvases: budget-test with all widgets mounted, not per-component.

Sellable: a "WebGL resilience audit" — context census, loss-simulation harness (this page's §0–§3 as the client-facing demo), eviction guards. 3–4 h per site.

8 · The ten rules

  1. Listen on the canvas, never the context (it isn't an EventTarget).
  2. preventDefault() in webglcontextlost — or the context is dead forever and restoreContext() silently no-ops.
  3. Grab WEBGL_lose_context before loss — getExtension() returns null on a lost context.
  4. Rebuild everything in the restored handler; zero handles survive (§3).
  5. Gate all GL calls on !isContextLost(); nothing throws — you'll never see the failure otherwise.
  6. Drain getError() — CONTEXT_LOST_WEBGL is a one-shot token (0x9242, then 0).
  7. Budget 16 contexts per page, iframes included; evict your own hidden contexts first.
  8. One canvas = one context type, first call wins — the webgl→webgl2 "fallback" needs a new canvas.
  9. Draw-and-read in one task, or set preserveDrawingBuffer:true; the cleared buffer never matches the still-on-screen frame.
  10. Simulate before you ship: if your page can't survive this page's §0 buttons, it can't survive a driver update.
