§00Why this tier exists

The OS alert surface — the only channel that reaches the user when the tab is hidden, minimized, or backgrounded.

Web Push (catalog entry) covers the server-delivered half of alerts. This tier is the engine half: how a notification is constructed, validated, permission-gated, displayed through two different doors, and observed. For OpenDrones it is the Mission Alert lane — battery/geofence/link advisories that must reach the operator while Mission Control sits on a background monitor. For Molt it is the render-done / review-requested ping for long-running client jobs.

The two doors: the page door new Notification(title, options) and the service-worker door registration.showNotification(title, options). They share one permission but not one contract — Android Chrome outlaws the page door entirely, and click routing differs (page: notification.onclick; SW: notificationclick on the worker, which works with no page open at all).

§15Ship checklist — 10 rules

  1. Never call the constructor on Android. new Notification() throws TypeError: Illegal constructor on Android Chrome — feature-branch on 'serviceWorker' in navigator && reg, use the SW door everywhere. And actions are SW-door-only on DESKTOP Chromium too: the page constructor throws TypeError: Actions are only supported for persistent notifications (live §04).
  2. One permission, two vocabularies. The static speaks default/granted/denied, Permissions API speaks prompt/granted/denied — and a permission set to denied via CDP can read 'default' on the static while the SW door rejects. Gate UX on the static, ground-truth on the SW door's rejection.
  3. One permission, read it triad-style: gate UX on Notification.permission, react to changes via permissions.query().onchange, never cache across reloads.
  4. Assume the gesture wall on requestPermission(). Firefox hard-requires it; Chromium's gesture-free behavior is engine state, not contract. Only ask from a click.
  5. Validation TypeErrors are not permission errors. Test filter/options shapes in any state — renotify without tag throws before the permission wall is consulted (order recorded in §04).
  6. The page door never throws for permission — it silent-no-ops. In denied state new Notification() still returns an instance (live §05); the SW door rejects TypeError: No notification permission. If you need to KNOW delivery failed, use the SW door.
  7. data is structured-cloned at construct time. Functions/DOM nodes throw DataCloneError; readback is a SECOND clone — identity is never preserved, deep-equality is.
  8. tag is your dedupe key. Same-tag notifications replace, not stack; renotify:true re-alerts on replacement but requires the tag. Mission-critical repeats: tag + renotify. Passive logs: tag + silent.
  9. close() is idempotent, onclose is not a contract. Desktop Chromium does not reliably fire onclose for programmatic or system closes — treat notification lifecycle as fire-and-forget; persist state yourself.
  10. CI can green-test the granted path. notifications is grantable via CDP/playwright per-origin (verified in this gate) — the anti-pattern is Window Management, where all four grant doors no-op. Test granted + denied + fresh triples.
