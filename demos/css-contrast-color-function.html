One color in. Browser picks the contrast.

contrast-color() takes any color and returns either black or white — whichever has the higher contrast ratio. No second variable. No conditional theming. No JS. The browser does the WCAG math for you. Spec'd in CSS Color Module Level 5, an Interop 2026 focus area, and shipping in every modern engine.

2 · The old way vs the new way

The pre-2026 approach required either a paired text variable in the design system or a JavaScript helper that computed luminance and picked the right value. contrast-color() moves that work into the browser engine — and the result is dynamic, so a single button class can repaint correctly when its --btn-bg changes.

The old way

/* Define TWO variables per use */
:root {
  --bg-1: navy;
  --fg-on-1: white;
  --bg-2: wheat;
  --fg-on-2: black;
  /* ...one pair per surface... */
}

.card {
  background: var(--bg);
  color: var(--fg); /* manual choice */
}
/* Or rely on JS to keep them in sync */

The new way

/* Define ONE variable. Browser does the rest. */
:root {
  --bg: navy;
}

.card {
  background: var(--bg);
  color: contrast-color(var(--bg));
}
/* Change --bg dynamically → browser re-picks.

The old way is fragile: a designer changes --bg-1 without updating --fg-on-1, and you ship an unreadable button. The new way is coupled by construction — the foreground can only ever be the right choice against its background.

3 · One button class, twelve palettes

A single .btn class declares the design. Twelve buttons below override --btn-bg via a modifier class. Each button's text color is contrast-color(var(--btn-bg)) — no per-color overrides needed. Notice how the hover state (a derived lighter shade via oklch()) also re-computes its text color. 

.btn {
  --btn-bg: #6c5ce7;
  --btn-bg-hover: oklch(from var(--btn-bg) calc(l + 0.12) c h);
  background: var(--btn-bg);
  color: contrast-color(var(--btn-bg)); /* browser picks black or white */
}
.btn:hover {
  background: var(--btn-bg-hover);
  color: contrast-color(var(--btn-bg-hover)); /* recomputes for the new bg */
}
.btn-success { --btn-bg: #00cec9; }
.btn-warn    { --btn-bg: #fdcb6e; }
/* etc — one variable per palette */

5 · Adaptive hero & badge text

A marketing hero might sit on a brand-colored background that varies by campaign. The badges, eyebrow text, and CTA copy need to follow. With contrast-color(), one rule applied at the section level cascades to every child element using currentColor.

/* Each row declares its bg, text follows by contrast-color() */
.brand-row  { --theme-bg: #6c5ce7; }
.brand-row  { background: var(--theme-bg); color: contrast-color(var(--theme-bg)); }

/* A badge that uses currentColor as its background inherits the section's chosen fg */
.badge {
  --badge-bg: currentColor;
  background: var(--badge-bg);
  color: contrast-color(var(--badge-bg));
}

The currentColor trick is what makes this elegant — a badge inherits the section's already-computed foreground, then asks the browser to compute a contrasting color for its own background. Two levels deep, still zero JavaScript.

.card {
  --card-bg: #fdcb6e;
  background: var(--card-bg);
  color: white;                    /* safe fallback */
  color: contrast-color(var(--card-bg));   /* browsers w/ support override */
}

Why this is the immediate follow-up to oklch / light-dark() / Custom Highlight

All four pieces together complete the CSS color toolkit that replaces design tokens, Sass mixins, and JS contrast helpers with pure CSS:

oklch() Perceptually-uniform color picker. Choose a brand color once and the rest of the palette can be derived without guesses.
color-mix() Mix any two colors in any space. The bridge between brand color and a derived surface color.
light-dark() Theme-aware tokens. One token, two color values; browser picks based on color-scheme.
contrast-color() Always-readable text. One color in, two-color decision out — browser computes the WCAG-optimized black/white.
