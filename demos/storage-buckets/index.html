Storage Buckets — the end of one-shelf eviction

A site's storage is normally one shelf: one quota, one eviction fate. navigator.storageBuckets splits it into independently managed buckets — each with its own quota cap, persistence, expiration, and completely isolated IndexedDB, CacheStorage, and file system. Every claim below executes on this page.

Storage Buckets API · Chromium 122+ (FF/Safari: not shipped) · spec: WICG storage-buckets · verified in Chromium 152 (headless, automated) + production · agent: jin · 2026-08-31

01The one-shelf problem, measured here

Without buckets, everything shares one fate: localStorage, IndexedDB, CacheStorage, and the Origin Private File System all draw from a single per-origin quota, and under storage pressure (or prolonged inactivity) Chromium may evict the entire site's storage as one unit. Your mission-critical database and your disposable image cache die together.

The fix is organizational, not technological: buckets give each workload its own shelf — quota, durability class, expiration, and endpoints — so eviction pressure on one bucket can never take another down with it.

02Create · enumerate · delete — the manager

Three methods on navigator.storageBuckets: open(name, options) (create or fetch — idempotent by name), keys() (enumerate bucket names), delete(name) (remove one bucket and everything in it). Running live:

Note what delete() is: storage destruction at namespace granularity. One call, and the bucket's IndexedDB + caches + files are gone — no iterating, no quota games. That's the whole point.

04Options — quota caps, persistence, expiration

open()'s options dictionary does real work. Each option probed live:

optionclaimlive result

Two asymmetries worth engraving: quota is a cap, not a reservation (default readback = the whole site shelf; a bucket can still be squeezed by other buckets), and persisted: true routes through the "persistent-storage" permission — in automated/headless contexts it silently resolves false instead of prompting. In Chrome, request it from a user gesture or navigator.storage.persist() first.

05Expiration — lazily enforced, brutally

Buckets can carry a wall-clock expiry. There is no timer and no event: expiry is checked when you next touch open() or keys(), and the bucket (all of it — IDB, caches, files) is collected then. await bucket.expires() reads it back — a method, per spec, though older docs show an attribute. The nastiest asymmetry, proven live: open(name, { expires: past }) throws TypeError — but bucket.setExpires(past) is accepted, silently killing the bucket at your next touch. Stale handles to a collected bucket reject with a DOMException — the spec says InvalidStateError, but Chromium 152 throws UnknownError on the estimate()/expires()/setExpires() paths after lazy expiry-collection.

06The isolation triad — three filesystems, zero leakage

Every bucket exposes its own indexedDB factory, caches (CacheStorage), and getDirectory() (a private OPFS). Same names, different universes — proven by writing colliding names into bucket-space and window-space, then cross-reading:

endpointcolliding namebucket seeswindow sees

Accounting is hierarchical: the bucket's estimate() reports only its own usage, while navigator.storage.estimate() reports the whole site — bucket usage included. A bucket can't hide bytes from the origin's budget.

07Production capstones

OpenDrones Mission Control — evidence must outlive the cache. Two buckets: mission-evidence (persisted — eviction-exempt, holds FAA-retention flight logs in bucket-scoped IndexedDB) and telemetry-cache (best-effort, quota-capped to ~50 MB, expiring weekly — the sacrificial tier). When a field tablet hits storage pressure, Chromium can reclaim the cache bucket while the evidence bucket survives untouched. Nuking just the cache after a sync is one HTTP header: Clear-Site-Data: "storage:telemetry-cache".

The two-tier contract in one line each: storageBuckets.open('mission-evidence', { persisted: true }) · storageBuckets.open('telemetry-cache', { quota: 52_428_800, expires: Date.now() + 7*864e5 })

Molt Studios — per-client shelves. A build tool that caches per-client assets in one origin-wide CacheStorage lets one heavy client starve the rest. Bucket-per-client with a per-bucket quota cap makes the split structural — delete('client-x') is offboarding in one call, data destruction included.


  

  

    
Gotcha wall — the traps that bite in production:

    
    
      
  • Chromium-only (122+; Firefox/Safari not shipped as of 2026-08). Feature-detect and fall back to the single shelf — design storage code against bucket-shaped interfaces so the fallback is a shim, not a rewrite.
    • 
      
  • Name rules are stricter than they look: lowercase-only charset, no leading _/- — and Chromium 152 rejects 64-char names the spec permits (observed ceiling: 63; plus an observed per-origin count ceiling around 51 buckets — don't mint unbounded buckets).
    • 
      
  • Spec drift is real: expires() is a method (docs showed an attribute); the durability option is accepted-but-spec-dropped; open() validates past-expires while setExpires() doesn't.
    • 
      
  • No eviction/expiry events: expiry is lazy (checked at open()/keys()), and best-effort buckets may be reclaimed under pressure before their expiry — treat expiration as an upper bound, persistence as the only guarantee.
    • 
      
  • Handles go stale silently: after expiry-collection or delete(), existing bucket objects reject — Chromium 152 with UnknownError after lazy expiry but InvalidStateError on other paths (spec mandates the latter for both) — re-open() by name after any boundary event.
    • 
      
  • Workers get it too (WorkerNavigator) — verified live below — so sync loops can run next to their data.
