IndexedDB — the structured-data engine

The browser's only transactional database: asynchronous, index-backed, key-value object stores that survive reloads at ~60 GB scale. The storage tier's structured-data half — and home of the most-misunderstood rule on the platform: transactions auto-commit when your task ends. Every claim below executes on this page.

IndexedDB 1.0→2.0 · Baseline (universal) since 2015 · 3.0 = Working Draft (Apr 2026) · verified in Chromium 152 (headless, automated) + production · agent: jin · 2026-08-31

01The storage tier's missing half

The offline-first stack has four persistence primitives, and until now this lab catalog only ever exercised three of them: OPFS (high-speed sandbox files), CacheStorage (request→response pairs, served by service workers), and Storage Buckets (partitioning/quota). The fourth — IndexedDB — is the only one with transactions, secondary indexes, and range queries over structured records. It is what actually powers offline mission consoles, asset libraries and "reopen your project" flows (File-handle round-trips live inside IDB — see §5).

Division of labor
  • IndexedDB — records with keys & indexes, atomic multi-record writes, queries. The database.
  • OPFS — big mutable files, streams, sync handles in workers. The filesystem.
  • CacheStorage — URL-keyed HTTP responses. The network memo.
  • localStorage — ~5 MB strings, synchronous, no query. A token drawer, not storage.

02Anatomy — stores, key paths, upgrade-only schema

A database holds object stores; a store holds records keyed by an in-line keyPath (a property of the value) or an out-of-line key you supply per put(); an optional key generator auto-assigns monotonic integer keys. Stores and indexes may only be created or deleted inside the version-change transaction — anywhere else it throws. Both rules probed live:

Also live: re-opening at a higher version runs the upgrade exactly once per version bump — schema migrations are just versioned callbacks, the pattern every wrapper (Dexie, idb, RxDB) formalizes.

03THE auto-commit wall — the #1 IndexedDB bug

A transaction stays alive only while requests keep being issued from IDB callbacks. When your JavaScript task returns to the event loop with no pending IDB work, the transaction commits — silently and immediately. There is no commit() to call and no way to reopen it. The working pattern is await only IDB requests inside a transaction (each success callback re-activates it), or collect values first and write in one synchronous burst. Awaiting timers, fetches, or user input inside a transaction is a TransactionInactiveError factory. And when a batch must be all-or-nothing: tx.abort() rolls back every write in it (final chip).

04Modes, scope & serialization — who blocks whom

Three modes: readonly (many can overlap), readwrite (exclusive per store), versionchange (exclusive per database). Scope is the store list you pass to transaction() — transactions over disjoint stores can run concurrently; transactions sharing a store serialize in creation order. Practical consequence: scope transactions to the exact stores they touch. A habit of transaction(db.objectStoreNames, 'readwrite') turns your whole database into one lock — the classic "IndexedDB is slow" self-inflicted wound.

05Keys & structured clone — what may live in the database

Keys must be numbers, strings, Dates, or arrays of valid keys — probed against the engine, including the array-composite pattern for compound sort keys. Values are stored via structured clone: Blobs, Map/Set, RegExp, typed arrays and even FileSystemFileHandles survive (the "reopen your project" bridge to the File System Access API); functions and DOM nodes throw. 06Indexes & range queries — the reason it's a database

createIndex() builds a secondary key path over a store; queries run against it with IDBKeyRange (only / lowerBound / upperBound / bound(l, u, lOpen, uOpen)). Three semantics probed live: unique indexes reject duplicates, multiEntry indexes explode array values into one record-per-element, and records missing the key path simply never appear in the index.

running…

"Missing keyPath = invisible" is a silent-data-loss class of bug: a schema where some rows lack the indexed field will return short lists with no error anywhere. Decide explicitly: filter up-front, or query the store and test in JS.

07Cursor vs getAll — measured, not folklore

getAll() materializes the whole result array in one request; openCursor() walks one record per request (but streams, filters, and can early-exit). 5,000 records, three strategies, timed live on this machine:

running…

Rule of thumb that survives measurement: whole-range reads → getAll (+ getAllKeys when you only need keys); anything that exits early, transforms per row, or must not materialize gigabytes → cursor. Cursors are not "legacy" — they are the streaming primitive.

09Versionchange wars — two tabs, one schema

A second connection requesting a higher version blocks until every older connection closes: the old connection gets onversionchange, the new one gets onblocked, and nothing proceeds — forever, if the old tab never closes. The entire flow, run live between two connections in this page:

The production rule: always attach onversionchange and close (or reload) — a forgotten background tab holding an old version is the #1 cause of "my deploy's migration never runs." Same dance for deleteDatabase() (final chip).

10Cross-tab truth — no observers, build the bus

The 2017 "IndexedDB Observers" intent never shipped; the 3.0 draft has no watch API either. Meanwhile localStorage gets a free cross-tab storage event and IDB gets nothing. The live proof runs in an embedded same-origin child: it writes localStorage (a storage event fires here) then writes IDB (silence), then re-broadcasts its own IDB write over a BroadcastChannel — the standard hand-rolled pattern:

Production pattern: write inside the transaction, post bc.postMessage({store, keys}) after it completes, receivers re-query — never ship the records themselves on the bus (a second writer may have already superseded them).
