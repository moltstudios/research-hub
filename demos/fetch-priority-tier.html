Priority Hints

fetchpriority, the fetch() priority option, and the scheduling tier beneath every page load

01 · Support Matrix — probed live in this page

The hint is universally shippable (Chrome 101+ Apr 2022 · Safari 17.2+ Dec 2023 · Firefox 132+ Oct 2024 → Baseline 2024). The telemetry is not.

Engine truth: Resource Timing's responsePriority field — the only JS-readable priority readback — is absent from stable Chromium 154 (also absent on Chrome for Testing 148; not mapped in MDN BCD at all). Priority is a hint you can set but cannot read back from script. Observability lives in DevTools' Priority column, not the Performance API.

03 · The Resource Timing Body-Consumption Trap

Live probe, this page, right now: three requests to the same URL class — only two will ever appear in the buffer.

Engine truth: fetch() resolves on headers, but a Resource Timing entry is minted only when the response body finishes. Leave the body unconsumed and the entry is withheld — it only appears later, if/when the idle connection drains the stream (with a delayed responseEnd), or never if the context closes first. XHR (onload = full body) always gets one immediately. Any RUM pipeline counting fetches via Resource Timing undercounts in-flight streams and mis-times abandoned ones. Confirmed on Brave 154 headless+headed and CfT 148.
04 · The Ordering Lab — 14 tiles vs 1 late hero

Recorded on Chromium 154 (Brave, localhost HTTP/1.1): 14 "tiles" fetched at t=0 (400 ms each, 6-7-socket pool), the hero created +250 ms late — sockets already saturated. Only priority can save it. Finish rank out of 15.

A · all default — hero is FIFO tail. Rank 13/15. No hints, no mercy.

B · tiles fetchpriority=low, hero default — demoting the bulk promotes everything else. Rank 7/15 (wave-2 leader).

C · tiles default, hero fetchpriority=high — promoting one also works vs non-low peers. Rank 7/15.

D · tiles low + hero high — both levers: hero effectively joins wave 1's cohort. Rank 6/15 — beat 9 tiles created 250 ms earlier.

Mechanism (measured): two effects stack — a throttle (low-priority requests are held back to roughly a wave at a time) and a queue reorder (when a socket frees, the highest-priority queued request dispatches first — the late HIGH hero consistently finishes ahead of queued LOW tiles: T1-T5@~840 ms, hero+T6@1240, T7-T10@~1245, T11-T14@~1645). Hints are relative signals: the win comes from what you demote, not what you promote.

05 · The Recipes
  • Molt hero (LCP): <link rel="preload" as="image" href="hero.avif" fetchpriority="high"> + <img fetchpriority="high"> in markup — the classic pairing; demote the carousel/below-fold imgs with fetchpriority="low" so the hero isn't competing with its own gallery
  • OpenDrones mission view: map tiles + asset thumbs default, telemetry poll left default, bulk rasters low — the measured pattern: demote the 14, the one that matters leads wave 2 without touching it
  • Don't bother: fetch(api, {priority:'high'}) among other fetches — same class already; reach for 'low' on the background work instead
<!-- LCP hero: promote ONE, demote the many -->
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high">
<img src="/hero.avif" alt="…" fetchpriority="high">
<img src="/gallery-1.avif" … fetchpriority="low">
<img src="/gallery-2.avif" … fetchpriority="low">

// background sync: demote, don't promote
fetch('/analytics-batch', { priority: 'low' })
06 · Negative Results (equally shippable)
  • new Request(url, {priority:'banana'}) → throws TypeError (enum-validated dictionary member in 154) — but the constructed Request exposes no .priority getter: write-only surface
  • responsePriority absent on stable 154 & CfT 148 — no script-side priority observability
  • XHR / sendBeacon / EventSource: no priority parameter exists — bulk demotion must be designed around them, not applied to them
