The Print Tier — CSS paged media, fragmentation & the PDF pipeline

Every client case study, invoice and mission report ships as a PDF built from HTML — yet the catalog had zero coverage of the print engine: @page, the 2015-era page-margin boxes Chromium only shipped in 131 (Nov 2024), fragmentation of grid/flex, widows/orphans break math, and the printToPDF parameter wall. This page live-probes the engine you're reading it in — parse-level here in-browser, behavior-level against real generated PDFs (each "PDF-proven" chip was enforced by a headless-Chromium gate that printed this very page's constructs and parsed the output). It is the output tier next to WAAPI (screen motion) and Motion Path (screen space): everything here is about the second rendering mode every browser carries and almost nobody tests.

§01 · The page model — @page anatomy & the preferCSSPageSize wall

A print document is a sequence of page boxes (page margin + page area), sized by @page { size; margin }. The first engine truth hits immediately: a headless/programmatic print ignores your CSS page size by default. Playwright/Puppeteer's page.pdf() and CDP Page.printToPDF default to Letter unless you pass preferCSSPageSize: true — your A4 stylesheet silently becomes a US-Letter PDF with reflowed line breaks.

live parse — what this engine kept of this page's own @page rules

source @page ruleengine keptmargin-box children
/* printToPDF honors your paper ONLY when asked: */
await page.pdf({ preferCSSPageSize: true });   // ← A4 from CSS
await page.pdf({});                            // ← Letter, silently
/* window.print() (the user path) always honors CSS size */
Units: @page is the one place raw mm/pt/in units are first-class. Measured on this engine: size: A4 + margin: 15mm 18mm puts body text at xMin = 57pt — exactly 18mm (51.02pt) page margin + the body element's 6pt default UA margin stacking on top. Reset body{margin:0} in print stylesheets or your margins are always 8px fatter than designed.

§02 · Page-margin boxes & page counters — a Chromium-131 exclusive

@bottom-center { content: counter(page) " of " counter(pages) } — running headers/footers in pure CSS, no JS, no PDF post-processing. Specified in 2006 (CSS Page 3), shipped by Chromium 131 (Nov 2024) — and by no other engine to this day (Firefox ✗, Safari ✗ as of Sep 2026; Safari only shipped core @page itself in 18.2). §03 · The fragmentation engine — grid & flex DO break now

Every StackOverflow answer since 2015 says "Chrome treats grid/flex as monolithic — they can't split across pages." That is stale. Measured on this engine (Chromium 148): a 1-column grid of fourteen 3cm rows printed G-00..G-08 on one page, G-09..G-13 on the next. Flex column: identical clean split. The monolithic era is over — which means long dashboards and card walls can finally print without display:block hacks.

fragmentation primitives

break-before/after: page

Forces a page boundary. PDF-proven markers: sections starting exactly at page tops.

break-inside: avoid — best-effort, not a lock

A 6cm card after 24cm of filler moved wholly to the next page (both markers together). A 40cm card taller than the page? It broke anyway — avoid is a request; oversized content always survives (no clipping, no loss).

grid fragmentation

1-col grid × 14 rows → 9 + 5 across two pages, borders intact at the seam — PDF-proven on the construct battery and re-proven every gate run.

flex fragmentation

Same test on display:flex; flex-direction:column → 9 + 5. Both engines-er-to-forget layout modes fragment.

/* the dashboard-to-report recipe */
@media print {
  .cardwall { display: grid; gap: 12px; }   /* splits page-to-page, 2026 Chrome */
  figure    { break-inside: avoid; }        /* keep photos whole */
  .section  { break-after: page; }
}

§04 · widows & orphans — the line-break math, measured

Two integers control how many lines a paragraph will tolerate having alone on either side of a page break: widows (lines at the top of the next page), orphans (lines left behind). Measured on this engine with a 54-line monospace paragraph against a measured 50-line page: default break = 50 + 4; adding widows: 5 moved the break to 49 + 5 — exactly one line pushed over. And orphans: 4 on a paragraph that would have started with 2 lines at a page bottom moved the entire paragraph to the next page.

break math (measured, monospace 14px/1.45, A4, 12mm margins)

C01..C54none (default widows 2)C01..C50C51..C544 widows ≥ 2 → break untouched
W01..W54widows: 5W01..W49W50..W54break moved back exactly 1 line

The Firefox hole: caniuse-era wisdom says widows/orphans are old news — but Firefox has never shipped them (BD: false as of Sep 2026; Chrome 25+, Safari 1.3+). An inverted holdout 20 years in: the "legacy print properties" are missing from the engine everyone assumed had everything. Your print stylesheet degrades silently there — breaks land wherever the line math falls.

§05 · The repeaters — position: fixed, thead & no-print chrome

Three print behaviors every report needs, all PDF-proven on this page's constructs:

probe battery

fixed repeats EVERY page… except rotated ones

A position:fixed bar painted on 20 of 21 probe pages — every page except the named landscape page, which got the margin-box footer but no fixed furniture. Fixed repeaters attach to same-orientation pages only. (Also why a fixed screen navbar must be display:none in print.)

thead repeats per page

A 60-row table across 2 pages printed THEAD-MARKER on both. Free column headers — no JS pagination.

@media print hides chrome

NAVBAR construct absent from every page. Also verified via Emulation.setEmulatedMedia('print') — computed display flips live on screen (§07).

@media print {
  nav, .no-print { display: none !important; }
  table { break-inside: auto; }
  tr    { break-inside: avoid; }   /* rows stay whole, thead repeats free */
}

§08 · Named pages — mixed-orientation PDFs & the leak

The page property (Chromium 85+, Firefox 110+) assigns elements to named page styles: .landscape-sec { page: rotated } + @page rotated { size: A4 landscape }. The probe PDF came out with page 5 physically rotated to 841.92 × 594.96 pt while every other page stayed portrait — a mixed-orientation document from one HTML file, the exact shape of a client report with a wide map in the middle.

the leak, measured

PDF paramsunnamed pagesnamed "rotated" page
preferCSSPageSize: trueA4 portrait (594.96×841.92)A4 landscape (841.92×594.96) ✓
preferCSSPageSize: false (default)Letter (CSS ignored)Letter landscape (792×612) — orientation leaks through, absolute size doesn't!
The leak: even when preferCSSPageSize:false suppresses your CSS paper size, a named page's orientation still applies — the engine rotates the param-chosen paper. Beautiful accident or nasty surprise depending on which side you're on; probe it, don't assume it.

§09 · The PDF pipeline — parameter wall & the two print paths

Two doors produce PDFs: the user path (window.print() → ⌘P → Save as PDF; always honors CSS size, subject to the user's Background-graphics checkbox) and the programmatic path (CDP Page.printToPDF / Playwright page.pdf(); Chromium-only, parameterized). The parameters that matter, all probed:
