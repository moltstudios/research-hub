The Core API — Connect, Read, Write

Three steps: request a port, open it at the right baud rate, and read/write via standard streams.

// 1. Request a port (requires user gesture — click, tap, keypress)
const port = await navigator.serial.requestPort({
  filters: [{ usbVendorId: 0x2DAE }]  // ArduPilot / Pixhawk vendor ID
});
await port.open({ baudRate: 115200 });

// 2. Read from the port (ReadableStream)
const reader = port.readable.getReader();
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  const bytes = new Uint8Array(value);
  console.log(`RX ${bytes.length} bytes`, bytes);
}

// 3. Write to the port (WritableStream)
const writer = port.writable.getWriter();
const cmd = new Uint8Array([0xFE, 0x09, 0x00, 0x16, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00]);
await writer.write(cmd);  // MAVLink HEARTBEAT request

Stream-based I/O — the key design decision

Both port.readable and port.writable are standard Streams API objects. That means you can pipe them through TransformStreams to decode text, parse binary protocols, or frame MAVLink packets — all without manual buffering:

// Decode ASCII + parse line-by-line via TransformStream
const decoder = new TextDecoderStream();
const lineStream = new TransformStream({
  buffer: '',
  transform(chunk, controller) {
    this.buffer += chunk;
    const lines = this.buffer.split('\n');
    this.buffer = lines.pop();
    lines.forEach(line => controller.enqueue(line));
  }
});

port.readable
  .pipeThrough(new TextDecoderStream())
  .pipeThrough(lineStream)
  .pipeTo(new WritableStream({
    write(line) { console.log(`> ${line}`); }
  }));
🔌

navigator.serial.requestPort()

Opens a system device chooser filtered by USB vendor/product ID. Requires user activation — the user picks the device.

📋

navigator.serial.getPorts()

Returns ports the user already approved for this origin. No popup — reconnect on page load.

📊

ReadableStream + WritableStream

Standard Streams API. Pipe through TransformStreams for protocol decoding, text parsing, or framing.

🎛️

setSignals / getSignals

Drive DTR, RTS control lines and read DSR, CD, RI. For hardware flow control and reset-to-bootloader.

📡

connect / disconnect events

Fire on navigator.serial when approved devices are plugged/unplugged. No polling needed.

🗑️

port.forget()

Revokes the origin's permission for that port. Chrome 103+. Clean disconnect for shared kiosks.

Section 5

Web Serial vs WebUSB vs WebHID vs Web Bluetooth

Four hardware-access APIs, different abstraction levels. Pick the one that matches your device's protocol.

📡 Web Serial

~72%

Level: Serial byte stream (virtual COM port)
Best for: Drones (MAVLink/MSP/CRSF), 3D printers (G-code), microcontrollers (Arduino/ESP32), industrial sensors
Device appears as: /dev/tty* or COM*

🔌 WebUSB

~70%

Level: Raw USB endpoints (control/bulk/interrupt)
Best for: Devices with custom USB protocols not exposed as serial. Flashing firmware, raw device control.
Device appears as: USB vendor/product IDs

⌨️ WebHID

~70%

Level: HID reports + collections
Best for: Game controllers, joysticks, custom input devices, drone RC transmitters with HID mode
Device appears as: HID descriptor

🔵 Web Bluetooth

~72%

Level: BLE GATT services/characteristics
Best for: Wireless sensors, BLE beacons, Bluetooth drone telemetry, fitness devices
Device appears as: GATT service UUIDs

When to use Web Serial (vs WebUSB)

Most drone flight controllers (Pixhawk, ArduPilot, PX4, Betaflight, INAV) expose a USB CDC-ACM virtual serial port. The OS assigns it a COM port (Windows) or /dev/ttyACM* (Linux/macOS). Web Serial is the natural interface — you get a clean byte stream at a configured baud rate.

Use WebUSB only when the device has a custom USB protocol that does NOT appear as a serial port (e.g., flashing raw firmware to an STM32 bootloader in DFU mode). For OpenDrones: Web Serial for telemetry/mission/params, WebUSB for firmware flashing.

OpenDrones Mission Control — Browser-Direct Flight Control

The production pattern: plug a Pixhawk via USB → browser connects via Web Serial → MAVLink telemetry streams with zero backend.

// Production MAVLink-over-WebSerial wrapper
class MAVLinkConnection {
  constructor(port, baudRate = 115200) {
    this.port = port;
    this.baudRate = baudRate;
    this.sequence = 0;
    this.handlers = new Map();
  }

  async connect() {
    await this.port.open({ baudRate: this.baudRate });
    this._startReader();
    this._startWriter();
  }

  async _startReader() {
    const reader = this.port.readable.getReader();
    let buffer = new Uint8Array(0);

    while (true) {
      const { value, done } = await reader.read();
      if (done) break;

      // Append to buffer and parse MAVLink frames
      const merged = new Uint8Array(buffer.length + value.length);
      merged.set(buffer); merged.set(value, buffer.length);

      const { messages, remaining } = this._parseFrames(merged);
      buffer = remaining;
      messages.forEach(msg => this._dispatch(msg));
    }
  }

  on(messageId, handler) {
    if (!this.handlers.has(messageId))
      this.handlers.set(messageId, []);
    this.handlers.get(messageId).push(handler);
  }

  _dispatch(msg) {
    const handlers = this.handlers.get(msg.msgId) || [];
    handlers.forEach(h => h(msg));
  }

  async send(msgId, payload) {
    const frame = this._encodeFrame(msgId, payload);
    await this.writer.write(frame);
  }

  // MAVLink v2 frame: [STX][LEN][INCOMPAT_FLAGS][COMPAT_FLAGS][SEQ][SYSID][COMPID][MSGID...][PAYLOAD][CRC]
  _encodeFrame(msgId, payload, sysId=255, compId=1) {
    const stx = 0xFD;
    const len = payload.length;
    const header = [stx, len, 0, 0, this.sequence++, sysId, compId,
                    msgId & 0xFF, (msgId >> 8) & 0xFF, (msgId >> 16) & 0xFF];
    const crc = this._crc16([...header.slice(2), ...payload]);
    return new Uint8Array([...header, ...payload, crc & 0xFF, (crc >> 8) & 0xFF]);
  }
}

// Usage — 5 lines to live telemetry
const port = await navigator.serial.requestPort({ filters: [{ usbVendorId: 0x2DAE }] });
const drone = new MAVLinkConnection(port);
await drone.connect();
drone.on(0, msg => console.log('HEARTBEAT', msg));     // #0
drone.on(33, msg => updateUI(msg));                    // #33 GLOBAL_POSITION_INT

Section 7

Security Model — User-Gated, Per-Site, Per-Port

The web doesn't get silent access to hardware. Every connection requires explicit user consent.

🔐

User Activation Required

requestPort() must be called from a user gesture (click, tap, keypress). No auto-connecting on page load.

👁️

No Device Enumeration

The page cannot list connected serial devices. getPorts() only returns ports the user already approved.

🎯

Per-Site, Per-Port

Permission is scoped to the origin AND the specific port. No blanket hardware access.

🚫

Zero Fingerprinting

The browser chooser shows all serial devices, not just matching ones. No device list leaks to the page.

🔄

Revocable

port.forget() (Chrome 103+) lets the page proactively drop access. User can also revoke via browser settings.

🏗️

Permissions-Policy

The serial Permissions-Policy directive controls which contexts can use the API. Block in iframes by default.

Firefox Add-On Gating — the extra layer

Firefox 151 adds an additional consent step: the first time a site requests serial access, Firefox shows an "add-on gating" prompt explaining what's being allowed before the port chooser appears. This is more informative than Chrome's approach and addresses the fingerprinting concerns that delayed Mozilla's implementation for 13 years. Enterprise admins can control access via the DefaultSerialGuardSetting policy.

Decision Matrix — When to Use Web Serial

Match the hardware-access API to the device protocol, not the other way around.

Drone telemetry (MAVLink/MSP/CRSF) Web Serial FC exposes virtual COM port. Byte stream + custom framing.

Microcontroller programming (Arduino/ESP32) Web Serial + WebUSB Serial for REPL/monitor, WebUSB for DFU/bootloader flash.
Firmware flashing (STM32 DFU) WebUSB DFU mode uses raw USB bulk endpoints, not serial.

📡 The 13-Year Story

Web Serial was first proposed in 2013. Chrome shipped it in 2021 (Chrome 89). Mozilla debated it for 13 years — citing security, fingerprinting, and the concern that "the web shouldn't talk to hardware." In May 2026, Firefox 151 finally shipped support with add-on gating, reversing the "harmful" position. The W3C WICG spec is now moving to WHATWG for formal standardization. Apple/WebKit remains opposed. The web platform can now talk to the physical world — and for OpenDrones, that means Mission Control runs entirely in a browser tab.
