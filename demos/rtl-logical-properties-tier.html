RTL & logical properties: the bidirectional layout tier

Our catalog had Intl (the formatting tier), Intl.Segmenter (the grapheme tier), CSS logical properties in passing — and zero coverage of direction itself: dir, :dir(), unicode-bidi, and the physical→logical property map. Across the 423-entry MC catalog, margin-inline-start scored 0 hits, :dir() 0, unicode-bidi 0, writing-mode 1 (in a passing mention).

2 · The :dir() island law

The dir attribute and the CSS direction property are independent sources of truth. CSS direction wins for layout. The dir attribute wins for :dir(). Set them to disagree and you get an island — an element that lays out LTR but whose :dir(rtl) selector matches.

THE HEADLINE — :dir(rtl) can match an element whose computed direction is ltr. Measured on CfT 155, Brave 156 and WebKit 26.5 (identical in all three):
Setup (on the element itself)computed direction:dir(rtl):dir(ltr)[dir="rtl"]a :dir(rtl) CSS rule fires?
THE PAGE-LEVEL VERSION IS WORSE. Set html { direction: rtl } (CSS, not the attribute) and the whole document lays out RTL — but document.documentElement.matches(':dir(rtl)') is still false, and document.body.matches(':dir(rtl)') is false, in all three engines. The :dir() pseudo-class walks the attribute chain, not the computed style — so a CSS-driven RTL site has a root that lays out RTL and reports LTR.

What this breaks

Any component library that themes itself off :dir() — or a design system whose RTL build swaps a stylesheet on html[dir=rtl] — is correct for attribute-driven RTL and silently wrong for CSS-driven RTL. And the island case is worse than both: an element can carry dir="rtl" while a framework's reset sets direction: ltr on it, and the :dir(rtl) rules fire against an LTR layout. Both directions of disagreement were measured.

3 · The unicode-bidi default split

unicode-bidi has an initial value of normal, and the UA stylesheet then overrides it for some elements. Chromium and Brave override it for block-level elements; WebKit 26.5 does not. The result is a rendering difference, not just a computed-value difference — and it is invisible in an English-only QA pass.

THE HEADLINE — the UA stylesheet's isolation default differs by engine family, and it changes where the text sits.
ElementChromium 155 / Brave 156 unicode-bidiWebKit 26.5 unicode-bidiSame?

Chromium family ISOLATES BLOCKS

A <div> gets unicode-bidi: isolate. Its own direction: rtl becomes the base direction of its contents, so the Arabic runs to the right edge of the block.

WebKit 26.5 DOES NOT

A <div> gets unicode-bidi: normal. It is not isolated, so its contents take the parent's base direction — and the text lands on the left edge.

The de-confounded cause

The divergence was bisected to the element's display, not to a mystery: setting display: block on a <li> does not change WebKit's behaviour, and forcing unicode-bidi: isolate on the <li> does not fix the layout either. What differs is the UA stylesheet's text-align default: Chromium gives a list item text-align: start, WebKit gives it text-align: left. With text-align: left the text is pinned to the left edge regardless of the base direction.

Measured with a Range over the text: the trailing digit lands at x =10.6 px when the run is not isolated (it is pulled into the RTL run) and at x =20.3 px when it is. The same HTML puts the number in a different place on a different engine.

4 · The WebKit used-margin law

The most damaging finding in this tier, and the only one that produces a wrong number rather than a different layout. In WebKit 26.5, getComputedStyle(el).marginLeft on a block-level element inside an RTL container returns the used margin — the leftover space — not the specified value.

THE FORMULA (WebKit 26.5 only): computedMarginLeft === containerWidth − childWidth − marginRight. Verified against 5 independent (container, child, margin) triples — 5/5 exact, including the cases where the specified margin was 0, 3, 5, 11 and 20 px.

Rule that survives: never read a computed margin as a proxy for the specified one. In WebKit the law does not fire for inline-block, inline, float, or an absolutely-positioned box — only for an in-flow block-level child of an RTL container.

THE CENSUS IS COMPLETE — there is no physical property without a logical twin. 32/32 pairs verified with CSS.supports(), each tested with its own value type (a length for widths, inline-start for float, start for text-align). An earlier pass of this census used '10px' for every twin and reported 8 false negatives — float, clear, text-align, resize, overflow-x, overscroll-behavior-x and the two border- colours all “failed” because 10px is not a valid value for them. Test a property with a value of its own type, or you will invent a gap that does not exist.

The mapping, direction by direction

Horizontal — flips with direction

margin-inline-start → margin-right in RTL · inset-inline-start → right in RTL · border-start-start-radius → border-top-right-radius in RTL · float: inline-start floats to the right in RTL.

Vertical — never flips

margin-block-start is margin-top in both directions. border-block-start-width is border-top-width in both. This is why a "vertical" logical property is safe to sprinkle without thinking.

THE PHYSICAL EXCEPTIONS — four properties have no logical twin and stay physical in RTL: transform: translateX() moves right in RTL (measured: +30 px in both directions — it is not mirrored); left/right offsets are physical unless you use inset-inline-*; overflow-x is physical (use overflow-inline); and resize: horizontal is physical.

6 · Vertical writing mode — where "inline" stops meaning "horizontal"

In writing-mode: vertical-rl, the inline axis runs top-to-bottom and the block axis runs right-to-left. The logical properties follow the axes, not the screen — which is the single most counter-intuitive fact in this tier.

THE MAP (measured, both directions, identical in all three engines): in vertical-rl, margin-inline-start lands on the TOP in an LTR paragraph and the BOTTOM in an RTL paragraph; margin-block-start lands on the RIGHT in both directions.
Declaration in writing-mode: vertical-rlparagraph LTR →paragraph RTL →

That is the whole trap: the inline axis rotates, the block axis flips, and the two compose. A Japanese vertical layout (vertical-rl, LTR paragraph) and an Arabic vertical layout (vertical-rl, RTL paragraph) put margin-inline-start on opposite edges of the same element. A component written once, tested once, breaks in the other.

7 · The scrolling sign law

In an RTL scroller, scrollLeft runs negative. This is not a WebKit quirk — it is the CSSOM View standard, and it is identical in all three engines, including the root scroller of a real dir="rtl" document.

OperationLTR containerRTL containerRTL dir="rtl" document root
THE TRAP — scrollLeft = 0 is the right edge in RTL, and the far-left edge is −max. Measured: an RTL scroller with scrollWidth 900 / clientWidth 200 reports scrollLeft = 0 at the right edge, scrollLeft = -700 at the left edge, and setting a positive value is silently clamped to 0. A carousel that does el.scrollLeft += delta moves the wrong way in RTL, and a carousel that does el.scrollLeft = 0 to "reset" jumps to the opposite end.
THE PORTABILITY RULE. el.scrollBy({ left: -delta }) is the only direction-agnostic scroll. scrollLeft arithmetic needs a sign flip: const dir = getComputedStyle(el).direction === 'rtl' ? -1 : 1;

8 · The dir attribute grammar

What the attribute accepts, what it silently ignores, and what it inherits. Measured with the attribute on the element itself, inside an RTL parent — the arrangement that exposes the inheritance rules.

dir attribute valueel.dir reflectscomputed direction:dir(rtl)Verdict
THE THREE SILENT IGNORES. dir="", dir="rtl " (a trailing space) and dir="bogus" all compute to the inherited direction — the attribute is dropped, not rejected, and nothing warns. dir="RTL" (uppercase) does work and reflects as "rtl". dir="auto" resolves from the first strong character — digits and punctuation are skipped, so dir="auto" on a field containing only "12345" is LTR, and "... مرحبا" is RTL.
