Origin Private File System (OPFS) — high-speed sandbox storage for offline-first web apps

The browser ships a real filesystem per origin. Files live in a private, OS-invisible sandbox, optimized for raw throughput, and accessible synchronously from Web Workers. It's the missing piece for offline-first PWAs, drone telemetry buffering, video chunk caching, SQLite-on-the-web, and any binary blob that currently eats IndexedDB's JSON overhead.

02The 5-line recipe — write, read, list, delete

From zero to a persistent file in your origin's private sandbox. The four primitives are getFileHandle, createWritable, getFile, and removeEntry. Every call is async on the main thread; in a Worker you can do synchronous I/O at line-rate speeds.

// Write a JSON blob to OPFS
const root = await navigator.storage.getDirectory();
const fh   = await root.getFileHandle('flight-log.json', { create: true });
const w    = await fh.createWritable();
await w.write(JSON.stringify(telemetry, null, 2));
await w.close();
// Read it back
const file = await (await root.getFileHandle('flight-log.json')).getFile();
const data = await file.text();

// List all entries in a directory
for await (const [name, handle] of root.entries()) {
  console.log(handle.kind === 'file' ? '📄' : '📁', name, handle.kind);
}

// Delete
await root.removeEntry('flight-log.json');

Why no permission prompt?

OPFS is sandboxed by construction — files are invisible to the OS file manager and cannot escape the origin. That means no Safe Browsing check, no requestPermission, no SafeBrowsing round-trip per write. It's the reason OPFS is dramatically faster than the user-visible File System Access API on the same hardware.

04The sync access handle — line-rate I/O from a Worker

The killer feature: createSyncAccessHandle() returns a synchronous file handle, available only inside dedicated Web Workers. The main thread sends a message; the worker writes/reads at native disk speed; main thread stays responsive. This is the missing primitive for SQLite-in-WASM, video chunk recording, and any binary blob pipeline that can't tolerate IndexedDB's JSON serialization overhead.

// Inside a dedicated Worker
const root = await navigator.storage.getDirectory();
const fh   = await root.getFileHandle('cache.bin', { create: true });
const h    = await fh.createSyncAccessHandle();

// Synchronous write at offset 0
const buf = new Uint8Array(4 * 1024 * 1024); // 4 MB
crypto.getRandomValues(buf);
h.write(buf, { at: 0 });
h.flush();   // ensure durability before close
h.close();

Security note — FROST (May 2026)

The FROST side-channel attack (CMU, published May 2026) uses OPFS write-timing patterns to infer content from other origins via SSD activity LEDs. The risk is theoretical and limited to physical-adjacent attackers, but it's the reason createSyncAccessHandle is restricted to dedicated Workers — the boundary gives the browser a permission gate to enforce isolation. Same response applies: rate-limit writes, batch updates, don't reflect OPFS timing into user-facing UI.

05OpenDrones Mission Control — offline telemetry buffer that survives no-signal flight

Drone pilots fly in remote areas. Cell signal drops for minutes at a time. Without OPFS, every telemetry packet the drone emits between flights has nowhere to land on the client. With OPFS, the Mission Control page buffers telemetry locally, persists it across reloads, and ships it when connectivity returns. No data loss, no server-side buffering contract.

The pattern

Every telemetry packet from the drone (via WebTransport stream) is appended to an OPFS file via createSyncAccessHandle in a Worker. When connectivity is online, a separate flush loop reads the file tail and ships it to the server via fetch. When connectivity drops, the buffer grows in OPFS. When the pilot reloads the tab, the file is still there. When they fly home, the buffer flushes in seconds.

// Telemetry worker — receives stream frames, writes to OPFS, drains on flush
self.addEventListener('message', async (e) => {
  const { kind, droneId, packet } = e.data;
  const root = await navigator.storage.getDirectory();
  const dir  = await root.getDirectoryHandle('missions', { create: true });
  const sub  = await dir.getDirectoryHandle('arc-001', { create: true });
  const fh   = await sub.getFileHandle(`${droneId}.bin`, { create: true });
  const h    = await fh.createSyncAccessHandle();

  if (kind === 'telemetry') {
    const len = h.getSize();
    h.write(packet, { at: len });
    h.flush();
  } else if (kind === 'flush') {
    // Read & ship in 64 KB chunks
    const len = h.getSize();
    const buf = new Uint8Array(65536);
    let pos = 0;
    while (pos < len) {
      const read = h.read(buf, { at: pos });
      await fetch('/api/telemetry', { method: 'POST', body: read.buffer });
      pos += read;
    }
    h.truncate(0); h.close();
    // or: keep tail, mark uploaded region with a header
  }
});

07Decision matrix — OPFS vs IndexedDB vs Cache API vs localStorage

The four storage primitives cover overlapping ground. Here's the rule of thumb for each — and the workloads where OPFS wins by 50–100×.

WorkloadWinnerWhy
JSON config (few KB)localStorageSync, simple, perfect for tiny KV pairs
Indexed records (10K–1M rows)IndexedDBCursor-based queries, transactions, mature
HTTP response cache (PWA shell)Cache APIBuilt for Request / Response objects
Binary blobs (video chunks, photos, splats)OPFSZero structured-clone overhead, byte-level access
SQLite database fileOPFSwa-sqlite writes to createSyncAccessHandle at near-native speed
Live recording buffer (WebCodecs frames)OPFSStream 60 fps VideoFrame chunks to disk without main-thread stalls
Mission replay cache (Gaussian splat scenes)OPFSPairs with WebGPU (P2) splat rendering; OPFS holds the .ksplat files locally for instant nav
Tile cache for offline mapsOPFSHolds MB-scale PNG/WebP tiles, ranges faster than IndexedDB blob stores
Cross-tab broadcastBroadcastChannelNot a storage API, but the right tool for "tab A updates, tab B hears"

The hard rule. When your blob is > 1 MB, OPFS beats IndexedDB by 50–100× because IndexedDB has to structured-clone every value. When your blob is < 100 KB and you need queryability, IndexedDB still wins because cursors and indexes are free. Cache API is for HTTP responses; don't repurpose it as a generic blob store.

Quota. OPFS shares the origin's storage budget with IndexedDB, Cache API, localStorage, and Service Worker registrations. Safari is generous (~60% of total disk), Chrome is constrained to ~60% of total disk per origin in practice (varies by available disk), Firefox caps at 10% of total disk per group. Call navigator.storage.estimate() before large writes; persist() to request a quota bump when needed.

// Quota check + persist() for large workloads
const { usage, quota } = await navigator.storage.estimate();
const need = 500 * 1024 * 1024; // 500 MB
if (quota - usage < need) {
  const granted = await navigator.storage.persist();
  if (!granted) throw new Error('storage would be evicted');
}
