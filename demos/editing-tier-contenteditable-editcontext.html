The Editing Tier — contenteditable, beforeinput & EditContext

Everything users do to text passes through one pipeline: the editing host (contenteditable, universal since 2010), the Input Events contract (beforeinput → DOM mutation → input, with getTargetRanges() exposing the about-to-be-edited range), and the new EditContext API (Chromium 121+) that flips the model — you own the text, the browser owns the IME. The catalog covered the Selection model layer (Sep 12) but never the editing surface. Every claim below is an executable chip, probed with real keyboard input on this engine.

Typing labs below say “harness: focus & type” — click the host, type the sequence shown, chips self-resolve from live events. On this page they are driven by a CDP input pipeline (real keys, no synthetic events).

§00 · Capability badges

Engine-gated truth, probed at load. EditContext is Chromium-only (FF/SF: not shipped as of Sep 2026); beforeinput + getTargetRanges are Baseline (Ch 60 / FF 87 / SF 10.1); contenteditable="plaintext-only" crossed Baseline in 2026 (Ch forever, SF 17, FF 136).

§01 · The editing host contract — values, inheritance & computed truth

contenteditable is an enumerated attribute: true, false, plaintext-only, or empty string. Children inherit the nearest ancestor's value unless they redeclare — contenteditable="false" islands inside a true host are the classic pattern (and the classic bug farm). isContentEditable is the computed read-only truth.

§08 · execCommand — deprecated since 2016, unremovable forever

One API, two superpowers nobody replaced: programmatic edits that land on the browser's undo stack, and queryCommandState. Direct DOM writes bypass the stack entirely — the #1 self-inflicted editor bug. Harness: execCommand('insertText','XYZ') → real ⌘Z → manual appendChild → ⌘Z again → execCommand('bold').

§09 · The undo model — coalescing & the manual-mutation hole

Type three characters as three separate keystrokes, press ⌘Z once — how much disappears? Consecutive typing is coalesced into one undo step in Chromium (live-probed below, because docs are silent). Then redo, then undo, then one more undo past the bottom of the stack — what the engine does there is the chip's honest answer: on this engine extra undos are never an error… and one of them walks straight into the next editing host's transactions (the cross-host bleed, live).

§10 · EditContext — you own the text, the browser owns the IME

Attach an EditContext to any focusable element (no contenteditable) and the element becomes an editing surface: typing fires textupdate (you apply it to the model with updateText()), the UA never mutates your DOM, and — per spec — must not fire input events against the host. No browser undo, no spellcheck, no default caret: you own all of it. The payoff: IME, virtual keyboards, and shape-writing all work, because you keep the EditContext's model in sync.
