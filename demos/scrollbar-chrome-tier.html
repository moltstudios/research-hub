§1 The mode detector — overlay vs classic, measured on your engine

Every scrollbar-geometry law forks on one question: does the scrollbar occupy layout? macOS overlay scrollbars float (zero layout); Windows/Linux classic bars consume 15–17px. The detector: force the viewport to be scrollable and compare innerWidth − documentElement.clientWidth. Runs inside the child frame below so this page never shifts.

THE OVERLAY DETECTOR. innerWidth − documentElement.clientWidth (with html{overflow-y:scroll}) is 0 under overlay scrollbars and ≈15–17 under classic. Every width/gutter number below is interpreted through this lens — the same browser reports different geometry per OS setting.

THE SAFARI COLOR VOID. WebKit 26.5 supports scrollbar-width (thin/none/auto) but has no scrollbar-color at all — CSS.supports('scrollbar-color','auto') is false and the computed property is undefined. Branded thumb colors reach Chrome + Firefox only; Safari gets shape but never color (unless you fall back to ::-webkit-scrollbar-thumb — which then triggers §4's exclusion on the others).

THE NONE TRAP. scrollbar-width: none removes every pixel of the bar — and the box remains fully scrollable (wheel, trackpad, keyboard, scrollLeft). Live: the none lane was programmatically scrolled before you read it. Hiding the bar is not disabling the scroller — and gives scroll users zero affordance (WCAG 2.1.1 / 2.5.5 exposure).

§4 The mutual-exclusion triangle

The standard properties and the ::-webkit-scrollbar pseudo-elements are one-way-at-a-time, and the disarm works in both directions. The lanes below are live: each box carries a 24px styled pseudo-bar, and then one standard property.

styled ::-webkit-scrollbar 24px, nothing else
+ scrollbar-width:auto
+ scrollbar-width:thin → pseudo-elements OFF
+ scrollbar-width:none → pseudo-elements OFF
THE EXCLUSION TRIANGLE (headline). (1) Any styled ::-webkit-scrollbar rule ⇒ the standard scrollbar-width/scrollbar-color are ignored for that element (MDN-documented; the classic silent killer — your modern properties die because a 2013-era rule still matches). (2) The inversion, less known: computed scrollbar-width ≠ auto ⇒ the pseudo-elements are ignored — set thin anywhere and your 24px custom bar is gone (measured: WebKit 24→0). (3) Restoring scrollbar-width:auto restores the pseudo-styling. One element can never show both systems.
THE GLOBAL-RULE LAW. The exclusion is per element, so a single global *::-webkit-scrollbar{...} (or one on body inheriting nothing but matching everything via descendant selectors) disables the standard properties site-wide, and a single scrollbar-width utility class on one panel disables that panel's custom bar. Audit both directions — each looks like the other's bug.

§5 The forced-classic split — and the stale-parts instability

What does a styled pseudo-bar do to layout? Live twin lanes: the styled box vs an unstyled box, same content. Then flip a runtime switch.

THE FORCED-CLASSIC SPLIT (headline). A ::-webkit-scrollbar{width:N} rule forces a classic layout bar on WebKit: the 24px rule measurably consumes 24px of box width, even on an overlay-mode OS. On Chromium (overlay mode) the same rule renders an overlay styled bar — 0px of layout. Firefox never applies the pseudo-elements at all. Same CSS, three geometry answers.
press the button…
THE STALE-PARTS INSTABILITY (WebKit, runtime). Flipping scrollbar-width at runtime should re-arm the exclusion — and on the bench it did under one probe generation (24→0) and stayed stale under another (24→24, double-rAF + 400ms settled), with static vs JS-injected stylesheets and inline-vs-absent initial values all implicated. Runtime switching between the two scrollbar systems is not a contract on WebKit — swap classes on a full re-layout and verify, never animate a property flip.

§6 The grammar — two colors or nothing — and the inheritance split

scrollbar-color accepts exactly auto or two colors. One color, dark, light — invalid everywhere, computed falls back to auto. scrollbar-width accepts exactly auto | thin | none — lengths are refused (14px unsupported in all three engines; size via the pseudo-elements or not at all).

THE INHERITANCE SPLIT. scrollbar-color inherits (set it on :root and every scroller on the page — including inside open shadow roots — gets the pair); scrollbar-width does not (each scroller must opt in; measured: thin parent, auto child). Design systems: theme colors globally, sizes per-component.
THE OVERLAY-ALIAS GHOST. overflow: overlay — the old Chromium-only value — still parses in all three engines and computes to auto. It is dead weight in 2026 stylesheets: delete it and use scrollbar-width/gutter on purpose.

THE FIREFOX COMPUTED-VALUE WALL. Firefox 151 returns "none" for getComputedStyle(el).scrollbarWidth on every element — bare, auto, thin, none — while CSS.supports and the actual layout obey the property. Chromium and WebKit serialize correctly (auto|thin|none). Any feature-detection or state-read via computed style lies on Firefox — use CSS.supports + your own source of truth.

THE WOULD-BE GUTTER LAW (headline, Chromium). Chromium reserves the would-be scrollbar width — default 15, thin 11, styled-pseudo 24, both-edges exactly 2× (48) — even on an overlay-mode OS where the actual bar takes zero layout. WebKit reserves nothing under overlay (the spec's answer). Firefox reserved nothing on this bench either (overlay; classic-mode Firefox on Windows does reserve). "Will scrollbar-gutter do anything on macOS Chrome?" — yes, 15px. "On Safari?" — no.
THE ASYMMETRY FAMILY. stable reserves for auto (overflowing or not!), scroll, and even hidden — never for visible, and scrollbar-width:none kills the gutter (no bar can ever exist ⇒ nothing to reserve). The folklore "gutter only matters when the scrollbar shows" is false on Chromium: the reservation is unconditional (per overflow-type).

§9 The gutter lives at inline-end — RTL mirrors it

Live LTR and RTL lanes with a full-width child; the readout is the child's offset from each edge of its scrollport. The gutter (and any classic bar) sits at inline-end: right in LTR, left in RTL.

dir=ltr
dir=rtl
THE INLINE-END LAW. Measured: LTR — 0px at the left edge, the gutter width at the right; RTL — mirrored exactly (left offset = gutter, right 0). stable both-edges reserves both sides symmetrically (measured 2× exactly: 30 default / 48 styled). Centered layouts stop knocking when the bar appears — but only where the gutter reserves at all (§8).

§10 The 100vw law — the overflow nobody writes on purpose

100vw is the viewport width including any classic scrollbar. The child frame (§1) is also measuring this: a 100vw bar vs a 100% bar inside a forced-scrollable document.

waiting for child frame…
THE 100VW LAW. Under a classic viewport scrollbar, width:100vw is wider than the visible content area by exactly the bar width ⇒ guaranteed horizontal overflow on every full-bleed hero that uses it. Under overlay scrollbars it is exactly 100% — the bug hides on every macOS dev machine and ships to every Windows visitor. Fixes: 100%, or reserve with scrollbar-gutter: stable on the root where supported. (Headless lane limit: all three engines run overlay viewports headless, so the child shows the overlay face — the classic face is the documented Windows behavior, live-checkable in any Windows browser.)

THE SHADOW-PASSTHROUGH. Inherited scrollbar-color crosses the shadow boundary (the inner scroller reads the host's pair — Chromium + Firefox), while scrollbar-width (non-inherited) stops at the host. Component libraries can theme scrollbar colors from outside a component and must set width inside it.
THE ROOT-PROPAGATION RULE. scrollbar-width/scrollbar-color set on html style the viewport's scrollbars (UA rule); set on body only, they style body's own boxes — the viewport keeps platform bars (measured: body-only rules leave the viewport untouched). Like overflow, the propagation is html→viewport, and a body-only rule is the classic "why didn't it work" ticket.

Method

4 probe batteries (~90 lanes) over one plain-HTTP loopback origin: surface census + grammar/serialization · width/exclusion matrices (layout deltas = offsetWidth − clientWidth, zero borders/padding on fixtures) · gutter arithmetic pairs (clientWidth diffs vs auto baselines, isolated per lane, re-appended fresh) · runtime-flip 2×2 (static vs injected stylesheet × inline-auto vs absent) · viewport/100vw lanes in a listener-first child frame. Chromium overlay-vs-classic de-confound via --disable-features=OverlayScrollbar,FluentOverlayScrollbar (no geometry change — the overlay-mode readings stood).

Lane limits

Bench runs overlay-mode macOS headless: default/thin layout widths, Firefox/WebKit gutter reservations, viewport propagation geometry, and the classic face of the 100vw law are the documented classic-mode behaviors (MDN/spec) plus live-checkable lanes here — Windows classic-mode numbers (15–17px) are not benched. Thumb colors are paint, not layout — unverifiable headless; the exclusion is verified through geometry where it produces any, and through MDN's documented contract where it doesn't (Chromium color lane). Real-Safari headed = human-hand lane.
