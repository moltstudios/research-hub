1. What is Gaussian Splatting?

A new way to represent 3D scenes — not triangles, not voxels, but millions of soft 3D colored Gaussians ("splats") trained from photos. The result is photorealism with sub-millimeter detail, captured in minutes from a phone.

Triangles (mesh) — sharp, clean, fast. Loses fine detail (leaves, hair, fabric).
Gaussians (splat) — soft, photoreal, captures every reflection. Slower, larger file.

The 4-minute summary

A 3D scene is represented not as a triangle mesh but as a set of anisotropic 3D Gaussians — each one a soft, elongated, semi-transparent colored blob. Each splat has:

  • Position (xyz) — where the splat lives in 3D space
  • Color (rgb) — what color it contributes when viewed from this angle
  • Shape (3×3 covariance matrix) — orientation and size in 3D, so each splat can be a flat disc, an elongated streak, or a fuzzy ball
  • Opacity (α) — how transparent it is

A scene captured from 200 phone photos can be trained into 1–5 million splats in ~30 minutes on a single GPU. The trained .ply file is ~50–500MB raw, ~5–30MB compressed. Rendered at 60fps in WebGPU, the scene looks like a photograph — because it was reconstructed FROM photographs.

Why now?

The original paper (3D Gaussian Splatting for Real-Time Radiance Field Rendering, Kerbl et al., SIGGRAPH 2023) required a CUDA-capable GPU and a native app. The 2025–2026 generation of browser renderers (Spark, GaussianSplats3D, web-splat, WebSplatter) runs it entirely in the browser. WebGPU is the unlock.

Why it matters here

OpenDrones: photoreal LiDAR/mission replay. Molt Studios: real-estate walkthroughs, e-commerce product viewers, before/after renovation captures, construction site progress viz. Same technique, many products.

3. Splat file format landscape

A trained scene is a few million splats. How you store them on disk and stream them to the browser matters. Five formats have emerged in 2025–2026 — each a different trade-off between file size, decode speed, and feature support.

.ply ~50–500 MB

The original research-paper output. ASCII or binary, uncompressed. Universal — every viewer reads it. Useless on the web.

ASCII or binary • Reference format
.splat ~50–200 MB

Antimatter15's compressed binary (32 bytes per splat: position fp16×3, scale fp16×3, color uint8×4, rotation uint8×4). The de-facto web standard for the last 18 months.

32 B/splat • Lossy
.spz ~5–25 MB

Niantic's Gaussian splat format. Heavy quantization + entropy coding. ~10× smaller than .splat. ~6 B/splat. Lossy but visually indistinguishable for most scenes.

6 B/splat • ~10× compression
.ksplat ~3–15 MB

Spark / World Labs format. Hierarchical chunks for streaming + progressive load. Designed for fetch() + range requests. Spark can stream it directly without decompressing the whole file.

Streamable • Progressive load
.sogs ~5–20 MB

Fraunhofer HHI's Self-Organizing Gaussians. Uses image-codec-friendly 2D rearrangement of splat attributes, then runs JPEG/XYZ on them. GPU-friendly decode, works in fetch().

GPU decode • Image-codec
.ply (compressed) ~10–40 MB

Newer .ply variants with built-in compression. Mixed adoption. Some research groups (INRIA) ship compressed PLY directly. Most viewers still want the standard format for compatibility.

Mixed adoption • Work in progress

5. WebGPU vs WebGL2 for splat rendering

Gaussian splats are sorted back-to-front per frame for correct alpha compositing. The sort is the bottleneck. WebGPU compute shaders run this on the GPU; WebGL2 forces the sort onto the CPU via WASM.

The compute-shader sort (the unlock)

Sorting N splats back-to-front per frame on the CPU takes O(N log N) — for 1M splats that's 20 million comparisons. WebGPU moves this to a parallel radix sort on the GPU, where it runs as a compute pipeline alongside the render pipeline. The frame budget recovers from "barely 15fps" to "60fps with headroom for effects."

// WebGPU compute shader — distance-sort splats back-to-front per frame
@group(0) @binding(0) var<storage, read_write> splatIndices: array<u32>;

@compute @workgroup_size(256)
fn sortSplatKeys(@builtin(global_invocation_id) id: vec3<u32>) {
  let i = id.x;
  if (i >= arrayLength(&splatIndices)) { return; }
  // Each invocation computes depth-key for one splat and atomic-writes into a bucket.
  // WebSplatter's radix-sort avoids the global-atomics gap with a multi-pass scheme.
  let depth = viewMatrix * splatPosition(i);
  atomicAdd(&buckets[depthBucket(depth)], 1u);
}

6. Spark + Three.js integration

The production pattern for loading and rendering a splat scene alongside regular Three.js meshes. 5 lines of import, 3 lines of setup, full camera-controls + scene-graph compatibility.

import * as THREE from 'three';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
import { SparkRenderer, SplatMesh } from '@sparkjsdev/spark';

// 1. Create a regular Three.js scene + WebGPU renderer
const renderer = await new THREE.WebGPURenderer().init();
const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(60, w/h, 0.1, 1000);

// 2. Add a regular mesh (works alongside splats — no special handling)
const box = new THREE.Mesh(
  new THREE.BoxGeometry(1, 1, 1),
  new THREE.MeshStandardMaterial({ color: 0x6c5ce7 })
);
scene.add(box);

// 3. Add a Gaussian splat scene from a .ksplat file
const splat = await SplatMesh.fromUrl('/scenes/garden.ksplat');
scene.add(splat);

// 4. Render — Spark adds itself to the renderer as a side-effect
new SparkRenderer({ renderer });
function tick() {
  renderer.renderAsync(scene, camera);
  requestAnimationFrame(tick);
}
tick();

Why this works as a drop-in

Spark operates at the render-graph level, not the scene-graph level. It hooks the WebGPU render pass and adds a splat-specific pass that runs alongside the mesh pass. The meshes and the splats share the same camera, the same OrbitControls, the same lighting, the same post-processing — none of that needs to change. The only thing different about splats is that they're sorted back-to-front per frame (because Gaussian alpha blending is order-dependent).

Capture pipeline (server-side)

  1. Drone records 4K video + LiDAR + IMU during the survey flight
  2. Server-side job (CUDA, postshot or gsplat CLI) trains the splat scene in ~30 min
  3. Trainer exports a .ksplat (11 MB for a 30s flight, 2.3M splats)
  4. Uploads to OpenDrones CDN with proper Cache-Control headers

Replay pipeline (browser-side)

  1. User opens the mission page in Mission Control
  2. Spark fetches .ksplat with streaming — first chunk renders in <1s
  3. WebGPU compute shader sorts splats back-to-front per frame (8ms for 2.3M splats)
  4. Spark renders splats alongside the WebGPU 3D airspace view (existing P2 entry)
  5. Telemetry overlay (battery, GPS, altitude) uses the same data layer as live missions

The new product (and the $value)

Today: pilots submit their flight logs, regulators see a spreadsheet. Tomorrow: pilots submit a splat capture, regulators (and clients, and insurance) see a photoreal 3D replay they can navigate from any angle. Survey accuracy, NFZ compliance, even "did the drone actually inspect the tower I claimed it did" — all answerable from the same artifact. This is the most defensible product OpenDrones can ship in 2026 because no other drone platform has it.
