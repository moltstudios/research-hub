The Concurrency Tier: shared memory, futexes & zero-copy workers

JavaScript is single-threaded per agent — but every tab can spawn dozens of agents (workers) and, since the Spectre-era re-enable, share real memory between them: SharedArrayBuffer is a byte array where a write in the worker is a read on the main thread, and Atomics is the fence that keeps those bytes predictable — plus a futex (wait/notify) so threads can sleep instead of spin. This is the layer under WebAssembly threads, emulators, DSP graphs and every high-throughput pipeline. This page runs live engine probes — and is itself served cross-origin isolated (COOP + COEP headers on this exact path), so every SAB lab actually executes. On a host without the headers it degrades honestly to clone-mode.

§1

Agents, agent clusters, and why "threads" means workers

ECMAScript calls each execution context an agent: your page is one, every new Worker() is another, each with its own JS heap and event loop. Agents that can reference the same memory form an agent cluster — in a browser that's the page plus its dedicated workers (and shared workers, and same-site iframes). Within one agent you never need atomics; across agents, plain reads/writes have no ordering guarantees at all. The concurrency tier has exactly three primitives:

PrimitiveSinceWhat it gives you
Worker (dedicated)Ch 2 · FF 3.5 · SF 4A second thread + a message channel (structured clone / transferables). Universal forever.
SharedArrayBufferCh 68 · FF 79 · SF 15.2One byte buffer, same bytes in N agents — zero-copy by construction. Gated on crossOriginIsolated.
AtomicsCh 68 · FF 78 · SF 15.2Uninterruptible read-modify-write, memory ordering, and wait/notify sleeping (futexes). Always available, even un-isolated.
The separation is deliberate: Atomics works on any page, but the sharing of memory is what Spectre made dangerous — high-resolution timers + shared memory = side-channel. So the SAB constructor is hidden (global reads undefined) and postMessage(sab) throws unless the document is cross-origin isolated. The wall is §2.
§2

The isolation wall — two response headers

January 2018: Spectre demonstrated that shared memory + precise timers lets a page read memory it shouldn't. Every engine pulled SharedArrayBuffer. 2020: it came back, but only for pages that opt into cross-origin isolation — a document-level state where the browser promises the page is fenced off from other origins:

# exactly two response headers, on the document itself:
Cross-Origin-Opener-Policy: same-origin        # my window ≠ your window (no shared browsing contexts)
Cross-Origin-Embedder-Policy: credentialless   # or: require-corp — my resources are fenced too

# then, and only then:
window.crossOriginIsolated  // → true
typeof SharedArrayBuffer    // → 'function' (was 'undefined')

COEP: require-corpEvery subresource must be same-origin, CORS, or carry Cross-Origin-Resource-PolicyThird-party images/scripts/fonts without CORP are blocked; cross-origin iframes must themselves send COEP

The real-world cost of isolation is integration, not performance: payment redirects, SSO popups and embedded third-party frames are what break. Scope the headers to the exact path that needs shared memory (that's how this page is deployed — see the vercel.json in §13), and leave the marketing site alone.

§3

Three ways to move data to a worker

Every cross-agent data movement is one of three modes. Knowing the cost ladder is the whole engineering decision:

ModeSyntaxCostAfterwards
Clone (structured clone)worker.postMessage(buf)Full copy, both heaps hold itOriginal untouched — two independent buffers
Transfer (move)worker.postMessage(buf, [buf])~free (handle handoff, no byte copy)Original detached — byteLength === 0, one owner
Share (SAB)worker.postMessage(sab) (isolated only)One copy, ever — then zero per messageSame bytes in both agents, forever; synchronize with Atomics
const big = new ArrayBuffer(1024*1024);
w.postMessage(big);        // clone   → 1MB copied into the worker heap
w.postMessage(big, [big]); // transfer → handle moves; big.byteLength === 0 now (detached!)

const sab = new SharedArrayBuffer(1024*1024);  // isolated pages only
w.postMessage(sab);        // share   → the worker's view sees YOUR writes, µs later
Read the three numbers as a ladder: clone pays bytes every message, transfer pays once per direction but forbids the sender from touching the data, share pays once total and both sides keep working memory. High-frequency streams → share. One-shot handoff → transfer. Small/irregular objects → clone is fine and simplest.
§4

SAB anatomy — views, slice, and the sharing fine print

A SharedArrayBuffer is API-identical to an ArrayBuffer (byteLength, views, slice) except for two asymmetries: it can't be detached by transfer, and clones share instead of copying. Probes on this engine:

const sab = new SharedArrayBuffer(64);
const i32 = new Int32Array(sab);        // a view — typed arrays stay local objects
i32[0] = 42;                                // plain write: eventually visible, no ordering promise
Atomics.store(i32, 0, 42);                 // ordered write: visible-before (see §6)

sab.slice(0, 4)                            // COPY out → NEW SharedArrayBuffer (type stays shared, data independent)
structuredClone(sab)                       // NOT a copy — new SAB object, SAME data block
§5

Atomics — the operation set

Nine operations, all static on Atomics, all uninterruptible (no torn read-modify-write, no lost update), all valid on integer typed arrays only — Int8/Uint8/Int16/Uint16/Int32/Uint32 plus the 64-bit pair BigInt64Array/BigUint64Array (values as BigInt). Return-value asymmetry is the #1 gotcha — every op returns the old value except store:

OpEffectReturns
load / storeread / ordered writevalue read / the value (only op returning the new one)
add / sub / and / or / xorRMW arithmetic/bitwiseold value
exchangeunconditional swapold value
compareExchange(a,i,old,new)swap only if current === old (CAS)old (tells you if it fired)
isLockFree(n)are n-byte atomics hardware-atomic here?boolean (experts-only optimization hint)
§6

Why plain i++ breaks — the lost-update race, live

ia[0]++ is three instructions: load, add, store. Two agents interleaving them lose updates — not maybe, deterministically at scale. Below: 4 workers each increment the same cell 50,000 times. Expected total: 200,000.

The other hazard: ordering

Even without races, plain writes can be reordered by compiler and CPU. The TC39 tutorial's canonical trap: a worker writes ia[42]=314159 then ia[37]=123456; a reader who saw the second write is not guaranteed to see the first — it can legally print 123456 then the old ia[42]. An atomic store is a release point: everything written before it becomes visible no later than it. Rule of thumb: synchronization cells are atomic, bulk data can stay plain — one atomic flag "publishes" a whole plain-written frame (the ring buffer in §11 is exactly this pattern).

Undefined ≠ crash: an unsynchronized read may observe a value that was never written (torn/garbage) on weakly-ordered cores. It's rare, it's architecture-dependent, and it's why "it worked on my machine" is not a concurrency proof.
§7

wait / notify / waitAsync — futexes for JavaScript

Spin loops burn a core. The futex pair lets an agent sleep on a memory cell until another agent wakes it: Atomics.wait(ta, i, expected, timeout) sleeps only if ta[i] === expected (else returns "not-equal" immediately), and returns "ok" when woken, "timed-out" otherwise. Atomics.notify(ta, i, n) wakes up to n sleepers and returns how many it woke — waking zero is a normal, cheap no-op.

// worker (blocking is fine here — it's not the main thread):
Atomics.wait(i32, 0, 0, 4000);     // sleep until i32[0] changes + notify, or 4s

// main thread:
Atomics.wait(i32, 0, 0, 0);        // ✗ THROWS on the main thread in Chromium/FF/SF
const r = Atomics.waitAsync(i32, 0, 0, 4000);
                                   // ✓ non-blocking — the ONLY main-thread legal form
r.async   // BOOLEAN: true = it went async (r.value is a Promise)
r.value   // Promise resolving 'ok'|'timed-out' — or the string 'not-equal' inline when r.async === false
These three primitives compose into every classical building block: mutex = wait/notify on a lock word; semaphore = counter + waitlist; condition variable = notify-all broadcast; producer/consumer = ring + two semaphores (§11). Libraries exist, but at this size most teams end up shipping the ~40 lines themselves.
§8

Growable SAB — resizable shared memory (Ch 111 / FF 128 / SF 16.4)

Pass { maxByteLength } to the constructor and the buffer can grow later — the address space is reserved up front (that's the point: no reallocation, no copy, no invalidation of other agents' views). It can never shrink.

const sab = new SharedArrayBuffer(64, { maxByteLength: 4096 });
sab.growable       // true
sab.maxByteLength  // 4096 (fixed at construction)
sab.grow(512);     // new bytes are ZEROED; byteLength 64 → 512
const track = new Int32Array(sab);   // length-TRACKING view: length grows with the buffer
sab.grow(32);      // ✗ RangeError — cannot shrink ("for security reasons", per MDN)
WebAssembly parallelism rides entirely on this tier: a shared WebAssembly.Memory is a SAB, wasm atomic instructions are always enabled, and the C++/Rust toolchains (pthreads via Emscripten, Rayon via wasm-bindgen) compile to workers + SAB + atomics. Master the JS layer and the wasm layer is the same mental model.
§9

SharedWorker — one agent for many tabs

A dedicated worker dies with its page. A SharedWorker is addressed by URL: first tab creates it, every other same-origin tab connects to the same running instance over its own MessagePort. It's the building block for one-connection telemetry fans, cross-tab state servers, and "only one tab does the work" electors (pair with Web Locks for the leadership decision itself).

§11

OpenDrones capstone — the zero-copy telemetry ring buffer

Mission Control's real problem isn't bandwidth, it's allocation churn: at high packet rates a postMessage-per-packet pipeline clones every frame into garbage that GC must reap on the SAME main thread that renders the HUD. The SAB ring is the fix: a fixed circular buffer in shared memory. The producer worker writes a 20-byte frame (seq, volts, alt, RSSI, CRC), then publishes it with one Atomics.store of the head sequence — an ordered release, so the frame's plain writes are guaranteed visible first. The main thread drains on rAF, zero allocations per frame. When the main thread freezes, the ring overwrites (bounded memory, honest drops); a message queue grows (no drops, unbounded latency). Both behaviors are visible below.

// control words: [0]=head(seq) [1]=tail(seq) — frames at byte 256, N slots × 20B
const FRAME = 5;
const ctl = new Int32Array(sab, 0, 8), frames = new Int32Array(sab, 256);
function produce(seq, volts, alt, rssi) {
  const o = (seq % SLOTS) * FRAME;          // slot words — plain writes
  frames[o]=seq; frames[o+1]=volts; frames[o+2]=alt; frames[o+3]=rssi;
  frames[o+4] = crc(seq);                    // integrity check word
  Atomics.store(ctl, 0, seq + 1);             // RELEASE: frame visible, then head
}

Decision ladder

You need…Use
Off-main-thread compute, one-shot dataWorker + transfer — no headers needed
High-frequency streams / shared stateSAB ring + atomics — worth the two headers
Sleep/wake coordinationwaitAsync (main) / wait (workers) + notify
One agent across tabsSharedWorker + Web Locks election
Native-code parallelismWASM threads = this exact tier under the hood
Do NOT reach for shared memory when messages would do: clone/transfer covers most apps with zero deployment cost, zero COOP/COEP integration risk, and dramatically simpler debugging (no data races on a heap you can't inspect). SAB earns its keep at sustained high frame rates, WASM threading, and cross-agent state that must be read while another thread writes it.
