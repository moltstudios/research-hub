§1 · Why this matters

The cipher layer ships with the browser

Every cataloged reliability primitive so far — Web Locks for tabs, OPFS for storage, WebTransport for moving bytes — assumes the bytes themselves are safe. They aren't. SubtleCrypto is the layer that makes data trustworthy: encryption (nobody reads it), signing (nobody changed it), hashing (prove what it is). No npm package, no key server round-trip, runs offline in a service worker.

The production fits

  • OpenDrones: tamper-evident mission evidence — SHA-256 the flight log, ECDSA-sign the digest with the pilot's key, ship {log, hash, sig, pubkey} as an integrity bundle for FAA Part 107 documentation. Any edit to the log, one byte, fails verification.
  • OpenDrones: seal telemetry into OPFS encrypted (AES-GCM) so a stolen laptop's cached flight data is unreadable; PBKDF2 derives the key from the pilot passphrase at unlock.
  • Molt Studios: encrypt lead-form PII client-side so third-party analytics scripts physically never see names/emails — the GDPR story writes itself; randomUUID for stable anonymous visitor ids.

Why "subtle"? The API warns you itself

MDN's warning is the docs headline: "It's very easy to misuse [these primitives], and the pitfalls involved can be very subtle." Key management and protocol design are expert territory — this demo shows the primitives and the failure modes, not a security product. Two hard rules inside: never reuse an AES-GCM IV (§5 proves why), never build your own password hashing from fast hashes (§3/§6).

§2 · Anatomy

One property, eleven methods

Everything hangs off crypto.subtle. Keys are CryptoKey objects — structured-cloneable (workers, IndexedDB, postMessage), and by default non-extractable (the raw bytes never leave the engine).

crypto.subtle.generateKey(alg, extractable, usages)   // keys & key pairs
crypto.subtle.importKey(format, data, alg, ext, usages) // raw/spki/pkcs8/jwk → CryptoKey
crypto.subtle.exportKey(format, key)                    // CryptoKey → bytes/JWK
crypto.subtle.encrypt(alg, key, data)                   // AES-GCM / AES-CBC / AES-CTR / RSA-OAEP
crypto.subtle.decrypt(alg, key, data)
crypto.subtle.sign(alg, key, data)                      // ECDSA / Ed25519 / RSA-PSS / RSASSA / HMAC
crypto.subtle.verify(alg, key, sig, data)               // → boolean (never throws on mismatch)
crypto.subtle.digest(alg, data)                         // SHA-1 / 256 / 384 / 512
crypto.subtle.deriveKey(alg, base, derivedAlg, ext, usages)  // PBKDF2 / HKDF / ECDH / X25519
crypto.subtle.deriveBits(alg, base, length)
crypto.subtle.wrapKey / unwrapKey(...)                  // key transport (AES-KW, RSA-OAEP)

// siblings on crypto itself (not subtle):
crypto.getRandomValues(u8)   // CSPRNG fill — Math.random() is NOT this
crypto.randomUUID()          // v4 UUID, no strategy needed
CSPRNG check available in workers http:// → undefined

Everything is Promise-based and async — the engine may offload to native crypto threads. There is no synchronous mode and no streaming: you hand it whole buffers (no incremental SHA-256 of a 2 GB file — chunk-and-merge is your problem, and naive concat breaks the hash).

§3 · Lab · Hashing

SHA family: identity, not secrecy

A digest is a one-way fingerprint. Same input → same digest; any change → unrelated digest (the avalanche effect). Hashing answers "is this byte-for-byte the thing I fingerprinted?"

The classic misuse, called out by OWASP

Fast hashes are not password storage. SHA-256 of a password runs millions of guesses/second on a GPU. Passwords need slow, salted derivation — PBKDF2 (§6, in WebCrypto) or argon2id (WASM library; not in WebCrypto). And for authentication-of-data use HMAC/ECDSA, not bare SHA — plain hashes fall to length-extension attacks (SHA-256 included; that's why HMAC exists).

§4 · Lab · Symmetric

AES-GCM: authenticated encryption in one call

GCM encrypts and authenticates (AEAD): the ciphertext ends with a 16-byte auth tag, and the call binds optional additional authenticated data (AAD) — context the decryptor must echo exactly or the whole decrypt fails. Wrong key, flipped bit, wrong context → OperationError. Silent corruption is not an option.

— press a button —
round trip ✓ ct = plaintext + 16 B tag all 3 attacks → OperationError

Read the chips as API behavior: failed decryption throws; failed verification (§7) returns false. Asymmetric APIs for asymmetric operations — know which one you're holding.

§5 · Lab · The killer gotcha

IV reuse breaks AES-GCM completely — proven live, without the key

GCM's core is counter-mode: ciphertext = plaintext ⊕ keystream, where the keystream depends on (key, IV) only. Reuse the IV with the same key → same keystream → the keystream cancels: c1 ⊕ c2 = p1 ⊕ p2. An attacker who knows one plaintext recovers the other. No key required. NIST SP 800-38D makes uniqueness a hard requirement. Watch it happen:

Scenario: the downlink encrypts two telemetry frames with the same key and the same IV (a "fixed IV" bug). The attacker captured both ciphertexts and knows frame 1 (a public status frame). They want frame 2 (the secret one).

— press the button —
p2 recovered without the key c1⊕c2 == p1⊕p2 (keystream cancelled)

The rule this lab exists for

Fresh random 96-bit IV for every single encryption: crypto.getRandomValues(new Uint8Array(12)), ship the IV alongside the ciphertext (it's not secret). Or per-sender: random 64-bit base + monotonic counter. Never new Uint8Array(12) zeros, never a constant from config, never "the timestamp" at high message rates.

§6 · Lab · Derivation

PBKDF2: passwords → keys, priced in milliseconds

Humans type weak secrets. PBKDF2 stretches a password into a real key by iterating HMAC hundreds of thousands of times — legitimate users pay once, brute-forcers pay per guess. OWASP (2026 cheat sheet): PBKDF2-HMAC-SHA-256 at ≥ 600,000 iterations where FIPS-140 compliance is required; argon2id preferred when you can ship WASM. Salt must be random per-password (stored alongside — it's not secret either).

— press the button —
600k runs in < 2 s here

Main-thread note: at 600k this blocks for hundreds of ms — SubtleCrypto works in workers, so derive in a worker and post the non-extractable key back (structured clone handles CryptoKey). UI never stutters.

§7 · Lab · Signatures

ECDSA, Ed25519 & RSA-PSS — the keygen & sign census

Signatures prove who produced data and that it wasn't altered — private key signs, public key verifies, and the public key is freely shareable. The modern-curve story quietly completed: Ed25519 & X25519 shipped in all three engines (Ed25519: Chrome 137, Firefox 129, Safari 17 — Baseline ~2025). Run the live census on this engine:

— press a button (RSA-2048 keygen takes a moment) —
all curves sign+verify ✓ tamper → verify() = false (no throw)

What to read in the table: signature sizes — Ed25519's flat 64 B vs RSA's 256 B matters on 512-byte MAVLink frames — keygen cost (RSA-2048 pays ~100× the curve keygen), and sign/verify asymmetry (RSA verifies fast but signs slow). The ECDSA byte count is itself a lesson: this engine returns exactly 64 B — raw IEEE P1363 r||s, not ASN.1/DER. That's the classic interop trap: OpenSSL, JWS/JOSE and older WebKit builds speak DER (~70 B); convert explicitly when signatures cross runtimes.

§8 · Lab · Key lifecycle

CryptoKey: non-extractable by design

A CryptoKey is an object, not bytes. Generate with extractable:false and the raw material cannot leave the engine — export throws, but sign/encrypt still work. That's the browser's own HSM-lite: XSS can use a key it can't steal. Usages are enforced at call time, not convention.

— press the button —
exportKey(non-extractable) throws public key exports as JWK importKey round-trip verifies ✓ wrong usage → throws

JWK is the interop format — JSON, base64url, no DER tooling needed. wrapKey (AES-KW / RSA-OAEP) moves keys between parties without raw exposure. CryptoKeys structured-clone into IndexedDB: store the non-extractable key, persist the capability, never persist the secret.

§10 · Molt Studios capstone

Lead-form PII, sealed client-side production pattern

Every analytics/tag script on a marketing site can read the DOM. What it deliberately is not

  • Not transport security — TLS does the wire; this does the payload and the page.
  • No streaming crypto — whole buffers only; hash large files by chunking with your own merge strategy.
  • No argon2id / scrypt — PBKDF2 is the in-platform stretching option; WASM libs for the memory-hard ones.
  • No post-quantum signatures here — the browser's PQ story lives in the TLS layer (hybrid X25519+ML-KEM), not SubtleCrypto.
  • Not a secrets vault — non-extractable keys mitigate exfiltration, but a compromised page can still use them. Design usages narrowly.
§12 · Recap

Take the five rules

  • 1 — Fresh IV every encryption. §5 is not theoretical; the demo recovers plaintext with zero key material.
  • 2 — AEAD or nothing. AES-GCM's tag means tampering fails loudly; raw AES-CBC mangles silently. Bind context with AAD.
  • 3 — Fast hashes never touch passwords. SHA-256 = fingerprints; PBKDF2 ≥600k = passwords.
  • 4 — Non-extractable keys are free safety. Generate extractable only to export; otherwise the engine jails the material.
  • 5 — Derive heavy, off main thread. Workers + structured-cloned CryptoKeys keep 600k iterations off the UI.
