element.moveBefore() — The DOM Move-Without-State-Loss Tier

The API that reorders the DOM without killing what lives inside the node: moveBefore() moves an element (or text node) like insertBefore() — but the browser does not disconnect it, so iframe documents, CSS animation frames, media playback, focus, scroll positions, popover/dialog state and custom-element identity all survive. The missing primitive behind every "my list re-sort reloaded the map / restarted the video" bug. Zero prior catalog coverage; every claim below is an executable chip, live-probed on this engine.

§01 · Anatomy & capability surface

ParentNode.moveBefore(node, child) ships on Element, Document and DocumentFragment (the ParentNode mixin): move node to become the child just before child (or last, if child is null) — same geometry as insertBefore, different physics: no disconnect, no state teardown. Chrome/Edge 133+ · Firefox 144+ · Safari ✗ through 27.2 + iOS ✗ (MDN, Sep 2026) — not Baseline; feature-detect + insertBefore fallback is mandatory.

The contract

parent.moveBefore(node, child) // move node before child
parent.moveBefore(node, null)  // move node to END of parent
parent.moveBefore(node, node)  // documented NO-OP (safe)

// vs the state-losing ancestor:
parent.insertBefore(node, child) // re-connects → state dies
parent.appendChild(node)         // same, append flavor

// the ship-shape wrapper:
function moveNode(parent, node, ref) {
  if (typeof parent.moveBefore === 'function')
       parent.moveBefore(node, ref ?? null);
  else parent.insertBefore(node, ref ?? null); // fallback
}

A custom-element companion arrives with it: connectedMoveCallback() fires instead of the disconnected/connected pair during a move (§05) — your teardown/setup logic stops double-firing.

§02 · The no-op law & the move-to-end

Two edge behaviors worth knowing before the battery: moving a node before itself is a spec'd no-op (no throw, no reorder), and null as the reference means "move to end" — exactly appendChild geometry, but state-safe.

§07 · The exception battery

moveBefore is stricter than insertBefore in exactly the ways that bite: the reference argument is required (1-arg call → TypeError — and live-probed below, insertBefore's 1-arg call throws the same way on this engine — pass null explicitly in both), it never adopts (both nodes must already live in the same tree), cross-document moves throw, and ancestors can't move into their descendants. The adoption asymmetry (the #1 migration trap)

// appendChild ADOPTS — this is how we all build lists:
list.appendChild(document.createElement('li')) // ✅

// moveBefore REFUSES fresh nodes — move-only primitive:
list.moveBefore(document.createElement('li'), null)
// ❌ HierarchyRequestError (not in the same tree)

// the two-step when you must insert+then reorder:
list.appendChild(fresh);
list.moveBefore(fresh, list.firstElementChild);

Existing code that "moves" by appendChild-ing freshly created nodes must branch: creation stays appendChild, reordering becomes moveBefore.

§11 · Ship checklist

  1. Feature-detect typeof Element.prototype.moveBefore === 'function' — never UA-sniff (Safari ✗ through 27.2).
  2. The reference argument is required: moveBefore(el) throws TypeError where insertBefore(el) silently appends.
  3. moveBefore never adopts — both nodes must already share a tree. Fresh nodes: appendChild first, then move.
  4. moveBefore(x, x) is a documented no-op — safe to call with computed references.
  5. Ship the wrapper (moveBefore ?? insertBefore) — §01 — and route every reorder through it.
  6. MutationObserver sees remove+add records for moves (§06) — diff positions; don't treat a move as a delete event.
  7. Custom elements: handle connectedMoveCallback and stop paying disconnect/reconnect on moves — audit teardown logic for double-fire bugs.
  8. State rides along: iframe document, CSS animation frame, focus/selection, scroll, popover, dialog, media playback (§03) — but verify on every target engine; MDN's list is the contract, the engine is the truth.
  9. JS closure state survives any move (§09 control) — only engine-managed state is at risk. Know which of yours is which.
  10. Live-pane dashboards: moveBefore is not an optimization, it's the difference between "sorted" and "every feed just blinked" (§08).
