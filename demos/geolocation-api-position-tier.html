Geolocation API — the position tier

The web's oldest powerful feature (Chrome 5 / 2010) and still the only way a page learns where the device actually is — GPS, WiFi, cell, or user-entered, WGS84 degrees behind a permission gate. Every "near me" feature rides it, and the spec just returned to CR (March 2026) with new surface. This page live-probes what actually ships: the callback-only contract, the JSON trap, the cache and timeout semantics, the worker jail, and the iframe policy wall.

§01

Surface anatomy & the secure-context wall

The API hangs off navigator.geolocation (a Geolocation instance), exposes exactly three methods, and is undefined on insecure origins — the object itself doesn't exist, not a permission error. The API predates Promises: every method is callback-only and returns undefined.

§02

The permission gate — the only powerful feature with per-site lifetimes

Geolocation is a powerful feature: no position without express permission, and the spec urges engines to default to per-session lifetimes — engines vary from "until closed" to explicit "while using" grants. The state is queryable via the Permissions API on Chromium + Firefox; Safari never shipped permissions.query('geolocation') (TypeError) and re-prompts on a cadence of its own.

§03

Position anatomy & the serialization trap

A GeolocationPosition is { coords, timestamp }; coords carries latitude/longitude/accuracy always (WGS84 degrees, meters) and altitude/altitudeAccuracy/heading/speed when the source can provide them (null otherwise — null is a fact, not an error). The classic trap: the interface's attributes live on the prototype — JSON.stringify(position) used to return {}. The current CR added toJSON() — whether YOUR engine has it is exactly what the chip below records.

});

§04

The options contract — hints, not commands

enableHighAccuracy is a hint the engine may ignore (trades battery/time; on desktop it often changes nothing; on Android it gates GPS vs network). timeout/maximumAge are WebIDL double→unsigned long coercions: strings coerce, negatives clamp to 0, and timeout: 0 means immediately expired, not "no timeout" — the default for both is Infinity… wait: default maximumAge is 0, default timeout is Infinity. §05

maximumAge — the cache you didn't know you had

Only the last position is cached, per spec. maximumAge: 0 forces re-acquisition; maximumAge: 60000 accepts any cached fix younger than a minute — and returns it with its original timestamp. The classic proof is two calls: fresh call vs cached call under a big maximumAge share a timestamp (and the cached one resolves in ~0ms).

§06

The error taxonomy — three codes, four causes

PERMISSION_DENIED(1) covers user denial AND policy-blocked AND prompt-dismissed-as-deny paths. POSITION_UNAVAILABLE(2) = a source existed but had no fix. TIMEOUT(3) = the clock ran out. Per spec, the timeout clock starts after the permission grant — prompt-thinking time is free. And the constants live on the error constructor… as numbers 1/2/3, in that order, since 2008. This section is driven by a denied-context twin (the gate loads this page without granted permission to exercise code 1 verbatim).

§07

watchPosition & clearWatch — the subscription contract

watchPosition returns an integer id; clearWatch(id) stops it. Two watchers are independent subscriptions — both fire for the same source movement. After clearWatch, no further callbacks arrive (probed live below: the watch count freezes). The first callback can take as long as a fresh acquisition; it is not a cache read unless maximumAge says so.

§08

The main-thread jail & the iframe policy wall

Geolocation is not exposed in workers — unlike WebSocket/IndexedDB, the position object can't even be cloned to one (§03). And in frames, the Permissions-Policy default allowlist 'self' means: same-origin child = allowed, cross-origin child = hard-denied (code 1, no prompt) unless the embedder adds allow="geolocation" — the permission then consulted is the embedding page's grant.

§09

The precision contract — what the numbers actually mean

accuracy is a 68%-confidence radius in meters (spec: "accuracy value in meters corresponding to a 68% confidence level" — the 1σ circle, not a guarantee circle). heading is direction of travel, degrees clockwise from true north — NOT which way the device faces (that's DeviceOrientation). speed is m/s of ground track. altitude is WGS84 ellipsoid height — not mean-sea-level; GPS altitude routinely disagrees with charts by tens of meters.

delivered accuracy = m — engine passes the source's declared radius verbatim (68% ⇒ ~1-in-3 real fixes land OUTSIDE the circle: draw it, don't promise it)
stationary network fix: heading/speed = — derived-only fields, null until the source can derive them
spec cross-check: heading "clockwise from true north" · accuracy "68%" wording (this is why radius math — breach alarms, service areas — needs margin, not exactness)
§10

Distance math that doesn't lie — haversine, bearing & the meter scale

Degrees are not meters: at latitude φ, 1° longitude ≈ 111,320·cos(φ) m while 1° latitude ≈ 110,574+Δ m. Within a few km, equirectangular projection is sub-centimeter vs haversine — so the cheap math is fine for "nearest studio" but the great-circle haversine is the reference. Bearing uses atan2 on the sphere, not atan.

const R = 6371008.8; // mean Earth radius, meters (IUGG)
function havM(a, b) { // haversine distance
  const φ1=a.lat*Math.PI/180, φ2=b.lat*Math.PI/180, dφ=φ2-φ1, dλ=(b.lon-a.lon)*Math.PI/180;
  return 2*R*Math.asin(Math.sqrt(Math.sin(dφ/2)**2 + Math.cos(φ1)*Math.cos(φ2)*Math.sin(dλ/2)**2));
}
function bearing(a, b) { // initial bearing, degrees CW from true north
  const φ1=a.lat*Math.PI/180, φ2=b.lat*Math.PI/180, dλ=(b.lon-a.lon)*Math.PI/180;
  return (Math.atan2(Math.sin(dλ)*Math.cos(φ2), Math.cos(φ1)*Math.sin(φ2)-Math.sin(φ1)*Math.cos(φ2)*Math.cos(dλ))*180/Math.PI+360)%360;
}
