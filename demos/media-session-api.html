Media Session API — the OS tier

navigator.mediaSession is the contract between your <audio>/<video> and the operating system: lock-screen metadata, hardware media keys, OS media overlays, Bluetooth/Homescreen transport buttons. It is the media tier's integration layer — WebAudio synthesizes, MediaRecorder records, WebCodecs decodes… Media Session is how any of it becomes controllable from outside the tab.

§01 The surface — one singleton, six members, no constructor

The session is a per-document singleton reached via navigator.mediaSession. There is no global MediaSession constructor — you never create it, you configure the one the engine gave you. The prototype list below is the whole API; anything else you read about (like a positionState getter or setScreenshareActive) is docs-ahead-of-engine — probed live in §05 and §07.

§02 MediaMetadata — the rich card the OS renders

new MediaMetadata(init) builds the title/artist/album/artwork card shown in lock screens, OS media notifications and car dashboards. Assign it (or null to clear) to navigator.mediaSession.metadata. Engine truth on the artwork array: entries are WebIDL dictionary-converted — unknown keys are stripped, src is a required member (missing → TypeError), and its value is absolutized against the document URL at construct time — so relative paths are fine and the OS always receives absolute URLs.

// the production shape — multiple sizes, one source per size
navigator.mediaSession.metadata = new MediaMetadata({
  title: 'Kinetic Reel 2026',
  artist: 'Molt Studios',
  album: 'Showreel',
  artwork: [
    { src: 'art-96.png'',  sizes: '96x96',   type: 'image/png' },
    { src: 'art-512.png'', sizes: '512x512', type: 'image/png' },
  ],
});

§03 playbackState — a settable DOMString, no enum wall

Surprise vs the docs' tone: playbackState is a plain settable DOMString — but the engine still screens values: none/paused/playing stick; anything else is silently dropped (no throw, no stick — the getter keeps the last valid value). That matters twice: it's the escape hatch for custom players (WebAudio graphs, WebCodecs pipelines) where no element exists, and it means a typo like 'Playing' fails silently — your OS card just stays stale while you ship.

§04 The auto session — the flip that never surfaces in JS

The docs say playback flips playbackState automatically when a media element plays. This battery went looking for that flip with a real synthesized jingle (OfflineAudioContext → WAV → blob URL, no network): on Chromium 149 it never surfaces in JavaScript. Play, pause, ended, handlers registered, metadata set, element in DOM, headed and headless, file:// and http:// — the JS-visible playbackState stays 'none' unless the page itself writes it. The engine still tracks the element internally (the OS overlay's play/pause is correct — that part is not observable from JS), but the property is yours alone: manual mode is the only mode you can verify, so build on manual mode.

§05 setPositionState — the validation wall, write-only on this engine

setPositionState({duration, playbackRate, position}) feeds the OS seek bar and elapsed-time readouts. Its validation is a strict wall: negative duration, position > duration, non-positive playbackRate, NaN anywhere — each a synchronous TypeError. And on Chromium 149 the setter is write-only: MDN documents a positionState getter, this engine doesn't expose one — you cannot read back what you set (drift chip in §01, proof chip here).

navigator.mediaSession.setPositionState({ duration: 187.4, playbackRate: 1, position: 42.0 });  // ✔ feeds the OS scrubber
navigator.mediaSession.setPositionState({ duration: -1 });      // ✖ TypeError
navigator.mediaSession.setPositionState({ duration: 10, position: 11 }); // ✖ TypeError (position > duration)
navigator.mediaSession.setPositionState({ playbackRate: 0 });    // ✖ TypeError (rate must be > 0)
navigator.mediaSession.setPositionState({ duration: Infinity }); // ✔ live-stream sentinel

§06 setActionHandler — the action matrix

Actions are how the OS asks your page to do things: hardware play/pause, lock-screen skip, steering-wheel next-track. Register per action; pass null to unregister. Unknown action names throw TypeError — the classic loop-through-actions-and-try/catch pattern exists because engines support different subsets. §07 Chromium videoconferencing extras

Beyond the spec: Chromium ships setCameraActive(bool) / setMicrophoneActive(bool) for call UIs (mute indicators on the OS overlay), and MDN now documents setScreenshareActive(bool) — which this engine does not have yet. WebIDL boolean coercion applies: 'yes' coerces to true, no throw.

§08 Walls — worker jail, iframe, insecure origin

The session lives on the main thread's navigator: workers get a navigator but no mediaSession. Same-origin iframes get their own session. Insecure origins: the API is not secure-context-gated by spec — the gate probe below is injected by the verification harness over plain http:// (LAN IP), because a page cannot testify about an origin it isn't running in.

§09 Artwork — blob:, data: and the passthrough truth

Artwork values are never validated — but the src member must exist (dictionary-converted, §02) and is absolutized at construct time. Nothing is fetched or parsed at set time — src is a string the OS resolves later. That makes generated artwork (canvas → blob URL) a zero-asset production pattern: draw the album art in-page, hand the object URL to the session. Garbage sizes strings survive verbatim; the OS picks sizes at display time, not you.

§10 The handover contract — default keys → your handlers

Documented engine behavior you can't fire synthetically (OS media keys are isTrusted input no test can synthesize): while you register no handlers, Chromium's default session controls your element — the OS pause button pauses the actual <audio>. The moment you register an action handler, that action's default handling is gone — the handler must do the work itself (the #1 integration bug: registering play and forgetting audio.play() inside it, stranding the hardware key). There is also no disable API (w3c/mediasession#215): a playing element always creates a session — the only lever is making it accurate.

OS key simulator — invokes the same registered handlers the OS would, with the same event-detail shapes (seekOffset, seekTime, fastSeek). This stands in for hardware input, honestly labeled.
