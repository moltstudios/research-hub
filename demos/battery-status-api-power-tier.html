Battery Status API — navigator.getBattery() — The Device-Power Tier

The browser's one honest answer to "how much runway does this device have?" — navigator.getBattery() → a BatteryManager with four readonly properties and four events. The tier the Notification capstone had to simulate because it was never cataloged. Zero prior coverage; completes the power family alongside Wake Lock (keep the screen on), Network Information (saveData) and Idle Detection. Live-probed on this engine — with three spec-vs-engine falsifications, the no-battery camouflage law, and a removed CDP lane that changes how you test this API forever.

§01 · Anatomy — four numbers, four events, zero methods

One entry point, one object. charging (boolean), level (0–1 double), chargingTime / dischargingTime (unrestricted doubles — Infinity is a legal, common value). Four EventHandler attributes for the four change events. No methods, no toJSON, no permission — the whole surface is read + subscribe.

The contract

const b = await navigator.getBattery();
b.charging          // true | false
b.level             // 0.0 … 1.0
b.chargingTime      // seconds to full · 0 if full · ∞ if discharging
b.dischargingTime   // seconds to empty · ∞ if charging

b.onlevelchange = …        // or:
b.addEventListener(
  'levelchange', …)  // + chargingchange,
                     // + chargingtimechange,
                     // + dischargingtimechange

§02 · The resolve — instant, gesture-free, permission-less

No prompt, no permissions.query vocabulary, no user-activation requirement. Measured: 3.6 ms from call to BatteryManager on a cold headless context. The spec has no permission step at all — the only gate is the secure context.

§03 · THE IDENTITY LAW — one promise, one manager, forever

The spec gives Navigator two internal slots — [[BatteryPromise]] and [[BatteryManager]], both initialized null, both created once. Measured consequence: every call returns the exact same Promise object and the exact same BatteryManager instance, for the document's whole life. Subscriptions survive; there is no second manager to race. (One per Navigator — a cross-origin iframe gets its own.)

Proof shape

const p1 = navigator.getBattery();
const p2 = navigator.getBattery();
p1 === p2                        // true  (same Promise object)
await p1 === await p2            // true  (same BatteryManager)

§04 · THE NO-BATTERY CAMOUFLAGE — desktops read "full & charging"

The spec mandates: [[Charging]] MUST be true if there is no battery or the state is unreportable; [[Level]] defaults 1.0; [[ChargingTime]] must be 0 if full or no battery; [[DischargingTime]] defaults +Infinity. So "no battery", "unable to report", and "plugged in, full" are the same four readings — indistinguishable by design (the spec's privacy clause even blesses obfuscation). This Mac mini has no battery; your phone might be full and plugged in — the API will never tell you which.

Rule: never branch UX on "this device has a battery" — you cannot know. Branch on what the numbers do: level drops while charging is false.

§05 · THE SECURE-CONTEXT WALL — absent, not denied

[SecureContext] on both the partial Navigator and BatteryManager. Live-probed on plain-HTTP LAN (100.124.171.106, isSecureContext === false): navigator.getBattery is undefined — the object-absent law, not a rejection. (Historical note: the method was exposed to non-secure contexts until spec PR #51.)

§06 · THE POLICY PHANTOM — Permissions-Policy: battery=() does nothing

Spec vs engine, round one. The spec's getBattery() steps include a real policy gate: if the Document is not allowed to use the "battery" policy-controlled feature → reject NotAllowedError. Measured on CfT 154 with live response headers:

§07 · The walls — workers, constructors, permissions vocabulary

Exposed=Window — and the engine agrees: a dedicated worker's navigator.getBattery is undefined (contrast Notification, which constructs in workers). The constructor is walled: new BatteryManager() → TypeError: Illegal constructor. And permissions.query({name:'battery-status'}) → TypeError — battery is not in the permissions vocabulary at all (same family as web-share).

§08 · THE EVENT GRAMMAR — one event per changed slot

Each of the four slots has its own notify algorithm: when the engine updates a slot's value, it fires that slot's event (battery task source) — a slot that doesn't change doesn't fire. A charging flip changes three slots at once (charging, and both times snap to their charging-side defaults), so plug-in moments legitimately fan out chargingchange + chargingtimechange + dischargingtimechange together; a pure level drift fires levelchange alone. Events carry no payload — you re-read the manager.

§09 · THE CDP LANE REMOVAL — you cannot emulate battery in CI anymore

Spec vs engine, round two — aimed at the test lane. DevTools' protocol historically shipped Emulation.setBatteryStatus; battery e2e tests used to be trivially emulable. Live census of CfT 154's protocol: 49 Emulation commands enumerated — no battery entry; zero battery/power matches across every domain. The lane was removed. Consequences: battery UX cannot be e2e-tested on current Chromium headless — the honest strategies are (1) spec-faithful SIM layers like §08 driving your real state machine, (2) real-device runs on laptops/phones, (3) feature-detect + graceful paths. (Sibling lane for contrast: Network Information's emulateNetworkConditions still fully drives that tier — and 154 even grew Emulation.setDataSaverOverride, correcting an older note that saveData lacked a knob.)

§10 · The fingerprint story — why Firefox removed it

2015–2016: the Olejnik/Englehardt research showed level + dischargingTime (seconds-precision, battery-wear-unique) formed a tracking identifier — two sites could link visits without cookies; a brief battery drop could even deanonymize. Firefox removed the API in 52 (2017); Safari never shipped it. Chromium stayed, and the spec grew privacy SHOULDs: don't expose high precision, MAY obfuscate, MAY gate in private modes. The camouflage of §04 is part of that answer. Modern read: on Android Chrome, level arrives quantized to 1% steps — the entropy is mostly gone, but the API remains Chromium-only, so treat it as a progressive enhancement, never a load-bearing signal.

Pilots lose missions to the ground device dying, not the drone. Thresholds: advisory at 30%, critical at 20%, stand-down when charging.

§14 · The ten-rule checklist

  1. Feature-detect typeof navigator.getBattery === 'function' — FF & Safari never resolve it.
  2. Cache the manager once — identity law guarantees one instance; subscribe forever.
  3. Read via one update() on all four events; don't trust any single property alone.
  4. Never infer "device has a battery" — the no-battery camouflage makes it unknowable.
  5. Serialize Infinity consciously — JSON.stringify turns it into null silently.
  1. Secure context only — plain HTTP gets undefined, not a rejection.
  2. Don't bother with a Permissions-Policy header — the engine ignores battery=().
  3. No CI emulation — the CDP lane is gone; SIM the grammar, real-device the flows.
  4. Gate on discharging + level, not level alone (charging at 15% is a different story).
  5. Degrade to timestamps — "last saved HH:MM" beats a battery UI that lies about support.
