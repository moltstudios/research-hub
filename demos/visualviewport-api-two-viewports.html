VisualViewport API — Two Viewports: the Keyboard, Pinch-Zoom & the Fixed-Position Trap

Every mobile page has two viewports: the layout viewport (the whole document CSS px) and the visual viewport (the window you actually see — shrunk by pinch-zoom, by the on-screen keyboard, by collapsing URL bars). window.visualViewport is the only API that tells you where that visible window IS and how big it really is. It is the fix for the #1 mobile-layout crime: position:fixed bars buried under the keyboard Universal since 2019–2021 (Ch 61 / FF 91 / SF 13) — ship ungated.

§1 · The model

Two viewports, one document

The layout viewport is the canvas the page is laid out into. The visual viewport is the porthole you look through. Pinch-zoom shrinks the porthole, not the canvas. The on-screen keyboard (on Android Chrome default) shrinks the porthole without relayout. Collapsing URL bars grow it. Desktop at rest: they are the same box, which is why this API feels invisible until your site hits a phone.

§2 · Anatomy

Seven read-only properties, three events

Units: all values are CSS pixels of the layout viewport. width/height are the visual box size in layout CSS px (so pinch-zoom scale 2 ⇒ width halves). pageLeft/pageTop locate the visual box relative to the document origin (like scrollX/scrollY, but for the porthole). offsetLeft/offsetTop locate it relative to the layout viewport's top-left — nonzero only when zoomed/panned or the keyboard pans the visual viewport.

Why the order matters

If your layout code reads viewport numbers inside a window resize handler and visualViewport resize fires after, you compute with stale visual metrics (or vice-versa). The robust pattern: coalesce both through one rAF.

§6 · The headline trap

position:fixed anchors to the LAYOUT viewport — the keyboard buries it

position:fixed; bottom:0 pins to the layout viewport. When the OSK shrinks the visual viewport (Android default), a fixed bar stays at the layout bottom — under the keyboard, invisible. The fix: recompute the bar's position from live visual metrics on every resize/scroll, coalesced through rAF. The function below runs unchanged against the real window.visualViewport in production and against this page's simulated one (a desktop browser cannot open a real OSK, and window-resize moves both viewports together — the divergence physically requires touch hardware).

/* The production recipe — duck-types any viewport-like object */
function pinToViewport(bar, vv, { margin = 8 } = {}) {
  let raf = 0;
  function update() {
    raf = 0;
    bar.style.top    = (vv.offsetTop + vv.height - bar.offsetHeight - margin) + 'px';
    bar.style.left   = (vv.offsetLeft + margin) + 'px';
    bar.style.width  = (vv.width - margin * 2) + 'px';
  }
  const onVp = () => { if (!raf) raf = requestAnimationFrame(update); };
  vv.addEventListener('resize', onVp);   // keyboard open/close, pinch, URL-bar collapse
  vv.addEventListener('scroll', onVp);   // visual pan (keyboard scroll-disambiguation on iOS)
  window.addEventListener('scroll', onVp, { passive: true });  // iOS fires these too
  window.addEventListener('resize', onVp);
  update();
  return () => { ['resize','scroll'].forEach(e => vv.removeEventListener(e, onVp));
                 removeEventListener('scroll', onVp); removeEventListener('resize', onVp); };
}
/* usage */ pinToViewport(document.querySelector('#cta'), window.visualViewport);

§7 · The Chromium escape hatch

VirtualKeyboard API — overlaysContent, boundingRect(), show()/hide()

The VisualViewport API reacts to the keyboard; the VirtualKeyboard API (Chromium 94+, not in Firefox/Safari) lets you opt out of the reaction: navigator.virtualKeyboard.overlaysContent = true stops the browser resizing the visual viewport at all, and geometrychange + boundingRect() hand you the keyboard's rect so you lay out around it yourself. show()/hide() request the keyboard programmatically (focused, touch-capable contexts only).

Live probes

When to actually use it

Drawing/whiteboard apps and chat UIs that must keep painting behind a translucent keyboard; games; kiosk surfaces. For forms, prefer VisualViewport pinning (§6) — it works in every engine.

Danger: with overlaysContent = true and no manual layout, inputs sit under the keyboard with zero browser help — you own everything.

Readouts

Spec truth: scale is the pinch factor applied to the visual viewport only. Layout px never change during pinch — so getBoundingClientRect() in a zoomed page reports the same CSS px while the user sees them magnified. Coordinate math across the boundary: visualX = (clientX − offsetLeft) / 1 at rest; a point at visual (vx,vy) within the visual box maps to layout (offsetLeft + vx·scale, offsetTop + vy·scale).

§10 · Production recipes

Where this earns its keep at Molt & OpenDrones

Molt — keyboard-aware sticky CTA on the lead form

const cta = document.querySelector('.hero-cta');
const vv = window.visualViewport;
let baseH = null;
function onVv() {
  if (baseH === null) baseH = vv.height;
  const kbOpen = baseH - vv.height > 150;      // heuristic
  cta.classList.toggle('kb-open', kbOpen);     // swap to compact style
  pinToViewport(cta, vv);                      // §6 recipe — never buried
}
vv.addEventListener('resize', () => requestAnimationFrame(onVv));

Mobile lead forms lose the submit button to the OSK constantly; this keeps it one thumb-tap away and restores on blur. Baseline cost: one rAF-coalesced listener.

OpenDrones — HUD that survives pinch on the map

const hud = document.querySelector('#flight-hud');
pinToViewport(hud, vv);                         // rides the visual viewport
hud.style.fontSize = `calc(13px / ${vv.scale})`; // readable at any zoom
hud.style.setProperty('--vh', vv.height + 'px');

vv.addEventListener('scrollend', () =>          // Safari: no scrollend on vv —
  settleBlink());                               // fall back to a 120ms debounce
const onVv = () => debounce(settleBlink, 120);
vv.addEventListener('scroll', onVv);

Pilots pinch into telemetry clusters; the HUD stays pinned + legible, and the map re-centers once the visual pan settles.

/* CSS-only covers toolbars (dvh) but NOT the keyboard; JS closes the gap: */
vv.addEventListener('resize', () => {
  document.documentElement.style.setProperty('--app-h', vv.height + 'px');

§11 · Gotcha wall + ship map

Live-probed engine truths & documented traps

1 · fixed ≠ visible. position:fixed pins to the layout viewport; keyboard + pinch move the visual one. Proven live in §6 (native bar bottom stays at layout bottom under the sim keyboard; pinned bar rides above).
2 · innerHeight lies on mobile. Toolbars and the OSK make window.innerHeight stale or keyboard-inclusive (the classic iOS complaint). vv.height is the number that matches the screen.
3 · iOS never resizes layout for the keyboard. No interactive-widget support — keyboard overlays, visual viewport shrinks/scrolls, dvh unchanged. Android: interactive-widget=resizes-content opts the layout in (then vv barely changes).
4 · iOS 26 regression watch (Sept 2025 reports): after dismissing the keyboard, visualViewport height/offsets can come back different from before it opened — re-measure on blur, never cache baseline heights across focus cycles.
5 · Events arrive in bursts. Keyboard open fires resize+scroll together; pan fires a scroll stream. Always coalesce via rAF (recipe does) — per-event layout writes thrash.
6 · Only the top-level window has one. In iframes, visualViewport ≡ layout metrics of the frame — proven live in §5. Don't ship keyboard-pinning code inside cross-domain embeds.
7 · scrollend is not everywhere. vv scrollend: Ch 126+/FF 150+, Safari ✗ — debounce fallback (§10).
8 · Browser zoom ≠ pinch. Ctrl+ + resizes CSS px + DPR with scale pinned at 1; pinch raises scale with layout untouched. Feature-detect by reading vv.scale, never DPR.
9 · Fractional values. vv.height arrives fractional at odd zooms/DPRs — round only at paint, never in comparisons.
10 · No worker access. visualViewport is window-only; workers must receive metrics by postMessage if they need them.
