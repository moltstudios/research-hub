Pointer Lock API — The Input-Capture Kiosk Tier

The API that makes the mouse a relative motion sensor: requestPointerLock() hides the cursor, seizes movement (movementX/Y deltas, infinitely past screen edges), and powers FPV drone control, 3D orbit, and immersive pan — the input-side sibling of Fullscreen (fill the screen) and Wake Lock (keep it on). Zero prior catalog coverage. Every claim is an executable chip, live-probed on this engine.

§01 · Anatomy & capability surface

Four members: Element.requestPointerLock(options?) (enter), Document.exitPointerLock() (leave), Document.pointerLockElement (who is locked), plus the pointerlockchange / pointerlockerror events on Document. Core is old and universal (Chrome 37 / Firefox 50 / Safari 10.1); the promise-returning shape arrived Chrome 92 and Safari 18.4 — Firefox still returns undefined. Always feature-shape-detect, never UA-sniff.

The contract

el.requestPointerLock()          // Chromium/SF18.4+: Promise<undefined>
                                 // FF: undefined (use events!)
el.requestPointerLock(
  { unadjustedMovement: true })  // raw input, Chromium 88+
document.exitPointerLock()       // always undefined — no promise
document.pointerLockElement      // el | null (the live truth)
document.addEventListener('pointerlockchange', …)
document.addEventListener('pointerlockerror', …)

Firefox and older Safari callers must treat the return as opaque and trust the events — the promise is a Chromium/Safari-18.4 convenience, not the contract.

Why it exists (the relative-motion law)

Unlocked, a mouse can only report where it is — once the OS cursor hits the screen edge, you stop getting useful deltas. Locked, the cursor vanishes and every event becomes pure relative motion (movementX/Y) that never clips: the FPV camera yaw keeps accumulating as the user keeps sweeping. This is the same input class as a flight stick — which is why every browser FPS and drone ground-station uses it.

Companion read: Pointer Events (setPointerCapture) captures who receives events — pointer lock captures what the events mean. Decision table in §13.

§05 · unadjustedMovement — the raw-input tier

{ unadjustedMovement: true } asks the OS for pointer deltas without acceleration curves — mandatory for competitive FPV/fps feel, Chromium 88+, rejects NotSupportedError where the platform can't provide it. The canonical pattern is the graceful retry: raw first, adjusted fallback. Also probed: do bogus option keys throw or vanish?

The retry ladder (web.dev canonical)

async function lockRaw(el){
  let p = el.requestPointerLock(
    { unadjustedMovement: true });
  try { if (p) await p; return 'raw'; }
  catch (e) {
    if (e.name === 'NotSupportedError') {
      el.requestPointerLock(); // retry adjusted
      return 'adjusted-fallback';
    }
    throw e;
  }
}

§06 · The Esc law & the re-lock suppression window

§08 · The iframe matrix — the sandbox-token law

Pointer lock is sandbox-token gated, not Permissions-Policy gated — a different mechanism from camera/fullscreen/BLE: an iframe needs sandbox="… allow-pointer-lock" (plus allow-scripts to run at all). Same-origin unsandboxed children inherit freely; cross-origin children are judged by their sandbox, not their origin. Three live children probe the matrix, plus the cross-frame one-lock law.

Child 1 — plain same-origin

No sandbox attribute → inherits full origin.

Child 2 — sandbox, no token

sandbox="allow-scripts allow-same-origin" — deliberately missing allow-pointer-lock.

Child 3 — sandbox + token

sandbox="allow-scripts allow-same-origin allow-pointer-lock".

Children load lazily; each posts its own lock attempt report. In gate mode all three are driven automatically. Cross-origin variant (production mirror) swaps child 1's src via ?crossbase=.

§09 · Secure-context & the worker jail

Two context questions that gate every other catalog tier. Is pointer lock secure-context-gated (object-absent on plain http, like camera/BLE)? And does any surface exist inside workers (the main-thread jail)?

Pointer lock is a Document/Element API — there is no navigator.pointerLock to lose or jail: the worker question resolves as "no document, no lock," probed once for the record.

§10 · The Keyboard sibling — Keyboard.lock() & layoutMap()

§14 · Ship checklist — 8 rules

  1. Trust events, not return values — FF returns undefined; wire pointerlockchange/pointerlockerror first, treat the promise as bonus.
  2. Gate the request behind a real click — transient activation is consumed; call lock before fullscreen.
  3. Read only movementX/Y while locked — clientX/Y/screenX freeze; keying camera code on client position deadlocks at the edges.
  4. Always pair pointerlockchange with pointerlockerror — failures surface on BOTH channels (§02); one-channel handlers miss half the truth.
  5. Honor the Esc suppression window — after Esc exit, a re-lock fails even with fresh activation (~1.25s engine cooldown); show a re-engaging state, don't spin.
  6. Never rely on seeing the Esc keydown — the engine spends the first Esc exiting the lock; your overlay's "press Esc to exit" copy is UI, not a keydown you'll observe.
  7. Always code the unadjustedMovement retry ladder — NotSupportedError is a platform answer, not an error; fall back to adjusted lock.
  8. Release on blur/visibilitychange — the engine may drop the lock when focus leaves; your HUD must reflect pointerLockElement === null, not your intent.

The 12-line canonical engage

canvas.addEventListener('click', async () => {
  try {
    await canvas.requestPointerLock({
      unadjustedMovement: true });
  } catch (e) {
    if (e?.name === 'NotSupportedError')
      canvas.requestPointerLock();
    // else: show overlay — do NOT loop
  }
});
document.addEventListener('pointerlockchange', () => {
  const on = document.pointerLockElement === canvas;
  ui.setMode(on); // one source of truth
});

One truth function keyed on pointerLockElement — never a parallel boolean you set by hand.
