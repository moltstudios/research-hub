The engine truth. The docs say "transient activation is required" — that's the entire pre-gesture validation wall. filters:[] throws the same wall as filters:[{vendorId:0x1209}]. The Chromium chooser UI is NOT a validation step; it IS the device-selection step. Headless renders no chooser → headless requestDevice AUTO-REJECTS with NotFoundError. §02 The chooser/pend truth — headless requestDevice rejects NotFoundError

Chromium headless SHORT-CIRCUITS the chooser: when no device matches the filter, the chooser appears, immediately auto-cancels, and rejects with NotFoundError "No device selected" in milliseconds. Live-probed ×6 valid filters across fresh contexts — ALL reject with this exact message. Real browsers behave the same when the user cancels the chooser; only headless is deterministic.

awaiting input…
Filter validation is UPSTREAM of the chooser. In-gesture live probe ×6 shapes: {protocolCode:0x01} alone → TypeError "A filter containing a protocolCode must also contain a subclassCode."; missing filters field → TypeError "Required member is undefined"; filters:null → TypeError "The provided value cannot be converted to a sequence." These reject synchronously without ever opening a chooser — bug, not user error.
Production rule. Never put requestDevice() on a critical path. Wrap in your own Promise.race([requestDevice, timeout]) + catch the three rejection styles separately: NotFoundError (user cancelled / no match), SecurityError (no gesture or permission revoked), TypeError (malformed filter — fix your code, do not retry).

The when() gift. WebUSB inherits the new Observable API for event subscription. navigator.usb.when('connect', {signal}) returns a real Observable (proven via .subscribe) — first-class integration with the rest of the reactive-streams pipeline (Observables `15758f35`).

§04 The Worker split — getDevices ✓, requestDevice ✗

WebUSB is half-exposed in Workers. You can subscribe to events and enumerate already-paired devices, but you cannot request new ones. The device-acquisition wall is main-thread-only — by design.

probing…
Pattern. Main thread: requestDevice + handler installation. Worker: long-running addEventListener('connect', ...) + getDevices() enumeration. The worker never acquires new devices, but it can drive transfers on already-paired ones (verified by the spec; the worker IS allowed to call device.transferIn/Out() on a device handed in via postMessage — only requestDevice is gutted).

§05 The context matrix — 5 contexts, navigator.usb presence

§07 The transfer surface — control / bulk-or-interrupt / isochronous

Three families, each with its own WebIDL signature and use-case:

MethodEndpoint typeReturnsUse case
controlTransferInendpoint 0 (default)USBInTransferResult {data, status}GET_DESCRIPTOR, vendor requests, class requests (HID report, MIDI)
controlTransferOutendpoint 0 (default)USBOutTransferResult {status, bytesWritten}SET_CONFIGURATION, vendor commands, MIDI sysex out
transferInBULK or INTERRUPT INUSBInTransferResult {data, status}DFU upload, firmware readback, sensor bulk reads

isochronousTransferInISOCHRONOUS INUSBIsochronousInTransferResult {data, packets[]}Audio class, video class, real-time streaming
isochronousTransferOutISOCHRONOUS OUTUSBIsochronousOutTransferResult {packets[]}Audio playback, video streaming
The four required setup calls before any transfer. (1) device.open() → opens a session (resets device on close); (2) device.selectConfiguration(c) → picks one of the configurations; (3) device.claimInterface(i) → exclusive access to one interface; (4) optional device.selectAlternateInterface(i, alt) → swaps alternate. Skip any → transfer throws InvalidStateError. The setup pattern is THE thing Web Serial hand-waves away (Serial ports open with a single call).

§08 forget() & permission decay — pair once, revisit later

User-granted permission decays after about a week (Chromium) — the device shows up in the chooser but the user is re-prompted on requestDevice. device.forget() (Chrome 101+) revokes the grant immediately and removes the device from getDevices().

probing…
Decay math (Chromium Sept 2026). User-paired: ~7 days before the chooser re-prompts. OPFS-style "persistent" grants don't exist for USB — every week the user re-approves. For OpenDrones field crews, that means: ship a launch-on-login flow that walks the operator through re-pairing the drone once a week. Or: use the Web Serial fallback for telemetry (always-on, no decay) and reserve WebUSB for firmware flashing only (a one-off weekly admin task).

§09 The security model — what WebUSB REFUSES

Per the W3C spec (sec 9), Chromium declines to expose four device classes even if the user requests them:

  • HID class (03h) — keyboards, mice, game controllers. Use WebHID instead.
  • Audio class (01h) — speakers, microphones, headsets. Use Web Audio getUserMedia.
  • Mass Storage class (08h) — USB sticks, drives. Use File System Access API.
  • Video class (0Eh) — webcams, capture cards. Use getUserMedia.
  • Hub class (09h) — hubs themselves, including built-in hub ports.
  • Smart Card class (0Bh) — CCID, NFC readers (some YubiKeys).
  • Billboard class (11h) + Diagnostic mode (DCh) + Miscellaneous (EFh) + Vendor-specific (FFh) with non-standard usage.

Workaround for "but my custom device uses HID class internally": add a vendor-specific interface (class FFh, subclass 00h, protocol 00h) alongside the HID interface, and grant permission to the vendor-specific interface. Chromium will then allow requestDevice to surface it.

Why this matters. WebUSB will NEVER ship a USB-keylogger-attack vector. Chromium's class-blocklist is the trust boundary. This is also why "WebUSB for flight controllers" doesn't work for many off-the-shelf boards — many FCs enumerate as HID by default. Add a vendor-specific interface, reflash the USB descriptors, and you're in.

§10 Capstone — OpenDrones flash flow (STM32 DFU in the browser)

STM32 microcontrollers (the heart of the OpenDrones flight controllers) ship with a USB DFU bootloader on a vendor-specific interface (class FFh). The flow:

  1. Operator enters "Update firmware" mode → page calls navigator.usb.getDevices() → if the DFU device isn't paired, requestDevice({filters:[{vendorId:0x0483}]}) opens the chooser.
  2. Page calls device.open() → selectConfiguration(1) → claimInterface(0).
  3. Page reads the DFU descriptor via controlTransferIn({requestType:'class', recipient:'interface', request:0x21, value:0, index:0}, 255).
  4. Page erases the target memory bank (transferOut with DFU_ERASE command), then writes the .bin file in 1024-byte chunks via transferOut to endpoint 0x01.
  5. Page finalizes with controlTransferOut({request:0x21, value:0x0100}, ...) → DFU_DNLOAD with 0-length payload → DFU_DETACH → device reboots.

The same flow that required a native installer (DFU Demo, stm32cubeprogrammer) becomes 30 lines of WebUSB + the .bin file the pilot downloads. Zero-install firmware updates in the browser.

Where WebUSB beats Web Serial for this. DFU is a vendor-specific class (FFh), not a CDC-ACM serial port — it doesn't show up under /dev/tty.* on macOS or COM* on Windows. Web Serial can't see it. WebUSB can.

§11 Capstone — Molt in-browser Arduino sketch uploader

Molt's portfolio site has a "Build with us" CTA → opens an in-browser sketch uploader for the visitor's Arduino Nano. The flow:

  1. Visitor clicks Upload to my Arduino → page calls requestDevice({filters:[{vendorId:0x2341, productId:0x0043}]}) (Arduino Uno CDC) or [0x1B4F, 0xF008/9/10/11] (various Nano/Mini).
  2. Page enumerates configurations via device.configurations → finds interface 0 (CDC data, endpoints 0x02 OUT / 0x82 IN + interrupt endpoint 0x83 IN).
  3. Page sends the bootloader protocol via the bulk OUT endpoint (avrdude-style stk500v2 over CDC). The sketch hex is streamed chunk-by-chunk with progress callbacks.
  4. On success, page resets the device via device.reset() → the new sketch runs immediately.
The "Molt does everything" demo. "Hey, we made a website that uploads Arduino sketches." That's a portfolio piece that ships via Vercel and runs in any Chromium browser. The same site can offer Arduino IDE compatibility (the requestDevice chooser IS the IDE's board picker). For a $5k+ portfolio site, this is the kind of differentiation that lands the next $20k retainer.

The cheat. If the device shows up as a serial port in your OS → Web Serial. If the device enumerates as a standard class → WebHID / Web MIDI / Web Bluetooth (pick by class). If the device enumerates as vendor-specific (FFh) with a custom protocol → WebUSB. The vendor-ID matching is the lookup table.

§13 The 7-rule ship checklist

  1. Cap-detect before any call. 'usb' in navigator + window.isSecureContext. Bail to Web Serial fallback if either is false.
  2. Wrap requestDevice in your own timeout. The page-level promise never rejects on a closed chooser; a 10-second Promise.race is the only reliable UX.
  3. Pair requestDevice with a click. Pre-gesture → SecurityError. The "Run in-gesture" button above proves the wall is transient.
  4. open / selectConfiguration / claimInterface BEFORE the first transfer. Skip any → InvalidStateError. Use the configuration tree walk from §06 as the path.
  5. close + forget on unmount. The session is held open for the lifetime of the page; reload-without-close leaks the interface until the device is unplugged.
  6. Read the configurations tree, don't hardcode endpoints. Two devices with the same VID:PID can have different configuration layouts. Read device.configurations[i].interfaces[j].alternates[k].endpoints[l] and discover the topology on first run.
  7. Ship the Web Serial fallback. CDC-ACM covers 80% of "custom-protocol USB" needs. If the device exposes BOTH a vendor-specific interface (WebUSB) and a CDC interface (Web Serial), Web Serial is the path of least resistance.
