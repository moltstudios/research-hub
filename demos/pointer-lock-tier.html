§1 · The automation wall the headline law

requestPointerLock() succeeds or dies depending not on your page, not on user activation — but on which window the browser believes it lives in. Under every default Playwright/Puppeteer launch it rejects in ~3.5 ms with WrongDocumentError: The root document of this element is not valid for pointer lock — even with a real trusted click, real activation, focus, and visibility. A real 2026 product team shipped this exact failure and could not root-cause it. This session bisected it to a single browser launch flag.

THE AUTOMATION WALL. Chromium-family: pointer lock requires the browser-side native view focus (RenderWidgetHostImpl::GotResponseToPointerLockRequest rejects with kWrongDocument when view->HasFocus() is false or CanBePointerLocked() fails — a different thing from document.hasFocus(), which reads true in every rejected lane). Windows created through Playwright's --no-startup-window path never get it. WebKit rejects with the honest message: “Pointer lock requires the window to have focus.” Firefox has no such gate — it locks even fully headless.

THE WRONG-DOCUMENT-AMBIGUITY. kWrongDocument (no native view focus) and kPermissionDenied (blocked) both reject with the same message: “The root document of this element is not valid for pointer lock.” One says your window is invisible to the lock machinery; the other says you are not allowed. Error-message routing that keys on the text cannot tell an automation environment from a policy block.

§2 · The startup-window law — the one-line fix

Bisected this session across five experiments: not --enable-automation, not the 40-flag arg list, not CDP, not the pipe transport, not the page-creation path (startup page, Target.createTarget, and window.open pages all behave identically on a normal launch). One flag explains everything:

THE STARTUP-WINDOW LAW. Chromium-family pointer lock needs the RWHV’s native view focus. A window created through the --no-startup-window path — which every default Playwright/Puppeteer launch passes — never acquires it, so every requestPointerLock() on every page rejects with WrongDocumentError ~3.5 ms later. Remove the flag and the same script, same page, same CDP click, locks.
// Playwright / Puppeteer test suites — the fix:
const browser = await chromium.launch({
  headless: false,                                // no native window ⇒ no view focus, ever
  ignoreDefaultArgs: [ '--no-startup-window' ],    // the one flag that un-breaks pointer lock
});
// Puppeteer (which passes it differently):
//   puppeteer.launch({ ignoreDefaultArgs: ['--no-startup-window'], headless: false })

What still cannot lock

Headless Chromium (any flags — there is no native view to focus). WebKit under Playwright both modes (its gate is window focus; no flag workaround measured). Firefox is the only family that locks fully headless.

What this means for CI

Pointer-lock E2E belongs in Firefox headless, or in headed Chromium with the flag removed, or against a real browser over CDP (connectOverCDP). A Chromium headless suite will report your production mouse-look as broken forever.

§3 · The retarget law — lock captures the pointer live

While the pointer is locked, every pointer event — pointermove, pointerdown/up, click, wheel — is retargeted to the locked element, no matter what physically sits under the cursor. The click handler of your 3D canvas receives events that “happen over” the sidebar. Measured identical in Chromium and Firefox.

THE RETARGET LAW. During lock: event.target === document.pointerLockElement for the whole pointer family, including wheel. The browser synthesizes the click at pointerup and targets it at the locked element (Chromium fires it for right-button too — with contextmenu suppressed; Firefox fires only pointerdown/up for right-click). Meanwhile document.elementsFromPoint() keeps reporting the real stack under the frozen coordinates — the API and the event router disagree, by design.

§4 · The frozen-coordinate law live

Lock the pad below, then move the mouse: clientX/Y and screenX/Y freeze at the last real mouse position at lock time — not the element center — while every move arrives as pure deltas on movementX/movementY. Measured frozen in both engine families, both coordinate systems.

THE FROZEN-COORDINATE LAW. During lock: clientX/Y = the lock point (the position of the last trusted move before the lock), screenX/Y frozen alongside. All motion is movementX/Y. A HUD that positions tooltips at clientX/Y pins them to the lock point for the whole session — the drag-layer must read movement, never client.

§5 · Movement semantics — and the two zero-laws

Outside lock, movementX/Y is the plain delta from the previous event. Inside lock it is the only truth — and it has two measured edge quirks, one per family.

THE DELTA LAW. Chromium during lock: every injected move of exactly (+100,0), (0,+80), (−60,−40), (+30,+10) reports exactly m100,0 / m0,80 / m-60,-40 / m30,10 — per-event deltas, byte-exact, no acceleration term in the automation lane (OS acceleration applies to real hardware motion, not to absolute-position injection).
THE FIRST-MOVE-ZERO LAW (Firefox). The first pointermove after acquiring lock reports movementX/Y = 0,0 in Firefox (both modes) — the internal reference is seeded at lock, the first delta is measured against it and zeroed. Chromium reports the true delta immediately.
THE POST-UNLOCK-ZERO LAW (Chromium). Mirror image: the first move after exitPointerLock() reports movementX/Y = 0,0 in Chromium — the unlock resets the renderer’s last-known mouse position, so the delta engine skips one beat. Firefox reports the true delta (+200,+100 measured). A camera that keeps consuming movement across an unlock/lock cycle eats one zero-delta frame per cycle, per family.

§6 · The promise split + the no-gesture law

Two API-shape truths measured this session — one stable split, one falsified folklore.

THE PROMISE SPLIT. Chromium-family and WebKit return a Promise from requestPointerLock() (resolves on lock, rejects with a DOMException carrying the result). Firefox 151 still returns undefined — the callback era (pointerlockchange/pointerlockerror events) is the only signal. Portable code needs both: const r = el.requestPointerLock(); if (r && r.then) r.catch(…) — and must not await blindly.
THE GESTURE LAW (rehabilitated). A page-context requestPointerLock() requires live transient activation — measured identical in Chromium and Firefox: a load-time script on a never-interacted page → pointerlockerror; a timer fired 6 s after the click (activation expired) → pointerlockerror; the same timer fired immediately → locks. Timers spawned by a gesture inherit nothing once the window closes. The stale docs are right after all — and this session’s first probe said otherwise for a reason ↓
THE PRIVILEGED-CALLER LAW (the QA artifact — falsified our own probe). The same no-gesture requests succeed when issued from Runtime.evaluate — CDP/WebDriver callers bypass the activation gate in both engines. Worse, measured A/B/C: a page’s own load-timer request is also allowed if the automation suite merely ran waitForFunction/waitForSelector earlier — while waitForLoadState/sleep-driven runs block it deterministically (3/3). The injected poller taints the page context; the gesture gate never fires. This session’s probe battery 10 published “no gesture needed, 4/4” off evaluate-driven lanes; batteries 15–18 de-confounded it and the law inverted. Any green pointer-lock e2e that locks via evaluate — or after a Playwright poll-wait — is fake-green: real users still need the gesture your test never provided.

§7 · Exit, idempotency, switch, removal — the lifecycle laws

Four lifecycle behaviors, all universal across the two lockable families:

Exit idempotency

document.exitPointerLock() when nothing is locked fires no events — a silent no-op (0 pointerlockchange). Safe to call defensively at teardown.

The switch law

Requesting a lock on B while A is locked (same document) switches instantly: one pointerlockchange, promise fulfilled, no error, no exit-then-enter pair. No cooldown.

The removal law

Removing the locked element from the DOM exits the lock with a pointerlockchange (element → null) — measured both families. React/Vue unmounts do not strand the lock.

The document-only surface

pointerlockchange/pointerlockerror fire on the document only; an iframe child’s lock never reaches the parent document (measured: parent count 0).

THE ESCAPE LANE (source-cited, automation-limited). For real users, Esc exits at the browser UI level — and Chromium then arms a re-entry cooldown (kUserEscapeCooldown: “Pointer lock cannot be acquired immediately after the user has exited the lock”, ~1.25 s) to kill lock-reflow abuse. This cannot be triggered from CDP/WebDriver key events — synthetic Esc does not exit a live lock (measured: still locked after keyboard.press('Escape') in both families). Test it with a human hand; build your re-entry UX around the cooldown anyway (§11).

§8 · The shadow retarget live

Lock an element inside an open shadow root: document.pointerLockElement is the host — the same boundary rule as focus (activeElement) and event retargeting. Measured identical in both families.

THE SHADOW RETARGET. inner.requestPointerLock() ⇒ document.pointerLockElement === host (identity-checked). The outer document can observe the lock but never sees the inner element; the design-system component that locks its own internals stays encapsulated — and the page-level “who is locked” check must not assume the lock target is the thing it gave the API.

§9 · The iframe grid — sandbox gates, and a permissions-policy ghost

Four live child frames, each with its own TRY LOCK button. The children are real documents reporting their own verdicts.

THE SANDBOX GATE. An iframe with sandbox="allow-scripts" (no allow-pointer-lock) is blocked in both families — Chromium: SecurityError + console “Blocked pointer lock … the ‘allow-pointer-lock’ permission is not set”; Firefox: silent pointerlockerror + warning. Adding allow-pointer-lock to the sandbox restores it. Embedding a locked map widget in a sandboxed host page requires the attribute, spelled exactly that way.
THE PERMISSIONS-POLICY GHOST. The allow="pointer-lock" iframe attribute is not a shipped feature name: Chromium logs Unrecognized feature: 'pointer-lock', Firefox logs “Skipping unsupported feature name” — and a cross-origin child locks fine without it (measured, both families). The policy-ized future is in the source tree but not in the 2026 gate; your allow= attribute today is decoration with a warning attached.

THE SURFACE. requestPointerLock lives on Element.prototype (not Document); exitPointerLock on Document only. movementX/Y exist on both MouseEvent.prototype and PointerEvent.prototype. onpointerlockchange/onpointerlockerror exist on document only — elements have no lock-event IDL.
