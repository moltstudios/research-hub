Popover API — the engine tier

The declarative overlay primitive, measured where the catalog had only docs: the hint void (WebKit treats popover="hint" as manual), the close-veto wall (beforetoggle is uncancelable on the close path — there is no unsaved-changes guard), the click-through law (the light-dismiss click also activates the page underneath) and the auto-margin trap (an unstyled popover is a centred position:fixed; inset:0; margin:auto box — author left/top alone do not move it).

1 · The surface census — what your visitor's engine actually ships

Every number below is read live in the page you are reading it in. The Popover API core (popover, showPopover, hidePopover, togglePopover, ToggleEvent) is universal. The interest invoker half is not.

Interest invokers (interestfor)

THE SUPPORT SPLIT (headline #1). The Popover API core is Baseline everywhere, but the interest invoker — the zero-JS hover/focus tooltip that button[interestfor] gives you — ships in Chromium only on this bench. Firefox 151 and WebKit 26.5: interestForElement is absent from HTMLButtonElement.prototype, InterestEvent is undefined, and :interest-source / :interest-target do not parse. A tooltip built on interest invokers is a Chromium-only feature today — ship a JS fallback, or drive a hint popover from focus events.

2 · The hint void — WebKit has no hint popovers

MDN documents three states: auto, hint, manual. On this bench only two exist in WebKit. Lane A needs a real click — light dismiss is handled by the browser's input layer, not by a DOM listener, so a synthetic event cannot exercise it.

THE HINT VOID (headline #2). Chromium 149 and Firefox 151 report el.popover === "hint"; WebKit 26.5 reports "manual" while the attribute still reads "hint" — the IDL and the attribute disagree. The behaviour follows the IDL: on WebKit a hint popover does not light-dismiss, does not answer Esc, does not close other hints, and is not closed by an auto popover opening. On Chromium and Firefox the same markup light-dismisses, answers Esc, closes sibling hints, and is closed by a newly opened auto popover. A tooltip built on hint behaves like a modal sticky panel in Safari.
THE IDL/ATTRIBUTE SPLIT (why it hides). el.popover = "hint" writes the attribute hint but reads back manual on WebKit (3/3 independent reads). Chromium and Firefox read back hint. el.popover = "bogus" reads back manual everywhere (the invalid-value default) while the attribute keeps the literal string — so getAttribute('popover') and .popover are two different truths in every engine.

3 · The close-veto wall — there is no unsaved-changes guard

The open direction is cancelable. The close direction is not. This is the single most dangerous law in the API for client work.

Live — the popover that refuses to open, then refuses to stay open

—

Event ledger

THE CLOSE-VETO WALL (headline #3). beforetoggle fires with cancelable: true on the open direction and cancelable: false on the close direction, in all three engines. preventDefault() inside the close-path handler is a silent no-op — defaultPrevented stays false and the popover closes anyway. Measured with a real Esc keypress and a real outside click, 3/3 engines. There is no way to veto a popover close. If a popover holds unsaved input, you must implement the veto before the browser takes the close request — intercept the Esc key and the outside pointerdown yourself, and do not rely on beforetoggle.
THE EVENT GRAMMAR (measured). beforetoggle: synchronous, bubbles: false, composed: false — a listener on document never sees it; listen on the popover itself. toggle: queued as a task (a microtask checkpoint after beforetoggle does not see it), cancelable: false, same bubbling. At beforetoggle time the popover is still closed (display:none, :popover-open false); at toggle time it is open (display:block). Do "about to open" work in beforetoggle, "is open" work in toggle.

4 · The click-through law — the dismiss click is also a page click

A popover is non-modal. The page underneath stays live. The light-dismiss click does not stop at the backdrop. Needs a real click.

Live — dismiss the popover, then watch the background

Open the popover, then click the background target.

What the probe measures

A real trusted click lands on the background target while the popover is open. The browser's light dismiss consumes the popover; the same gesture's click then reaches the background target's activation handler. The gate repeats it with a real Playwright mouse click and reads the same counter.

THE CLICK-THROUGH LAW (headline #4). The outside click that dismisses a popover also activates whatever it landed on. Measured with a real trusted mouse click in all three engines: the popover closed and the background button's click handler ran (count = 1, event.detail = 1). The ::backdrop does not block pointer events — its computed style resolves in every engine, but it is transparent to input. Production consequence: on a drone map, an operator who opens a telemetry popover over a marker and then clicks “RTH” on the map behind it fires the RTH — the dismiss click is the click. Put destructive actions outside the popover's own hit area, or use <dialog>.showModal() when the background must be inert.

5 · The auto-margin trap & the viewport containing block

An unstyled popover is not “where you put it”. It is position:fixed; inset:0; margin:auto — shrink-to-fit, centred in the viewport. Author left/top alone do not move it, because the UA's auto margin keeps absorbing the free space.

Geometry readout

THE AUTO-MARGIN TRAP (headline #5). The UA box for a popover is position:fixed; inset:0; margin:auto, shrink-to-fit, centred (measured: a 48×30 content box lands at left 630 / top 435 in a 1280×900 viewport). Author position:absolute; left:100px; top:100px (no margin reset) lands the popover at left 666px / top 485px — not 100/100 — because the auto margin still absorbs the remaining space (measured identically in all three engines). The fix is one word: margin:0 (→ 100/100) or inset:auto (→ 100/100). Serialization split: getComputedStyle(el).margin returns "435px 629.906px" on Chromium, "435px 629.90625px" on WebKit, and the literal "auto" on Firefox — while the used geometry is byte-identical. Never string-compare a computed margin; never assume a popover lands where you set its offsets.
THE TOP-LAYER CONTAINING-BLOCK LAW. A popover in the top layer is not positioned by its nearest positioned ancestor: a position:absolute popover nested inside a position:relative map container resolves its left/top against the viewport, not the container (measured: left:30px; top:50px inside a container at (100,80) lands at viewport (30,50) — 3/3 engines). A HUD “positioned relative to the map” is therefore wrong by default: use an explicit anchor-name / position-anchor pair instead of relying on the ancestor.
THE REMOVE-ATTRIBUTE LAW (silent layout break). Removing the popover attribute while the popover is open closes it (the element leaves the top layer) but does not hide it: the UA's display:none goes away with the attribute and the element returns to normal flow as a static, full-width block (measured: display:block, position:static, 1280px wide, sitting in the document flow at its source position) — 3/3 engines. In React, conditionally dropping the popover attribute while it is open leaves a visible full-width block in the layout. Remove the element, or close it before the attribute goes.

6 · The implicit-anchor split — which CSS form picks up the invoker

MDN: a popover opened by a popovertarget invoker gets an implicit anchor reference to that invoker, so anchor() inside the popover resolves against it. Measured across five forms — the split is not “Chromium vs the rest”, it is which CSS syntax you use.

The four forms, measured live

The lanes run once after load; ↻ re-runs them. A–C are real invokers you can click yourself — each opens its popover the declarative way (that is the mechanism under test).

Why the forms differ

The implicit reference is created by the activation, and it is consumed by different CSS syntaxes in different engines. Form D proves the other half: the reference is created by a declarative activation only — a programmatic showPopover() establishes no implicit anchor at all, even on Chromium. That is the React trap: onClick={() => ref.current.showPopover()} has no invoker to anchor to.

THE IMPLICIT-ANCHOR FUNCTION SPLIT (headline #6). With a declarative popovertarget invoker and bottom: anchor(top); left: anchor(left) inside the popover: Chromium 149 resolves it to the invoker (popover left = invoker left); Firefox 151 and WebKit 26.5 do not — the anchor() function resolves against the popover's own static position and the popover lands at the viewport's top-left corner (0,0). The control proves it is not the feature: an explicit anchor-name + position-anchor works in all three engines, and position-area: top — which honours the implicit anchor — works in all three as well. So the split is specifically the anchor() function form. Ship the explicit form: anchor-name on the trigger + position-anchor on the popover.
THE IMPLICIT-ANCHOR ACTIVATION LAW (the React trap). The implicit reference exists only for a declarative activation. Measured with one document, five activations: a declarative popovertarget click → resolves (Chromium); a programmatic showPopover() → does not resolve in any engine; a programmatic togglePopover() → does not resolve; a programmatic showPopover({source: invoker}) → resolves on Chromium only (live lane E — the source populates ToggleEvent.source, but the implicit anchor from it is still Chromium-only). Production rule: in a React component, either use the declarative popovertarget attribute (and do not call showPopover() yourself), or set an explicit anchor-name — never rely on the implicit reference from a programmatic open.
THE SUPPORTS() LIE (supporting detail). CSS.supports('position-anchor', 'implicit') is false in all three engines — yet Chromium resolves the position-anchor: implicit declaration anyway (measured: the popover lands on the invoker). Feature-detect the behaviour, never the keyword.

7 · The declarative-fight law — popovertarget + onClick cancel each other

The most common React wiring for a popover is both halves at once: the declarative attribute and a click handler that calls showPopover(). Measured: they fight, and the popover loses.

Live — the double-wired invoker

—

Event ledger

THE DECLARATIVE-FIGHT LAW (headline #7). An invoker that carries both popovertarget="p" and a click handler calling p.showPopover() ends with the popover closed — in all three engines, every time. The handler's showPopover() opens it (one beforetoggle open), then the declarative activation's default action toggles it closed in the same tick (a second beforetoggle close, measured at the identical timestamp). Rule: pick one. Use popovertarget and let the browser own the state, or drop the attribute and own it in JS — and if you own it in JS, add the explicit anchor-name, because the implicit reference only exists on the declarative path.

8 · The exit-animation split — only Chromium transitions a closing popover

The recipe everyone ships is transition-behavior: allow-discrete + display in the transition list, so the popover fades out instead of vanishing.

Live — open, then close, and watch the transition ledger

Runs on load — opens the popover, lets the entry settle, then closes it.

Transition ledger

THE POPOVER-EXIT-DISCRETE SPLIT (headline #8). With transition: opacity .3s, display .3s; transition-behavior: allow-discrete on the popover: Chromium 149 fires the full discrete set on close — transitionrun/start/end for display and opacity (and overlay when listed) — and the element is painted through the exit. Firefox 151 and WebKit 26.5 fire ZERO transition events on close: the popover simply disappears (measured with a real Esc keypress, 3/3). The control isolates it: the same CSS on a plain <div> fires its opacity transitions normally in all three engines — only the popover's own discrete display transition is missing in Firefox and WebKit. Cross-engine fallback: animate opacity with a visibility/display delay pattern (the same shape as the <dialog> tier), and do not depend on a transitionend listener to clean up — in two of three engines it never fires.
THE overlay PROPERTY SPLIT. CSS.supports('overlay','auto') is true only in Chromium; Firefox and WebKit parse transition-property: overlay but do not expose the property. Listing overlay in the transition is harmless (it is a no-op elsewhere) but it must never be the thing you wait on.

9 · The re-entrancy law — no InvalidStateError, just recursion

MDN warns that calling showPopover() inside a beforetoggle handler “will throw an InvalidStateError”. Measured: it throws nothing.

Live — guarded vs unguarded re-entrancy

—

What happened

The unguarded lane runs inside a sandboxed iframe so its stack-overflow error cannot take down the page you are reading. The parent listens for the child's error event.

THE RE-ENTRANCY LAW (headline #9). Calling showPopover() from inside a beforetoggle handler does not raise InvalidStateError in any of the three engines. It re-enters the handler (measured depth 2 with a depth guard). Unguarded, it recurses until the engine aborts the task with “Maximum call stack size exceeded” (Chromium/WebKit) or “too much recursion” (Firefox) — an uncaught page error, not a catchable DOMException. Never call a popover method from inside its own beforetoggle handler. If you need to re-show after a veto, defer it to a task (queueMicrotask / setTimeout) — or use the spec-shaped guard yourself.

10 · The error grammar & the no-op grammar

The API mixes three DOMException families and two silent no-ops. Both halves matter in production.

CallResultWhat it means
THE NO-OP WALL (the half people get wrong). showPopover() on an already-showing popover is a silent no-op: no exception, no events at all, state unchanged (measured 3/3). The same for hidePopover() on a hidden popover. This is the opposite of <dialog>.showModal(), which throws InvalidStateError on a second call. Guard with el.matches(':popover-open') — a popover toggle handler that assumes “show always opens” will silently do nothing on the second click.
THE TOGGLE-RETURN LAW. togglePopover() returns the new state (a boolean), and accepts force as a boolean or an options object — togglePopover({force:true}) opens, togglePopover(false) closes. A bogus force value is ignored rather than rejected (no throw), so a typo silently falls back to “toggle”.

11 · The implicit-ARIA law — the accessibility tree is not the DOM

MDN: an invoker linked by popovertarget gets an implicit aria-expanded and aria-details relationship. Measured: neither exists in the DOM — in any engine.

Live — what the DOM can see

What the accessibility tree can see

Measured in the probe battery with Chromium's Accessibility.getFullAXTree CDP command (the AX tree is not reachable from page JavaScript, so this panel shows the recorded values rather than a live read).

THE IMPLICIT-ARIA LAW (headline #10). With a declarative popovertarget invoker, getAttribute('aria-expanded') is null, el.ariaExpanded is null, and aria-details is absent from the IDL entirely ('ariaDetails' in inv === false) — in all three engines, before and after opening. The relationship exists only in the accessibility tree: Chromium's AX tree reports the invoker's expanded property as false → true → false across the open/close cycle. Consequence: an automated audit that reads attributes or IDL sees nothing — a popover invoker looks exactly like a plain button to every DOM-level audit and to every snapshot test. If you assert on it, assert on the AX tree (or write the attribute yourself).
MDN CORRECTION. MDN's claim that an implicit aria-details relationship is set up is not observable on this bench: Chromium's AX tree carries expanded but no details property, and no engine surfaces an aria-details attribute or IDL member. Treat the implicit relationship as aria-expanded only.
