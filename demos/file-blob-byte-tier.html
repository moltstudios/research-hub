File & Blob: the byte tier

Every web app that accepts a file — a CSV import, a logo upload, a drone flight-log download — crosses this tier. It is the most-used API on the web and the least-read one. Our catalog had File System Access (real files on disk), Drag & Drop (the drop channel) and OPFS (the sandbox store) — and zero coverage of the byte objects themselves: File, Blob, FileReader, FileList, object URLs.

Everything below is measured. 7 probe suites × 3 engines (Chrome-for-Testing 155, Brave 156, WebKit 26.5) — plus the live lab in §1, which re-runs the laws in your browser, right now.

§1 · The BOM-snip law

Same bytes. Same page. Two different strings — depending on which API you ask.

THE HEADLINE. Blob.text() and FileReader.readAsText() sniff a UTF-16 BOM and decode the payload as UTF-16. TextDecoder, Response.text() and fetch().text() do not. A UTF-16 CSV uploaded by a Windows user reads as clean text on one path and as mojibake on the other — in the same tab, in the same millisecond.

    THE TRAILING-UNIT LAW. A UTF-16 payload whose length is ODD ends in an incomplete code unit. Chromium drops it silently (the string ends one character early — no error, no U+FFFD). WebKit emits a U+FFFD for it. So the two engines do not merely differ in whether they sniff — they differ in what they do with a half character.
  


  

    THE SNIFF BEATS YOUR ENCODING ARGUMENT. readAsText(blob, 'utf-8') on a UTF-16 BOM file still decodes as UTF-16. The encoding argument is honoured only when there is no BOM to override it — with 'iso-8859-1' you get real Latin-1, but with 'utf-8' on a BOM'd file the BOM wins.
  







  
§2 · The silent-type trap

  
Why file.type is empty for files you built yourself — and why the browser never sniffs content.


  

    THE TYPE LAW. A file the user picked gets its type from the OS extension map — .txt → text/plain, .json → application/json, .csv → text/csv. A file you construct with new File([blob], 'data.csv') gets type === "" — the constructor does not infer from the extension, and it does not inherit the Blob part's type. You must pass {type:'text/csv'} explicitly.
  


  

    NO CONTENT SNIFFING, EVER. A .png whose bytes are not a PNG gets image/png anyway (the extension wins). A .txt whose bytes are a PNG gets text/plain. The browser never looks at the content. Never trust file.type to mean "this is really a PNG" — and never trust an empty file.type to mean "unknown format".

§3 · The second-truncated timestamp

  
File.lastModified is millisecond-resolution on Chromium and second-resolution on WebKit.


  

    THE GRANULARITY LAW. The same file on disk (mtime …174143) reads back as 1793366174143 in Chrome-for-Testing 155 and Brave 156 — and as 1793366174000 in WebKit 26.5. WebKit truncates the millisecond component to zero. The value is still a valid epoch-ms number, so nothing throws; it is just up to 999 ms wrong.
  


  

    THE MISSING-MEMBER LAW. File.prototype.lastModifiedDate — the legacy Date accessor — exists in Chromium and Brave and is absent in WebKit 26.5. It is not in WebKit's File.prototype at all (key-set diff, not value eyeballing). Code that reads file.lastModifiedDate.getTime() throws TypeError on Safari and works everywhere else.
  


  

    THE CONSTRUCTOR LAW. new File([], 'x.txt') defaults lastModified to now (millisecond precision, even in WebKit). An explicit {lastModified: 123456789} is kept exactly. A fractional value (123456789.9) is truncated to an integer. A negative value is kept (-5). NaN → 0. A string → 0 (no throw). A huge value (1e18) is kept but exceeds Date's safe range in Chromium (it clamps to 9211727563254776) while WebKit keeps 1e18 exactly.

§4 · The FileList surface gap

  
The HTML spec defines FileList.namedItem(). No shipping engine implements it.


  

    THE ABSENT-MEMBER LAW. FileList.prototype is exactly three members in all three engines: constructor, item, length. namedItem() — which the HTML spec defines and MDN documents — is absent everywhere. input.files.namedItem('a.txt') throws TypeError in Chrome, Brave and Safari alike.
  


  

    IT IS NOT AN ARRAY. input.files is not an Array: Array.isArray() is false, .find().map().filter()undefined (it has no Array prototype in its chain), and .map()is iterable ([Symbol.iterator] present) and array-like (length + item(i)). Array.from(input.files) is the only safe normaliser.
  


  

    THE LIVE-LIST LAW. input.files returns the same object every time, and that object is live: after input.value = '' the very same FileList reads length === 0. Do not cache input.files and expect it to still describe the selection later — and do not expect a snapshot.
  


  

    THE CLEAR LAW. input.files = [] throws TypeError (it is a read-only accessor; the setter converts to a File and fails). The supported clear is input.value = ''.
  


  

    
    
  

  

  







  
§5 · The multipart filename law

  
What the server actually receives when you append a Blob to a FormData.


  

    THE "blob" FILENAME LAW. formData.append(name, blob) with no filename sends filename="blob" — the literal string blob, lower-case, on every engine. formData.append(name, blob, 'x.txt') sends filename="x.txt". A File sends its own name. A File with name === '' sends filename="" — an empty filename, not the word "blob".
  


  

    THE CONSEQUENCE. An upload that receives filename="blob" loses the user's filename — the server cannot show "report.csv" back to the user, cannot de-duplicate by name, and cannot route by extension. Every frontend that does fd.append('file', file) with a constructed File and no explicit name ships "blob" to the server.
  


  

    THE TYPE LAW ON THE WIRE. An untyped Blob goes out as Content-Type: application/octet-stream. A typed Blob keeps its type. A File with an empty type still sends a Content-Type header — application/octet-stream. The multipart body was byte-identical across all three engines (1043 bytes, same boundary shape, same headers).
  


  

    
    
  

  

  







  
§6 · The Blob surface + the slice law

  
What Blob actually exposes, and the slicing rules that bite.


  

    THE SURFACE LAW (Chromium family has two extra members). Blob.prototype is constructor, size, type, slice, arrayBuffer, stream, text everywhere — plus bytes() and textStream() in Chromium and Brave. bytes() returns a Promise (not a live view), textStream() returns a ReadableStream. Both are absent in WebKit 26.5. Feature-detect with typeof blob.bytes === 'function', never by parsing the prototype.
  


  

    THE TYPE-NORMALISATION LAW. A Blob's type is lower-cased ('TEXT/PLAIN' → 'text/plain') and must be a valid MIME type — but the validation is loose in a way that surprises: '  text/plain  ' is kept with its spaces, 'text/pläin' (non-ASCII) is silently dropped to '', and a control character makes the whole type empty. A type of 'text/plain%20x' is kept verbatim. An empty type is the normal result of a typo, not of a typeless blob.
  


  

    THE SLICE LAW. slice() clamps: a negative index counts from the end, an end past the length clamps, and start > end yields an empty blob (not an error). slice(0, NaN) → empty. slice(0, Infinity) → the whole blob. A type is only carried over if you pass one explicitly (slice(0,2) loses it, slice(0,2,'text/plain') keeps it).
  


  

    
    
  

  

  







  
§7 · The stream-chunk law

  
There is no chunk-size contract. Do not write code that assumes one.


  

    THE NO-CONTRACT LAW. Blob.stream() chunk boundaries are not specified and not stable. Measured over 12 repetitions per size in each engine:
  


  
Blob sizeChromium 155Brave 156WebKit 26.5


  

    WHAT THAT MEANS. WebKit delivered the whole blob in one chunk in 48 of 48 measured reads. Chromium and Brave split — but not at a fixed boundary (65 536, 131 072 and 262 144 all appeared, in varying combinations, within the same size). A reader that assumes "one chunk per 64 KiB" breaks; a reader that assumes "one chunk total" breaks on Chromium. Accumulate and re-chunk yourself.

§8 · The object-URL lifecycle

  
The URL you hand to an <img> carries no filename.


  

    THE FILENAME-LOSS LAW. URL.createObjectURL(file) produces blob:http://origin/<uuid> — the filename is not in the URL and there is no Content-Disposition header on the fetch response. The Content-Type survives (text/plain for a .txt File). If you need the name on the other side, you must carry it yourself — an <a download="name.txt"> keeps it, an object URL does not.
  


  

    THE REVOCATION LAW. After URL.revokeObjectURL(u), a fetch(u) rejects (TypeError: Failed to fetch in Chromium/Brave, TypeError: Load failed in WebKit) and an <img src=u> fires error. Revoking twice does not throw. Revoking a URL that was never created does not throw. But revoking while a read is in flight does not cancel it — the 1 MiB read completed.
  


  

    
    
  

  

  







  
§9 · The FileReader contract

  
Four modes, one event order, and a reader you can reuse.


  
Moderesult typeEvent orderNotes


  

    THE EVENT-ORDER LAW. Every mode fires loadstart → progress → load → loadend in that order. progress is lengthComputable with loaded === total === blob.size — a single progress event, not a series. loadend fires for every outcome, including abort and error; if you only listen for load, an aborted read never resolves.
  


  

    THE REUSE LAW. A FileReader can be read again after it finishes — the second readAsText on the same reader works and returns the new content. Two readers on the same Blob run concurrently without interfering. abort() sets readyState back to DONE (2) and leaves result === null.
  


  

    THE TYPE-WALL LAW. readAsText(null) and readAsText('not a blob') throw a TypeError — but with different wording per engine: Chromium says "parameter 1 is not of type 'Blob'", WebKit says "Argument 1 ('blob') to FileReader.readAsText must be an instance of Blob". Never string-match an engine error.
  


  

    
    
  

  

  







  
§10 · The OpenDrones flight-log importer

  
A capstone that ships the corrected rules — the file-tier law turned into working code.


  

    THE SHIPPED RECIPE. A flight-log importer that reads a user-picked .csv must:
    
① read the bytes as an ArrayBuffer (never a string first);
    
② sniff the BOM itself — FF FE → UTF-16LE, FE FF → UTF-16BE, EF BB BF → UTF-8, else UTF-8;
    
③ decode with TextDecoder(encoding) on the exact encoding it chose;
    
④ never trust file.type for anything but a hint;
    
⑤ carry the filename explicitly when uploading (fd.append('log', file, file.name));
    
⑥ treat file.lastModified as second-resolution (Safari) — do not use it for ordering uploads in the same second.
