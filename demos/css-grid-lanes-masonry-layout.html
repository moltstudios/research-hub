CSS Grid Lanes: native masonry finally shipped in CSS

After a 7-year journey through the CSS Working Group, Pinterest-style packing is a display type: display: grid-lanes. Safari 26.4 shipped it first. Chromium and Firefox are landing the final syntax. This page is a live field guide.

Checking your browser…
01 · The 3-line recipe

Masonry without JavaScript, columns hacks, or ResizeObservers

Grid Lanes is defined in CSS Grid Layout Module Level 3. You apply a new display type, define lanes with the full power of grid-template-*, and the browser packs each item into whichever lane gets it closest to the top — like cars changing lanes in traffic. DOM order is preserved, so tab order and screen readers follow source order.

/* The whole API, distilled: */
.container {
  display: grid-lanes;                          /* new display type            */
  grid-template-columns: repeat(auto-fill, minmax(250px, 1fr)); /* lanes = grid tracks */
  gap: 16px;
}
/* That's it. No media queries. No JS. Responsive by default. */

✅ Why it matters

  • Replaces Masonry.js / Isotope / CSS columns hacks — zero layout JS, zero CLS from position calculations
  • Infinite scroll that keeps working while new items append — the browser re-packs natively
  • Accessible by construction: visual order follows DOM order (unlike columns)
  • Inherits all of Grid: minmax(), fr, span, explicit placement, negative line numbers

📦 Spec & status (Aug 2026)

  • Spec: css-grid-3 — syntax finalized & “safe to commit to memory” (WebKit)
  • SHIPPED Safari 26.4+ (first!), GNOME Web
  • IN PROGRESS Chrome/Edge — updating from the display: masonry experiment (140, behind flag) to final grid-lanes syntax
  • NIGHTLY Firefox — old grid-template-rows: masonry syntax behind flag; updating

03 · The new property

flow-tolerance — how “chill” are your drivers?

The one genuinely new concept in Grid Lanes. When two lanes are nearly the same height, strict packing would shuffle items across the page for a 1-pixel win — scrambling the visual order versus tab order. flow-tolerance declares how close is a “tie”: differences smaller than the threshold are ignored, and content flows in writing-mode order instead. Default: 1em.

Drag the slider and watch the numbered cards (they show their DOM order) re-pack. High tolerance ≈ reading-order-friendly, roughly left-to-right. Zero tolerance ≈ tightest possible packing, maximum shuffling.

04 · Two directions

Waterfall ↔ Brick — one property apart

Define columns → vertical waterfall (classic Pinterest). Define rows → horizontal brick layout (items flow inline, packing toward the start edge). Direction is inferred by the new initial value grid-auto-flow: normal — no explicit orientation property needed yet (the CSSWG is still deciding between reusing grid-auto-flow or a new grid-lanes-direction).

05 · Full Grid power

Spanning lanes, featured content, explicit placement

Because lanes are grid tracks, every placement primitive you know works: spanning for featured items, alternating track widths, and pinning with line numbers — including negative numbers counted from the end (grid-column: -3 / -1 = last two lanes, no matter how many exist).

06 · What it replaces

The old ways — and why they hurt

🚫 CSS columns hack

Items flow top-to-bottom down column 1, then column 2… Your DOM order ≠ visual order. Screen readers and keyboard users encounter a shuffled page; “find on page” highlights items far from where you’re looking. Also unbalanced columns and broken infinite scroll.

Reading order here: 1 → 4 → 2 → 5 → 3 → 6. Confusing for assistive tech.

🚫 JS libraries (Masonry.js, Isotope)

  • +18KB min+gz of JS, plus layout thrash on every resize/image-load
  • Position calculations cause layout shift (CLS) and janky first paint
  • Fragile: breaks with lazy-loaded images, web fonts, dynamic content unless manually relayed
  • Dies when JS fails — no-layout flash

🤷 Regular grid + align-items: start

  • Order preserved, but ragged gaps accumulate per row — the exact problem masonry solves
  • This is, however, the ideal fallback for @supports (see section 10)

09 · Ship it today

Three progressive-enhancement strategies

From WebKit’s own guidance — you do not wait for three engines. Pick the strategy that matches your tolerance:

StrategyHowBest for
① Grid fallback
RECOMMENDED		@supports (display: grid-lanes) enhances; base layer = display: grid + align-items: startContent sites, galleries, dashboards. Zero JS, zero risk, ragged-but-fine fallback. What every live demo on this page does.
② JS polyfill gateif (!CSS.supports('display','grid-lanes')) → load Masonry.js as the layout enginePixel-critical designs that must pack perfectly everywhere today. Accept the JS cost on non-Safari.
③ Columns fallback@supports not (display: grid-lanes) { columns: 3 }Only when the DOM-order divergence of columns is acceptable (decorative tiles, no focusable children).
/* Option ① — the one to memorize */
.gallery {
  display: grid;                                  /* fallback first, no @supports needed */
  grid-template-columns: repeat(auto-fill, minmax(210px, 1fr));
  gap: 16px;
  align-items: start;
}
@supports (display: grid-lanes) {
  .gallery { display: grid-lanes; align-items: auto; }  /* tight packing unlocks */
}

/* Option ② — JS gate for pixel-perfect-everywhere */
if (!CSS.supports('display', 'grid-lanes')) {
  const s = document.createElement('script');
  s.src = 'https://unpkg.com/masonry-layout@4/dist/masonry.pkgd.min.js';
  s.onload = () => new Masonry('.gallery', { itemSelector: '.ph' });
  document.head.appendChild(s);
}
