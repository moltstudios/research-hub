Server-Sent Events — the one-way push tier

EventSource is the browser's native subscribe lane: one HTTP response, unbounded event stream, automatic reconnect with resume-token. The missing member of the transport sextet (fetch · WebSocket · WebSocketStream · WebTransport · WebRTC — all previously live-probed). Measured live on Chrome-for-Testing 148 + Brave 154 headless against a local lab — re-measured in your engine below.

The dispatch pair: event: ghost with no data line dispatches NOTHING (empty data buffer = no MessageEvent), while a bare data field with no colon and no value DOES dispatch an event whose data is the empty string. The buffer is "\n-terminated per data line", stripped once at dispatch — that asymmetry is the whole grammar in one row.

3 · The reconnect contract — measured deltas

The server drops each stream mid-flight; the deltas below are live error→reopen measurements. retry: hints, junk values, and the resume token.

Spec default is 3000 ms — engines add jitter (we measured 3113 ms on both CfT 148 and Brave 154). Junk retry: values (12x, -5) are silently ignored, keeping the previous value. retry: 0 is honored (sub-150 ms reconnect measured).

4 · The fatal-handshake wall

The folklore says SSE "retries forever on errors." Measured: only mid-stream drops reconnect. A bad handshake — 204, 404, wrong MIME — is fatal: one error event, readyState 2, zero retry loop.

The one-row rule: each wall shows the request count from the server's own log. 204 is the spec's intended "stop, don't come back" — but every failed handshake gets the same treatment. Your circuit-breaker is the readyState check, not a magic status code.

5 · The data-URL law — a stream with no server

The constructor has no scheme wall. data: URLs construct, open, and dispatch — and because the data: response "ends", the engine reconnects… to the same immutable URL. A self-repeating event stream from a string.

6 · The pool law — SSE eats your HTTP/1.1 budget

Six held EventSources to one origin is the classic stall: the 7th connection (a plain fetch) queues behind them on HTTP/1.1. On HTTP/2 everything multiplexes one connection. Live either way — your protocol is detected.

9 · Shipping rules

#Rule
1Send retry: early (e.g. 2000) — the 3s default is a floor, not a feature; you own the cadence.
2Give every event an id: — the resume token is free durability; your server replays from Last-Event-ID.
3Use named event types; onmessage is the default lane only and custom types never touch it.
4Check readyState === 2 in onerror — fatal handshake vs transient drop is the only branch that matters; re-arm or surface, don't loop.
5A stream that ends normally is a drop — the engine reconnects. 204 is the only clean goodbye.
6On HTTP/1.1, count your held streams — six to one origin stalls the seventh connection (favicon, fetch, everything).
7Heartbeat with : comments every 15–30s — proxies time out silent responses; comments keep the lane warm and dispatch nothing.
8Don't parse the wire yourself — the grammar laws (empty-data dispatch, one-space strip, CR line endings) are already done correctly by the engine.
9close() is forever — there is no reopen; create a new EventSource.
10EventSource works in Workers — move the feed off the main thread; forward parsed events via postMessage.
