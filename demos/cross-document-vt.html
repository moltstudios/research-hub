What It Is

Cross-document view transitions (the MPA variant) extend the View Transitions API to work across separate page loads. Both pages opt in via a single CSS at-rule. When the user clicks a same-origin link, the browser:

  1. Snapshots elements with matching view-transition-name values on the old page
  2. Loads the new document, snapshots the same-named elements on the new page
  3. Animates position, size, and styling between the two snapshots via CSS pseudo-elements
  4. Resolves at compositor-thread speed (no main-thread blocking)
The killer feature: This is the first time in web history you can build a multi-page app that feels like a SPA without writing any router, hydration logic, or animation code. Just CSS.

The One-Rule Setup

Add this to global.css in your Next.js root layout, or to any stylesheet that ships on every page:

/* Enable cross-document transitions between same-origin pages */
@view-transition {
  navigation: auto;
}

/* That's it. Browser now cross-fades between pages by default. */

The navigation: auto value opts in for these navigations:

  • traverse — back/forward (your history)
  • push — link clicks, programmatic history.pushState
  • replace — when not initiated by browser chrome (e.g. not from address bar)

Excluded by design: address-bar typing, bookmarks, reloads, form-submitted GETs. The user always controls when a transition fires.

Shared Element Morphing

The real magic. Assign the same view-transition-name to elements on both pages and the browser auto-animates between them:

/* shop.html — product grid card */
<img class="thumb"
     src="/img/arc.jpg"
     style="view-transition-name: arc-hero">

/* product.html — full hero image */
<img class="hero"
     src="/img/arc.jpg"
     style="view-transition-name: arc-hero">

/* That's it. Click the thumb → image morphs from grid cell → full hero */

Customize the morph

/* Old image: zoom in slightly as it fades */
::view-transition-old(arc-hero) {
  animation: 350ms ease-out both fade-out, shrink-out;
}
::view-transition-new(arc-hero) {
  animation: 350ms ease-out both fade-in, grow-in;
}

@keyframes shrink-out { to { transform: scale(0.92); } }
@keyframes grow-in   { from { transform: scale(1.08); } }

Dynamic Control: pageswap & pagereveal

Two new lifecycle events let you customize per-navigation. The killer use case: change which element is "shared" depending on which link was clicked, even though the destination page only knows its own structure.

// On source page (shop.html) — set the active shared element
window.addEventListener('pageswap', (e) => {
  if (e.activation?.entry) {
    const url = new URL(e.activation.entry.url);
    // Find which thumb was clicked
    const id = document.querySelector('a[href$="' + url.pathname + '"]')
                      ?.dataset.vtId;

    // Tell the destination which name to use
    e.activation.entry.url = new URL(
      url.pathname + '?vt=' + encodeURIComponent(id), url
    );
  }
});

// On destination page (product.html) — read it and rename
window.addEventListener('pagereveal', (e) => {
  const id = new URL(location.href).searchParams.get('vt');
  if (id) {
    document.querySelector('.hero img')
      .style.viewTransitionName = id;
  }
});

This is the pattern that lets you have one product detail template that morphs in whichever product card was clicked — without needing per-product pages with hardcoded names.

Graceful Degradation

If a browser doesn't support cross-doc view transitions, the navigation just works as a normal hard page load — no error, no flicker, no broken layout. Users on old browsers see the same old instant page swap. Users on new browsers get the smooth morph. Same code path, same HTML.

/* Always ship. Worst case: instant navigation. */
@view-transition { navigation: auto; }

/* Optional: opt individual links OUT (e.g. logout, admin) */
<a href="/logout" class="no-vt">Log out</a>

.no-vt { view-transition-name: none; }

Accessibility: Reduced Motion

Wrap your transition animations in a reduced-motion guard. Users with vestibular disorders should get an instant cut, not a 350ms morph.

::view-transition-old(root),
::view-transition-new(root) {
  animation-duration: 0.35s;
}

@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(root),
  ::view-transition-new(root) {
    animation-duration: 0.001s; /* instant */
  }
}

Next.js 16 Implementation

Next.js 16 has first-class support. Add the at-rule in your root layout's stylesheet and you're done — no component wrappers needed for the MPA variant:

// app/globals.css
@view-transition {
  navigation: auto;
}

/* Customize the default cross-fade */
::view-transition-old(root) { animation: fade-out 0.3s ease-out; }
::view-transition-new(root) { animation: fade-in  0.3s ease-out; }

@keyframes fade-out { to { opacity: 0; } }
@keyframes fade-in  { from { opacity: 0; } }

Then just give any element a view-transition-name on both source and destination pages. No React component changes. No router config. Just CSS.

Gotchas

  • Same-origin only. Won't transition across different domains (security boundary). The browser respects this for you.
  • 4-second timeout. If the new page takes longer than 4s, the transition is skipped and you get a normal load. This is intentional.
  • Unique names per page. If you give the same view-transition-name to multiple elements on one page, only the last one in DOM order participates. Use unique names per logical element.
  • Server-side rendering required for the source HTML to be available when the transition begins. With Next.js static export, the old DOM is already in memory when navigation starts.
  • Form submissions don't trigger transitions unless you wrap them in history.pushState + manual handling. The default is to skip for predictable behavior.
