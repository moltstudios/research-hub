Form UX that waits for the user.

:user-invalid and :user-valid are the modern replacement for :invalid / :valid. They match a form control only after the user has actually interacted with it — so empty required fields don't light up red on page load, and you can write form validation styles with zero JavaScript.

Chrome 119+ Safari 16.5+ Firefox 88+ ~96% global support Baseline 2026

The problem with :invalid

The legacy :invalid pseudo-class fires the instant the browser parses <input required> — which means a pristine form with empty required fields lights up red the moment the page loads. Users read red as "I broke something," and they haven't typed a single character.

❌ :invalid (old)

input:invalid {
  border-color: red;
}

Fires on page load. Empty required field is "invalid."

✅ :user-invalid (new)

input:user-invalid {
  border-color: red;
}

Fires only after the user has interacted. Empty field sits neutral.

:user-valid and :user-invalid are the centerpiece, but they pair with a few siblings that solve the rest of the form styling story. None of them require JavaScript.

Patterns that ship

1. Subtle live feedback — no shake, no toast

A green-tinted background + border on success. A red-tinted background + border on failure. Pair with :has() to also show a small "✓ valid" pill on the right. 

input:user-valid {
  border-color: var(--success);
  background: var(--success-soft);
}

input:user-invalid {
  border-color: var(--danger);
  background: var(--danger-soft);
}

/* Reveal an error message only when the field is in user-invalid state */
.field:has(input:user-invalid) .feedback {
  display: block;
}

2. Auto-mark required fields

Combine :required and :optional with the input itself — no class needed on the label, no manual toggling. 

input:required ~ .required-mark { opacity: 1; }
input:optional ~ .required-mark { opacity: 0; }

3. Range-constrained inputs

:in-range and :out-of-range work on number, range, date, time, datetime-local, and month inputs. Pair with :user-invalid if you only want the warning after the user has typed. 

input:out-of-range {
  border-color: var(--warning);
  background: var(--warning-soft);
}

Try changing it to 3.

4. Floating label (no JS, no transform on parent)

:placeholder-shown matches while the field is empty. Use the + combinator to lift the sibling label. The placeholder attribute must be a single space — that's the trick. 

.float-field input:not(:placeholder-shown) + label {
  transform: translateY(-12px) scale(.78);
}

5. Styling autofilled fields

Browsers paint their own yellow/blue background on autofilled fields and historically blocked background-color overrides. The workaround: a very long transition on the background color, which the autofill paint cannot fast-forward through. 

input:-webkit-autofill,
input:autofill {
  -webkit-text-fill-color: var(--text);
  box-shadow: 0 0 0 1000px var(--accent-soft) inset;
  transition: background-color 9999s ease-in-out 0s;
}

6. Color the whole field group with :has()

The killer combo. :has() lets you style the label, the wrapper, an icon, a help-text element, or an error message based on the input's validation state — without JavaScript and without classes on every child. 

/* Reveal the error message slot */
.field:has(input:user-invalid) .feedback {
  opacity: 1;
  max-height: 40px;
}

/* Color the label icon */
.field:has(input:user-valid) .icon {
  color: var(--success);
}

/* Tint the entire card if ANY child input is invalid */
.form:has(input:user-invalid) {
  box-shadow: 0 0 0 2px var(--danger-soft);
}

Accessibility — color is not enough

A red border alone is invisible to screen readers and to anyone who can't distinguish the color. Keep a real text error message, wire it up with aria-describedby, and let the :user-invalid styling be the visual layer on top of that — not the whole story. 
<div class="field">
  <input
    id="email"
    type="email"
    required
    aria-describedby="email-error"
    aria-invalid="true" <!-- set via JS or :has()'s sibling -->
  />
  <div id="email-error" class="error-msg" role="alert">
    Please enter a valid email address.
  </div>
</div>

CSS can handle the styling — but :user-invalid does NOT automatically set aria-invalid. You either need a tiny JS toggle, or you can use the :has() parent pattern combined with a small inline JS snippet that flips aria-invalid on input events. For application logic validations ("passwords must match", "username already taken"), you still need JS to call setCustomValidity() — CSS validation styles reflect HTML constraints only.

Browser support

  • Chrome 119+ (October 2023)
  • Edge 119+ (October 2023)
  • Safari 16.5+ (May 2023)
  • Firefox 88+ (April 2021 — Firefox was the early implementer)

Reached Baseline "Widely available" in April 2026 — safe to use without a fallback on public sites. For long-tail legacy browsers, treat :user-invalid as progressive enhancement and keep the :invalid + .touched JS fallback.
