1 · Engine

Every probe on this page runs in your browser against the live engine. The chips under each section record what this engine actually did — not what the docs said it would do.

2 · The model: attributes → flags → gate

Constraint validation is three layers. Attributes (required, pattern, min/max/step, minLength/maxLength, type=email|url|number|date) declare constraints. The engine evaluates them into a flag set on element.validity. The gate: a form only fires submit when every submittable, validating control has validity.valid === true.

attributes→ValidityState flags→checkValidity() / reportValidity()→blocked: invalidorsubmit event

4 · The dirty-flag wall — tooLong / tooShort ignore script-set values

The headline falsification. Common claim: "setting value programmatically past maxLength makes checkValidity() fail at submit." False in this engine — and by spec. The length flags require the dirty value flag, which only real user edits (or autofill) set. Framework-managed values — including the React native-setter + dispatched input event recipe — never set it.

Cell 2 is the falsified claim: 6 chars past maxLength=3, set by script → no flag. Cell 3 is the escape hatch: the user typed 4 valid chars, then script shrank maxLength below the typed length → flag fires (dirty was already set). Cell 5 is the React pattern — still gated. Type into cell 4 yourself and watch it fire.

5 · type=number — the empty-value trap

Type letters into a number field: the engine can't parse them, so input.value is '' — but the text is still visible in the box and validity.badInput is true while valueMissing is false. Code reading .value to decide "user left it empty" lies; only badInput tells the truth.

Also live here: maxLength is reflected in the DOM but has no effect on number inputs — the constraint only applies to text-like controls.

6 · Flags stack, and step math snaps forward

One value can raise several flags at once — -4 in a min=0 step=3 field raises rangeUnderflow and stepMismatch together. And stepUp() does not round-to-nearest — it snaps to the next lattice value above the current one (4 → 6, never 3, even though 4 is nearer 3).

The stepMismatch bubble is the one native message that does math for you: it names the two nearest valid values.

7 · setCustomValidity — precedence, coexistence, clearing

A custom message replaces the native one in validationMessage and raises customError, but native flags stay true underneath — useful: your async validator can add a message while the required-check still reports its own flag. Clearing with '' restores the native message. Whitespace-only counts as set. Long messages are kept verbatim — no truncation.

The async validator pattern

Debounce the check, keep a "pending" state out of validity (there is no validating flag — track it yourself), then set/clear:

input.addEventListener('input', debounce(async () => {
  const taken = await api.checkCallsign(input.value);
  input.setCustomValidity(taken ? 'Callsign already taken' : '');
  // re-run the form's UI if it's showing errors:
  form.reportValidity(); // or your own error surface
}, 350));

8 · The submission gauntlet — five ways through, one way around

Same form, five entry points, three different outcomes. checkValidity is silent; reportValidity walks DOM order focusing the first offender; requestSubmit() runs validation then fires submit; a plain submit() skips both validation and the event; and noValidate — probed live — skips validation only at submission: form.checkValidity() still returns false and still fires invalid.

Watch the focus ring: reportValidity and Enter-key submission focus field a — first in DOM order, always.

Implicit submission (Enter) — the single-field rule

A form with no submit button and exactly one text input submits on Enter (after validation). Add a second text input and Enter does nothing — implicit submission requires a default button, or that the form not be "blocked" by multiple text fields. Both probed live below.

9 · The invalid event — non-bubbling, per-control, payload-free

invalid is one of the few form events that does not bubble — a bubble-phase listener on the form hears nothing; you need capture: true or per-element listeners. It fires once per invalid control in DOM order, and carries no validity snapshot — read e.target.validity yourself.

Probed at load: a form-level bubble listener + a capture listener, then form.checkValidity() on a form with three invalid fields.

The a11y gap: aria-invalid is never set for you

The engine focuses offenders and paints bubbles, but it never writes aria-invalid. Delegated fix:

form.addEventListener('invalid', e => {
  e.target.setAttribute('aria-invalid', 'true');
}, true); // capture — it doesn't bubble
form.addEventListener('input', e => {
  if (e.target.validity.valid) e.target.removeAttribute('aria-invalid');
});

10 · Group semantics — radios heal each other, fieldsets eat constraints

Radio groups: required is a GROUP property

required on ONE radio makes every member of the group report valueMissing while none is checked — including members without required. Checking any sibling heals all of them. Probed live.

—

Checkboxes: indeterminate is not checked

A required checkbox that is indeterminate is still valueMissing — indeterminate is a paint state, not a value. Probed live.

—

fieldset[disabled] + the first-legend exemption

A disabled fieldset de-activates descendant controls — willValidate false, excluded from FormData — except controls inside the first <legend>, the historical exemption so the "enable this section" checkbox can live in the legend. Probed live.

—

form= association — inputs outside the form

An input with form="id" (the attribute — the IDL input.form property is read-only) validates with that form and joins its FormData. Probed live with the stray field below this card.

Ship it like this

  • Always gate submit through the engine: requestSubmit(), never submit() (skips the gate AND the event).
  • Listen for invalid with capture: true — it never bubbles.
  • Never trust input.value === '' on type=number — check badInput.
  • Length validation only fires for user-typed values — server-side length checks are still mandatory; the dirty-flag wall is an open door for script-set values.
  • Don't string-match validationMessage — localized. Branch on flags.
  • Keep aria-invalid in sync yourself (§9 recipe).
  • :user-invalid for styling, flags for logic, setCustomValidity for async.
