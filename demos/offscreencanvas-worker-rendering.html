OffscreenCanvas — Rendering Moves Off the Main Thread

canvas.transferControlToOffscreen() hands the pixel pipeline to a Web Worker. The render loop survives main-thread jank, DOM parsing, JSON crunching — everything that made canvases stutter. Baseline since March 2023.

01

The problem it solves

A <canvas> normally renders on the main thread — the same thread that parses your JSON, walks the DOM, and executes every script. When the main thread blocks, every canvas on the page freezes with it: spinners stop, charts smear, telemetry walls go still. Our Long Animation Frames research (Aug 18) measured exactly these stalls; the scheduler API (Aug 19) mitigates them. OffscreenCanvas removes the rendering from the contended thread entirely.

Three pieces make it work:

const off = el.transferControlToOffscreen();      // one-way: the element becomes a proxy
const worker = new Worker(url);
worker.postMessage({ canvas: off }, [off]);          // off is a TRANSFERABLE — zero-copy handoff
// worker: ctx = canvas.getContext('2d'); requestAnimationFrame(render); // rAF EXISTS in workers

The canvas element stays in the DOM (layout, CSS, stacking all normal) — but its bitmap is owned and painted by the worker. The worker's requestAnimationFrame is paced to the display vsync, exactly like the main-thread one, and each rAF callback's drawing is committed to the screen automatically at frame end (the old explicit commit() is deprecated).

03

The transfer protocol, end to end

// ---------- main thread ----------
const el = document.querySelector('canvas');
const off = el.transferControlToOffscreen();
const worker = new Worker('renderer.js');
const dpr = window.devicePixelRatio;                // workers can't see it (cross-engine) — send it
worker.postMessage({ cmd:'init', canvas: off, dpr,
                     w: el.clientWidth, h: el.clientHeight }, [off]);

new ResizeObserver(([e]) => worker.postMessage({      // the ONLY safe resize path
  cmd:'resize', w: e.contentRect.width, h: e.contentRect.height, dpr
})).observe(el);

// ---------- renderer.js (worker) ----------
onmessage = ({data:d}) => {
  if (d.cmd === 'init' || d.cmd === 'resize') {
    canvas.width  = Math.round(d.w * d.dpr);            // buffer size, owned HERE now
    canvas.height = Math.round(d.h * d.dpr);
    ctx = canvas.getContext('2d'); ctx.scale(d.dpr, d.dpr);
  }
};
(function loop(t){ draw(t); requestAnimationFrame(loop); })(); // vsync-paced, auto-committed

Message vocabulary that works in production: init, resize, start/stop, theme (colors), data (telemetry push), stats (worker reports fps back). Every property that used to be a variable read becomes a message. That is the whole cost of adoption — and the entire rendering state lives in one place, testable in isolation.

Why transfer, not structured-clone? The OffscreenCanvas is a transferable object — postMessage with it in the transfer list moves ownership with zero pixel copies. Sending it without the transfer list would clone (and throw for this type).

Four canvases, four rolling telemetry traces — all owned by one worker, drawn in a single rAF loop. This is the Mission Control pattern: a telemetry wall becomes one worker message stream instead of four rAF loops competing with React on the main thread.

10

Gotcha — worker rAF sleeps when the tab hides

Worker requestAnimationFrame is display-paced — and when the document is hidden, it stops firing, just like main-thread rAF. For ambient rendering that's exactly right (zero wasted battery). For telemetry that must keep consuming while backgrounded, switch the loop to setTimeout/setInterval on visibilitychange:

addEventListener('visibilitychange', () => {
  if (document.hidden) { cancel = true; tick = setInterval(consume, 100); }  // keep draining the queue
  else                  { clearInterval(tick); cancel = false; requestAnimationFrame(loop); }
});
document.visibilityState: visible worker rAF frames while hidden: 0

Switch to another tab for a few seconds and come back — the counter proves the pause (live, self-verifying).

Production rules & gotchas

RuleDetail
One-way doortransferControlToOffscreen() is permanent. Element-side getContext() throws InvalidStateError; width/height are worker-owned (probe §4).
Resize only via messagesResizeObserver on the element → postMessage {w,h,dpr} → worker sets canvas.width/height and re-scales the context.
Send DPR explicitlyprobing… — always pass it from the main thread; don't rely on the worker seeing it.
commit() is deadFrames auto-commit at the end of each worker rAF callback. The old explicit ctx.commit() is deprecated — don't port it from 2019 tutorials.
Bitmaps are single-usetransferToImageBitmap() clears the source canvas; the returned bitmap neuters after transferFromImageBitmap() (probe §6).
One context forevergetContext('2d') then getContext('webgl') returns null — pick the context type at init, it's permanent.
2D surface ≈ completeText, measureText, filters, gradients, images all work. drawFocusIfNeeded() doesn't exist (no focus model in workers).
Graceful fallbackFeature-detect 'transferControlToOffscreen' in el; fall back to the same draw function on the element. One renderer source, two homes — Baseline makes the fallback nearly dead code (~98%).

Adopt when

Telemetry walls and dashboards (OpenDrones), hero/canvas animations on marketing pages that must survive scroll + hydration jank (Molt), any pipeline that pixel-processes or encodes images, WebGL/WebGPU scenes that deserve their own thread, export/screenshot generation.

Skip when

The canvas is static or tiny (a QR code, a one-time chart) — a worker + message protocol is overhead for nothing. And if the main thread is only occasionally busy, the scheduler API (P3, Aug 19) fixes that with one wrapper function — reach for OffscreenCanvas when rendering itself is the load.
