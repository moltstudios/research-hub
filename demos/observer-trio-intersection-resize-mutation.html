00 What your browser says right now

Three constructors, three Baseline-anywhere tiers: IntersectionObserver (Ch 51 / FF 55 / SF 12.1, Baseline 2019), ResizeObserver (Ch 64 / FF 69 / SF 13.1, Baseline 2020), MutationObserver (universal since ~2015). The interesting rows are the tier-2 options.







✓All three observers ship everywhere — the entire core trio is Baseline widely-available; gate nothing, feature-detect only the tier-2 options below


iscrollMargin (the newest IO option — margins on nested scroll containers) is feature-detected on this page by validation behavior, not by a property: there is no getter for constructor options anywhere in the API


!trackVisibility / isVisible (IO v2) and device-pixel-content-box (RO) remain Chromium-only — treat as progressive enhancement









01 IO anatomy — the first-callback contract


Registering a target with observe() always schedules one initial notification, delivered right after the next render opportunity — even if the target is completely offscreen. You never need a "prime the pump" manual check; the engine reports the current state unprompted. Below: a target positioned ~1200px below this fold, observed the moment this section rendered.

…Initial entry arrives without any scrolling — isIntersecting:false, ratio 0, delivered <1s after observe()


…rootBounds = the viewport rect for a null root (and null only inside cross-origin iframes — privacy fence)


…entry.time is a DOMHighResTimeStamp relative to time origin — not Date.now(); order entries by it, never by arrival


iOne observer, many targets — entries arrive batched in one callback; the 2nd arg is the observer itself for unobserve-in-callback patterns









02 Thresholds & the notification-suppression contract


The entire performance story of IO: callbacks fire only on threshold crossings, not on scroll. Between crossings, the engine is silent. Lab: a 220px-tall scroller with a 120px target and thresholds [0, .25, .5, .75, 1]. It self-drives through 14 scroll stops — many within the same threshold band — and counts observer callbacks vs stops.

…Band-scrolling is silent — 14 stops, only ~5-7 crossings → callbacks; the engine swallowed everything between thresholds (this is why IO beats scroll listeners, structurally)


…ratio at crossing ≈ the threshold, not exactly it — notifications are frame-quantized; never assert equality, assert a window


…The touching quirk — scrolled to exact edge-contact: isIntersecting reads true with intersectionRatio 0 (rects touching count as intersecting)


!threshold:[0] is an edge, not "invisible": default threshold 0 fires the moment any pixel (or the touching edge) enters — use a small positive threshold (0.05) for "meaningfully visible"

04 scrollMargin — margins on the nested scroller (the 2024+ option)


When the target sits inside a nested scroll container between it and the root, clipping normally kills the intersection at the inner scroller's edge. scrollMargin grows that inner clipping rect — "count as visible slightly before it clips in." Use case: pre-warming rows in an inner panel of a dashboard before the user scrolls the panel itself. Lab: outer root + inner scroller, target hidden by the inner clip.

05 IO v2 — trackVisibility & isVisible (Chromium-only)


Plain IO answers "is it inside the root box" — an ad can be intersecting at ratio 1.0 and still be covered by an overlay, opacity:0, or a transform. IO v2 (trackVisibility:true) adds a real visibility check; isVisible lands on every entry. The cost is why delay exists: visibility math is expensive — MDN documents a clamp that quietly raises any delay below 100ms; the lab constructs delay:50 and lets the engine's actual behavior (clamp or throw) settle it. Lab: an opaque cover slides over an intersecting target — v2 entry flips isVisible while a v1 twin stays isIntersecting:true.

07 ResizeObserver anatomy — the three boxes, the immediate callback

Unlike IO, it always has geometry — and it comes in three boxes: contentRect (legacy DOMRect, content box), borderBoxSize/contentBoxSize (arrays — one entry per fragment), and the Chromium-only devicePixelContentBoxSize. …Immediate first callback — both twins delivered their current size at observe() time, before any interaction (same contract as IO)


…contentRect = content box — A: 200px content + 34 padding + 6 border = 240 border-box; B: 200 declared → 160 content. The box option picks which box you're notified ABOUT; contentRect always reports content

08 devicePixelContentBox — the DPR truth for canvases


The sharpest tool in RO: box:'device-pixel-content-box' reports the content box in integer device pixels — the exact backing-store size the compositor will use, accounting for browser zoom and device scale, immune to CSS rounding. This is the number canvas.width wants. Probe (runs at YOUR current DPR — reload zoomed and it re-proves):


probing…




…dpxContent = round(cssContent × devicePixelRatio) — byte-exact integer math, while getBoundingClientRect hands you fractional CSS px that produce blurry canvas backing stores when naively multiplied


!It only fires when exact — under fractional zoom/scale where the engine cannot compute exact integer device px, the dpx entry is simply NOT delivered (you get no callback for that box, not a rounded guess); always keep a content-box observer as the driver


iChromium-only — gate by try/catch on observe(el, {box:'device-pixel-content-box'}) (TypeError = unsupported): ResizeObserver.supportedEntryTypes is a Firefox-only helper — it's undefined in Chromium 152, verified live on this page; Safari/Firefox derive css × DPR (fractional-DPR blurriness there is a 1px problem)









09 The famous error — ResizeObserver loop, live-fired


Every RO callback that changes its own target's size schedules another notification → the loop the engine guards: after one frame cycle it gives up, fires a window error event — ResizeObserver loop completed with undelivered notifications. — and continues next frame. It's on error-monitoring dashboards worldwide and it is benign by design. This lab fires a real one (button-only — it is a genuine console error on purpose) and shows the page surviving.




cycles: 0 · window error captured: none yet


SELF-RESIZING BOX


Fix in production: write the size change in a requestAnimationFrame (defers to next frame → no loop), or only mutate when the value actually changed.






…The loop error is non-fatal — box keeps resizing across frames; the error event fires with that exact message and the page never breaks (it's a warning wearing an error's clothes)


✓Don't silence it blindly — filter that exact message in error reporting (Sentry/OctalSpace users: mark ignore) but investigate RECURRING ones: a real feedback loop hides behind the same message









10 MutationObserver anatomy — the options matrix & the batching engine


MO watches a subtree for DOM changes and delivers batched records at the microtask boundary — never per-mutation. Three independent switches (childList, attributes, characterData), three amplifiers (subtree, attributeFilter, the two *OldValue flags — note they're separate flags: attributeOldValue and characterDataOldValue). The auto-probe below fires five probes; the playground lets you build your own observer.

…The characterData trap — observing the ELEMENT with characterData:true fires 0 records when its text node's data changes; you need subtree:true (or observe the text node directly). Probe 1 measures both sides


…3 synchronous mutations → 1 callback, 3 records — delivery is microtask-batched; per-change callbacks do not exist (probe 2)


…takeRecords() drains the queue — 2 pending mutations returned synchronously; the scheduled callback then receives 0 (probe 3)


iNo "moved", no computed style, no old NEW value — a move is remove+add; style changes only surface as the style attribute string; oldValue is opt-in per category









11 OpenDrones capstone — 10,000-row virtual wall, DPR-exact HUD, live log tail


Three production pieces, one section. (1) The virtual wall: 10,000 telemetry rows as pure data; two span-sentinels (full-extent divs above and below the render window — not zero-height markers) drive a ±14-row render window — the DOM never holds more than ~35 rows no matter where you jump. Why spans: the 9 AM draft shipped zero-height sentinels and the jump battery live-falsified them — IO speaks only on threshold crossings, and a viewport that jumps clean over a 1px marker produces zero events: the window stayed at rows 0–34 while the viewport sat at scrollTop 200,000, rendering blank. Span-sentinels fix it structurally: after every re-anchor the viewport is either inside the window (content already correct) or inside a span (a boundary was crossed → recompute from scrollTop). (2) The HUD: a canvas sized by ResizeObserver in exact device pixels, surviving live container resizes. (3) The tail: a MutationObserver watches the mission log the way you'd watch a WebSocket-injected stream — detection with zero polling.

Ship rules



IO: share ONE observer per config (entries batch); unobserve one-shots in the callback; callbacks stay sub-ms — schedule heavy work to rIC/scheduler.yield (catalog 1bbb030b); prefetch band ≥ 1 viewport on slow networks; threshold 0.05+ for "meaningfully visible"; ratio is frame-quantized — never assert equality.


RO: observe fires immediately — no priming; write only in rAF if the callback changes layout (loop error §09); prefer borderBoxSize[0].inlineSize over contentRect (writing-mode-safe, no legacy quirks); dpx box for canvas backing stores (Chromium gate).


MO: characterData needs subtree or the text node itself; oldValue is opt-in per category; takeRecords() before disconnect to not lose the tail; disconnect() when done — an MO holding a detached subtree pins it against GC.
