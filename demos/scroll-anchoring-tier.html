CSS Scroll Anchoring — the overflow-anchor tier

The browser's built-in "don't move what I'm reading" mechanism: when content changes above the viewport, the engine quietly adjusts the scroll offset to keep the visible content still. Shipped in Chromium since 56 and Firefox since 66 — and newly in Safari 27 (Sept 2026), which finally made it Baseline. Zero prior coverage in the 450-entry catalog: not one passing mention.

Probed live in CfT 149 · Firefox 151 · WebKit 26.5 (the Playwright WebKit build already carries the Safari 27 implementation) over a plain-HTTP loopback origin, fresh document per lane, ~90 lane-runs. Every law below re-measures itself in your browser on this page.

THE HEADLINES: the insert-vs-mutate wall · the origin law · the path suppression triggers · the inline-axis void · the snap row-loss split (WebKit) · the priority void (spec'd but shipped nowhere)

§1 Support census — and the Safari holesurface

The property grammar is two keywords: overflow-anchor: auto | none. It applies to all elements, is not inherited, and has no JavaScript surface at all — no API, no event, no anchor-node readback. The only observable is behavior: the scroll offset itself.

THE SAFARI HOLE. §2 THE INSERT LAW — node insertion above the anchor adjusts the scroll, exactlythe core

Insert a 34px row above the viewport of a scrolled feed: every engine moves scrollTop by exactly +34 — the visible rows do not move a single pixel. This is the mechanism, and it is free: no listener, no resize observer, no manual compensation. Insert 3 rows in one DocumentFragment → one combined +102 adjustment.

THE BATCH LAW. One fragment of N nodes = one adjustment of the combined height. Batch your prepends.

§3 THE ORIGIN LAW — at scroll zero there is no anchorthe floor

The selection algorithm's second step: if the scroller "is not scrolled away from the origin of its scrolling area in its block flow direction, do not select an anchor node." At scrollTop 0 nothing is above the viewport, so no anchor is selected — and a zero scroll offset is also a suppression trigger. Inserting above content you haven't scrolled past simply grows the page downward.

Consequence for tests: any e2e lane that asserts anchoring must first scroll past zero — at the origin the no-op is spec-correct, not a bug.

§4 THE MUTATION WALL — insertions anchor, geometry changes on the anchor's path do notthe trap

The spec's suppression triggers: a computed-value change of top/left/right/bottom · margin · padding · width/height/min-*/max-* · position · transform on any element on the path from the anchor to the scroller suppresses that window's adjustment. The non-obvious half: the trigger list only covers the anchor's ancestor path. A sibling above the viewport growing does not trigger — it adjusts. A wrapper around the viewport content growing does trigger — content visibly jumps.

THE PATH-MUTATION WALL. "Anchoring keeps my page still" is only true for insertions and non-path mutations. Grow, pad, margin or transform any element that contains the viewport content and the engine deliberately refuses to compensate — your content visibly jumps, 3/3 engines. Every "expandable section above the fold" and every "revealed-by-transform" panel hits this.

§5 THE INLINE-AXIS VOID & THE BLOCK-FLOW LAWaxes

Anchoring compensates movement along the block-flow axis only. In a normal horizontal-tb overflow-x scroller, inserting at the inline start (the left) shifts every item 60px with zero compensation. Rotate the writing mode — vertical-rl, where block flow is horizontal — and the same insertion at block start adjusts scrollLeft by exactly −60 (negative coordinates, the RTL-style axis), 3/3 engines.

THE INLINE VOID. Horizontal carousels and timeline strips get no anchoring in horizontal-tb — the block-flow axis is vertical there. The axis follows the writing mode, not the scroll direction.

§6 THE IMAGE LAW — the motivating case, measuredCLS

Scroll anchoring was invented for this: an unsized <img> above the viewport finishes loading, its height goes 0→150, and the article you're reading would traditionally jump 150px. Measured: the engine compensates exactly +150 on all three. The twin lane reserves the box upfront (width/height in CSS) — then loading changes nothing, and correctly nothing is adjusted. Two ways to have a stable page: reserve space, or let anchoring eat the shift.

Reserve-space still wins for anything you control (dimensions on media, skeletons) — anchoring is the safety net for everything you don't.

§7 THE EXCLUSION GRAMMAR — none poisons the subtree, and auto cannot rescue itopt-out

The property is not inherited — a child of a none element reads auto in getComputedStyle — but the anchor-selection rule walks the ancestor chain: "C is not viable if any ancestor up to the scroller is in an excluded subtree." So auto on a leaf inside a none subtree is inert: measured, the leaf's own subtree shift is uncompensated on all three engines. And none on the scroller itself is the kill switch for the whole box.

THE NOT-INHERITED-BUT-POISONED SPLIT. Reading getComputedStyle(el).overflowAnchor === 'auto' tells you nothing about whether el can anchor — an ancestor's none excludes it invisibly. There is no API that reports the effective state.

§8 THE NESTED RE-ARM — descendant scrollers turn anchoring back onnesting

The spec note: it is not possible to turn anchoring back on for descendants of a none element — except descendant scroll containers, which automatically re-enable anchoring for their own scrolling box unless they too declare none. Measured: outer document none, inner scroller still adjusts its own inserts, 3/3.

§9 THE NOISY ADJUSTMENT — anchoring fires real scroll eventsevents

Spec: the adjustment "is a type of scrolling… and generates scroll events." Confirmed 3/3 — your scroll listener fires for an adjustment the user never performed, and scrollend fires too. Engine detail: Chromium sometimes splits one adjustment into two scroll events (stable 2-of-1 on a fragment batch, ×3 reps; 1 with timeout settle), Firefox and WebKit fire exactly one. An animated insertion (CSS keyframes height 0→60) is tracked frame-by-frame: ~18–19 scroll events over a 300ms growth, 3/3 — the adjustment is continuous, not a single settle-at-end jump.

Instrumentation hazard: scroll-rate analytics, "user is reading" heuristics and infinite-scroll triggers all see anchoring adjustments as user scrolls. There is no flag on the event — isTrusted is true. Guard with a DOM-mutation window (e.g. ignore scroll events within one frame of a MutationObserver batch).

§10 THE SNAP ROW-LOSS SPLIT — WebKit re-snaps a row earlyengine split

In a scroll-snap-type:y mandatory scroller, spec says anchoring is "limited to adjustments that would be allowed by re-snapping." Measured with row-identity (which row tops the viewport after a 60px insert above): Chromium and Firefox adjust +60 and re-land on the same row (800→860, row 20→row 20, ×3 stable). WebKit lands one row earlier (800→820, row 20→row 19, ×3 stable) — the same insert silently eats a row of content on the WebKit family inside snap containers.

§11 THE PINS — at-max keeps the pin, removal returns exactlygeometry

Two edge laws, both 3/3 exact: (1) a feed scrolled to the maximum offset and prepended above adjusts +60 and remains at the new maximum — the bottom-pin survives prepends with zero code (the pattern chat apps hand-roll with scrollTop = scrollHeight re-pins). (2) Removing the inserted node re-anchors back exactly (960→900) — the adjustment is symmetric and reversible. And the adjustment lands at the first layout-forcing read: reading scrollTop synchronously right after the insert already returns the adjusted value (the spec's "suppression window" closes at that query), 3/3.

§12 THE PRIORITY VOID — the spec's focus rule ships nowherespec vs engines

The spec defines anchor priority candidates: the DOM anchor of the focused area when it's an editable field, and the current find-in-page match — they win anchor selection outright. Measured with focus asserted (document.activeElement verified) and a mutation that moves only the focused row's subtree: no engine re-anchors to the focused input — delta 0, top-of-viewport candidate kept, 3/3. Find-in-page cannot be driven headless (honest lane limit), but nothing suggests it fares better. The spec promise your editor-in-a-scroller needs is simply not there.

THE PRIORITY VOID. Don't build on "the browser anchors to what I'm typing in" — it doesn't, anywhere measured. Reserve space or compensate manually around editable regions.

§14 Molt audit — the "page jumped" review, 12 checksmolt

  1. HIGH — Expanding sections above the viewport inside the same wrapper as the reading content: path mutation → suppressed → guaranteed jump (§4C). Every accordion/FAQ/collapsible above content.
  2. HIGH — Reveal animations via transform on a wrapper containing viewport content: uncompensated 60px+ visual jumps (§4D).
  3. HIGH — Unsized media above the fold relying on anchoring alone for Safari ≤26: no net there — ship dimensions or skeletons.
  4. HIGH — Snap carousels that insert above (banners, "new" badges): WebKit + old Safari eat a card (§10).
  5. HIGH — Scroll-analytics treating anchoring adjustments as user engagement: isTrusted true, no flag (§9).
  6. MED — Prepend-by-margin/padding/transform instead of node insertion: works nowhere, jumps everywhere (§4).
  7. MED — Horizontal inline-axis strips assuming anchoring: no compensation in horizontal-tb (§5).
  8. MED — e2e asserting raw scrollTop after DOM mutations: expect the anchoring delta on Chrome/Firefox/Safari 27, absence on Safari ≤26 — gate it.
  9. MED — Editor-in-a-scroller counting on focus anchoring: the priority void (§12).
  10. MED — Reading getComputedStyle().overflowAnchor to detect effective anchoring: not-inherited-but-poisoned (§7) — it lies.
  11. LOW — overflow-anchor:none sprinkled as a "performance fix" without a measured jump: you're disabling the net, not fixing the cause.
  12. LOW — Counting on scrollend per adjustment: fires, but the count is not contract-grade (§9).

Sellable as a half-day "reading-stability audit" — checks 1–5 pass code review on every stack and jump in production.

Falsified this session

  • "Anchoring adjustments are silent." False everywhere — they are real scroll events with isTrusted:true (and scrollend), exactly as the spec text says. My own pre-bench recollection was the folklore.
  • "Anchoring keeps the page still on content changes." Only for insertions and non-path mutations — the suppression-trigger list (height/padding/margin/transform/insets/position on the anchor's path) kills compensation for the most common hand-rolled reveal patterns, deliberately.
  • "overflow-anchor inherits." gCS says no; behavior says subtrees — the ancestor-chain exclusion makes it act inherited for anchor candidacy while the computed value stays auto.

De-confounds (4)

  • The reserved-image false negative — my first image lane set explicit width/height from parse: no layout change on load → correctly no adjustment → looked like "images don't anchor." The unreserved twin is the real lane (+150 exact).
  • The transform no-op lane — transforming a sibling above the viewport moves nothing (transform ≠ layout) → "suppressed" was vacuous. The honest lane transforms the anchor's ancestor and measures the uncompensated visual shift via getBoundingClientRect.
  • The verdict-constant bugs — hardcoded scrollTop=1000 expectations met the 900px scroll clamp on three lanes (nestedRearm, removeProbe, scrollEvents flags read false while the behavior was correct). Report measured before/after, never the intended constant.
  • The vertical-rl coordinate flip — scrollLeft runs negative in vertical-rl; my first "before: 0" lane had refused its own scroll set. Negative half-range + scrollLeftMax diagnostics fixed it.

Lane limits

  • Real Safari 27 untested by automation — the Playwright WebKit 26.5 build already carries the 27 implementation (property parses, laws behave); the App-store Safari 27 row is a human-hand confirmation, pending.
  • Find-in-page priority candidates cannot be driven headless — the focus lane is the measured proxy.
  • scrollend count varies with settle pattern (1–2) — not contract-grade; ≥1 observed on all engines for single adjustments.
