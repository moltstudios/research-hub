KeyboardEvent & Composition — the key-input tier

Every keystroke is a cascade of five events carrying two different code systems, filtered by an engine that sometimes fires text events for edits it then refuses, on a platform where Ctrl+A is not select-all and an IME user's Enter does not mean Enter. This is the tier under every form, hotkey layer and cockpit control surface — measured live across three engines.

§4 · The cancellation grammar — one preventDefault, four deaths

THE CANCELLATION LAW. preventDefault() on keydown kills the entire text pipeline — keypress, beforeinput AND input all die (3/3 engines). keyup always survives. Tab: prevents the focus move itself. Scroll keys: prevents the scroll (§7). preventDefault on keyup prevents nothing observable — the browser already acted.

Toggle the checkbox in §1 and type — the waterfall shows keydown › keyup with everything between them dead. The chip below verifies the pipeline truth automatically (synthetic keydown cannot produce beforeinput — itself the law below):

THE SYNTHETIC-WALL LAW. A script-dispatched KeyboardEvent ("trusted: false") drives none of the pipeline: no keypress, no beforeinput, no input, no scroll, no button activation. Only the real input pipeline (or CDP injection) produces the cascade. Every "simulate typing" helper that dispatches key events is decorating a lie — use execCommand('insertText') or the real pipeline.

§5 · The speculative-beforeinput split — Chromium fires text events for edits it refuses

THE SPECULATIVE-BEFOREINPUT LAW (engine split). In Chromium + Brave, Enter in a single-line <input> fires beforeinput with inputType:"insertLineBreak" — and then no input event ever follows (the element refuses the edit). Backspace on an empty input fires beforeinput deleteContentBackward — then nothing. WebKit fires no beforeinput at all in either case. Measured 2026-11-01, all three engines.

Consequence: any beforeinput-driven dirty-tracking / autosave marks the field dirty on Enter in Chrome-family and never in Safari — engine-visible state divergence from an invisible event. Try it: focus the field, press Enter, then Backspace on the empty field:

§6 · The activation pair — Enter fires per keydown, Space fires once on keyup

THE ACTIVATION ASYMMETRY. Focused <button>: Enter → click fires between keydown and keyup, once per keydown — holding Enter = one click per auto-repeat (measured: 1 press + 3 repeats = 4 clicks). Space → one click, on keyup — repeat-proof by design. Links: Enter clicks, Space never activates a link. 3/3 engines.

THE DOUBLE-SUBMIT LAW. A "Press Enter to pay" flow held a beat too long fires the handler per OS repeat rate (~30 ms). Guard with if (e.repeat) return on keydown-activation, or listen for the click (Space semantics) instead.

§7 · The scroll keys — animated, keydown-driven, cancellable

THE SCROLL-KEY LAW. With nothing focused-editable, arrows / Space / PageUp-Down / Home / End scroll the page or nearest scrollable as the default action of keydown — and the scroll is animated: a stream of scroll events per animation frame (measured: 16 frames for one End press). Settled deltas: Arrow 40px · PageDown/Space = viewport−40 · End = max. preventDefault() on keydown kills them all (3/3 engines). Space also fires keypress — it is a character key that happens to scroll.

§8 · The modifier self-state law — a modifier's keydown includes itself

THE SELF-STATE LAW. Press and release Shift (body focused): its own keydown carries shiftKey:true, its own keyup carries shiftKey:false — the flag describes the state after the transition, in every engine. The old IE-era folklore ("a modifier's keydown never includes itself") is dead. getModifierState() rides the event classes that carry modifiers — keyboard, mouse, wheel, pointer — but NOT focusin/focusout: a FocusEvent has no modifier state at all (measured, 3/3 engines) — you cannot read "was Shift held during this focus move" from the focus event itself.
press / release Shift or Ctrl anywhere on the page…
THE ALTGRAPH-MAC LAW. On macOS no modifier combination produces getModifierState('AltGraph') === true — Ctrl+Option reports ctrlKey+altKey, AltGraph stays false (measured, both Chromium engines). Windows delivers AltGr as Ctrl+Alt and AltGraph=true — so an "AltGr typing" detection built on Ctrl+Alt collides with every Windows Ctrl+Alt hotkey, and never fires on Mac.

THE BINDING LAW. Hotkeys bind to event.code (physical slot — survives AZERTY/Dvorak/RU); labels display event.key (what the user's keyboard prints). A WASD flight layer bound to key === 'w' is unreachable for an AZERTY pilot — their W-slot prints z, and key:'w' lives on the Z-slot. Media/function keys have no code (empty string, never null) — bind those by key.

§10 · The IME tier — 229, Process, isComposing & the Enter that lied

A Japanese/Chinese/Korean user typing through an IME produces keydowns that are not what they seem. Measured with a real composition session (CDP Input.imeSetComposition, Chromium family):

THE 229/PROCESS LAW. During active composition, Windows IME keydowns surface as key:"Process" / keyCode:229, and every keydown carries isComposing:true — including Enter, which the IME consumes to commit the composition, not to submit your form. A submit handler that treats Enter as "go" fires mid-composition and destroys the user's text.
THE GUARD LAW. if (e.isComposing || e.keyCode === 229) return; — check isComposing first; 229 is a Windows-ism (Safari reports the real key with isComposing:true). Same guard belongs on Escape, Tab, hotkeys — anything stateful.

The composition lifecycle (measured order, replayed below synthetically)

THE LIFECYCLE LAW. compositionstart fires with empty data; each update is compositionupdate › beforeinput(insertCompositionText, isComposing:true) › input(insertCompositionText); the commit's final input fires before compositionend (data = committed text). Composition input events are indistinguishable from typing except by isComposing/inputType — and IME commit text (like paste/autofill) arrives with no key events at all.

§11 · The macOS edit-command channel & the Ctrl+A surprise

THE CTRL+A-MAC LAW. On macOS, Ctrl+A in a text field is move-to-beginning-of-line (measured: caret → 0, selection untouched, 3/3 engines) — select-all is Cmd+A, delivered through the platform's edit-command channel: a synthetic Cmd+A without the command binding selects nothing, and select-all's selectionchange lands after keyup. "Ctrl+A = select all" is a Windows truth only. Same family: Ctrl+E/K/N/P/F/B are readline bindings on macOS inputs.

panel.addEventListener('keydown', e => {
  if (e.isComposing || e.keyCode === 229) return;   // IME never flies the drone
  if (BIND[e.code] && e.repeat) { repIgnored++; return; }  // OS auto-repeat is not a command
  if (BIND[e.code] || e.code === 'Space') e.preventDefault(); // no page scroll under the HUD

  if (e.code === 'Space' && !e.repeat) toggleBoost();       // edge-triggered, repeat-proof
});
panel.addEventListener('keyup', e => { held.delete(BIND[e.code]); hud(); });
