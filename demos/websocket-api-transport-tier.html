WebSocket API — The Transport Tier's Workhorse

One TCP connection, one HTTP upgrade, then full-duplex frames forever: the transport under every realtime dashboard, telemetry bridge, and multiplayer client since 2011 (Baseline Jul 2015). This page live-probes the real engine — constructor URL rules, the close-code wall, send() state gates, the never-resetting bufferedAmount — and runs a byte-faithful RFC 6455 codec SIM to expose what the API hides: handshake bytes, masking, the ping/pong layer, frame length forms, and the closing handshake choreography.

1 · Environment & the Transport Quartet

Where WebSocket sits: fetch/HTTP is request-response, WebSocket is bidirectional-ordered over one TCP connection, WebRTC is peer-to-peer media/data, WebTransport (Baseline Mar 2026) is HTTP/3 + QUIC streams & datagrams. WS is the only one Baseline-everywhere and proxy-friendly — still the default for server push behind corporate proxies today.

3 · Constructor URL Rules — Fragments Throw, http:// Is Legal

All probes below run against the real constructor. Predictions come from the WHATWG WebSockets spec; chips report what THIS engine actually did. REAL ENGINE

Constructor callSpec saysEngine did

The sleeper rule: http(s):// URLs are rewritten to ws(s):// and relative URLs resolve against the page base URL — the constructor is a URL parser, not a scheme checker. And fragments don't get stripped — they're a hard SyntaxError (a URL with a fragment can never be a WebSocket URL).

4 · close() — the Code Wall & the [Clamp] Trap

Live matrix: fresh socket per row, each close() called synchronously while CONNECTING (validation happens before any network). Allowed on the wire: 1000 exactly, or 3000–4999. Everything else → InvalidAccessError. Reason > 123 UTF-8 bytes → SyntaxError. REAL ENGINE

The [Clamp] row is the sneaky one: WebIDL [Clamp] truncates fractional codes toward zero before validation — so close(4000.9) quietly becomes a legal 4000 (no throw) while close(2999.5) becomes an illegal 2999 (throws). Half a unit decides the outcome.

Facts baked in by the spec: mode "websocket", referrer no-referrer, redirect mode "error" (a 3xx FAILS the connection — no redirect following, ever), credentials include (cookies ride along), and CSP connect-src governs. There is no CORS preflight — any origin can dial any server; the Origin check is the server's job.

8 · Frame Anatomy — the Wire Under the API

Every message is a frame: FIN bit, 4-bit opcode, mask bit, then a length in one of three encodings (7-bit inline, 16-bit, 64-bit), a 4-byte mask key (client→server always), and the XOR-masked payload. Fragmentation — one message, three frames (§5.4)

A sender MAY split any non-control message across continuation frames (opcode 0); the receiver reassembles before onmessage fires — you never see the seams in the API. Control frames can interleave between fragments but can never be fragmented themselves (≤125 bytes, FIN forced).

9 · The Closing Handshake & the Close-Code Registry

close() doesn't tear down TCP — it starts a 4-step dance: client close frame → server close frame echo → both TCP FINs → close event with wasClean:true. Skip any close frame (socket dies) and the UA synthesizes code 1006, wasClean:false. Step through it: SIM

Close-code registry (RFC 6455 §7.4 + IANA)

Dashed = never on the wire. 1005/1006/1015 are synthesized by the UA about the connection (no status / abnormal / TLS fail) — they appear in close events but can never be sent, and passing them to close() throws (§4 proved it live). 1010 is client-only (“server didn't negotiate my extension”). 3000–3999 = libraries/frameworks, 4000–4999 = yours (OpenDrones uses 4001 dropout, 4002 schema).

10 · Backpressure — bufferedAmount Is the Whole API

TCP backpressure exists, but the API surfaces it only as a number you must poll: send() never blocks and never errors on a slow server — the buffer just grows, silently, until memory hurts. WebTransport/streams expose real backpressure (await a writer); WS makes you watch the gauge. Run it: SIM · numbers cross-checked against a real noread server in §14

SimPeer — reading = truereadyState 1 · OPEN

readyState stays OPEN the entire time. No event fires. No error comes. Only the number moves.

// The production pattern: an HWM gate around every bulk send
async function sendBurst(ws, chunks) {
  for (const c of chunks) {
    while (ws.bufferedAmount > HWM) await sleep(16); // poll, poll, poll
    ws.send(c);
  }
}

Spec edge, per MDN: if the buffer is full and data can't be queued, the socket is closed automatically — in practice you hit OOM long before. There is no onbufferdrain, no promise, no callback. A number. That's the API.

13 · Ship Map — When WebSocket, When Not

NeedUseWhy
Server push, ordered messages, universal clients, proxies/CDNs in the wayWebSocketBaseline everywhere since Jul 2015; every infra box speaks the upgrade; Socket.IO/SignalR/Phoenix/GraphQL-WS all ride it
Unordered datagrams, many parallel streams, HTTP/3 end-to-endWebTransportQUIC native backpressure + no head-of-line blocking (cataloged Mar 2026)
One-way server→client feed (news, ticks, progress)SSEPlain HTTP, auto-reconnect built in, trivially proxied
Peer-to-peer or mediaWebRTCNot a server-transport problem

Known ceilings: WS rides HTTP/1.1's upgrade — there is no shipped browser API for WebSocket over HTTP/2/3 (the experimental WebSocketStream never shipped); if you need multiplexed streams over one connection, that's WebTransport. Practical limits: browsers cap concurrent sockets (low hundreds), frames are max 64-bit length but intermediaries choke far earlier, and bufferedAmount is your only flow-control signal.

Production checklist: wss:// only · server-side Origin check (no CORS saves you) · subprotocol string as your version channel (?…|v=2) · heartbeat JSON + watchdog · HWM gate on bulk sends · reconnect policy keyed off close code · binary frames on hot paths (JSON parse at 30 Hz × N drones is a real CPU line item).
