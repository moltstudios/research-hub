Highlight arbitrary text ranges without breaking the DOM

A search feature used to mean el.innerHTML = el.innerHTML.replace(…) — wiping event listeners, breaking React render boundaries, and silently failing when a match crossed a tag. The CSS Custom Highlight API lets you "paint" highlights over any text range using the new ::highlight(name) pseudo-element. 01Try it: live inline search

The CSS Custom Highlight API is the modern way to highlight arbitrary text ranges in a webpage without touching the underlying DOM. Instead of wrapping each match in a <mark> element, you create a JavaScript Range object, pass it to a Highlight instance, register it with CSS.highlights.set(name, highlight), and style it using the ::highlight(name) pseudo-element. The browser does the rest — paint, layering, repaint on viewport scroll — all on its own thread.

The API shipped in Chrome 105 (August 2022), then Safari 17.2 (December 2023), and finally Firefox 140 (June 2025) — making it complete cross-browser coverage. The ::search-text and ::search-text:current pseudo-elements shipped in Chrome 144 in 2026, letting you finally style the browser's native find-in-page highlight in your own brand colors. The Interop 2026 project has the Custom Highlight API as a focus area, so expect rapid feature consolidation across all browsers.

The single most important thing about this API: the DOM stays untouched. You can highlight across element boundaries (e.g. a span that wraps an inline <code> tag inside a <p>), the old innerHTML.replace() trick silently fails in that case — the Range object can span any text node sequence. Event listeners attached to children survive unmolested, React reconciliation is not invalidated, and Vue's diff doesn't notice anything happened at all.

You can register as many named highlights as you want, each with its own CSS color and style. A search-result highlight can be yellow, the currently-focused search match can be pink, a user-2 highlight from a collaborative tool can be teal, and a "warnings" highlight can be red — all on the same paragraph, layered via paint order. The browser composites them like SVG: later layers in CSS.highlights paint on top of earlier ones. This is why collaborative editors like Figma and Notion can show multiple cursors and selections without any DOM mutations at all.

How it works under the hood: when you call CSS.highlights.set(name, hl), the browser stores the Range objects in a paint-only layer keyed by name. The ::highlight(name) selector targets elements in that layer. No new nodes are inserted into the document tree — only paint operations are added. This is why highlights can span across arbitrary DOM boundaries and don't trigger React/Vue/Solid re-renders.
🔍 Bonus pattern: press ⌘+F / Ctrl+F in this page. The browser's native find-in-page matches are highlighted by the built-in ::search-text pseudo-element (Chrome 144+, Edge). The currently-focused match uses ::search-text:current (pink).

02The replacement: innerHTML vs. Range

Side-by-side, two ways to do the same task. The one on the right replaces every framework anti-pattern on the left.

❌ Old way — innerHTML hack

element.innerHTML = element.innerHTML.replace(/foo/g, '<mark>$</mark>')

  • Destroys all event listeners on descendants
  • Invalidates React/Vue/Solid reconciliation
  • Silently fails when match crosses element boundaries
  • Escapes user input wrong = XSS hole
  • Forces re-layout on every search update
  • Can't stack multiple highlights on the same text

✅ New way — Range + Highlight

CSS.highlights.set('search', new Highlight(...range))

  • Zero DOM mutations — listeners survive
  • Framework-agnostic — no re-renders triggered
  • Range crosses element boundaries freely
  • No string concatenation = no injection risk
  • Paint-only — composited on the GPU thread
  • Stack unlimited named highlights (search, user, warn…)

03The four-step recipe

Every implementation of this API follows the same four steps. Memorize them and you can build search, comments, code annotations, collaborative cursors — anything that needs to "paint over" text.

// 1. Create Range objects (one per match)
const range = new Range();
range.setStart(textNode, startOffset);
range.setEnd(textNode, endOffset);

// 2. Bundle ranges into a single Highlight
const hl = new Highlight(range1, range2, range3);

// 3. Register under any name you choose
CSS.highlights.set('search', hl);
// CSS.highlights.delete('search');  // to clear
// CSS.highlights.clear();           // to wipe all

// 4. Style via the ::highlight() pseudo-element
<style>
  ::highlight(search) {
    background: #fdcb6e;
    color: #1a1a2e;
  }
</style>

04All the highlight pseudo-elements

Five built-in + one custom. Each targets a different source — some are browser-native (selection, find), others are yours to define.

Pseudo Source Browser-managed? Stacked?
::highlight(name) Custom — ranges you create No, you control Yes, any name
::selection User pointer selection Built-in (always on) Single layer
::search-text Browser find-in-page matches Built-in (Chrome 144+) Current uses :current
::target-text URL text fragments #:~:text=foo Built-in (everywhere) Single layer
::spelling-error Spell-check underlines Built-in (Firefox sets it) Single layer
::grammar-error Grammar-check underlines Built-in (Firefox sets it) Single layer
Layer order matters. When two highlights overlap on the same text, the last one registered in CSS.highlights (or the highest-priority pseudo-class) paints on top. The order is roughly: ::selection → ::target-text → ::search-text:current → ::search-text → custom highlights in registration order. You can also override paint order with custom-highlight-priorities in the registry.

07Multi-layer stack — three highlights on one paragraph

A single passage of text, three different highlight layers applied to overlapping ranges. The browser composites them in the order their Pseudo-class wins.

Permanently painted on this paragraph: "highlight" in teal and "DOM" in red. Your query adds a yellow layer on top.

The CSS Custom Highlight API is one of the few DOM-less DOM APIs. You define text ranges in JavaScript and the browser paints the visual style on top — but the DOM stays exactly as you authored it in HTML. This is the structural difference between a CSS Custom Highlight and the legacy innerHTML.replace() trick: no markup is added, removed, or wrapped. Event listeners on children survive, React reconciliation does not fire, and the same paragraph can carry an unlimited stack of named highlights at once.

If your query happens to overlap the teal "highlight" or red "DOM", you should see all three colors layered on the same text — yellow on the visible surface but green/red showing through where the search didn't match. The ::highlight(name) layers compose just like SVG paint operations.

⚡ Performance characteristics

Highlights live on the compositor thread — they don't trigger layout, paint, or DOM mutation. Scrolling stays at 120fps even with thousands of highlighted ranges. CSS.highlights.set() is an O(n) operation on n ranges, and the browser reuses the existing text nodes. Compare to innerHTML.replace() which tears down the DOM tree, deserializes HTML, reattaches listeners, and triggers full layout.
