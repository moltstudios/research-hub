The Font Loading Tier — @font-face, document.fonts & font-display

typography · platform tier · universal since 2014 — every client site ships a web font, and the browser ships a whole machinery for it that almost nobody reads: a FontFaceSet you can query, a load/error grammar with exact exception types, a three-period display timeline, and a metric-override system that can make the font swap invisible. The docs describe the intent; this page measures the engine. Every law below is re-probed live in your browser — the chips are computed, not printed.

THE THREE-OBJECT LAW. @font-face declares a face; the FontFaceSet (document.fonts) holds every face the document knows — CSS-connected ones included; the FontFace object is one face with its own load promise and its own status (unloaded → loading → loaded | error). 2 · THE check() LIE — the most-used line of font code on the web

queryresultwhat it actually means
THE NEGATIVE-DETECTOR LAW. document.fonts.check('16px "MyFont"') returns true for a family that does not exist anywhere — not in the document, not on the system. It returns false only when a face is declared in the document and has not finished loading. So the classic guard
if (document.fonts.check('16px "Inter"')) { …show the styled UI… }
passes even when the web font was never declared at all. check() answers "is this face pending?" — it does not answer "is this font ready?". Measured live on the table above. Also measured: check() ignores weight and style — after a 400-only face loads, check('900 16px "Inter"') is true (the browser synthesises the bold) — so it can never warn you about a missing weight.

3 · check() vs load() — the request law

check() never touches the network

load() always does

THE INTENT LAW. check() is a query: it never initiates a download (measured: 0 network requests). load('16px "Family"') is a command: it fetches the face even if nothing on the page uses it, and resolves with the array of matching faces (an empty array for a family that doesn't exist — it does not reject). Use check() to ask, load() to command, and face.loaded to await one specific face.

4 · Three request laws — what the network sees

local() first wins without a download

unicode-range defers the download

format() hints are not enforced

requestURLbyteswhy
THE SUBSET LAW. A face whose unicode-range does not cover the text on screen is never fetched — measured: the CJK-range face requested 0 bytes until a codepoint inside its range was actually rendered. That is how subsetting turns into bytes: declare the ranges, and the browser only downloads the slices the page really uses. THE LOCAL LAW. src: local('Arial'), url(…) short-circuits: when the machine has the font, the URL is never requested (measured 0 requests). THE FORMAT LAW. a format() hint that lies (format('truetype') on a WOFF2 file) is ignored by Chromium — the file still loads. THE 404 LAW. a broken @font-face still fires a network request and logs a console error on every page load; its face status becomes error and check() returns false for it forever.

5 · The error grammar — five ways a font fails

Pick a failure mode…
failureexceptionmessage (verbatim)
THE TWO-EXCEPTION LAW. A font failure is always one of two DOMExceptions and never a bare Error: NetworkError (the bytes could not be fetched — a 404, a CORS refusal, an undecodable data URL) and SyntaxError (the request was malformed — an unparseable src string, or an ArrayBuffer that is not a font). The split is not intuitive: a data URL with valid base64 that is not a font reports NetworkError, while the same garbage handed over as an ArrayBuffer reports SyntaxError: Invalid font data in ArrayBuffer. Note that the constructor never throws for a bad src — the error surfaces from load().

6 · The font-display timeline — measured, not quoted

The three periods (CSS Fonts 4)

blockinvisible fallback — the text is laid out but not painted swapvisible fallback — painted immediately, replaced when the font lands failurethe UA treats it as failed → normal font fallback

Every value of font-display is a different block/swap pair: block = short block + infinite swap · swap = ~0 block + infinite swap · fallback = ~0 block + 3 s swap · optional = ~0 block + no swap · auto = the UA's choice.

What Chromium actually did (measured, pixels)

valueink @350 msink @2.4 sswapped?

Measured on Chromium 155 with a 1.5 s artificial font delay: the "ink" column is the count of dark pixels inside the text box, read back from a PNG screenshot of the live page.

THE AUTO LAW. The default — font-display: auto — is not "swap". Chromium resolves it to block behaviour: measured 0 ink pixels at 350 ms with the font 1.15 s away. A web font that arrives late therefore leaves a hole in the page for up to three seconds unless you say otherwise. THE OPTIONAL LAW. optional is the only value with no swap period: measured, the font arrived at 1.5 s and the text never changed — it stayed the fallback for the life of the page. That is the only setting that can promise zero layout shift, at the price of possibly never showing your brand font. THE FALLBACK LAW. fallback has a 3 s swap period: with a 4 s font it gave up and stayed on the fallback, while swap (infinite swap period) still swapped at 4 s.

7 · The ready promise law

THE MEMOISED LAW. document.fonts.ready is one memoised promise object. Add a face to the set after the page settled and document.fonts.ready is still the same object — it does not become a new promise for the new work. Measured: await document.fonts.ready after adding a face resolved in 0 ms while the face's own status was still unloaded. So await document.fonts.ready is not a way to wait for a font you just added — await face.load() / face.loaded instead.

8 · The metric-match recipe — computed live

/* press the button — this @font-face is generated from YOUR engine's numbers */
THE SCALING LAW (headline). size-adjust multiplies the glyph outlines and the metrics — including ascent-override, descent-override and line-gap-override. Measured: size-adjust: 50% together with ascent-override: 100% on a 40 px font produced a final ascent of 20 px, not 40. Every recipe on the web that writes the target's ascent straight into the override is therefore off by exactly the size-adjust factor. The correct form is:

size-adjust = targetWidth / fallbackWidth
ascent-override = (targetAscent / sizeAdjust) / fontSize
descent-override = (targetDescent / sizeAdjust) / fontSize

— and it lands: measured, the adjusted fallback matched the target's width to 0.1 px and its line box and ascent/descent to 0 px. One caveat the measurement exposes: the ratio is string-dependent (the same two fonts gave 96.6 % on one string and 98.4 % on another) — measure with a representative string, or use a real tool (fontkit / capstyle).

9 · THE CAPSTONE — the font swap, measured as layout shift

Two identical phone-sized viewports (390 px wide) side by side. Both load the same web font at the same moment. The left one uses the raw fallback; the right one uses the metric-matched fallback the button in §8 generated. Each viewport reports its own Cumulative Layout Shift, measured by a real PerformanceObserver inside the frame.

raw fallback Arial

adjusted metric-matched

THE SWAP-SHIFT LAW. When the web font lands, the line box changes height (the web font's ascent+descent ≠ the fallback's) and the headline can re-wrap — everything below it moves. Measured on the phone-sized frames: the raw fallback moved the content below by 8 px and booked a layout-shift entry; the metric-matched fallback moved 0 px. A font swap is a layout event, not a paint event — which is exactly why font-display: swap costs you CLS and why size-adjust + the metric overrides are the fix. THE CLS FORMULA (Chrome's rule): impact fraction × distance fraction — the moved area over the viewport area, times the move distance over the viewport height. The same 8 px move is worth far less CLS on a large desktop viewport than on a 390 px phone, which is why the numbers here are per-frame.

10 · The FontFace IDL — the descriptor surface

descriptorCSSdefaultreadable from JS?
THE UNDOCUMENTED ONE. Chromium exposes FontFace.sizeAdjust — and accepts sizeAdjust in the constructor's descriptor dictionary — even though MDN's FontFace reference does not list it. Measured: new FontFace('X', src, { sizeAdjust: '80%' }) reflects back as '80%'. That means you can build the metric-matched fallback entirely in JavaScript — no build step, no per-project CSS — which is the difference between a font system and a font hack.

12 · Capstones — what to ship

Molt — the font pipeline

One @font-face per family with font-display: swap, a metric-matched local() fallback generated from a representative string, preload for the one face above the fold, and unicode-range subsets so the browser only pulls the slices the page uses. The measurement above is the QA step: check the adjusted fallback's width and line box against the web font — a Δ of more than half a pixel is a shift waiting to happen.

OpenDrones — the flight HUD

Telemetry numbers are read at a glance while the operator's hands are busy. A late web font there is a safety issue, not a polish issue: the numeric HUD must be metric-matched to the fallback so the readouts never reflow mid-flight, and the operator-critical font should be optional or preloaded — never auto (which paints nothing for up to 3 s).

Decision matrix — font-display

swap = the default choice for content sites (the fallback is visible instantly, the swap may shift — fix it with the metric overrides). optional = for above-the-fold heroes on slow connections (never shifts; the web font may never appear). block = only for print-like hero type. fallback = a middle ground. auto = Chromium's block behaviour — never write it, write what you mean.

The one rule

Never gate a UI decision on document.fonts.check() — it returns true for fonts that do not exist. Gate on await face.load() (or on a document.fonts.load() promise you started yourself), and read the real state from face.status.
