02

The cubic-bézier ceiling

Béziers are single-hump curves. They can overshoot once — but they cannot oscillate, settle, or dip-then-launch. linear() is a point list, so any curve shape is expressible.

A — cubic-bezier(0.34, 1.56, 0.64, 1) · the classic "overshoot" back curve
B — sampled damped spring via linear() · overshoot and settle
C — anticipate-dip → launch → settle · literally impossible in one bezier
Press play — the dots run the same 700ms lap.
Why it matters: A lands past the flag and stops dead (no settle). B overshoots ~27% then physically decays. C dips backwards first — the "anticipation" principle from every animation textbook — then commits. Only point-lists can do all three.

04
Stop lengths & hold segments

  
An optional percentage (or two) after each number controls when that output happens: one value sets its start time; two values pin a constant hold.

  

    
A — linear(0, 0.25, 1) · equidistant: 0.25 lands at 50%

    

    
B — linear(0, 0.25 75%, 1) · explicit start: 0.25 waits until 75%

    

    
C — linear(0, 0.25 25% 75%, 1) · hold: output frozen at 0.25 from 25%→75%

    

    

  

  
Hold segments are the sleeper feature: "move fast, pause, continue" used to need multiple keyframes. Now it's one timing function — and it composes with any property, including transitions.

Live validator — what the engine accepts

  
Only structural violations (3+ percentages on one stop) hard-reject the declaration. Ordering and range violations pass the parser and get silently normalized at computed-value time — probed live with CSS.supports() + a serialization probe in your browser:

  

    
    

      
      
      
      
      
      
    

    
    

  

  
Live-verified in Chrome 148 — the silent-normalization semantics: an inverted hold 0.5 80% 20% is accepted then coalesced to a zero-length hold at 80%; a cross-stop decrease 0.6 40% clamps up to the previous 50%; -10% clamps to 0%; but 110% is kept and drags the final stop to 110% too. None of these throw — the curve you wrote is never the curve you get. Trust the computed serialization, not the parser. Only 3+ percentages on one stop actually reject. (And output numbers may be negative or >1 — that's undershoot/overshoot, legal by design.)

Overshoot semantics per property

  
The same curve peaks at 1.15 output progress. Whether you see that depends on the property: transforms and lengths overshoot; opacity and color channels clamp at their natural range.

Rule of thumb: put spring curves on transform + opacity. Opacity-overshoot never renders (clamped to 1), and layout properties like width overshoot fine but animate on the main thread — the opposite of what we want for INP.







  
07
The keyframe-segment gotcha

  
animation-timing-function applies to each keyframe segment, not the whole animation. A spring curve on a 4-keyframe animation = the spring restarting at every waypoint.

  

    
A — 4 keyframes (0% · 33% · 66% · 100%) × spring easing → spring restarts 3×

    

    
B — 2 keyframes (from → to) × same spring easing → one clean physical move

    

    

    
Both use the identical timing function. A wobbles at each waypoint; B settles like a real object.

  

  
Fix: springs belong on 2-keyframe animations or transitions. Need waypoints? Chain separate animations, or move the easing into the segment that matters: @keyframes k { 0% {…} 100% {…} } with intermediate motion expressed in the curve itself — not the keyframes.

10
Duration discipline — match the settle time

  
A spring curve assumes it owns the full settle window. Pin a snappy spring (settle 463ms) to a generic 300ms duration and the animation ends mid-flight, past the target.

  

    

      
    

    

    

    
Curve's natural settle: 463ms. Current duration: 300ms.

  

  
This is the #1 way sampled springs go wrong in production. Generate the curve and the duration together — treat them as one unit (a token pair), never mix a spring curve with a hand-picked number.

Native spring()not shippednot shippednot shippedproposal #280 since 2016

    

    
Native spring() status: proposed to CSSWG in 2016 (issue #280, Apple-driven — WebKit even built an experimental impl); as of Aug 2026 it's still absent from the css-easing-2 editor's draft, MDN, and caniuse. Sampled linear() is the production technique — and when spring() eventually lands, your generated curves keep working identically.

    
Ship pattern

    
/* token pair — curve + duration travel together */
--ease-snap: linear(0 0%, .173 8.3%, …, 1 100%);
--dur-snap: 463ms;

/* capability gate (linear() is Baseline — gate is nearly vestigial) */
@supports (animation-timing-function: linear(0, 1)) { … }

/* motion-safety swap */
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 1ms !important; transition-duration: 1ms !important; }
}

    
Toolbox

    
Generators: linear-easing-generator.netlify.app (Jake Archibald — JS function or SVG → stops, spring/bounce/elastic/Material presets), kvin.me/css-springs (perceptual-duration UX), spring-easing npm (WAAPI/GSAP/Framer integration for when you need runtime re-targeting). DevTools: click the timing-function icon in the Animations pane to drag stops live (Chrome 114+).

    
Performance posture

    
Sampled springs run on the animation timeline — for transform/opacity that's compositor-thread, zero main-thread work per frame. A JS spring (Framer Motion et al.) runs physics on the main thread every frame; moving decorative springs into static CSS is free INP headroom — the mitigation half of our LoAF (Aug 18) and scheduler (Aug 19) research. ~25 stops ≈ 300 bytes gzipped per curve; four tokens cover a whole design system.

    
When to still use JS springs

    
Gesture-driven re-targeting (drag-to-fling with live velocity handoff) needs a runtime solver — a static curve can't accept mid-flight velocity. Hybrid: JS spring during the gesture, then hand off the settle to a CSS transition for the release.
