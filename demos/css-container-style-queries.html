01 The Problem: JS Class Toggling Everywhere

Every design system has the same pattern. A card has variants — primary, success, danger. The old solution: JavaScript reads a data attribute, toggles a CSS class, and the class applies styles. Two sources of truth. JavaScript doing CSS's job. Users can break it in DevTools by deleting the class.

❌ Before: JS + Class Toggling

  • JS reads data-variant and adds .card--primary
  • Two sources of truth (attribute + class)
  • Users can break it in DevTools
  • JS framework binding required
  • Class names are global namespace pollution
  • Cannot cascade — each component must be individually toggled

✅ After: @container style()

  • Set --variant: primary on any ancestor
  • One source of truth — the CSS custom property
  • No JS. No classes. No DevTools breakage.
  • Cascades to ALL descendants automatically
  • Custom properties are scoped, not global
  • One wrapper change updates the entire subtree
/* Old: two sources of truth */
.card--primary { background: oklch(0.55 0.2 260); color: #fff; }
.card--danger  { background: oklch(0.55 0.2 30); color: #fff; }

// JS: read attribute, add matching class
const card = document.querySelector('.card');
card.classList.add('card--' + card.dataset.variant);

/* ──────── vs ──────── */

/* New: one source of truth, zero JS */
@property --variant {
  syntax: "<custom-ident>";
  initial-value: default;
  inherits: true;
}

.card-wrap { container-name: card; }

@container card style(--variant: primary) {
  .card { background: oklch(0.55 0.2 260); color: #fff; }
}
@container card style(--variant: danger) {
  .card { background: oklch(0.55 0.2 30); color: #fff; }
}

/* HTML: just set the property on the container */
/* <div class="card-wrap" style="--variant: primary"> ... </div> */

06 The @property Pattern — Type-Safe Queries

Why @property matters for style queries

Without @property registration, custom properties have no known type and no initial value. Style queries on unregistered properties can behave unpredictably — a container that never set --variant might match style(--variant: default) or might not, depending on browser interpretation.

With @property, you get: (1) a known type (syntax), (2) an initial value (reliable fallback), (3) controllable inheritance. The style query becomes deterministic.

/* Register the property — gives the query a type and fallback */
@property --variant {
  syntax: "<custom-ident>";    /* accepts: default | primary | success | danger | ... */
  inherits: true;              /* children inherit the value */
  initial-value: default;      /* containers that don't set it get "default" */
}

/* Now the query is reliable: unregistered containers → "default" → no match */
@container style(--variant: primary) {
  /* only fires when a container explicitly sets --variant: primary */
}

/* Boolean-style: query for existence of a value different from initial */
@container style(--variant) {
  /* fires when --variant is anything OTHER than "default" (the initial-value) */
}

Composable axes — the killer pattern

Multiple custom properties create independent, composable styling axes. --tone controls color personality. --density controls spacing. --mode controls content visibility. Each axis is queried independently but applied to the same elements. This replaces nested class modifiers like .card--primary--compact--catalog.

/* Three independent axes — no BEM modifier explosion */
@property --tone { syntax: "<custom-ident>"; inherits: true; initial-value: purple; }
@property --density { syntax: "<custom-ident>"; inherits: true; initial-value: comfortable; }
@property --mode { syntax: "<custom-ident>"; inherits: true; initial-value: showcase; }

/* Tone axis — color personality */
@container style(--tone: blue) { .card { border-color: rgba(96,165,250,0.3); } }

/* Density axis — spacing and content visibility */
@container style(--density: compact) { .card { padding: 12px; } }

/* Mode axis — layout strategy */
@container style(--mode: catalog) { .card { grid-column: span 1; } }

/* All three compose: blue + compact + catalog → one unified card style */
/* Without: .card--blue--compact--catalog (BEM nightmare) */

07 Combining Size + Style Queries

Container queries can mix size conditions and style conditions in a single @container rule. This means a component can respond to both its width and its theme — in one declarative rule.

/* Container needs container-type for the size query part */
.dashboard-panel {
  container: panel / inline-size;
  --theme: dark;
}

/* Combined: panel is wide AND dark-themed */
@container panel (width > 400px) and style(--theme: dark) {
  .chart {
    grid-template-columns: 1fr 2fr;
    background: #0a0a0a;
    color: #fafafa;
  }
}

/* Narrow panel + compact density → strip metadata */
@container panel (width < 250px) and style(--density: compact) {
  .chart .meta { display: none; }
}

/* Boolean composition: NOT + AND + OR */
@container style(--theme: dark) or style(--theme: midnight) {
  .icon { filter: invert(1); }
}
@container not style(--legacy: true) {
  .component { animation: fadeUp 0.4s ease; }
}

Important: Style queries on regular CSS properties (like style(color: red) or style(font-weight: bold)) are not yet supported in any browser. Only custom property queries work today. The spec is designed for arbitrary properties — future browsers will close this gap.

Current limitation: custom properties only

The CSS specification allows style queries on any CSS property (style(font-weight: bold), style(display: grid)). However, no browser currently implements style queries on regular CSS properties — only custom properties (CSS variables) are queryable. The spec is ready; browser implementation is the gap.

Fallback strategy

For older browsers (Firefox < 151, Safari < 18), use @supports to detect support and fall back to class-based theming:

/* Fallback: traditional class theming */
.card--primary { background: oklch(0.55 0.2 260); }

/* Progressive enhancement: override with style queries where supported */
@supports (container-type: inline-size) {
  @container style(--variant: primary) {
    .card { background: oklch(0.55 0.2 260); }
  }
  /* hide the fallback class in supporting browsers */
  .card--primary { background: revert; }
}

09 Decision Matrix — When to Use Style Queries

Use Case Style Queries? Why
Design system component variants (primary / success / danger) ✓ YES One axis, one property, zero JS. Kills BEM modifier explosion.
Multi-theme switching (light / dark / brand) ✓ YES Removes .dark class from <html>. Container-scoped theming.
Density modes (compact / comfortable) ✓ YES Composable with tone/theme. No extra classes per density × tone combo.
Responsive component layout (based on parent width) ✗ SIZE Use @container (width > 400px) — size queries, not style queries.
Feature flags (show/hide premium features) ✓ YES Set --plan: premium on a wrapper. CSS handles the rest.
Page-level layout changes (mobile vs desktop) ✗ MEDIA Use @media — viewport-level queries are still correct for page shells.
OpenDrones dashboard panels (view + status) ✓ YES Two independent axes — perfect for style queries.
React state-driven styling (loading / error / data) ⚠ MAYBE If state is already in React, data-* attributes may be simpler.

  • Yes P3 — directly improves every design system build. Pairs with @property (P1), container size queries (P2), @scope (P2), and CSS nesting to create the modern component styling stack. The theming pattern alone (replacing .dark classes) is worth adopting in every new project.

Stack composition

Container style queries are the theming layer of the modern CSS toolkit:

  • Size queries (P2, @container (width > 400px)) — responsive layout
  • Style queries (this entry, @container style(--theme: dark)) — responsive theming
  • @property (P1) — type registration for reliable custom property queries
  • @scope (P2) — DOM-scoped styling rules
  • CSS nesting (Baseline 2023) — readable component CSS
  • light-dark() (P2) — automatic light/dark color switching
  • View Transitions (P1/2) — smooth animated changes between states

Together: a complete, zero-JS component theming system that five years ago required a CSS-in-JS library, a theme provider, class name composition, and React context.
