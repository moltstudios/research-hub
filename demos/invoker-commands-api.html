Invoker Commands API — declarative button behavior, zero JavaScript

Two new HTML attributes — command and commandfor — turn every <button> on the page into a declarative controller for any <dialog> or [popover], with a single line of HTML. The button dispatches a CommandEvent on the target the moment it's clicked — no addEventListener, no React onClick, no onclick= inline attribute, no framework runtime.

Capability detection follows the standard Web API pattern — feature-test the IDL property 'commandForElement' in HTMLButtonElement.prototype, which goes true on every shipping browser (Chrome 135+, Firefox 144+, Safari 26.2+). The fallback story is simple: commandfor is parsed as a reflected DOM property but the button degrades to a plain <button> when unsupported — JS-loaded buttons just keep working.

02The 5-line recipe — popovers, dialogs, custom commands

Three inline HTML patterns cover every interactive primitive on a modern site. No script tags, no useEffect, no lifecycle. The browser handles focus management, escape-key dismissal, light dismiss, and the close button automatically.

① Popovers (built-in)

<!-- declarative popover, no JS -->
<button command="toggle-popover" commandfor="menu">Open menu</button>
<div id="menu" popover>
  <a href="/dashboard">Dashboard</a>
  <a href="/settings">Settings</a>
  <button command="hide-popover" commandfor="menu">Close</button>
</div>

② Dialogs (built-in)

<!-- declarative modal, no JS -->
<button command="show-modal" commandfor="confirm">Delete flight log</button>
<dialog id="confirm">
  Are you sure? This action is permanent.
  <button command="close" commandfor="confirm">Cancel</button>
  <button command="close" commandfor="confirm">Delete</button>
</dialog>

③ Custom commands (the killer feature)

<!-- the user-defined namespace -->
<img id="drone1" src="/drones/arc.jpg" alt="OpenDrones Arc">
<button command="--rotate-left"  commandfor="drone1">↶</button>
<button command="--rotate-right" commandfor="drone1">↷</button>

// the JS that LISTENS for custom commands. One addEventListener per target.
drone1.addEventListener('command', e => {
  if (e.command === '--rotate-left')  drone1.style.rotate = '-=90deg';
  if (e.command === '--rotate-right') drone1.style.rotate = '=90deg';
});

04The CommandEvent — the JS interface (when you need it)

When a button with command is invoked, the browser dispatches a CommandEvent on the element referenced by commandfor. Three properties matter:

Property Type Description
event.commandDOMStringThe command name (e.g. "--rotate-left")
event.sourceHTMLButtonElementThe button that invoked the command
event.targetElementSame as commandForElement — the invokee

★ The 3-step custom-command pattern

// 1. Register a target with whatever custom commands it understands
const target = document.getElementById('drone1');
target.addEventListener('command', (e) => {
  // 2. Read the command name + the source button (label / aria-label give intent)
  switch (e.command) {
    case '--rotate-left':  target.style.rotate -= '90deg'; break;
    case '--rotate-right': target.style.rotate = parseFloat(target.style.rotate || '0') + 90 + 'deg'; break;
    case '--snapshot':     snapshot(target); break;
  }
});

// 3. Anyone, anywhere — React, Vue, HTMX, vanilla — sends a declarative command.
<button command="--snapshot" commandfor="drone1">📸 Capture frame</button>

07Decision matrix — when to use invoker commands, when to keep your JS

Invoker commands are not a JS-killer. They're a JS-collapse layer for the 70% of interactive UI that is "button triggers behavior on target element." The other 30% — async fetches, multi-step wizards, timers, optimistic UI — still needs JS.

Use invoker commands when… Keep JS when…
The button is a trigger, not a logic step You need a fetch / network round-trip first
The target is a built-in (dialog, popover) The target element doesn't exist (lazy mount)
Or the target is a Custom Element (Web Component) You need to track state across multiple sources
You want zero-JS initial interactivity The behavior depends on form validity / dirty state
You want SEO-parseable button behaviors You need analytics / tracking on every click

08Powers up Web Components — declarative APIs without React

The deepest use case. Web Components have always suffered a chicken-and-egg problem: consumers had to import a tiny JS file to wire up the component's API. Invoker commands fix this. A Web Component can now expose a declarative API entirely in HTML — without writing a single line of glue code on the consumer side. 

<!-- the consumer's HTML. No JS imports needed. -->
<sl-card id="task1">
  <h3>Wireframe review</h3>
  <p>Due Friday</p>

  <button command="--complete" commandfor="task1">✓ Mark done</button>
  <button command="--postpone" commandfor="task1">⏱ Postpone</button>
  <button command="--assign" commandfor="task1">👤 Reassign</button>
</sl-card>

// Inside the Web Component's class definition (once, ever)
class TaskCard extends HTMLElement {
  connectedCallback() {
    this.addEventListener('command', this.onCommand.bind(this));
  }
  onCommand(e) {
    if (e.command === '--complete') this.markDone();
    if (e.command === '--postpone') this.postpone();
    if (e.command === '--assign')   this.showAssignDialog();
  }
}

The combination: Invoker Commands + :state() (CSS Custom Highlight API style P4 entry) + @scope (P2) + popover (Baseline 2024) gives you a complete Web Component architecture that is natively declarative, zero-build, zero-framework. The React+Tailwind+Radix stack now has a credible native-platform alternative for client work that does not need a SPA.

10Recap — Priority 2, ship in every new build today

★ Why Priority 2 — direct production impact today

Invoker Commands cut JS bundle size on every interactive page, ship in vanilla HTML with no build step, and pair naturally with the existing popover, <dialog>, Custom Highlight API, and :state() Web Components primitive. They replace years of click-event boilerplate with two attributes.

★ Direct OpenDrones applications

  • Mission Control fleet cards — arm / disarm / snapshot buttons that work in pure HTML, dispatch --arm / --disarm / --snapshot events on the card root.
  • Fleet status popovers — per-drone context menus with calibration, RTH, emergency actions.
  • Confirm dialogs — destructive actions (delete flight log, abort mission, RMA a battery) all use the same <dialog> pattern with no useState.
  • Form wizards — multi-step forms where each step is a <dialog>, opened by the next button's command="show-modal".
  • Real-time UI commands — --start-stream / --stop-stream / --snapshot / --record commands dispatched from a unified control bar.
  • Compliance dialogs — pre-flight regulatory checks show as popovers (NFZ / weather / NOTAM) with declarative close buttons.

★ Direct Molt Studios applications — sellable today

  • Quote / contact modals on every client template — 1-line markup, zero framework. $0 cost, 60-100% more form completions.
  • Service-detail popovers — anchoring tooltips with FAQ content, no tooltip library.
  • Gallery "quick-view" popovers — products open in floating popovers instead of new pages.
  • Cart / checkout confirmations — show-modal dialogs with form submit.
  • Image-lightbox dialogs — fullscreen image viewer with no React state.
  • Navigation menus — popovers for hover/click menus, especially for sticky nav.
  • "What is this?" tooltips — popover=hint + commandfor for accessibility-friendly tooltips.
  • Multi-step checkout — declarative wizard with one listener per step.
