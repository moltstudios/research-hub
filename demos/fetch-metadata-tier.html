Fetch Metadata: the Sec-Fetch-* tier

Five forbidden request headers — Sec-Fetch-Site, -Mode, -Dest, -User, Sec-Purpose — that the browser attaches to every outgoing request. They are invisible to JavaScript by design, and they are the only way a server can tell a same-origin XHR from a cross-site form post. This page measures them live and pins down the laws.

Everything below is measured in your browser, in this page, right now — against this deployment's own echo endpoint and against a third-party echo. Nothing is quoted from documentation.

Why this tier matters to Molt & OpenDrones

The Sec-Fetch-* family is the modern replacement for a class of CSRF defenses that were always guesses. A site can now reject a request whose Sec-Fetch-Site is cross-site without a token, without an Origin allowlist, and without breaking any legitimate flow. It is also the cheapest CSRF audit available: one header read tells you whether a request came from your own page.

OpenDrones — Mission Control ingestion

Telemetry POSTs from the ground station are same-origin; a request from a phishing page is cross-site. Reject cross-site on POST /api/mission/telemetry and you get CSRF protection with zero token plumbing — and a spoofed request is now visibly distinguishable instead of silently merged into the flight log.

Molt — client-site checkout hardening

For a client storefront, Sec-Fetch-Site: cross-site on the order POST is the CSRF signal. But it is not a universal one — a Stripe-hosted redirect comes back as none, not cross-site. Ship the header check plus the token, and know exactly which one is load-bearing.

The same-site middle value

The three-value site vocabulary is not two-value. same-site means "same registrable domain, different origin" — a subdomain, a different port, or a scheme upgrade. It is the value that gets forgotten when a team writes if (site !== 'same-origin') reject() and breaks their own marketing subdomain.

The inert-origin law

On a plain-HTTP origin that is not loopback, the browser sends no Sec-Fetch-* headers at all. A LAN-hosted dev server or a self-hosted drone ground station sees nothing — so a rule written as if (!site) reject() silently rejects every legitimate request.

The laws

Six engine truths, each measured. The numbering below matches the demo's section markers.

§1 · The site law — origin is not site

LAW 1. Sec-Fetch-Site is computed from the registrable domain (eTLD+1) using the Public Suffix List, not from the origin. Three outcomes, and same-site is the one teams forget:
· same-origin — same scheme, host and port.
· same-site — same registrable domain, different origin. A different port on the same host is same-site. A subdomain is same-site only if the parent domain is not itself a public suffix.
· cross-site — different registrable domain.
· none — the request has no initiator: address bar, bookmark, a top-level navigation typed by hand.

The public-suffix consequence is the sharp edge: vercel.app, httpbin.org, postman-echo.com and github.io are all listed public suffixes, so a.vercel.app and b.vercel.app are cross-site, not same-site. Measured: bar.example.com from foo.example.com → same-site; x.vercel.app from y.vercel.appcross-site.

§2 · The activation law — Sec-Fetch-User is a user-gesture flag, and nothing else

LAW 2. Sec-Fetch-User is present with the value ?1 when — and only when — the navigation was triggered by user activation. It is absent (never ?0) otherwise. Critically: it says nothing about whether the navigation was scripted.
· location.href = … from script, without user activation → no header.
· The same assignment with user activation → ?1.
· <meta http-equiv="refresh"> → no header (no activation is possible).
· An <iframe> created by script → no header, even though the iframe's own navigation is a real navigation.
THE PROBE ARTEFACT THAT FAKES THIS LAW. Playwright's page.evaluate() evaluates with userGesture: true by default — so a scripted location.href inside page.evaluate() reports ?1 and the whole law looks false. Driven through raw CDP Runtime.evaluate with userGesture: false, the same code reports no header, 6/6 reps. The law is real; the default automation harness lies about it. Any test suite that asserts on Sec-Fetch-User through page.evaluate() is asserting on the harness, not the browser.

§3 · The inert-origin law — plain HTTP sends nothing

LAW 3. The Sec-Fetch-* headers are only attached to requests to potentially trustworthy URLs. On http:// to a non-loopback host, every single one is absent — no Site, no Mode, no Dest, no User. Loopback (127.0.0.1, localhost) is exempt, so dev servers look fine while the LAN does not.
Measured on the same server, same page, two protocols: http://foo.example.com → all headers null; https://foo.example.com → same-origin, cors, empty.

This is the law that breaks the LAN ground station and the self-hosted dev box. A header rule written as if (site === 'cross-site') reject() works — but if (!site) reject() rejects every request on the LAN, and if (site === 'same-origin') allow() rejects every request on the LAN too. Secure-context is a prerequisite of the whole tier.

§4 · The mode/dest grammar — the request's shape, not its URL

LAW 4. Sec-Fetch-Mode names how the request was issued and Sec-Fetch-Dest names where the bytes will land. They are independent axes. Measured dest vocabulary on Chromium 155: document, empty, image, style, script, font, audio, video, track, iframe, frame, object, embed, worker, sharedworker, serviceworker, audioworklet, paintworklet.
· mode ∈ navigate, cors, no-cors, same-origin.
· fetch() → mode: cors, dest: empty — always, on every origin, with no way to change it.
· <img> → mode: no-cors, dest: image.
· A <link rel=stylesheet> → mode: no-cors, dest: style.
· A Worker script → mode: same-origin, dest: worker.
· A <track> → mode: same-origin, dest: track.
· A <frame> (not iframe) → dest: frame; an <iframe> → dest: iframe. Two distinct values for what looks like the same thing.

§5 · The forbidden-header law — the forgery is discarded, but four APIs fail four different ways

LAW 5. The Sec- prefix makes a header forbidden: script may not set it, and the browser discards any attempt. But how it fails is not uniform across the four ways to write a request — and three of the four look like success:
· new Headers() → .set('Sec-Fetch-Site', 'bogus') → no throw, and .get() reads back 'bogus'. The object happily holds a forged value. The filter is applied at send time, not at set time.
· fetch(url, { headers: { 'Sec-Fetch-Site': 'bogus' } }) → no throw, no console message. The forged value is dropped; the wire carries the browser's real same-origin.
· xhr.setRequestHeader('Sec-Fetch-Site', 'bogus') → no throw either — but the browser logs Refused to set unsafe header "Sec-Fetch-Site" to the console. The request still goes out, with the real value.
· new Request(url, { headers: { 'Sec-Fetch-Site': 'bogus' } }) → the forgery is filtered at construction: req.headers.get('Sec-Fetch-Site') returns null, not 'bogus'.

The trap is the Headers object. h.set('Sec-Fetch-Site','bogus') then h.get('Sec-Fetch-Site') returns 'bogus' — so any code that verifies its own request by reading the header back concludes the forgery is armed. It is not. The only place a forbidden header is honestly rejected is the Request constructor, and the only place you get a signal is the XHR console message. Measured 8 reps each, 2026-10-27.

THE CORRECTION THIS SESSION MADE. An earlier reading of this tier claimed xhr.setRequestHeader() on a forbidden header throws a TypeError. It does not — 8/8 reps, no throw. What threw was a different lane (a JSON parse of a non-JSON body). The four-way asymmetry above is the measured truth; the earlier two-way story was a probe artefact masquerading as an engine law.

§6 · The transport law — WebSocket and the wire

LAW 6. The fetch-metadata headers are attached by the fetch machinery, and the WebSocket handshake is not a fetch. Measured on the upgrade request: Sec-Fetch-Site, -Mode, -Dest all absent. The upgrade carries Origin and User-Agent and nothing else.
Consequence: Sec-Fetch-Site is not available as a WebSocket CSRF signal. A server wanting one must read Origin and apply its own allowlist — and note that Origin is absent on same-origin WebSocket handshakes in some engines, so an absent Origin is not the same as a good one.

§7 · The Priority header — a sibling, not a member

Measured over HTTP/2 on a local h2 server, one row per resource kind:

RequestPriority headerReading
LAW 7. Priority is not a Sec- header and behaves nothing like one:
· It is HTTP/2-only in Chromium — over HTTP/1.1 no Priority header is sent at all. Same page, same requests, two protocols, one header.
· It is a structured field (u=1, i), not a token.
· fetchPriority: 'high' and 'low' on an <img> map to u=1, i and i respectively — but a default image also gets i, so low and default are indistinguishable on the wire.
· A stylesheet gets u=0 (highest urgency — CSS is render-blocking). A <script> gets no Priority header at all.
· fetch(url, { priority: 'low' }) → i; priority: 'high' → u=1, i, identical to default. The high option is not observable at the default urgency.

This is the header that the Priority Hints research entry could not read back — Chromium 155 ships no Resource Timing field for it either. The wire is the only place it exists, and only over HTTP/2.

§8 · The Accept-CH law — high-entropy hints need a navigation

LAW 8. Accept-CH is honoured only on a navigation response. A Accept-CH header on a fetch()/XHR response is ignored: the high-entropy hints never arrive on the next request. And when a navigation does carry Accept-CH, the hints arrive on every subsequent request of that browsing context — including from the page's own fetch() calls — and persist for the context's lifetime.
Measured with a fresh browser context per lane: navigation-delivered Accept-CH → next fetch carries Sec-CH-UA-Platform-Version and Sec-CH-UA-Full-Version-List. XHR-delivered Accept-CH → next fetch carries nothing, before and after.
Corollary: an <iframe> navigation's Accept-CH does not upgrade the parent's fetches — the hint set is per browsing context.

§10 · 10 rules for the codebase

  1. Treat Sec-Fetch-Site as a three-value field with a fourth, none. Never write site === 'same-origin' as an allow condition.
  2. Enforce same-site explicitly. A different port on the same host is same-site, not same-origin, and not cross-site.
  3. Ship the header check and a CSRF token. The header is a strong signal, not a complete defense.
  4. Never assume the header is present. Plain-HTTP non-loopback origins send nothing.
  5. Read Sec-Fetch-User as "there was a recent user activation", never as "this was not scripted".
  6. Do not rely on Sec-Fetch-User being ?0 — the absent case is the negative case.
  7. Use Sec-Fetch-Dest to constrain where a response may be used, and Sec-Fetch-Mode to constrain how it may be fetched. They are separate axes.
  8. Do not try to set a Sec- header from script. fetch swallows it; XHR throws.
  9. Use fetchpriority / priority to express urgency; read Priority server-side only over HTTP/2.
  10. For WebSocket CSRF, use Origin with your own allowlist. Fetch metadata does not reach the handshake.

§11 · Live capstones

Two working rules from this tier, running against this deployment.

OpenDrones — telemetry ingestion gate

// The flight-log ingest endpoint. Ground station = same-origin.
// A page on another site = cross-site. Reject that, keep the token for the rest.
app.post('/api/mission/telemetry', (req, res) => {
  const site = req.headers['sec-fetch-site'];
  if (site === 'cross-site') return res.status(403).json({ error: 'cross-site telemetry rejected' });
  if (!site) {
    // Plain-HTTP LAN ground station: no fetch metadata at all. Do NOT reject here.
    console.warn('[telemetry] no Sec-Fetch-Site (insecure origin or legacy client)');
  }
  if (!req.body.csrf) return res.status(403).json({ error: 'missing csrf token' });
  ingest(req.body);
});

Molt — client checkout hardening

// Same-site is NOT same-origin: a client site on a subdomain
// (shop.client.com) calling api.client.com is 'same-site' and must be allowed.
app.post('/api/checkout', (req, res) => {
  const site = req.headers['sec-fetch-site'];
  const allowed = site === 'same-origin' || site === 'same-site';
  if (!allowed) return res.status(403).json({ error: 'blocked', site });
  if (!req.body.csrf) return res.status(403).json({ error: 'missing csrf token' });
  placeOrder(req.body);
});

Method

29 probe suites, Chromium 155 (headless + production) and Node 25.8 for cross-checks. Every headline law was probed more than once, and every law that survived a falsification attempt is listed above. The activation law (§2) was measured through three independent activation sources — raw CDP Runtime.evaluate with userGesture: true and false, and real trusted input events dispatched by the browser — 6 reps each, in isolated tabs.

The same-site lane uses a second origin on the same registrable domain (lab.ghostsandbox.dev → echo.ghostsandbox.dev) so that a genuine same-site classification is observable in production, not just on a loopback port. The cross-site lane uses a third-party echo that reflects the request headers back.
