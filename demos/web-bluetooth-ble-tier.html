Web Bluetooth — the BLE Tier

The missing rung of the hardware ladder — after Pointer 74209a4e, Gamepad/WebHID 31a7c6c0, MIDI cb52f4b1 and Serial e3ec543b: the contract between your page and Bluetooth Low Energy peripherals. navigator.bluetooth → chooser → GATT services/characteristics → notifications. Live-probed on Chromium-for-Testing 154 (macOS, adapter present): the validation wall, the activation contract, the reconnection door, and the walls — including the one the CDP mock-device domain hits.

§00 Caps — the surface census

Web Bluetooth is Chromium-only in 2026 (Chrome/Edge 56+; Safari has never shipped it; Firefox remains behind a flag). The whole GATT object model exists as interfaces whether or not hardware answers — which means most of the contract is probeable without a single device.

§01 The model — advertise, choose, connect, notify

A BLE peripheral advertises (small packets: name, services, manufacturer data). Your page declares what it wants via filters; the engine surfaces matching devices in a native chooser — the user picks one, and that pick is a permission grant the origin keeps. Then you connect to its GATT tree: Server → Services → Characteristics → Descriptors, each addressed by UUID. Standard services have 16-bit assigned numbers (0x180F battery) that expand to full 128-bit UUIDs under the Bluetooth base UUID.

The one-sentence version: filters describe the advertisement you want, the chooser turns a user pick into a durable grant, getDevices() later hands back the granted devices (even powered-off), and every payload you ever read arrives as a DataView you decode yourself.

§02 The validation wall — synchronous errors before any chooser

requestDevice(options) validates your filter grammar before it asks the user anything. Every one of these is a TypeError that rejects immediately — no chooser, no gesture needed to see the error. This is the layer you can (and should) fully unit-test offline.

Manual lab — throw matrix

// the filter grammar, enforced at call time:
navigator.bluetooth.requestDevice({ filters: [{ services: ['battery_service'], namePrefix: 'OD-BLE' }] })
navigator.bluetooth.requestDevice({ acceptAllDevices: true, optionalServices: ['battery_service'] })
// both specified → TypeError · both absent → TypeError · filters: [] → TypeError
// unknown service name → TypeError('Invalid service name: …')

§03 The activation contract & the chooser

requestDevice() requires transient user activation (a recent click/keydown, ~5s window) — the native chooser is the permission prompt. getAvailability() tells you whether an adapter exists before you promise the user a scan. On this headless probe host the adapter is real (availability: true), which exposes an engine truth the docs skip: without a renderable chooser, the promise neither resolves nor rejects — it pends. A pending requestDevice must never sit on your critical path.

Manual lab — real chooser (Chromium desktop / Android, adapter on)

click to open the native chooser 
// on a user machine this opens the OS chooser; on pick you get the device:
btn.onclick = async () => {
  const d = await navigator.bluetooth.requestDevice({
    filters: [{ namePrefix: 'OD' }], optionalServices: ['battery_service', 'heart_rate'] });
  const srv = await d.gatt.connect();  // → §06 census, §10 capstone
};

§04 getDevices() — the reconnection door

The chooser grant is durable. getDevices() returns previously-granted devices — including out-of-range and powered-off ones — with no activation, no prompt. This is the reconnect path for kiosks and mission hardware: chooser once during setup, silent reconnection forever after.

// setup day: user picks the drone's BLE module in the chooser (grant stored)
// every launch after: silent inventory, no gesture, no prompt
const known = await navigator.bluetooth.getDevices();
known.forEach(d => d.addEventListener('gattserverdisconnected', reconnect));

§05 The UUID registry — names, 16-bit numbers, canonical form

BluetoothUUID is a static dictionary: assigned-names ('battery_service', 'battery_level'), 16-bit numbers (0x180f), and full UUID strings all normalize to the canonical lowercase 128-bit form under the base UUID 0000xxxx-0000-1000-8000-00805f9b34fb. Anything else throws — including names that "look right".

§06 The GATT object census — interfaces without hardware

You don't need a device to know the contract. Every GATT class ships its full prototype surface on any Chromium engine — this census is what your code compiles against, and it's how you detect forget()/watchAdvertisements() support before calling them.

§07 The worker jail

Like geolocation and mediaDevices before it: navigator exists inside workers, navigator.bluetooth does not. Web Bluetooth is a window-document API — permissions are per-document, so the main thread owns the radio.

§08 The context walls — secure context, iframe policy

Two hard gates before any of the above matters: insecure origins lose the object entirely (not "denied" — absent, like camera/geolocation), and iframes live under the bluetooth Permissions Policy with default allowlist 'self': same-origin children inherit, cross-origin children are blocked at the call (NotAllowedError/SecurityError + a Permissions policy violation console line) unless the embedder delegates allow="bluetooth".

§09 The walls & docs-drift ledger

What the probe host could not do — recorded the same way as every wall in this series: the CDP mock-device domain is absent on Chromium-for-Testing 154 (page- and browser-level sessions both), so no synthetic GATT via DevTools; the scan extensions (requestLEScan, onadvertisementreceived, watchAdvertisements) sit behind experimental/flag gates; and the support matrix outside Chromium is the tier's shipping constraint.

§12 Ship map — when BLE, when not

Web Bluetooth earns its slot when the hardware speaks BLE GATT, the operator runs Chromium (kiosk, desktop console, Android field tablet), and the interaction is chooser-once/reconnect-forever. For anything else in the hardware ladder there is a better rung.

NeedUseWhy
Drone/robot over a serial cable or USB radioWeb Serial e3ec543bMAVLink-style framed byte streams; byte-level control BLE can't give
Custom USB firmware/HID deviceWebHID / WebUSB 31a7c6c0Report descriptors, raw endpoints — BLE GATT has no equivalent
Musical instruments, some sensorsWeb MIDI cb52f4b1Full-duplex byte streams over BT/MIDI with a saner permission story
Battery/sensor/telemetry GATT peripheralsWeb Bluetooth (this)The only web door into GATT services & notifications
iOS/Safari operators in the fieldNative shell (WebView + plugin)Engine never shipped the API; no polyfill exists for a radio
Background/always-on scanningNative appScanning extensions are experimental; chooser model is foreground-first

The 7-rule ship checklist

1  feature-detect: if (!navigator.bluetooth) → honest absence UI, never a dead button
2  availability() before promising a scan (adapter may be off/absent)
3  validate filters offline — every TypeError in §02 is pre-chooser, pre-gesture
4  requestDevice only behind a click; never on load, never awaited on a critical path (it can pend)
5  getDevices() + gattserverdisconnected → auto-reconnect ladder (exponential backoff, honest state)
6  decode DataView payloads yourself, little-endian unless the spec says otherwise; guard getUint16 offsets
7  kiosk/Chromium-only tier: pair with a Serial/HID fallback or a native shell for the Safari/iOS fleet
