Typography · CSS Inline Layout Module 3

CSS text-box-trim — pixel-true text, no more half-leading air

Every glyph you render floats inside an invisible box taller than the letters themselves — the font's ascent + descent, plus half-leading from line-height. That phantom air is why button text never optically centers, badges never align to their icons, and headings carry a hidden gap no margin value can fix. text-box-trim + text-box-edge cut the box to the actual ink edges — cap height to baseline — with one declaration, zero JS.

§1 · The invisible problem

What is half-leading?

A block of text contributes a box to layout that is not font-size tall. It is the font's own ascent + descent (metrics baked into the font file, usually ≈1.2em for Latin fonts) — and when line-height is larger, the difference is split as half-leading on top and bottom:

/* the formula nobody writes but everybody fights */
halfLeading = (lineHeight − (ascent + descent)) / 2
contentArea = ascent + descent        // font metrics, NOT font-size

The result: a 44px heading with line-height:1.1 still pushes several pixels of empty air above the caps and below the baseline — different amounts per font, invisible in devtools, and different again at every line-height. This is the air text-box-trim removes.

§2 · The 30-second pitch

One line kills the gap

ARMED · GPS 3D RTL · 12% BATT 
.label {
  text-box-trim: trim-both;
  text-box-edge: cap alphabetic;  /* box = cap height → baseline */
}

The chips above carry a fixed 10px vertical padding — but each one's visual height silently differs from its layout height by the font's phantom air. Toggle trimming and watch the dots, text, and border snap into optical alignment (green = trimmed). No line-height gymnastics, no magic padding numbers, no ::before spacing hacks.

This is the feature Apple co-designed and shipped first (Safari 18.2, Dec 2024) — it's how native platform labels sit flush in their pills. If our design bar is "would Apple ship this?" — they did, in the engine.

§8 · Semantics

line-height stays, trim ≠ line-height: 1

text-box-trim trims the block's start and end edges (the space above the first line and below the last line) — it does not touch the spacing between lines, and it does not depend on line-height at all: it uses font metrics, which is why it's stable across fonts where line-height hacks are not.

Inner line spacing (1.6) is untouched; only the outer air collapses. That's why trimming is safe for accessibility — reading rhythm inside paragraphs is preserved.

§9 · Gotchas

Four things that bite

1 · Descenders hang outside cap alphabetic. The under-edge snaps to the baseline, so g y p q j paint below the box. Visually fine in open layout — but overflow:hidden ancestors, tight sibling stacking, or scroll snapping can clip them. Rule: static labels with known-case text → cap alphabetic; anything that might contain descenders → cap text.
2 · It is font-metric math, not geometry. Swap the font (or weight) and the trim changes with it — that's the feature (optical truth per font). But screenshot-diff tests and pixel-perfect Figma handoff need the real loaded font, not a fallback.
3 · Support is newer than it looks. Chrome/Edge 132–133 (Feb 2025) and Safari 18.2 (Dec 2024) have it; Firefox only since 154 (≈Jun 30 2026) — MDN's "not Baseline" banner predates that Firefox ship and is stale. Samsung Internet (30) still lacks it. Not Baseline-labeled yet — treat as progressive enhancement, not foundation.
4 · Interop detail: shorthand ordering. text-box: trim-both cap alphabetic and text-box: cap alphabetic (implies trim-both) both work in current engines; prefer longhands in production CSS — drafts changed shape twice (it began life as leading-trim/grapheme-trim) and tooling/polyfills target the longhands.

Adoption posture: ship today, ungated. Worst case in a non-supporting browser is… today's rendering — the exact spacing we already ship. There is no layout cliff, no IACVT trap, no declaration-drop hazard: the property simply doesn't exist there. The one discipline worth keeping is don't bake pixel offsets that assume the trim landed (e.g. negative margins sized to the phantom air) — keep padding/margins neutral so both modes look intentional.

/* optional explicit gate — only if you want to vary padding per mode */
@supports (text-box-trim: trim-both) {
  .chip { padding-block: 8px; text-box-trim: trim-both; text-box-edge: cap alphabetic; }
}
@supports not (text-box-trim: trim-both) {
  .chip { padding-block: 10px; }  /* compensate optical size */
}
Re-check trigger: Samsung Internet >30 and the official Baseline flag (Firefox 154 completed the set ~7 weeks ago; MDN/BDL lag). Also watch Tailwind — open discussion to promote text-box utilities is underway.

§12 · Cheat sheet

Copy-paste kit

/* 1 · the workhorse: uppercase UI labels */
.ui { text-box-trim: trim-both; text-box-edge: cap alphabetic; }

/* 2 · anything that may contain descenders */
.mixed { text-box-trim: trim-both; text-box-edge: cap text; }

/* 3 · optically centered fixed-height button */
.btn { display:flex; align-items:center; height:56px;
       text-box-trim: trim-both; text-box-edge: cap alphabetic; }

/* 4 · honest heading margins */
h1,h2,h3 { text-box-trim: trim-both; text-box-edge: cap alphabetic; }

/* 5 · CJK flush blocks */
.cjk { text-box: trim-both ideographic ideographic; }

/* 6 · hero: flush top, breathing bottom */
.hero-title { text-box-trim: trim-start; text-box-edge: cap text; }

Pair with text-wrap: balance (already in our toolkit) for headlines that are both optically boxed and optically wrapped — the two halves of the 2026 typography tier.
