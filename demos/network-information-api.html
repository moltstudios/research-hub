Network Information API + navigator.onLine — The Connectivity Tier

The browser's two answers to "how good is my link?" — navigator.connection (the Chromium estimate tier: effectiveType, rtt, downlink, saveData) and navigator.onLine (the universal coarse half, with its online/offline events). Completes the adaptive-delivery tier alongside Compute Pressure, Speculation Rules, and the transport entries. Zero prior catalog coverage. Every claim is an executable chip, live-probed on this engine — plus a CDP-emulated falsification battery that produced four headline engine truths.

§01 · Anatomy — two APIs, one story

The spec lists six-ish fields on NetworkInformation. The desktop engine ships five — type and downlinkMax are privacy-stripped on desktop Chromium (undefined here; type survives on Android, where it reads cellular/wifi/ethernet). navigator.onLine is the universal half — Baseline forever, every engine, no gating at all.

The contract

const c = navigator.connection   // NetworkInformation | undefined
c.effectiveType  // 'slow-2g'|'2g'|'3g'|'4g'   (the tier verdict)
c.rtt            // ms, quantized estimate, 50ms steps (obs.)
c.downlink       // Mbps estimate, 0.05 steps (obs.)
c.saveData       // boolean — user's Data-Saver request
c.type           // 'cellular'|'wifi'|… ANDROID-ONLY (undefined desktop)
c.downlinkMax    // ABSENT desktop (spec legacy)
c.onchange       // null | Function + 'change' event

navigator.onLine // boolean — "has a network interface"
addEventListener('online',  …)   // fires AFTER connection change
addEventListener('offline', …)

§03 · The quantization ladder — rtt walks in 50 ms steps, and effectiveType follows RTT, not downlink

What the ladder proves

  • rtt ≈ 90% of emulated latency, quantized to 50 ms steps (0/50/100/250/550/1150/2350). The documented "25 ms rounding" is not what this engine does at these values.
  • 4g→3g boundary between rtt 250 and 550; 3g→slow-2g between 1150 and 2350. The 2g band lives between (est. ~1400–2000).
  • downlink was 9 the whole sweep and the tier still demoted — effectiveType tracks RTT. Docs describing dual-condition (rtt OR downlink) tiers do not match observed behavior; downlink alone never demoted anything here.

Live tier-consistency check

Reads your real rtt right now and derives the tier from the observed ladder — a mismatch means the engine used inputs you can't see (or kept a stale verdict).

Mismatch is a warn, not a fail: the estimator weighs history you can't query — treat effectiveType as a hint, never a contract.

§04 · HEADLINE — offline is a “4g” connection

Emulate offline:true and the engine reports rtt: 0, downlink: 0, effectiveType: "4g" while navigator.onLine === false. The RTT ladder runs on rtt=0 → every tier check passes → your dead link is labeled 4g. Any code that picks video quality or asset weight from effectiveType alone will try to stream 4K down a link that doesn't exist.

The event ordering (live capture)

change  → rtt 700, downlink 0.45, eff 3g   // slow emul
change  → rtt 0,   downlink 0,    eff 4g   // ← OFFLINE = 4g
offline → window event
change  → rtt 100, downlink 1.45  // emul cleared
online  → window event

connection change fires BEFORE online/offline. If your handler reads navigator.onLine inside a change listener, it sees the NEW state — but during the offline transition it still reads a "4g" effectiveType. Pair them, always.

The only safe gate

function linkUp()      { return navigator.onLine; }
function safeTier() {
  if (!navigator.onLine) return 'offline'; // NEVER trust eff here
  const c = navigator.connection;
  return c ? c.effectiveType : 'unknown';  // FF/Safari land here
}

§05 · The silent surfaces — mutation, granularity, and what isn't gated

Mutation: mode-dependent

c.rtt = 999 → TypeError in strict mode / modules, silent ignore in sloppy mode (live probe caught both shapes — value never changes either way, no change event). All five fields are getter-only properties on the prototype (Navigator.prototype.connection is the descriptor home). Object.keys(c) === [].

Downlink steps: 0.05, not 0.25

Live values 1.45 / 1.5 / 1.55 / 1.6 — the documented "rounded to nearest 0.25 Mbps" is falsified on this engine. Don't build switch statements on bucket boundaries.

The anti-jail law

Ships on insecure origins (plain HTTP LAN — verified present), ships in dedicated workers, no Permissions-Policy directive, no permission prompt, no grant, no iframe gate. The least-gated tier in the whole catalog — it's an estimate, so nobody's privacy wall applies… except the two fields they deleted (§01).

§07 · saveData — the user's request you must honor

saveData is a boolean the user sets in the OS/browser (Data Saver / Low Data Mode). It is a request, not a hint: when true, your delivery tier should drop to its lightest ladder regardless of how good the estimate looks. On desktop dev boxes it is almost always false; on metered cellular it is the single most valuable bit you get — and no emulation door flips it (no CDP knob).

§11 · Ship checklist

  1. Feature-detect connection on every read — FF/Safari are object-absent; never destructure unguarded.
  2. Gate on onLine BEFORE reading effectiveType — offline is labeled "4g" (§04).
  3. Treat estimates as hints: per-context, history-weighted, quantized. Never persist them; never branch UX on bucket edges.
  4. Honor saveData as a hard floor — force the lightest ladder when true.
  1. Wire both channels: connection change (delta) + window online/offline (state) — change arrives first.
  2. Ignore type/downlinkMax on desktop — undefined; Android-only fields.
  3. In CI, drive states with CDP Network.emulateNetworkConditions — this tier is fully emulable (offline flip included).
  4. When the estimate isn't enough, measure your own transport (ping over WS/WebTransport) — ground truth beats every estimate.
