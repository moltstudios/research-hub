Document Picture-in-Picture — always-on-top windows for arbitrary HTML

Open an always-on-top mini-window that holds any DOM you can build — live drone feeds, video calls, calculators, chat widgets, timers. The browser floats it above every other app, and it lives until the opener does. Pairs with WebRTC (P3) and WebTransport (P2) to ship the real-time v3 stack for OpenDrones Mission Control.

01Live capability detection

One check: "documentPictureInPicture" in window. Plus @media (display-mode: picture-in-picture) to detect when content is being rendered inside the PiP window. Firefox 151 closed the cross-browser gap in April 2026 — the API is now production-ready for all desktop evergreen browsers except Safari.

05The 5-line recipe book

Document PiP is genuinely tiny. The full API surface: requestWindow(), the window property, the enter event, and a media query. Below is the minimum code for each of the 4 most common patterns.

① Open & move an element in

const pip = await window
  .documentPictureInPicture
  .requestWindow();
pip.document.body
  .append(myElement);

② Set custom size

const pip = await window
  .documentPictureInPicture
  .requestWindow({
    width: 320,
    height: 420,
  });

③ Style when inside PiP

@media (display-mode:
  picture-in-picture) {
  body { background: #0a0a0f; }
  .close-btn { display: none; }
}

④ React to close

pip.addEventListener(
  'pagehide', () => {
  parent.append(myElement);
  // restore state
});

⑤ The complete production pattern

// 1. Feature-detect
if (!('documentPictureInPicture' in window)) {
  // Fallback: show inline, or fall back to native <video> PIP
  return;
}

// 2. Open the PiP window (requires user gesture)
async function popIntoPip(el, w, h) {
  if (window.documentPictureInPicture.window) {
    window.documentPictureInPicture.window.close();
    return;
  }
  const pip = await window.documentPictureInPicture
    .requestWindow({ width: w, height: h });

  // 3. Copy stylesheets so the moved element looks the same
  for (const sheet of document.styleSheets) {
    try {
      const css = [...sheet.cssRules].map(r => r.cssText).join('');
      const style = pip.document.createElement('style');
      style.textContent = css;
      pip.document.head.append(style);
    } catch {
      const link = pip.document.createElement('link');
      link.rel = 'stylesheet';
      link.href = sheet.href;
      pip.document.head.append(link);
    }
  }

  // 4. Move the element in
  const host = el.parentNode;
  pip.document.body.append(el);

  // 5. Restore on close
  pip.addEventListener('pagehide', () => host.append(el));
}

06Stylesheet copy & the display-mode media query

The PiP window opens with a fresh document — no styles inherited. You have to copy the CSS that styles the moved element, or it'll render unstyled. The 15-line helper above iterates document.styleSheets, copies local rules, and falls back to <link> for cross-origin sheets. For PiP-specific styling, the @media (display-mode: picture-in-picture) query lets you change the look based on context.

The 3-place where Document PiP diverges from the inherited CSS

  1. No stylesheets by default. You must copy them across, or the moved element renders with browser defaults. The MDN helper above handles local + cross-origin.
  2. No fonts in some browsers. If your styles reference custom fonts via @font-face or font-family, you may need to inline a <link rel="preload" as="font"> in the PiP document head.
  3. No storage isolation. The PiP window is same-origin with the opener, so localStorage, IndexedDB, and sessionStorage are shared — which is what makes event listeners and state work seamlessly.

07Document PiP vs. the legacy <video> PiP API

The classic HTMLVideoElement.requestPictureInPicture() (shipped 2018) is limited to a single <video> element, with browser-rendered controls you can't customize. Document PiP replaces all of that with a full HTML document in an always-on-top window — it can hold any DOM, with your styles and your event handlers.

Feature Video PIP (2018) Document PIP (2023+)
Content type Single <video> element only Arbitrary HTML, CSS, images, controls
Custom controls No (browser-rendered) Yes (your DOM, your styles, your JS)
Multiple streams No (canvas hack required) Yes (just append all <video> elements)
Browser support ~99% (Baseline 2018+) ~80% desktop (Chrome 116, Edge 116, FF 151)
Requires user gesture Yes Yes
Style based on context No Yes (@media (display-mode: picture-in-picture))
State preservation Yes (video continues) Yes (JS realm shared with opener)
Use case fit Single video watching Any UI you want to keep on top

08When to use Document PiP vs alternatives

Document PiP is the right tool for "keep this DOM always-on-top while the user does other things." It's not a replacement for tabs, modal dialogs, or full apps. Use this decision tree.

✅ Use Document PiP when…

  • The user needs to monitor a stream while doing other work — drone feed, security cam, video call, music player.
  • The UI is a tool the user keeps open — calculator, timer, chat, captions, scratch pad.
  • The user needs to switch context frequently — pilot filing reports, agent on a call, designer tweaking while watching a tutorial.
  • You'd otherwise build a canvas-into-PiP hack to fake it (the old way to put a multi-tile video call into PiP).

❌ Don't use Document PiP for…

  • Simple single-video watching. Use the native <video> PiP API instead — universal support, no copy code.
  • Full apps that need tabs/url bar/storage isolation. Use a regular window or a PWA.
  • Mobile. Chrome for Android doesn't support it (yet), iOS Safari has only native video PiP. Use bottom sheets / picture-in-picture on the OS level.
  • Surprise the user. The window only opens on a user gesture (button click), and is visible to them — don't auto-open.

10Recap — Priority 3, with a clear upgrade path

Document Picture-in-Picture is a Baseline 2026 feature that completes the always-on-top story for the modern web. It pairs with every other real-time entry on the platform to ship the v3 stack:

  • WebRTC P3 (2026-07-11, MC 8c498f00) — the v1 single video PIP, the canvas-into-PiP hack, and the SFU for distributing drone video to 50 operators. Document PiP replaces the canvas hack — just move the entire MediaStream tile panel in.
  • WebTransport P2 (2026-07-09, MC ddbf98c1) — telemetry over HTTP/3 + QUIC. Combined with Doc PiP, you can keep a live telemetry HUD on top of an arbitrary other app while the underlying WebTransport connection streams new frames.
  • WebGPU P2 (2026-07-02, MC 3cd08370) — the 3D airspace view. A Doc PiP window can host a small WebGPU canvas for a 2D map preview, while the main tab runs the full 3D scene.
  • Custom Highlight API P1 (2026-07-02, MC 88005595) — when the pilot log search results are moved into Doc PiP, ::highlight(search) still works there because the stylesheets were copied.
  • View Transitions P2 — document.startViewTransition() on the PiP window produces a smooth morph when the moved widget changes its state, e.g., a successful landing on a mission.

Why P3, not P1/P2

  • Not P1 — the Safari gap (~20% of users) is still a hard one. For Molt client deliverables, you cannot ship a feature that breaks in Safari. OpenDrones Mission Control can ship it (built target = Chrome/Edge/Firefox), so for that project it's closer to P2, but for cross-client P1 it's P3.
  • Not P2 — the lack of mobile support is a real constraint. For Molt client work targeting mobile audiences (e.g., a consumer real-estate app), Doc PiP is unavailable on the most-used device. P2 entries (WebGPU, WebTransport) ship on mobile.
  • Yes P3 — it's a strong foundational primitive, pairs with every other real-time entry on the platform, is genuine ship-today infrastructure for OpenDrones pilots, and the Firefox 151 ship closed the desktop gap. The natural moment to pull it into production: when WebRTC (P3) is wired up for a live feed, and the team wants a persistent window for it.
