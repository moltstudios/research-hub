§1What Local Network Access is — and what replaced what

Two designs, one goal (stop public sites from CSRF-ing the LAN/loopback): the old Private Network Access preflight design is on hold; the shipped LNA permission asks the user once per site. This demo page is itself served from a public HTTPS origin — every live probe below runs the real milestone-1 scenario: public page → your machine's loopback.

THE PUBLIC→LOOPBACK WALL: from a public HTTPS page, requests to http://127.0.0.1:* / http://localhost:* are blocked before the network on Chromium — fetch TypeError: Failed to fetch, CSS/image onerror, WebSocket net::ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS — with a console line that calls itself “CORS policy”. It is not CORS: no ACAO header on the target fixes it, and the permission is the only key.
public https page→loopback target·Chromium: permission gate·FF: loads classically·WebKit: mixed-content wall
Timeline (documented + measured): Chrome 138 flag → 142 prompt ships (Oct 2025) → 156 drops the enterprise opt-out (stable Oct 20 2026) — enforcement is no longer opt-out-able in managed Chrome. Loopback→loopback and LAN→LAN are not in milestone 1; a future milestone extends to all cross-origin requests with local destinations.

§3The permission surface — live census

The permission name is local-network-access (dashed) on the Permissions API. The underscore spelling and local-network-access in the wrong casing both throw. State machine: prompt → granted | denied, live via onchange.

navigator.permissions.query({ name: … }) — four spellings, live

THE ASK-VIA-FEATURE LAW: there is no permissions.request(). The prompt is triggered by the gated request itself — a fetch/link/WS to a local-space destination fires it once per site (user-gesture-free). On headless/automation the prompt is replaced by context.grantPermissions(['local-network-access'], { origin }) — the e2e recipe (§7).

§4targetAddressSpace — the annotation enum (live)

fetch’s targetAddressSpace option pre-declares the destination’s space. Valid values are exactly loopback | local | private | public (case-sensitive WebIDL enum IPAddressSpace — localhost, LOCAL are TypeErrors). Chromium enforces a match law: annotation must equal the destination’s actual space.

THE MATCH LAW (Chromium): targetAddressSpace must equal the destination’s real IP address space. Console truth: “Request had a target IP address space of `local` yet the resource is in address space `loopback`” — a mismatch block that no permission rescues. Why annotate at all: it earns the mixed-content exemption for known-local requests (https page → http local target) on engines that implement it — the exemption that keeps OpenDrones-style local links loadable.

§6Grant flows — the two working keys

Everything below is recorded from live grant-flip lanes (Playwright grantPermissions, which flips the same site permission the prompt sets).

User flow (the prompt): a gated request from your site fires Chrome's “Look for and connect to any device on your local network” prompt once per site; Allow persists in site settings (icon left of the URL). Deny → every subsequent gate read is a silent block; the site can detect via permissions.query state denied and link to settings — never re-prompt loops.
Automation flow (e2e): context.grantPermissions(['local-network-access'], { origin: 'https://your-site' }) → the LNA-gated lanes all open (measured: fetch 200, WS open, css load); permissions.query reads granted live. For local dev (Vite/webpack on localhost), note dev pages are loopback-origin: same-space requests are exempt — the wall only bites when the page origin is public.
THE REFUSED-LOOKALIKE: once granted (or on Firefox), the observable failure changes to connection refused — indistinguishable in page-JS from a block unless you read the console/netlog. CI lanes asserting “not blocked” on a machine with no listener manufacture false failures — assert the console line class, not just fetch resolution.

§7OpenDrones capstone — the base-station link, post-LNA

OpenDrones Mission Control is a public page that wants telemetry from a base station on the operator's machine/LAN. Post-156 that is exactly the gated scenario. The resilient link recipe, each lane live on this page.

Pre-flight board (live): query the permission → state chip; then one gated probe per transport (fetch/WS) with verdict chips; a denied state gets one calm settings link.
permission: … telemetry fetch: … telemetry WS: … fallback: mission-link relay (public origin) when local is denied
public page→permission probe→granted: direct ws://127.0.0.1 or LAN/denied: relay via public origin
Recipe: (1) feature-detect 'onpageswap' in window-style — here: permissions.query({name:'local-network-access'}) resolving at all = Chromium-family gate exists; (2) probe once per session, remember the verdict; (3) never assume FF/WK behavior parity — FF has no gate (their users' local links just work), WK users need the http→https fix (serve the base station over TLS or relay).

§9Method, falsifications & lane limits

Method. 6 probe generations, ~40 lanes: two plain-HTTP loopback origin pairs (127.0.0.1:8871→8872; localhost:3000→3001), a real public HTTPS origin (this site), a live hand-rolled RFC6455 WS server, Chromium 149 + Firefox 151 + WebKit 26.5 (Playwright builds, macOS). Verdicts from page-JS resolution + console capture + a server-side request log (the log is the receipt: blocked-by-permission requests NEVER reach it; granted ones do, with Origin + Sec-Fetch-Site cross-site).
Falsified this session (my own):
FALSIFIED“THE LOOPBACK PNA WALL (Chromium-only, 2026): a loopback page loading CSS from any other loopback origin is blocked” — the 11/13 CSSOM session's recorded law. Re-probed exactly (localhost:3000→3001): loads + applies on ALL three engines. The block that session actually hit was the public→loopback face of the same console wording — mis-scoped by origin. Corrected everywhere it shipped (cssom demo + MC row + RESEARCH.md).
FALSIFIED“WebSockets are not yet gated by LNA” (the Chrome blog's known-issues table, still live). Measured at 149: ws://127.0.0.1 from a public page → net::ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS; granted → open. The gate is LIVE for WS.
INSTRUMENTFirst-generation WS lanes measured against a dead port — every “blocked” verdict was connection-refused. A live server (or the console discriminator) is mandatory before recording gate laws.
INSTRUMENTgrantPermissions names are engine-specific (‘local-network-access’ worked on CfT; others may differ) — verify the grant actually flipped permissions.query state before asserting unblocked behavior.
Lane limits. Chromium face measured on a Playwright 149 build (no stable-channel Chrome installed on the bench; 149's surface is post-156 enforcement-by-default). The permission-prompt UI itself is human-hand (headless replaces it with grantPermissions). WebRTC/WebTransport gating unprobed this session (spec says planned; WS measured live). No Windows/Android lanes; no enterprise-policy lanes. “FF ignores targetAddressSpace” measured on 151 — check per release.
