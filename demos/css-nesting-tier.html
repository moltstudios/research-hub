The CSS Nesting Tier — &, the :is() specificity, and the tooling blindness

css-techniques · platform tier · Baseline 2023 (Chrome 120 / Firefox 117 / Safari 17.2) — CSS nesting is the first native alternative to a preprocessor. It looks like Sass, and it is not Sass: the & selector takes the maximum specificity of its parent list (the :is() rule), not the sum of a compiled chain, and a single #id in a parent list infects every branch. It also silently changes what & means in JavaScript selector APIs. Every law below is re-probed live in your browser — the chips are computed, not printed.

1 · Surface census — what ships, and under what name

THE FOUR-MEMBER SURFACE. CSS nesting ships as one selector feature (&) plus one CSSOM rule type (CSSNestedDeclarations). There is no CSS.Nesting namespace, no nestingRules flag, no constructor to feature-detect. Feature-detect with CSS.supports('selector(&)') — measured true on every engine that ships it. The CSSRule type constants do not include a nesting entry: CSSRule.NESTING_DECLARATIONS and CSSRule.NESTED_DECLARATIONS are both undefined, and CSSNestedDeclarations reports type === 0 — the same value as an unknown rule. Detect the class, never the constant.

2 · THE :is() LAW — the specificity of & is the maximum of its parent list

nesting shapemeasured specificitywhat a preprocessor emits
THE MAXIMUM, NOT THE SUM. & behaves like :is(): its specificity is the highest specificity present in the associated selector list — not the specificity of the branch that actually matched. Measured by brute force: a competitor rule with N extra classes was added before each nested rule; the nested rule beat every competitor up to a measured ceiling, and lost to the next one. That ceiling is the specificity.

Concretely, #a, b { & i { … } } compiles to :is(#a, b) i — specificity 1-0-1 — so it beats .foo i (0-1-1) even for the b branch, where #a is never used. Sass, by contrast, emits #a i and b i separately (1-0-1 and 0-0-1). Same source, different cascade.

3 · THE ID INFECTION — one #id poisons every sibling branch

control no ID in the parent list

infected an ID in the parent list

THE INFECTION LAW. Add #id to a parent selector list and the entire nested rule jumps to 1-0-x — the ID's specificity is applied to every branch of the list, including the class-only ones. Measured: .inf-id, #inj-id-never { & .kid { … } } produces a rule of specificity 1-1-0; the flat competitor .inf-id .kid (0-2-0) loses to it. In the control lane (no ID) the flat competitor wins the tie. The same infection happens one level down: .P { #pid, .sib { & .t { … } } } also measures 1-x-0.

THE NEVER-MATCHING BRANCH (the sharp edge): the ID in the demo (#inj-id-never) does not exist in the DOM — its branch never matches anything — and it still infects the class branch. Specificity is computed from the selector text, not from what matched.

THE PRACTICAL TRAP: adding an ID to a parent list "just to be safe" silently rewrites the specificity of every rule nested under it. In a design system, one #root in a shared list can outrank every utility class below it. This is the opposite of what most developers expect from a parent list.

4 · THE SASS DIVERGENCE — the same source, two different cascades

SAME SOURCE, DIFFERENT CASCADE. This lane writes the same rule twice — once nested, once in the flat form a preprocessor would emit — and measures which one wins. Measured outcomes:

· Parent list with an ID — native .sd-id, .sd-cls { & .kid } is 1-2-0; the preprocessor's flat .sd-id .kid is 1-1-1 and its .sd-cls .kid is 0-2-0. The native rule beats both flat rules. The .sd-cls branch, which should be a harmless 0-2-0, now inherits the ID.
· Parent list without an ID — native .sd-ctl { & .kid } is 0-2-0 and the flat .sd-ctl .kid is the same 0-2-0 — a tie, so the later rule wins (source order).
· Two-level nesting — .P { .m { & .t } } measures 0-3-0: each nesting level adds its own class, exactly like Sass. Depth is where native nesting and Sass agree.

THE RULE OF THUMB: nesting depth behaves like Sass; a parent selector list does not.

5 · THE TOOLING BLINDNESS — & in JavaScript is a scope root, not a CSS parent

expressionresultmeaning
THE SCOPE-ROOT LAW. document.querySelectorAll('& .k') does not throw and does not mean "the CSS parent". In a DOM selector API, & is parsed as the scope root — exactly equivalent to :scope. Measured: outer.querySelectorAll('& .k') and outer.querySelectorAll(':scope .k') return the identical element list; at document level, '& .k' ≡ ':root .k'. At the document root, querySelectorAll('&') returns the html element — one node, the root.

WHY IT BITES: the CSSOM hands you the nested selector verbatim: sheet.cssRules[0].cssRules[0].selectorText is literally "& .k". Any code that feeds a selectorText straight into querySelectorAll therefore resolves against the document root, not against the rule's parent — silently selecting the wrong elements, with no error. matches() is stricter: el.matches('& .k') returned false for the very element the rule targets, while el.matches(':scope .k') also returned false but el.matches(':root .k') returned true. Never feed a nested selectorText to a DOM selector API. Write the flat selector yourself, or use :scope.

6 · Syntax lanes — what parses, what dies, and what silently changes meaning

writtenmeansmeasured
THE RELAXED-SYNTAX LAW. Since the 2023 "relaxed syntax" change, a nested selector may omit &. But omitting it changes the meaning: .rel { span { … } } is a descendant selector (equivalent to .rel span), not a compound. To target the same element you must write &.self. Measured: &.self matched the element; the bare .self did not.

THE CONCATENATION LAW. Sass's &__child is not supported — .conc { &__child { … } } parsed but matched nothing (the whole nested rule was dropped, no error). Writing &element is also invalid (a type selector cannot precede a class in a compound); only element& is legal. Measured: &element → rule dropped; element& → matched the element.

THE INVALID-RULE LAW. An invalid nested selector kills only that nested rule — the parent rule and the sibling nested rules survive. Measured with & %invalid: the parent's own declarations still applied and the following & .valid still matched.

THE ORDER LAW. Declarations after a nested rule still win over it when specificity ties — .ord { color: A; & { color: B } } → B (later), but .ord { & { color: B } color: A } → A. The nested rule's position in the source is what counts, not whether it is "inside".

7 · The :hover footgun — :hover without & hits the child

Hover the child of the orange box:

hover me
THE DESCENDANT-HOVER LAW. .hv { :hover { … } } — with no & — compiles to .hv :hover, a descendant selector. Hovering a child therefore styles the child, not the parent you wrote the rule inside. Measured: hovering the child gave the child the nested rule's colour, while the parent's own :hover colour also applied (the parent is hovered too, because the pointer is inside it). The fix is one character: &:hover, which compiles to .hv:hover and measures only the parent.

This is the single most common native-nesting bug: you nest :hover inside a component, the hover state lands on a descendant, and the component's own hover affordance silently never fires.

8 · At-rules inside a nested rule — the map

at-ruleinside a nested ruleCSSOM typenote
THE AT-RULE MAP. @media, @supports, @container, @layer, @scope and @starting-style all nest cleanly and appear in the CSSOM as their own rule types (CSSMediaRule, CSSSupportsRule, CSSContainerRule, CSSLayerBlockRule, CSSScopeRule, CSSStartingStyleRule).

THE KEYFRAMES DROP (headline). @keyframes inside a style rule is silently discarded: the CSSOM contains no CSSKeyframesRule at all, the animation never runs (measured opacity constant at 1 across 5 samples), and no console error is emitted. The animation name still appears in animation-name, so the element looks configured but never animates. @keyframes must stay at the top level.

THE NESTED-DECLARATIONS ORDER LAW. When a rule mixes declarations and nested rules, the CSSOM splits it: declarations before the first nested rule stay on the parent CSSStyleRule, and everything after becomes a CSSNestedDeclarations child — including plain declarations. Measured .nd { color: A; @media screen { color: B } color: C } → parent style = A, children = [CSSMediaRule, CSSNestedDeclarations(C)], and the computed colour is C — the last declaration wins, exactly as if it were flat.

10 · Capstones — how this lands on real work

Molt component CSS without a preprocessor

Native nesting removes the Sass/PostCSS dependency for component styles. But the ID infection means a shared parent list like .card, #card is a trap — keep parent lists to one class per branch, or use :where() to zero the branches you don't want to win. The :hover footgun is the most common shipped bug: always write &:hover, never bare :hover.

OpenDrones the HUD state machine

A mission panel with armed / flying / failsafe states is exactly the shape nesting is good at: one &.flying / &:hover / &[data-link="los"] block per state, with the base declarations in the parent. The tooling blindness matters here: any test that reads selectorText off the CSSOM and feeds it to querySelectorAll will resolve against the document root. Use :scope or flat selectors in tests.

Sellable "CSS nesting audit"

A 2–3 hour client-site pass: (1) grep for bare :hover / :focus inside nested rules (the descendant bug), (2) grep for #id inside parent lists (the infection), (3) grep for &__ (dropped rules), (4) grep for @keyframes inside rules (dropped animations), (5) check every selectorText consumer in the JS.

Don't ship a preprocessor for nesting alone

Nesting is native now (Chrome 120 / Firefox 117 / Safari 17.2 — Baseline 2023). If you still need Sass for nesting, you are paying a build step for a feature the browser has shipped for three years — and inheriting Sass's specificity semantics, which differ from native in the exact way that bites the ID infection. Migrate the nesting, keep the preprocessor for the rest.

11 · THE SCOPE-PROXIMITY ORDER — where nesting meets @scope

contestwinnerlaw
THE ORDERED TRIAD. The cascade inside @scope is not specificity-then-order — it is specificity → scope proximity → source order. Measured, all three engines identical:

· Scoped vs unscoped, equal specificity → THE SCOPE WINS, regardless of source order. A scoped rule written first beat a flat rule written later; and a scoped rule written later also beat a flat rule written first. This is the opposite of the normal cascade, where the later rule wins the tie — and it is silent, so a scoped component rule will quietly outrank a global utility class of the same specificity.
· Scoped vs unscoped, DIFFERENT specificity → SPECIFICITY STILL WINS. A scoped .z (0-1-0) lost to a flat .z.z.z (0-3-0), and a scoped .t (0-1-0) lost to a flat #t7 (1-0-0). Proximity is a tiebreaker, not an override — it cannot beat specificity.
· Inner scope vs outer scope → THE INNER SCOPE WINS, again regardless of source order (the inner scope won even when it was written first and the outer last). That is the whole point of @scope: a nested component beats its own container.

PRACTICAL CONSEQUENCE: @scope + native nesting is the cleanest way to ship a component that must beat a global stylesheet — but you must know that the tie-break is proximity, so a scoped rule of the same specificity beats a flat one no matter where it sits in the file.

The specificity ladder was measured by discriminator brute force: for each nesting shape a competitor rule with N extra classes was injected before the nested rule, and the nested rule's colour read back; every competitor was verified with Element.matches() before its verdict was counted, so a competitor that failed to match could never inflate a ladder. Every law on this page re-probes live in the visitor's engine — the page is its own falsifier.

Method note (a bug this page caught). The first ladder implementation measured the competitor's specificity as a descendant chain (.p .c1 .c2) instead of a compound (.p.c1.c2). That made every competitor fail to match, and the ladder reported a flat "beat 8" for all shapes — a plausible-looking wrong answer. The fix was to verify every competitor with matches() and to assert the match before counting the verdict. Any specificity measurement that skips that assertion is measuring nothing.
