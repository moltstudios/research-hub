Programmatic Scrolling — the smooth-scroll tier

Every anchor link, scroll-to-error, chat auto-follow, skip-link and telemetry feed rides on three primitives: scrollIntoView(), CSS scroll-behavior and the scrollend event. This page measures them live in your browser: the three-engine duration split (WebKit ~150 ms fixed vs Chromium ~1 s for the same scroll), the scrollend grammar (Firefox never fires it for wheel), the interrupt laws, and the reduced-motion myth.

§2

The scrollend grammar — what fires it

THE SEQUENCE LAW: one scrollend per scroll sequence — and its grammar has edges the docs skip. Measured bench (3 engines): smooth programmatic = 1 · instant programmatic = 1 (yes, instant scrolls fire it too) · no-op scroll (already at target) = 0 events at all · keyboard End = 1 (after its own ~100–150 ms animation) · wheel = 1 per gesture on Chromium + WebKit, but Firefox fires ZERO scrollend for wheel scrolls — even with a 5-second settle. THE PAYLOAD SPLIT: the event is a plain Event in Chromium/WebKit but a UIEvent (with detail:0) in Firefox · bubbles:true, cancelable:false, composed:false · for the viewport it fires with target: document. On an element scroller it fires on the element with bubbles:false — it never reaches a document-level listener.

The body-ignore law — where scroll-behavior must live

THE PROPAGATION LAW: body { scroll-behavior: smooth } does nothing for the viewport — overflow propagates body→html, but scroll-behavior does not. Only html { scroll-behavior: smooth } governs window scrolling (measured 3/3: body-only = an instant 1-event jump, identical to no rule at all). §4

The negotiation — explicit behavior vs CSS, and the enum wall

THE OVERRIDE LAW: an explicit behavior:'instant' beats a live html{scroll-behavior:smooth} (3/3 — one scroll event, no animation) · behavior:'auto' follows the CSS (animated, 3/3) · scrollTop = x and scrollTo(x,y) also follow the CSS. THE ENUM WALL (engine split): scrollTo({behavior:'bogus'}) — WebKit and Firefox throw TypeError ("not a valid enum value"); Chromium silently accepts any string and treats it as auto. A typo'd behavior never errors on two-thirds of the traffic. THE CSS KEYWORD GAP: CSS.supports('scroll-behavior','instant') is false everywhere — the CSS grammar is only auto | smooth; instant exists only in the JS enum.

§5

The interrupt lab — the un-cancellable flight

THE INTERRUPT SPLIT (headline): fire an instant scrollTo mid-smooth-flight. Firefox cancels cleanly and lands exactly on the instant target (2 scrollends: the dead flight's + the jump's). WebKit cancels cleanly (1 scrollend, exact landing). Chromium does not fully cancel: the jump lands, then the dying animation's last frames carry it past your target by its in-flight velocity — measured +20 px (interrupt at 50 ms, slow) and +205 px past the requested 2 000 (interrupt at 300 ms, fast). THE WHEEL-ABSORB LAW: a trusted wheel during a programmatic flight is absorbed on Chromium + WebKit (the trajectory never dips; the flight wins) but cancels it on Firefox (dip measured, flight dead, page settles where the wheel left it). If your UI promises "user scroll cancels the auto-scroll", that promise is engine-dependent.

§6

The reduced-motion myth

THE MYTH, FALSIFIED (headline): the folklore says "browsers turn off smooth scrolling for prefers-reduced-motion: reduce users." No measured engine does — not for CSS scroll-behavior:smooth, and not for explicit behavior:'smooth': with the media feature emulated to reduce, the 3 000 px flight still animated at 883 ms (Chromium) · 201 ms (WebKit) · 684 ms (Firefox). The CSS spec permits UAs to ignore smooth — none of the three does. If you care, you must gate it yourself:

const reduce = matchMedia('(prefers-reduced-motion: reduce)').matches;
const behavior = reduce ? 'instant' : 'smooth';
el.scrollIntoView({ behavior, block: 'start' });

§7

The scrollIntoView geometry — block grammar, nearest, margin/padding

THE ALIGNMENT FORMULAS (universal, measured 3/3, viewport V, element height E, target offset T): start → T · center → T − (V−E)/2 · end → T + E − V · nearest → the minimal scroll: no-op if fully visible, end-align if the target is below, start-align if above — and for an element taller than the viewport, nearest resolves to start. No-arg scrollIntoView() = block:'start'; legacy booleans survive: true = start, false = end. THE MARGIN LAW: scroll-margin expands the target's box on both edges (start-align lands at T − m; end-align at T + E + m − V) and stacks additively with scroll-padding on the scroller (measured 400 → 350 → 310 for margin 50, +padding 40). Alignment targets the client box — a bordered scroller's border shifts every landing (the sticky tier's scroller-border law, scroll-side).

§8

The nested walk & the frame walk

THE ANCESTOR WALK: scrollIntoView scrolls every scroller in the chain — a target two boxes deep moves the inner box to align it AND walks the outer to reveal the inner (measured outer=1500 + inner=1600, instant and smooth, 3/3). THE FRAME WALK: a target inside an iframe that scrollIntoViews itself also scrolls the parent document to reveal the frame — same-origin: 3/3 engines. Cross-origin split (headline): Chromium + Firefox still walk the parent; WebKit does not (parent stayed at 0 with the child verifiably scrolled — measured with a postMessage ack from the child). A "scroll to my embedded widget" contract with a third-party frame silently fails on Safari.

The snap interplay — you cannot land off-snap

THE SNAP VICTORY: in a scroll-snap-type: y mandatory scroller, a programmatic scrollTo(420) (between the snap points) never lands at 420 — in the bench's 300-px panels it snapped to 300 with a single scroll event [300]; in this page's 180-px panels 420 snaps to 360. Smooth animates toward 420 and the snap correction re-lands snapped (2 scrollends on Chromium/Firefox, 1 on WebKit). The sub-pixel grammar — three engines, three roundings

THE ROUNDING SPLIT: scrollTo({top: 100.5}) — Chromium rounds half-up (→101, and three scrollBy(+0.5) calls accumulate +3), WebKit floors (→100, three +0.5 calls accumulate +0 — the half-pixels are eaten), Firefox rounds half-down (100.5→100 but 100.7→101). Same grammar on the root and on element scrollers. A pixel-exact "scroll exactly 0.5 px per tick" stepper moves at different speeds per engine.

§11

The surface census — clamps, ghosts & the non-standard survivor

Measured 3/3 unless noted: scrollTo(0, 99999) clamps to max (4 300 here) · negative → 0 · top:'0' string coerces silently · unknown dictionary options are ignored · window.scroll !== window.scrollTo (distinct function objects, both length 0) · legacy scrollTo(x, y) numbers still work · onscrollend setter exists on window + document. THE SURVIVOR: scrollIntoViewIfNeeded() — WebKit-born, non-standard — lives on in Chromium + WebKit, absent in Firefox. Its semantics measured: not visible → centers; fully visible → no-op; partially visible → minimal reveal (start-align, not center). THE RTL NEAREST SPLIT: in an RTL horizontal scroller, inline:'nearest' for an out-of-view target aligned the near edge on Chromium/Firefox (−3208) but scrolled 61 px further to the far edge on WebKit (−3269) — the only geometry lane that split.
