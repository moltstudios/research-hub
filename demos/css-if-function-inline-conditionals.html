The if() function: if/else logic inside CSS property values

CSS finally has a ternary operator. if() puts branching logic in the value of any declaration — driven by style queries on the same element, media queries, or feature queries — and it re-evaluates live as conditions change. No wrapper classes, no duplicated rules, no JavaScript.

01 · What it is

One function, three kinds of conditions, zero extra rules

if() takes a semicolon-separated list of condition : value; branches. Conditions are evaluated in order, and the first one that's true wins — its value becomes the value of the property. An optional else branch always matches and closes the chain.

/* three condition types — mix freely inside one if() */
color: if(
  style(--scheme: dark): #eeeeee;   /* style query on THIS element    */
  media(width < 700px): #111111;  /* media query                    */
  supports(color: lch(50% 0 0)): lch(50% 0 0); /* feature query        */
  else: #1c1b1f;                   /* always-true default            */
);

Before if()

Every conditional value meant a separate rule — a wrapper class, a media block, or a @supports fork — duplicated per property:

.card { padding: 20px; }
@media (width < 700px) {
  .card { padding: 14px; }
}

With if()

The branching lives where the value lives. One declaration, responsive by construction:

.card {
  padding: 20px;
  padding: if(media(width < 700px): 14px;
                else: 20px;);
}

Why it matters

Design tokens stop needing token-per-variant explosion. A component can carry its own variant logic inline — --variant: featured flips six properties with six one-line if()s, no cascade gymnastics.

02 · Syntax

Anatomy of a branch list

The five rules that matter

1. Condition and value are separated by a colon; branches are separated by semicolons (the last one is optional).

2. No space between if and ( — if (…) invalidates the whole declaration.

3. First true branch wins; evaluation stops there.

4. else always evaluates true — and short-circuits everything after it, whatever its position.

5. A single invalid branch doesn't kill the function — the parser skips to the next branch. Only if nothing matches does if() return the guaranteed-invalid value.

Valid, legal, and inadvisable

The parser is forgiving to a fault. These are all valid:

background-color: if(else: yellow);
background-image: if();        /* empty! */
background: if(
  else: none;                 /* else FIRST… */
  style(--a: 1): red;          /* …never evaluated */
);

An else in first position makes every later branch dead code. Useful for debugging (put a url("debug.png") branch in to prove a condition misfires), useless otherwise.

06 · supports() conditions

Inline feature queries — @supports moved into the value

Gradual enhancement used to cost a whole @supports block per property. With if(supports(...)) the fallback sits next to the enhancement, in the same declaration:

color: if(
  supports(color: lch(75% 0 0)): lch(75% 0 0);   /* modern color if available */
  else: rgb(185 185 185);                        /* srgb fallback */
);

/* selector support queries work too */
margin-top: if(supports(selector(:buffering)): 1em; else: initial;);

08 · Failure semantics

No match, no else → guaranteed-invalid, not a fallback

The IACVT trap

When no branch matches and there's no else, if() returns the guaranteed-invalid value. Inside a custom property that means the property behaves as unset — and any var() consuming it falls back:

--pill: if(style(--mode: a): "A";);  /* no else */
content: var(--pill, "—");      /* shows — unless --mode: a */
var() fallback test
resolved content → (waiting)

Flip --mode on the chip with the buttons — only a produces output; everything else (including unset) hits the var() fallback.

Per-branch graceful degradation

One malformed branch doesn't invalidate the function — that branch is skipped and evaluation continues. This is per-branch IACVT, kinder than most CSS failure modes:

color: if(
  style(--t: 1): not-a-color;   /* skipped */
  style(--t: 1): rebeccapurple; /* used! */
  else: gray;
);

Contrast with var(), where one bad substitution poisons the declaration. if() quarantines failures to the branch.

09 · The fallback rule

if() does not degrade gracefully — the cascade does

This is the one production rule to burn in: a browser without if() drops the entire declaration (it's an unknown function). There is no internal fallback. You provide one with a static declaration on the line above — the classic cascade pattern, same move as var() fallbacks:

.thing {
  background: #f4f2ee;  /* 1. static value every browser parses */
  background: if(style(--mode: neon): linear-gradient(90deg, #7df9c8, #7ec8ff);
               else: #f4f2ee;);  /* 2. upgrade for if() browsers */
}

Both boxes below set --mode: neon. The left one has the static fallback line; the right one doesn't. In an if() browser they look identical — in every other browser (current Firefox, stable Safari), the right one loses its background entirely:

10 · Composition

if() inside shorthands — branch only the part that changes

An if() can sit inside a larger value, so the parts that never change stay out of the branches. The badge below toggles its border style while width and color stay static:

badge with composed border 
.badge {
  border: 3px yellow if(style(--dash: 1): dashed; else: solid;);
}

Nesting if() inside if() values is legal too — but at that point, consider whether a single @container style() block or an extra custom property would read better. if() rewards shallow logic.
