**THE TWO-COORDINATE LAW (headline #1):** `zoom` splits every measurement API into two coordinate systems. **Painted px** — `getBoundingClientRect()`, `IntersectionObserver`, hit-testing, `getComputedStyle().width` → **260**. **Layout px** — `clientWidth`/`offsetWidth`/`scrollWidth`/`scrollTop`, `getComputedStyle` of the *element* → **120/130/320/100px/130**. **THE FLOW LAW (headline #2):** `zoom` is **not** `transform: scale()` — it consumes **93 px** of flow for the same 200×80 painted box where `scale()` consumes **48 px**. Percentage layout is resolved in the parent's zoomed space, so the visible result is zoom-invariant. This is why zoom "just works" for responsive layouts and why the layout-px numbers are the ones that matter when you do the math.
**THE MULTIPLICATION LAW:** `zoom` does **not** inherit, but effective zoom **compounds** — 2 × 3 = 6. `currentCSSZoom` is **layout-derived**: an element with `display:none` reports **1** while its computed `zoom` is `"2"`. Read `currentCSSZoom` for truth, never the computed style.
**THE CHROME-150 SPLIT (headline #3):** `zoom` became **animatable in Chrome 150** — CfT 148 gives **0 animation objects** and the value snaps; **CfT 155 interpolates** (1.0664 → 1.1332 → 1.2 → 1.2664 → 1.3332 over 500 ms). **`CSS.supports('transition-property','zoom')` is `true` on BOTH** — the feature query reports the *grammar*, not the *engine's* animation capability, so it is a **grammar lie**. **THE VALIDATION LAW:** `zoom:0` / `0%` parse but compute to **1** — zoom never collapses (unlike `transform:scale(0)`, which does). `-1`, `-50%`, `NaN`, `Infinity`, `reset` are **dropped** → computed 1. `zoom:1e2` is valid → **100**. `calc(infinity)` computes the string `"infinity"` but Blink clamps the **used** value to **1,000,000**. `currentCSSZoom` is a **float32** — `1.7` reads back as `1.7000000476837158`.

**Extras:** zoom × scale compose **multiplicatively** (100 px → 600 px at zoom 2 + scale 3) · `scrollTop` is **layout px** (100 → 200 painted) · replaced elements scale by **natural size** (20×10 SVG → 40×20 painted, `offsetWidth` 20) · `position:fixed` descendants **ARE** zoomed in Blink · Typed OM `attributeStyleMap.set('zoom','1.25')` is accepted.

## 223 · Responsive Image Selection — the srcset/sizes tier: the ceil rule, the 100vw default, the preload match law [2026-10-25]
**MC:** `2086cf98-acd1-4a57-afc2-b57923ca0e13` · P3 · performance · demo `demos/responsive-image-selection-tier.html` (62,417 B, HTTP 200, byte-exact) + assets `demos/ri/` (4 JPEG renditions 22/60/114/177 KB + 1 AVIF 50 KB, 423 KB total) — **primary new entry**, zero prior coverage of the selection algorithm itself (grep srcset/sizes/currentSrc/`loading=lazy`/`<picture>` across 241 MC entries → only passing mentions inside the CWV row; the decode tier `7d843fba` and Priority Hints `205` cover the other halves). The HTML standard leaves the pick **implementation-defined** ("in an implementation-defined manner, choose one image source"), so everything below is measured on Chromium 155 (CfT).
**THE CEIL RULE (headline #1):** Chromium picks the **smallest candidate whose density is ≥ the DPR**, not the closest. Sweep (CDP `deviceScaleFactor`): DPR 1→1x · **1.25→2x** · 1.5→2x · 1.75→2x · 2→2x · 2.5→3x · 3→3x. The 1.25 case (Windows 125% scaling, 1.25× phones) buys the 2× file = **4× the pixels for +25% density**. The old spec wording ("highest density not greater than the desired") is dead — today's spec promises no pick at all. Fractional `1.5x` descriptors ARE accepted.
**THE SIZES OMISSION LAW (headline #2):** `sizes` is the only input that says how wide the image paints; omit it → source size = **100vw** → the largest candidate is "correct" and gets downloaded. Measured in the demo @1280 (a 50vw-wide image): with `sizes="50vw"` → w800 = **58.9 KB wire**; without `sizes` → w1600 = **173.0 KB wire** = **2.94× the bytes for the same pixels on screen**. Bytes scale with area, so the saving is (viewport / painted-width)².
**THE PRELOAD MATCH LAW (headline #3):** Chromium reuses a preloaded image only when the preload's `imagesrcset` + `imagesizes` resolve to the **same candidate** the img will pick. Matched → **1 request**; mismatched `imagesizes` → **2 requests** (preloaded file AND the img's own candidate); a plain `href` preload with no `imagesrcset` → **2 requests**. The classic "preload didn't help" = the preload preloading the wrong file.
**THE AUTO LAW (headline #4):** `sizes="auto"` resolves against the element's used width, but only if that width is known when the pick happens — Chromium races it against the **first layout**. Short page → correct file (measured **4/4** across a matrix: srcset in markup vs injected by script × in-viewport vs below-the-fold); long page → the pick lands before layout, the source size stays unresolved, every candidate's density goes infinite and the engine takes the **largest** file. The demo measured **both** outcomes with identical markup (local: the largest file; deployed page: the correct file) and the pick is **sticky** — re-setting the srcset or resizing does not revisit it. Eager images never allow auto-sizes → the 100vw rule (deterministic).
**THE ORDER LAW:** `<picture>` sources are a **priority list** — the first surviving source wins (`media` must match, `type` must be decodable), never the "best" one (measured: a matching source picks the 1600 px file with a 400 px file right below it); the `<img>`'s own `src` is the fallback and is **ignored** whenever a source wins → `img.src` ≠ `img.currentSrc`.
**THE PER-CANDIDATE INVALIDITY LAW:** a bad entry is dropped **alone**, the rest of the set survives (`1x` + `800w` → the 1× candidate WINS — the "mixing invalidates the whole srcset" folklore is false). `0w` → parse error, dropped, the other candidate still loads. `0x` → **not** an error: the spec wants "infinite natural dimensions" and Chromium clamps them to the LayoutUnit max — **measured naturalWidth = 33,554,431 px** (2^25−1). Duplicate density → the **first** wins.
**THE RESIZE LAW (upgrade, never downgrade):** shrink the window → the already-selected larger file stays (no re-download); grow it → the larger candidate is selected and a **second** file is downloaded (measured `sizes="50vw"`: 1280→w800, 600→w800, 1280→w800, 2000→w1200 (2nd request), 900→w1200).
**THE LAZY THRESHOLD:** a lazy image is fetched ~**1,200 px** before the viewport (measured; CDP 3G throttling did NOT move it; Chromium documents 1,250/2,500 px). **THE DECODE TRAP:** `await img.decode()` on an unloaded lazy image **never settles** (measured "STILL PENDING after 3 s") → the common `await decode(); classList.add('loaded')` pattern **deadlocks the page**; a broken source rejects with `EncodingError` ("The source image cannot be decoded").
**THE IDL SPLIT:** `img.src` reflects the **attribute** ("" when absent — it does NOT fall back to the document URL in current Chromium); `img.srcset`/`img.sizes` echo attribute strings (never the computed source size); `img.naturalWidth` is the **density-corrected** width (at DPR 2 the 800 px file reports 400). Only `img.currentSrc` tells the truth. **THE CSS LAW:** `image-set()` selects by **density only** — no `sizes`, no `media`, no `type` → a 300 px box at DPR 2 downloads the 800 px file (2.7× the pixels it needs).

## 224 · The Font Loading Tier — @font-face, document.fonts & font-display: the check() lie, the auto=block law, the metric-match recipe [2026-10-26]
**MC:** `763b5e68-89a5-4869-99d5-674c975768f2` · P3 · typography · demo `demos/font-loading-tier.html` (50,376 B, HTTP 200, byte-exact) + `demos/font-lab-iframe-child.html` (6,566 B — the phone-frame specimen) — **primary new entry**. The typography tier already had Variable Fonts, COLRv1, text-box-trim/edge and Local Font Access cataloged — the tier was missing its **loading** leg.
**THE CHECK() LIE (headline #1):** `document.fonts.check('16px "NoSuchFamilyXyz"')` → **true**. check() returns **false only** for a face that IS declared in the document and has not finished loading — it is a **negative detector**, not a readiness probe. Measured: unknown family → true · system font (Arial) → true · declared + pending → false · after load → true. It also **ignores weight and style**: after a 400-only face loads, `check('900 16px "Inter"')` → **true** (the browser synthesises the bold), so it can never warn about a missing weight. The classic guard `if (document.fonts.check('16px "Inter"')) { showStyledUI() }` passes even when the font was never declared.
**THE INTENT LAW (headline #2):** check() **never** initiates a download (measured **0 requests**); `load('16px "Family"')` **always** does (measured **1 request**) and resolves with the matching faces — and on an unknown family it resolves with an **empty array**, it does not reject.
**THE AUTO LAW (headline #3 — the big one):** the default `font-display: auto` is **not** swap. Measured on Chromium 155 with a 1.5 s artificial font delay, counting dark pixels in a PNG screenshot of the live page: **auto → 0 ink at 350 ms** (identical to `block` — the text is laid out with the fallback's metrics but **not painted** for up to 3 s). `block` → 0 ink at 350 ms. `swap` → 5 325 ink at 350 ms (fallback paints instantly). `fallback` → 5 325 ink at 350 ms, swaps at 1.5 s. **`optional` → 5 325 ink at 350 ms AND 5 325 ink at 2.4 s** — the font *arrived* at 1.5 s and the text **never changed**: optional is the only value with **no swap period**, i.e. the only one that can promise **zero** layout shift (at the price of possibly never showing the brand font). With a 4 s font, `fallback` gave up at its 3 s swap period and stayed on the fallback while `swap` (infinite swap period) still swapped at 4 s.
**THE SCALING LAW (headline #4):** **`size-adjust` multiplies the metric overrides too.** Measured: `size-adjust: 50%` + `ascent-override: 100%` on a 40 px font → final ascent **20 px**, not 40. Every recipe on the web that writes the target's ascent straight into the override is off by exactly the size-adjust factor. Corrected form: `size-adjust = targetWidth/fallbackWidth` · `ascent-override = (targetAscent/sizeAdjust)/fontSize` · `descent-override = (targetDescent/sizeAdjust)/fontSize` — **verified end-to-end**: adjusted fallback matched the target's width to **0.10 px** and its line box/ascent/descent to **0 px** (target 519.91 → adjusted 519.81 px at size-adjust 98.391 %, ascent-override 99.094 %, descent-override 25.409 %). Caveat the measurement exposes: the ratio is **string-dependent** (the same two fonts gave 96.6 % on one sample string and 98.4 % on another) → measure with a representative string or use fontkit/capstyle.
**THE READY LAW (headline #5):** `document.fonts.ready` is **one memoised promise object** — adding a face later does **not** re-arm it (measured `r3 === r1`). `await document.fonts.ready` after adding a face resolved in **0 ms** while that face's status was still `unloaded`. Await `face.load()` / `face.loaded` instead. Related: `document.fonts.clear()` removes **only** the JS-added faces — the CSS-connected faces survive (size 7 → 6, the @font-face families still present).
**THE TWO-EXCEPTION LAW:** a font failure is always **NetworkError** (404 / CORS / undecodable data URL — including valid-base64 garbage in a data URL) or **SyntaxError** (`The source provided ('…') could not be parsed as a value list.` for a malformed src — the *constructor* never throws, `load()` does; `Invalid font data in ArrayBuffer.` for a non-font buffer). The split is unintuitive: the same garbage is a NetworkError as a data URL and a SyntaxError as an ArrayBuffer.
**THE REQUEST LAWS:** `local()` first → the URL is **never requested** (0 bytes). `unicode-range` → the face is **not fetched** until a codepoint inside its range is actually rendered (0 requests → 1 request after a CJK char) — that is how subsetting becomes bytes. A **lying `format()`** hint is ignored (a WOFF2 declared `format('truetype')` still loads). A broken `@font-face` still costs a request + a console error on every page load; its status becomes `error` and check() returns false for it forever.
**THE SWAP-SHIFT LAW (capstone):** a font swap is a **LAYOUT** event, not a paint event. Measured in two 390 px phone frames (a real PerformanceObserver inside each): the **raw** Arial→Inter fallback moved the content below the headline **8 px** (CLS **0.01204**); the **metric-matched** fallback moved **0 px** (CLS **0.00000**). At 375 px: 12 px / CLS 0.01468 vs 0 px / 0.00000. Chrome's CLS formula (impact × distance fraction) means the same 8 px costs 4× more on a phone than on a desktop — measure the CLS, not the pixels.

**THE 8 HEADLINE ENGINE LAWS (all measured, all three engines identical):**
1. **THE `:is()` LAW — `&` SPECIFICITY IS THE MAXIMUM OF ITS PARENT LIST, NOT THE SUM.** `&` behaves like `:is()`: its specificity is the **highest** specificity in the parent list, not the specificity of the branch that actually matched. Measured by **discriminator brute force** (competitor rule with N extra classes injected *before* the nested rule; every competitor verified with `Element.matches()` before its verdict counted). Measured ladder: `.P { & .k }` → **0-2-0** · `.P { .m { & .k } }` → **0-3-0** · `.P { .m { .n { & .k } } }` → **0-4-0** · `#P, .P { & .k }` → **1-1-0** · `.P { & .k.k2 }` → **0-3-0** · `.P { & :is(.k) }` → **0-2-0** · `.P { & .k:not(.z) }` → **0-3-0** · `.P { &.self }` → **0-2-0**. Concretely `#a, b { & i { … } }` compiles to `:is(#a, b) i` = 1-0-1 and beats `.foo i` (0-1-1) **even for the `b` branch** where `#a` is never used; Sass emits `#a i` and `b i` separately (1-0-1 and 0-0-1). Same source, different cascade.
2. **THE ID INFECTION — one `#id` poisons every sibling branch.** `.inj-id, #inj-id-never { & .kid { … } }` → **1-1-0**, which BEATS the flat competitor `.inj-id .kid` (0-2-0). In the control lane (no ID) the flat competitor wins the tie. **THE SHARP EDGE: the ID in that demo does not exist in the DOM — its branch never matches anything — and it still infects.** Specificity is computed from the selector TEXT, not from what matched. Same infection one level down (`.P { #pid, .sib { & .t } }` → 1-x-0).
3. **THE SASS DIVERGENCE — depth agrees, list breadth does not.** Parent list **with** an ID → native wins both branches, the preprocessor's flat output loses (native ≠ Sass). Parent list **without** an ID → native ties the flat form 0-2-0 (later rule wins on order). Two-level nesting → native ties the flat form 0-3-0. **Rule of thumb: nesting DEPTH behaves like Sass; a PARENT SELECTOR LIST does not.**
4. **THE TOOLING BLINDNESS — `&` in JavaScript is a SCOPE ROOT, not the CSS parent.** `document.querySelectorAll('& .k')` does **not** throw and does **not** mean "the CSS parent" — in a DOM selector API `&` is parsed as the **scope root**, exactly equivalent to `:scope`. Measured with a DOM holding one `.tb-k` inside the parent and one outside: `'& .tb-k'` → **2** (= `:root .tb-k` = `:scope .tb-k`), while the flat `'.tb .tb-k'` → **1**. And `el.matches('& .k')` is **false** for the very element the rule targets, while `el.matches(':root .k')` is true. **Why it bites:** the CSSOM hands you the nested selector **verbatim** — `rule.cssRules[0].selectorText` is literally `"& .k"` — so any code that feeds a `selectorText` straight into `querySelectorAll` resolves against the **document root** and silently selects the wrong elements, with no error.
5. **THE DESCENDANT-HOVER LAW — the most common shipped bug.** `.hv { :hover { … } }` with no `&` compiles to `.hv :hover` — a **descendant** selector. Hovering a **child** styles the **child**, not the parent you wrote the rule inside; the parent's own `:hover` also applies because the pointer is inside it. The fix is one character: `&:hover`. Same trap for `:focus`, `:focus-visible`, `::before`, `::after`.
6. **THE CONCATENATION LAW — Sass's `&__child` is NOT supported.** `.conc { &__child { … } }` parsed and matched **nothing** — the nested rule was silently dropped, no error, no console warning. `&element` is **invalid** (a type selector cannot lead a compound); only `element&` is legal and it targets the **parent itself**. A bare type selector (`div { … }`) is a descendant, not the same element.
7. **THE KEYFRAMES DROP — `@keyframes` inside a style rule is SILENTLY DISCARDED.** The CSSOM contains **no** `CSSKeyframesRule` at all, the animation **never runs** (opacity constant at 1 across 5 samples) while the control `@keyframes` at top level animated normally, and **no console error** is emitted. The name still appears in `animation-name`, so the element looks configured but never animates. `@font-face` is dropped the same way.
8. **THE SCOPE-PROXIMITY TRIAD — where nesting meets `@scope`.** The cascade inside `@scope` is **specificity → scope proximity → source order**, not specificity-then-order. (a) Scoped vs unscoped at **equal** specificity → **the scope wins, regardless of source order** (measured in both directions: scoped-first beat flat-later, and scoped-later beat flat-first) — the opposite of the normal cascade, and silent. (b) Scoped vs unscoped at **different** specificity → **specificity still wins** (scoped `.z` 0-1-0 lost to flat `.z.z.z` 0-3-0; scoped `.t` 0-1-0 lost to flat `#sp7` 1-0-0) — proximity is a **tiebreaker**, not an override. (c) Inner scope vs outer scope → **the inner wins**, again regardless of source order.
**MORE ENGINE LAWS:** **THE CONSTANT GAP** — `CSSRule.NESTING_DECLARATIONS` and `CSSRule.NESTED_DECLARATIONS` are **both undefined**, and `CSSNestedDeclarations` reports `type === 0` (same value as an unknown rule); detect the **class**, never the constant; `CSSNestedDeclarations.prototype` = exactly `['style','constructor']` and it IS a `CSSRule` instance. **THE SURFACE** — one selector feature + one CSSOM rule type, no `CSS.Nesting` namespace and no constructor; feature-detect with `CSS.supports('selector(&)')`; `CSS.supports('selector(&div)')` is **false**, `CSS.supports('selector(div&)')` is **true**. **THE NESTED-DECLARATIONS ORDER LAW** — declarations before the first nested rule stay on the parent `CSSStyleRule`; everything after becomes a `CSSNestedDeclarations` child, including plain declarations; the computed colour is still the last one. **THE INVALID-RULE LAW** — an invalid nested selector kills **only that** rule; parent and siblings survive. **THE ORDER LAW** — a trailing declaration wins a tie against a nested rule (position in source counts, not "inside"). **THE AT-RULE MAP** — `@media` / `@supports` / `@container` / `@layer` / `@scope` / `@starting-style` all nest cleanly with their own CSSOM rule types; `@keyframes` + `@font-face` are the only two dropped. `:where(.q) & .k` contributes **zero** from the `:where()` branch → 0-2-0, so `:where()` is the tool for de-listing a branch without lifting the others.
