**THE TWO-COORDINATE LAW (headline #1):** `zoom` splits every measurement API into two coordinate systems. **Painted px** — `getBoundingClientRect()`, `IntersectionObserver`, hit-testing, `getComputedStyle().width` → **260**. **Layout px** — `clientWidth`/`offsetWidth`/`scrollWidth`/`scrollTop`, `getComputedStyle` of the *element* → **120/130/320/100px/130**. **THE FLOW LAW (headline #2):** `zoom` is **not** `transform: scale()` — it consumes **93 px** of flow for the same 200×80 painted box where `scale()` consumes **48 px**. Percentage layout is resolved in the parent's zoomed space, so the visible result is zoom-invariant. This is why zoom "just works" for responsive layouts and why the layout-px numbers are the ones that matter when you do the math.
**THE MULTIPLICATION LAW:** `zoom` does **not** inherit, but effective zoom **compounds** — 2 × 3 = 6. `currentCSSZoom` is **layout-derived**: an element with `display:none` reports **1** while its computed `zoom` is `"2"`. Read `currentCSSZoom` for truth, never the computed style.
**THE CHROME-150 SPLIT (headline #3):** `zoom` became **animatable in Chrome 150** — CfT 148 gives **0 animation objects** and the value snaps; **CfT 155 interpolates** (1.0664 → 1.1332 → 1.2 → 1.2664 → 1.3332 over 500 ms). **`CSS.supports('transition-property','zoom')` is `true` on BOTH** — the feature query reports the *grammar*, not the *engine's* animation capability, so it is a **grammar lie**. **THE VALIDATION LAW:** `zoom:0` / `0%` parse but compute to **1** — zoom never collapses (unlike `transform:scale(0)`, which does). `-1`, `-50%`, `NaN`, `Infinity`, `reset` are **dropped** → computed 1. `zoom:1e2` is valid → **100**. `calc(infinity)` computes the string `"infinity"` but Blink clamps the **used** value to **1,000,000**. `currentCSSZoom` is a **float32** — `1.7` reads back as `1.7000000476837158`.

**Extras:** zoom × scale compose **multiplicatively** (100 px → 600 px at zoom 2 + scale 3) · `scrollTop` is **layout px** (100 → 200 painted) · replaced elements scale by **natural size** (20×10 SVG → 40×20 painted, `offsetWidth` 20) · `position:fixed` descendants **ARE** zoomed in Blink · Typed OM `attributeStyleMap.set('zoom','1.25')` is accepted.

## 223 · Responsive Image Selection — the srcset/sizes tier: the ceil rule, the 100vw default, the preload match law [2026-10-25]
**MC:** `2086cf98-acd1-4a57-afc2-b57923ca0e13` · P3 · performance · demo `demos/responsive-image-selection-tier.html` (62,417 B, HTTP 200, byte-exact) + assets `demos/ri/` (4 JPEG renditions 22/60/114/177 KB + 1 AVIF 50 KB, 423 KB total) — **primary new entry**, zero prior coverage of the selection algorithm itself (grep srcset/sizes/currentSrc/`loading=lazy`/`<picture>` across 241 MC entries → only passing mentions inside the CWV row; the decode tier `7d843fba` and Priority Hints `205` cover the other halves). The HTML standard leaves the pick **implementation-defined** ("in an implementation-defined manner, choose one image source"), so everything below is measured on Chromium 155 (CfT).
**THE CEIL RULE (headline #1):** Chromium picks the **smallest candidate whose density is ≥ the DPR**, not the closest. Sweep (CDP `deviceScaleFactor`): DPR 1→1x · **1.25→2x** · 1.5→2x · 1.75→2x · 2→2x · 2.5→3x · 3→3x. The 1.25 case (Windows 125% scaling, 1.25× phones) buys the 2× file = **4× the pixels for +25% density**. The old spec wording ("highest density not greater than the desired") is dead — today's spec promises no pick at all. Fractional `1.5x` descriptors ARE accepted.
**THE SIZES OMISSION LAW (headline #2):** `sizes` is the only input that says how wide the image paints; omit it → source size = **100vw** → the largest candidate is "correct" and gets downloaded. Measured in the demo @1280 (a 50vw-wide image): with `sizes="50vw"` → w800 = **58.9 KB wire**; without `sizes` → w1600 = **173.0 KB wire** = **2.94× the bytes for the same pixels on screen**. Bytes scale with area, so the saving is (viewport / painted-width)².
**THE PRELOAD MATCH LAW (headline #3):** Chromium reuses a preloaded image only when the preload's `imagesrcset` + `imagesizes` resolve to the **same candidate** the img will pick. Matched → **1 request**; mismatched `imagesizes` → **2 requests** (preloaded file AND the img's own candidate); a plain `href` preload with no `imagesrcset` → **2 requests**. The classic "preload didn't help" = the preload preloading the wrong file.
**THE AUTO LAW (headline #4):** `sizes="auto"` resolves against the element's used width, but only if that width is known when the pick happens — Chromium races it against the **first layout**. Short page → correct file (measured **4/4** across a matrix: srcset in markup vs injected by script × in-viewport vs below-the-fold); long page → the pick lands before layout, the source size stays unresolved, every candidate's density goes infinite and the engine takes the **largest** file. The demo measured **both** outcomes with identical markup (local: the largest file; deployed page: the correct file) and the pick is **sticky** — re-setting the srcset or resizing does not revisit it. Eager images never allow auto-sizes → the 100vw rule (deterministic).
**THE ORDER LAW:** `<picture>` sources are a **priority list** — the first surviving source wins (`media` must match, `type` must be decodable), never the "best" one (measured: a matching source picks the 1600 px file with a 400 px file right below it); the `<img>`'s own `src` is the fallback and is **ignored** whenever a source wins → `img.src` ≠ `img.currentSrc`.
**THE PER-CANDIDATE INVALIDITY LAW:** a bad entry is dropped **alone**, the rest of the set survives (`1x` + `800w` → the 1× candidate WINS — the "mixing invalidates the whole srcset" folklore is false). `0w` → parse error, dropped, the other candidate still loads. `0x` → **not** an error: the spec wants "infinite natural dimensions" and Chromium clamps them to the LayoutUnit max — **measured naturalWidth = 33,554,431 px** (2^25−1). Duplicate density → the **first** wins.
**THE RESIZE LAW (upgrade, never downgrade):** shrink the window → the already-selected larger file stays (no re-download); grow it → the larger candidate is selected and a **second** file is downloaded (measured `sizes="50vw"`: 1280→w800, 600→w800, 1280→w800, 2000→w1200 (2nd request), 900→w1200).
**THE LAZY THRESHOLD:** a lazy image is fetched ~**1,200 px** before the viewport (measured; CDP 3G throttling did NOT move it; Chromium documents 1,250/2,500 px). **THE DECODE TRAP:** `await img.decode()` on an unloaded lazy image **never settles** (measured "STILL PENDING after 3 s") → the common `await decode(); classList.add('loaded')` pattern **deadlocks the page**; a broken source rejects with `EncodingError` ("The source image cannot be decoded").
**THE IDL SPLIT:** `img.src` reflects the **attribute** ("" when absent — it does NOT fall back to the document URL in current Chromium); `img.srcset`/`img.sizes` echo attribute strings (never the computed source size); `img.naturalWidth` is the **density-corrected** width (at DPR 2 the 800 px file reports 400). Only `img.currentSrc` tells the truth. **THE CSS LAW:** `image-set()` selects by **density only** — no `sizes`, no `media`, no `type` → a 300 px box at DPR 2 downloads the 800 px file (2.7× the pixels it needs).
