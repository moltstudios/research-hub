MediaDevices, getUserMedia & MediaStreamTrack — the camera tier, live-probed

Every camera, microphone and capture flow starts here. This page live-probes the engine contract on your browser: the privacy wall on device labels, the two-track constraint negotiation (bare = wish, exact = law), the track lifecycle truth (self-stop fires no ended), the capability wall (torch/zoom are device gifts, not API rights) and the ImageCapture holdout matrix. Capstones: an OpenDrones inspection camera and a Molt client photo booth.

§01The door — mediaDevices, secure context & the worker jail

The whole capture tier hangs off one object. It is absent (not denied) on insecure origins, and it never grew a worker story — capture is a main-thread privilege.

// The three doors that must ALL be open:
navigator.mediaDevices?.getUserMedia({ video: true, audio: true })  // door 1: object exists
// door 2: isSecureContext === true (http://localhost is a secure context; http://lan-ip is NOT)
// door 3: you are on the main thread — workers see navigator, but navigator.mediaDevices is undefined

§02enumerateDevices — the label privacy wall

Device ids enumerate freely; device labels are fingerprint-gated behind a granted capture permission. This is why your device picker must render after a permission (or you show "Camera 1, Camera 2" anonymously).

const pre = await navigator.mediaDevices.enumerateDevices(); // before ANY grant
pre[0].label === ""            // ← live-probed: labels sealed pre-permission
await navigator.mediaDevices.getUserMedia({ video: true });   // grant happens
const post = await navigator.mediaDevices.enumerateDevices();
post.find(d => d.kind === 'videoinput').label  // now "FaceTime HD Camera" / "Fake Device"

§03Constraint negotiation — bare value vs exact

The #1 copy-paste trap: a bare constraint value is an ideal — the engine silently falls back to whatever it has. Only { exact: … }` turns a wish into a law, and law-breaking rejects with OverconstrainedError naming the guilty constraint.

getUserMedia({ video: { width: 9999 } })            // RESOLVES — engine picks best fit (silent fallback)
getUserMedia({ video: { width: { exact: 9999 } } }) // REJECTS — OverconstrainedError, e.constraint === 'width'
getUserMedia({ video: { unicorn: { exact: 1 } } })  // live truth: unknown keys are IGNORED, not rejected
getUserMedia({ video: false, audio: false })        // live truth: TypeError "At least one of audio and video…"

§04applyConstraints — re-negotiating a LIVE track

Constraints are not just for construction. track.applyConstraints() re-negotiates a running track; an exact miss rejects but the track survives untouched. On an ended track it's InvalidStateError.

§05Track lifecycle — stop(), clone(), enabled vs muted

The engine truth most code gets wrong: stopping your own track fires no ended event (that event is for external death — device unplugged). enabled = false is silence/blackness, not release. clone() shares the source: stopping the original does not stop the clone.

track.stop()            // readyState → 'ended'; idempotent; NO 'ended' event for self-stop
track.enabled = false   // black frames / silent audio — camera indicator STAYS ON (not a release)
const t2 = track.clone() // new track id, same live source
track.stop(); t2.readyState // 'live' — the clone is an independent subscription

§06Stream anatomy — ids, active, addTrack

A MediaStream is a mutable bag of tracks with an ephemeral id. stream.active is derived: it flips false only when every track has ended.

§07The video element plumbing — srcObject

srcObject is the zero-copy path (no blob URL, no MIME negotiation). For unattended playback: autoplay muted playsinline — mobile engines refuse otherwise. Dimensions come from the track, at loadedmetadata.

§08ImageCapture — the Chromium holdout

takePhoto() goes through the device's still pipeline (real flash, full sensor resolution); grabFrame() returns an ImageBitmap of the live video. Firefox and Safari never shipped ImageCapture — the cross-browser still-frame path is drawImage(video) onto a canvas.

§09Permission tiers — query, denial & dismissal

Chromium exposes camera/microphone through the Permissions API; Firefox and Safari don't (feature-detect or try/catch). And the error taxonomy matters: NotAllowedError covers user-denial and policy-block — check the console for the policy tell.

§10The iframe policy wall

Default permissions-policy allowlist for camera is 'self': same-origin children capture freely, cross-origin children are hard-blocked (NotAllowedError + Permissions policy violation console error) unless the embedder adds allow="camera". Same wall as geolocation and fullscreen.

§11contentHint & getSupportedConstraints

contentHint tells the encoder what the track IS ('detail' for documents, 'motion' for games, 'speech' for voice) without changing capture. The static vocabulary — getSupportedConstraints() — is the API's full menu, but it says nothing about YOUR device: that's track.getCapabilities().

§12The capability wall — torch/zoom are device gifts

The API vocabulary lists torch, zoom, focusMode… but a device that lacks them rejects exact attempts with OverconstrainedError. Never render a torch button without reading getCapabilities() first — this is the honest-UI rule.
