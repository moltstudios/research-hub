Window Management API
the multi-monitor control-room tier

window.getScreenDetails() enumerates every display attached to the machine — the API behind multi-screen mission control, video walls and trade-show booths. Live-probed on Chrome for Testing 154 (macOS arm64): the four-door CDP grant no-op, the auto-deny headless prompt, the iframe activation wall, and the permission that no test harness can grant.

§01Capability surface — the one door

What the engine exposes before any permission is requested.

The API is a single method on Window: window.getScreenDetails(). The original Chromium 100–108 shape — navigator.windowManagement.getScreenDetails() — is gone from CfT 154: navigator.windowManagement is undefined. Older docs and half the tutorials still show the removed door. There is exactly one.

§02The permission — hyphen only, and it can't be granted by tests

permissions.query({ name: 'window-management' }) — the name contract, live.

The input name must be hyphenated. Underscore and camelCase throw TypeError at the Permissions boundary. Unlike Local Font Access (whose PermissionStatus.name reads back local_fonts with an underscore), the readback here matches the input verbatim.

THE CDP FALSIFICATION (probed this cron, engine truth): Chromium's CDP exposes four grant doors for permissions — Browser.grantPermissions scoped + unscoped (enum name windowManagement, accepted) and Browser.setPermission scoped + unscoped (descriptor name window-management, accepted). All four return success. None moves the needle. permissions.query stays prompt; the call still rejects. Bogus names DO throw (Unknown permission type / Invalid PermissionDescriptor name) — so the enum validation is live; the grant just doesn't land. The window-management permission lives in a browser-profile layer no automation protocol reaches. Your CI cannot green-test a granted state. Plan for it.

§05The iframe policy door — two walls, two messages

Same-origin vs cross-origin (no allow) vs cross-origin with allow="window-management". Children report via postMessage.

Default allowlist is self: same-origin iframes share the top-level permission state; cross-origin frames are policy-blocked — and the engine tells you which wall you hit. Policy denial reads NotAllowedError: Permission denied. But add allow="window-management" and the message changes to NotAllowedError: Transient activation is required to request permission. — the activation gate that iframes must pass before the prompt can even be requested. Two different walls, one enum value, distinguished only by message text.

Cross-origin child: GitHub Pages mirror (research-hub) in production; pass ?crossbase= for a local second origin (the localhost/127.0.0.1 trick). Child outcomes vary by context — headless auto-deny, headed pend, granted resolve — the chips classify what actually happened.

§06The placement misconception — positioning never needed this API

Live: window.open with far coordinates + moveTo from the opener.

The #1 misconception: "Window Management lets you place windows." It doesn't. It lets you see the screens. Placement is legacy: window.open(url, name, 'left=…,top=…,width=…,height=…') and opener-owned moveTo() work without any grant — always have. You only need the enumeration to know where to send them. (Popup blockers may still veto programmatic opens outside a gesture — the button below runs in-gesture.)

§07window.screen — the free tier and the fingerprint gate

The legacy Screen object already carries multi-monitor fields. Zero permission.

Prototype census, live: availLeft, availTop, isExtended, onchange — the first two are legacy-universal (they even exist on non-secure origins); isExtended (a boolean: "this machine has 2+ displays") is gated behind secure context and ships without any permission. That's the fingerprinting controversy in one property: it partitions users by hardware setup for free, and it's why Mozilla (anti-fingerprinting position, bug 1753149) and Apple have refused the whole API. getScreenDetails() itself is object-absent on non-secure origins (verified: about:blank, opaque origin, isSecureContext false → undefined).

§08The granted state — the live object contract

What resolves after a real user clicks "Allow". Spec-anchored; per-field verification requires a granted session (§02 explains why CI can't fake one).

ScreenDetails is a live EventTarget: screens (array of ScreenDetailed), currentScreen, events screenschange (a display was connected/disconnected) and currentscreenchange (the window moved/resized across displays). Re-query the same object instead of re-calling. ScreenDetailed extends the legacy fields with label (OS display name — "Built-in Retina Display", "DELL U2720Q"), devicePixelRatio, isInternal, isPrimary, and coordinate-space availLeft/availTop where screen N's origin is relative to the primary's top-left. Mirrored displays are excluded from screens (extended only). MDN's own open-per-screen example is the canonical placement recipe — combined with §06's truth: enumerate with the API, place with window.open.

const details = await window.getScreenDetails();        // after real "Allow"
details.addEventListener('screenschange', renderWall);  // hot-plug a display
for (const s of details.screens) {
  window.open('/hud', 'hud-' + s.label,
    `left=${s.availLeft},top=${s.availTop},width=${s.availWidth},height=${s.availHeight}`);
}

§10Capstone — OpenDrones control-room launcher

One click: request the screen map → render every display → deploy the HUD windows.

The use case: a flight-ops desktop runs 2–3 displays — telemetry wall, live map, comms. Today the crew drags windows into place every morning. With the API: request the map once (persistent grant), render the layout, deploy per-screen windows at exact coordinates with the right content preloaded. screenschange re-renders when a display is hot-plugged mid-mission. Single-screen fallback: the launcher degrades to window.screen + one centered window, honestly labeled.

no map requested

In-gesture getScreenDetails() → real prompt on a real display → grant → map. Headless/gate: honest auto-deny state, fallback ladder renders instead. Deploy opens one in-gesture popup per known screen (simulated HUD via about:blank + document.write — popup-blocker-safe inside the click).
