CSS zoom + Element.currentCSSZoom

layout-scaling tier · css-viewport-1 · Baseline 2024 / 2026 — zoom is the only CSS property that scales layout, not just paint. transform:scale() resizes pixels and leaves the flow alone; zoom changes the box, re-lays out its siblings, and multiplies down the ancestor chain. That makes it the right primitive for a client-site text-size control and a ground-station HUD legibility toggle — and the wrong primitive for everything else. 2 · THE FLOW LAW — zoom re-lays out, scale() does not

zoom: 2 takes real flow space

zoom

transform: scale(2) paints only

scale
THE LAW. Both boxes paint at the same pixel size, but only zoom moves the next sibling down: a zoomed block's painted height (80 px) is what the flow consumes, so the sibling starts at y = 88 instead of y = 48. A transform keeps the layout height at 40 px and the sibling starts at 48 — the box visually overflows its own space. Zoom changes the document's layout; scale changes the picture of it. That is the entire reason to choose one over the other.

3 · THE TWO-COORDINATE LAW — the DOM APIs split (headline)

APIvalue at zoom:2coordinate system
THE LAW. getBoundingClientRect(), IntersectionObserver rects and hit-testing report painted / screen pixels. clientWidth, offsetWidth, scrollWidth, getComputedStyle() lengths and ResizeObserver.contentRect report layout pixels (zoom already divided out). The exact identity, measured live: rect.width === offsetWidth × currentCSSZoom. Any measuring code that mixes the two is off by exactly the zoom factor — which is why a HUD that reads offsetHeight and a chart that reads getBoundingClientRect() disagree the moment you zoom.

4 · THE MULTIPLICATION LAW — nested zoom compounds

THE LAW. zoom does not inherit, but its effective value multiplies down the flat-tree chain: a zoom:3 child inside a zoom:2 parent paints at 6×, and a grandchild with no zoom of its own still reports currentCSSZoom === 6. The spec calls this effective zoom; Element.currentCSSZoom is the read-back for it. And it is layout-derived, not cascade-derived: an element with zoom:2; display:none computes zoom: "2" but reports currentCSSZoom === 1, because it has no layout.

5 · THE PERCENTAGE INVARIANCE LAW — percentages are zoom-proof

THE LAW. A percentage width always paints as that percentage of the containing block's painted width — the zoom factor cancels out of the result. What zoom changes is the computed length in layout coordinates: with a 400 px parent, width:50% computes to 200px at zoom 1, 100px at zoom 2 and 50px at zoom 4 — while the painted width stays 200 px in every case. Zooming a percentage-based grid therefore does not break the proportions; it changes the coordinate space your JS reads.

6 · THE CHROME-150 SPLIT — zoom became animatable

idle
THE LAW (measured on two engines). zoom is animatable from Chrome 150 (MDN BCD: is_animatable → Chrome 150, Firefox 126, Safari never). On Chrome for Testing 148 a transition: zoom produces zero animation objects and the value snaps to its final value; on Chrome for Testing 155 the same transition interpolates smoothly. Worse: CSS.supports('transition-property','zoom') returns true on both — the grammar accepts the property name even where the engine will not animate it. Never ship a zoom transition without measuring the mid-flight value; Safari never animates it at all, so every zoom transition needs a fallback or a feature gate.

The same split applies to @keyframes: Chrome 148 keeps the element at its from value for the whole duration and only lands on the end value at the end (no interpolation, no animation object), while Chrome 155 samples intermediate factors.

7 · The validation law — what survives the parser

THE LAW. zoom:0 and zoom:0% parse (CSSOM keeps them) but compute to 1 — the element renders at normal size and never collapses, unlike transform:scale(0) which collapses it to nothing. Negative values, NaN, Infinity and the non-standard reset keyword are dropped at computed-value time (computed = 1). Two surprises worth knowing: zoom:1e2 is valid (computes to 100), and an infinite or overflow-large factor is clamped by the engine's used value at 1,000,000 (a Blink-specific cap that is not in the spec).

8 · CSS ZOOM ≠ BROWSER ZOOM — the root-zoom lab

THE LAW. html { zoom: 2 } does not simulate Ctrl +/−. The inner viewport width and every media query stay at the real viewport (innerWidth unchanged, (min-width: 2000px) still false), and devicePixelRatio / visualViewport.scale are untouched — but descendant boxes are scaled, so a width:100vw child paints at 2× the viewport width and creates a real horizontal scrollbar (the probe below reports the live overflow for its own frame). Root-level zoom therefore needs an overflow guard; browser zoom needs none because the viewport itself shrinks.

  1. zoom is a layout operation; scale() is a paint operation. Pick by intent, never by habit.
  2. Two coordinate systems exist. rect/IO/hit-test = painted; client*/offset*/scroll*/gCS/RO = layout.
  3. Multiply by hand when you compare them: rect.width === offsetWidth × currentCSSZoom.
  4. Nested zoom compounds — read currentCSSZoom, never the authored zoom, when you need the effective factor.
  5. currentCSSZoom is layout-derived: a display:none element reports 1 no matter what its CSS says.
  6. Percentages are zoom-invariant in paint; only the computed length changes.
  7. Animating zoom is a Chrome-150+ feature — Safari never shipped it, Chrome 148 snaps. Gate on a measured mid-flight value.
  8. zoom:0 does not collapse the element — it computes to 1.
  9. Never zoom html: media queries and the viewport do not follow, so 100vw overflows.
  10. Zoom the component, not the page — a content wrapper keeps the chrome (nav, footer, sticky bars) in its own coordinate system.
