2 The Old Way vs. The New Way

Before :open, there were two approaches to styling open state — both with real downsides.

❌ Before: Attribute Selector + JS

  • [open] works on <details> and <dialog> only
  • <select> open state was invisible to CSS
  • <input type="date"> picker state was invisible to CSS
  • JS class toggling for <select> and pickers
  • Class can drift out of sync with real state
  • Failure point during hydration / race conditions
  • Two sources of truth: attribute/class + real state

✅ After: :open Pseudo-Class

  • One selector for all four element types
  • Works on <details>, <dialog>, <select>, <input> pickers
  • Always in sync — reads real semantic state from the browser
  • Zero JavaScript for purely visual state
  • Progressive enhancement: unsupported browsers ignore it safely
  • Composes with :has(), :not(), all combinators
  • One mental model, one code pattern
/* BEFORE — three different techniques, manually wired */
details[open] > summary { /* attribute selector — only works for details/dialog */ }
details.is-open > summary { /* JS class — redundant with [open] */ }
.select-wrapper.is-active select { /* JS class for select — no CSS hook existed */ }

// JS class toggling for select open state (the code :open deletes)
selectEl.addEventListener('focus', () => {
  selectEl.closest('.select-wrapper')?.classList.add('is-active');
});
selectEl.addEventListener('blur', () => {
  selectEl.closest('.select-wrapper')?.classList.remove('is-active');
});
// ↑ This was literally the only way to style a select's open state. Now it's gone.

/* AFTER — one selector, all elements, zero JS */
details:open > summary       { color: var(--accent); }
dialog:open                   { animation: pop 0.2s ease-out; }
select:open                   { border-color: var(--accent); }
input[type=color]:open        { box-shadow: 0 0 0 3px var(--accent-glow); }

3 Pure-CSS Accordion — <details> with :open

The classic use case. Click any accordion item — the summary, chevron, and border all react to the open state. No toggle event listener. No .is-open class. Pure CSS.

What is the :open pseudo-class? ▶
A CSS pseudo-class defined in Selectors Level 4 that matches any element currently in an open state — <details>, <dialog>, <select>, and picker <input>s. It reads the browser's internal semantic state, not a DOM attribute or JS class.
Which elements does :open match? ▶
<details> — while expanded.
<dialog> — while shown via show() or showModal().
<select> — while its dropdown picker is displayed.
<input type="color|date|datetime-local|time|month|week"> — while the native picker is visible.
How is :open different from [open]? ▶
[open] is an attribute selector — it only works on elements that reflect their state as an HTML attribute (<details> and <dialog>). :open is a pseudo-class that reads internal state directly, covering <select> and <input> pickers too. It's a strict superset: :open = [open] + select pickers + input pickers.
Does :open work with Popover API? ▶
No — use :popover-open for elements with the popover attribute. :open targets elements with open/closed states (details, dialog, select, inputs). :popover-open targets popover show/hide state. They're complementary, not overlapping.
Is there a :closed pseudo-class? ▶
No. The CSS Working Group rejected :closed because :not(:open) already covers it cleanly. The default styles you write for the closed state apply automatically when the element isn't open.

The entire CSS driving the accordion above:

details.accordion-item {
  border: 1px solid var(--border);
  border-radius: 8px;
  transition: border-color 0.2s;
}
details.accordion-item:open {
  border-color: var(--accent-glow); /* glow when open */
}
details.accordion-item:open summary {
  color: var(--accent);
  background: var(--accent-dim);
}
details.accordion-item:open summary .chevron {
  transform: rotate(90deg); /* rotate chevron on open */
  color: var(--accent);
}
/* The closed state is just the default — :not(:open) implied */

Entrance animations on <dialog> using :open — no toggle event listener, no requestAnimationFrame hack. The browser fires the animation the moment showModal() opens the dialog.

Note on exit animations: :open fires when the dialog opens, but there's no :closing pseudo-class yet. Exit animations on <dialog> still require the close event + setTimeout pattern (or the proposed Closed Watchers / transitions for dialog closing). :open handles the entrance; exit is a known gap.

5 Select Dropdown — Open-State Highlight + Parent Styling

This is where :open does something genuinely new — the [open] attribute selector could never touch <select>. Now you can react in CSS to the dropdown being expanded, and even style the parent <label> via :has(select:open).

The <label> border + background change when the <select> is open — that's label:has(select:open), a pattern that was simply impossible before.

/* Style the select itself when open */
select:open {
  border-color: var(--accent);
  box-shadow: 0 0 0 3px var(--accent-glow);
  background-color: var(--bg-elev);
  /* Flip the dropdown arrow to point up */
  background-image: url("data:image/svg+xml,…up-arrow…");
}

/* Style the PARENT label when the child select is open — was impossible before! */
label:has(select:open) {
  background: rgba(124, 92, 255, 0.05);
  border-color: var(--accent);
}

/* Body scroll lock when ANY select is open (advanced) */
html:has(select:open) {
  overflow: hidden;
}

6 Input Picker Styling — Date, Color, Time

Native pickers (type="date", type="color", etc.) now expose their open state to CSS. The card border + background react when the picker is visible — no focus/blur event juggling.

/* Style the picker card when its input is open */
.picker-card:has(input:open) {
  border-color: var(--accent);
  background: var(--accent-dim);
}

/* Style the input itself when its picker is showing */
input[type=date]:open,
input[type=color]:open,
input[type=time]:open,
input[type=datetime-local]:open {
  border-color: var(--accent);
  box-shadow: 0 0 0 3px var(--accent-glow);
}

/* Compose with :has() — style a sibling label */
label:has(+ input:open) {
  color: var(--accent);
  font-weight: 700;
}

7 :open + :has() Power Patterns

The real power of :open emerges when you compose it with :has(). These patterns were completely impossible in pure CSS before — they required mutation observers, framework bindings, or manual class toggling.

/* 1. Body scroll lock — one line replaces the JS toggle pattern */
html:has(dialog:open) { overflow: hidden; }

/* 2. Global "is anything open?" indicator */
body:has(:open) .status-bar { opacity: 1; }
body:not(:has(:open)) .status-bar { opacity: 0.5; }

/* 3. Summary label swap — "Expand" becomes "Close" */
details > summary::after { content: "Expand"; }
details:open > summary::after { content: "Close"; }

/* 4. Sibling hint — reveal when a details panel is open */
.hint { opacity: 0; transition: opacity 0.2s; }
details:open ~ .hint { opacity: 1; }

Progressive Enhancement — Safe Today

The best part: :open is safe to use right now, even before 100% support. Browsers that don't understand the selector simply ignore the rule. Your <details> still expands, your <dialog> still opens, your <select> still drops down — they just miss the extra styling.

/* Safe progressive enhancement pattern */

/* 1. Default styles — work everywhere */
summary { color: var(--text); }

/* 2. Enhanced styles — :open browsers only */
@supports selector(:open) {
  details:open summary {
    color: var(--accent);
    background: var(--accent-dim);
  }
}

/* 3. Legacy fallback — [open] attribute for older browsers */
@supports not selector(:open) {
  details[open] summary {
    color: var(--accent);
  }
}
Why no polyfill is needed: :open only adds visual polish. The underlying elements (<details>, <dialog>, <select>) have their own native open/close behavior that works in every browser. The pseudo-class just gives you a CSS hook for styling — if the browser doesn't support it, the element still works perfectly, it just doesn't get the enhanced styles.

Why Priority 3 (Not P1, Not P5)

Not P1 — :open enhances existing UI; it doesn't unlock fundamentally new capabilities like WebGPU or Container Queries do. Most sites function fine without it.

Not P5 — Baseline 2026 with ~96% support is ship-today territory. The patterns it enables (accordion styling, dialog animations, select highlight) are immediately useful for every client project. Far too impactful for low priority.

Yes P3 — Direct production use for every Molt client build (FAQs, modals, forms). Direct OpenDrones Mission Control use (telemetry panels, mission details). Composes with the existing P1/P2 CSS toolkit (:has(), Anchor Positioning, View Transitions). A high-impact enhancement primitive that deletes boilerplate JS from every project.
