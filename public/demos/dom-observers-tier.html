Why observers exist

Push vs pull — the death of the scroll-handler loop

The pre-observer pattern was pull: listen to scroll/resize events, then call getBoundingClientRect() on everything you cared about, every event, on the main thread. It thrashed layout, it missed changes that were not scroll-driven (element resized by content, DOM edits), and each library shipped its own loop. Observers invert it to push: you register interest once; the engine, which already computes layout and visibility for painting, tells you when a line was crossed — batched, coalesced, off your hot paths.

The contract every observer shares

  • Callback gets a batch — an array of records/entries, not one event per change. Design for N.
  • Initial notification always fires — observe() alone (no change yet) delivers current state. There is no "priming" hack needed.
  • Async by design — you observe results (layout, DOM state), never the causes. No event storm.
  • takeRecords() — drain the pending queue synchronously; drained entries never reach the callback.
  • unobserve(target) surgical · disconnect() nuclear (and re-observe() after disconnect works).

ResizeObserver · the famous error

"ResizeObserver loop…" — reproducing the error-tracker classic

Write the observed element's size inside the callback and you create a cycle: resize → notify → resize. The spec breaks the deadlock by processing elements deeper in the DOM each iteration; leftovers are deferred to the next frame and the engine fires a well-known ErrorEvent on window. It is a warning wearing an error's uniform — but it floods Sentry-style trackers because it arrives via window.onerror with the message below. Clipping is the truth, not the viewport: intersection is computed against the intersection of the root rect and every clipping ancestor between root and target. A target "in the viewport" but inside overflow:hidden is not intersecting. That is why IO replaces scroll math entirely — it already knows about every clip container.

takeRecords() — drained vs delivered

IO computes entries during rendering and delivers them at frame end — by the time your task runs again, the queue is empty. Probe: observe off-screen target, takeRecords after delivery → 0; the real crossing later → 1 callback. The deterministic flush proof lives in §11 (MutationObserver), where records queue at mutation time. IO's takeRecords matters in the same task as a geometry change — the flush-then-disconnect unmount pattern.

IntersectionObserver · the 2023+ addition

scrollMargin — pre-visibility firing inside scroll containers

rootMargin on an implicit root has a known blind spot: nested scroll containers clip targets, and expanding the viewport box doesn't help — the clip still wins. scrollMargin (Chrome/Edge 120+, Dec 2023; Chromium-only as of Sep 2026) grows the clipping rectangle of each scroll container between target and root. IntersectionObserver v2 — visibility, not geometry

trackVisibility + delay — "is it actually visible to a human"

v1 answers geometry ("does the rect overlap"). v2 adds trackVisibility: true + delay: the engine occlusion-checks the target (covered by other elements, tiny, or distorted away) and reports entry.isVisible. The notification rate is clamped to delay ≥ 100ms because the check is expensive. Chromium-only (Chrome 74+; Firefox & Safari have not shipped as of Sep 2026) — capability-gate it.

MutationObserver

The DOM change log — batching, microtasks & the ordering nobody expects

MO callbacks run BEFORE promise microtasks

HTML spec: "notify mutation observers" is step 1 of perform a microtask checkpoint — ahead of the promise job queue. Probe: mutate, then queue Promise.resolve().then(...). Expected order: sync → MO(n) → P1 → timeout.

observed order
—

Practical: an MO callback can run before .then chains that were queued by the very code making the mutation — cleanup/teardown order matters.

One task, five mutations → one batch

All mutations in the same task coalesce into one callback with one record each. Records carry type, target, addedNodes/removedNodes, attributeName, oldValue (only if you asked).

Mutations queue at mutation time; delivery waits for the microtask checkpoint. Call takeRecords() in the same task and the callback never fires — the flush-then-disconnect unmount pattern, proven live.
