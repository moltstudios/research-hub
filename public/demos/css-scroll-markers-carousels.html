CSS Scroll Markers & ::scroll-button()

Native carousels — pagination dots, prev/next buttons, keyboard arrows, screen-reader tablist semantics and auto-disabling state — generated by the browser from pure CSS (CSS Overflow Level 5, Chrome/Edge 135+). The navigation layer of the JS-carousel stack, deleted: no library, no hydration, no re-render bookkeeping — and it works with JavaScript disabled.

This engine hasn’t shipped CSS carousels (Firefox/Safari as of Aug 2026). The scrollers below degrade to plain scroll areas — exactly the zero-risk fallback described in §10. See probe results in the badges above.
The one-paragraph story: a scroll container (overflow:auto) can grow browser-generated buttons (::scroll-button(left|right|up|down)) that page 85% of the scroll area and auto-disable at the ends, and its children can grow markers (::scroll-marker) collected into a ::scroll-marker-group — real focusable elements that jump to their item, highlight via :target-current when in view or snapped, and read as a tablist with arrow-key navigation. Everything below is labs proving each claim live.

§3 · STATE PROOFS

Buttons page 85% · auto-disable · dots track position

Three claims you shouldn’t take on faith. Click Next page and watch the readout: with snap points, one click steps exactly one snap position; on a free scroller the raw step is 85% of the client width (proven in §6). Buttons disable themselves at each end, and every dot swap is CSS reacting to scroll position with zero JS:

Flight plancorridor + no-fly
Ground stationantenna heading
RecoveryRTL + catch net
Debrieftelemetry export
click a button → measuring…

Auto-disable is browser-enforced state: the generated button is a real button element — when no more scrolling is possible in its direction, the engine sets :disabled on it. No scroll handler computing scrollLeft === 0 ever again.

Why 85%, not 100%? A full-page jump would hide the continuity cue — the sliver of the next/previous item that tells users which direction they’re moving. 85% keeps ~15% overlap. On single-item snap carousels it effectively steps one slide; on multi-item scrollers it steps “almost a page”.
§4 · MARKER CONTENT LAB

Dots are content — accessible names are mandatory

A marker exists only when its content is non-none. What you put there is its accessible name: "" is a WCAG 4.1.2 violation (nameless control), a bare " " works but names nothing, and attr() pulls real names from markup. Compare two sibling carousels:

The text is visually hidden via text-indent overflow — name announced, dot shown. The production choice.

Marker ≠ item. Markers attach to points of interest, not necessarily every child. A 10-episode series wants 2 “Season” markers, not 10 dots; a gallery wants thumbnail markers. The marker is an in-page link — “which content does this jump to?” is the only question that determines its count. (See §11: phase markers on a 6-card deck.)
§5 · GROUP PLACEMENT & TAB ORDER

scroll-marker-group: before | after | none

The generated group is placed in tab order and layout order (not DOM structure). Toggle it and press Tab inside this card — with before, dots come before the scroller’s content; with after, they come after the buttons; with none, the group (and its tablist semantics) vanishes entirely:

group: after
Focus methen press Tab
Dots are one tab stoparrows move between them
Buttons followper group placement

Semantics you get for free: the group renders as tablist, each marker as a tab — one tab stop, arrow keys roam between markers (focusgroup behavior), screen readers announce position. The a11y rule baked into the spec: match visual order to tab order — dots displayed at the bottom of the carousel → use after.

§6 · DIRECTION MATRIX & THE RAW 85%

Four buttons, one 2-D scroller, no snap

Up to four ::scroll-button() per container — physical (left/right/up/down) and logical (inline-start/inline-end/block-start/block-end) arguments, plus * to style all. This scroller deliberately has no snap points, so clicking a button reveals the raw page step. Watch the readout: it should land near 85% of clientWidth per click:

(0,0)+X →+Y ↓ 560 × 400 canvas
click any arrow → scrollLeft 0 · scrollTop 0 · last step —

Vertical carousels work identically — the features are axis-agnostic (the OpenDrones log scroller in §11 is a y-axis example with up/down buttons).

§8 · COLUMN MARKERS

::column::scroll-marker — markers per column, not per item

Multicol content inside a scroller fragments into columns — and each column can grow a marker (::column::scroll-marker). The reading-pattern carousel: paginated text/cards where a dot = one column of content, no item-level structure required:

Sortie log — column 1: preflight checks, battery temps nominal, IMU cal OK…
Column 2: launch at 14:02, climb-out 4.2 m/s, wind 9 kt NW…
Column 3: survey grid 82% complete, gimbal −12° pitch…
Column 4: RTL triggered, catch net armed, landing 14:31…
Column 5: debrief notes, 3 retakes flagged, data offloaded…
Column 6: pack voltage 44.1V, cycle #214 logged…

The scroller is a column-width container — the browser fragments content, and each ::column fragment gets a marker. Square dots = column markers; same :target-current highlight.

§9 · BRING YOUR OWN LINKS

scroll-target-group: auto — real <a> tags as markers (Ch 140+)

The inverse of §2: instead of generating pseudo-markers, promote real markup. Any element containing <a href="#fragment"> links becomes a marker group when given scroll-target-group:auto; the links keep working as plain in-page navigation everywhere — including engines without carousel support. §10 · SHIP RULES & TRAPS

The fallback ladder, and the ways this bites

1 · It is a zero-risk enhancement

The unsupporting-engine experience is a plain scrollable area — content fully accessible via scroll/swipe/keyboard. There is no layout cliff, no broken state; you simply lose the buttons/dots affordance (or keep real-link navigation via §9). Never JS-gate the content itself.

2 · Gate styles, don’t gamble selectors

An unknown pseudo-element kills its whole selector list (same comma-death as :has()). Keep carousel styling in its own rules, or wrap with @supports:

@supports selector(::scroll-marker) { …carousel affordances… }

3 · Snap is optional but strongly recommended

Buttons and markers work without scroll-snap-type, but navigation lands mid-item and feels broken. With mandatory snapping, markers land on snapped positions cleanly.

4 · What CSS carousels can NOT do yet (Aug 2026)

  • No cyclical/infinite wrapping — end-of-list stops; the Chrome team lists wrap-around as future platform work. Infinite logo reels still need JS (or accept the finite UX).
  • No autoplay — no native auto-advance; scroll-driven animations can fake a progress indicator, but a true timed carousel still wants JS.
  • Firefox & Safari: not shipped — Chromium-only (~2/3 traffic). Cross-engine parity needs the §9 real-links pattern or a JS library fallback.
  • Marker count ≠ page count automatically — with multiple items visible, markers attach to items, not “pages”; several markers can read as :target-current at once. Model points of interest (§4), or snap one item per view.

5 · Positioning pattern

Generated controls are siblings inside the scroller — the documented layout is position:absolute + position-anchor to the carousel (anchor-name), with justify-self:anchor-center for centered dot rows. Anchor() resolves against the scrollport, so controls pin visually and never scroll away with content. Anchor positioning itself is near-universal (Chrome 125 / Firefox 147 / Safari 26).

Verdict

Priority 3 — adopt on Molt builds now as progressive enhancement; keep a JS-library escape hatch until Firefox/Safari ship.

  • The win: the entire carousel control layer — buttons, dots, active-state, keyboard, ARIA tablist, disabled states — becomes ~20 lines of CSS with zero JS, zero hydration, zero CLS. Accessible-by-default beats almost every hand-rolled or library carousel.
  • The constraint: Chromium-only (~2/3 of traffic). Content must never depend on it; controls are the enhancement.
  • The ladder: plain scroller everywhere → real-link markers (§9) where navigation must survive → generated buttons/markers (§2) where affordance is the cherry.
  • Pairs with: scroll-snap (base), anchor positioning (overlay placement), scroll-driven animations (progress indicators), scroll-state() queries (edge reveals), content alt-text syntax for names.
  • Watch: css-overflow-5 is actively growing — links/tabs group values are in the editor’s draft, and wrap-around scrolling is on the Chrome roadmap.
