Streams API — the missing pipe tier: pipeTo, pipeThrough, backpressure & TransformStream

Every transport we've cataloged — WebTransport, Web Serial, WebRTC data channels, fetch().body — hands you a ReadableStream. MediaRecorder, WebCodecs and OPFS accept them. But the stream itself — the reader protocol, desiredSize, pull cadence, pipeTo's four flags, tee() fork semantics, BYOB zero-copy reads, gzip on a pipe — was never cataloged as its own primitive. This is the pipe tier: the wire never drowns the UI, and a slow UI never blocks the wire.

1. The reader protocol — chunk, done, lock

A stream is a queue with a protocol: getReader() takes an exclusive lock, read() resolves {value, done} one chunk at a time, done:true is the end-of-stream sentinel (value then undefined). The producer side is a source (push via controller.enqueue, or pull on demand), the consumer side is a reader or a pipe. Everything else in this page is this loop with policy.

Live: a push source, read one-by-one

ready

The whole primitive

const src = new ReadableStream({
  start(c){ for(const x of [10,20,30]) c.enqueue(x); c.close(); },
});
const r = src.getReader();          // exclusive lock
await r.read();  // {value:10, done:false}
await r.read();  // {value:20, done:false}
await r.read();  // {value:30, done:false}
await r.read();  // {value:undefined, done:true}

One reader at a time — src.getReader() while locked throws TypeError. Cancellation flows upstream: r.cancel() invokes the source's cancel().

2. Anatomy: push vs pull, and the default HWM = 1

A source can push everything into the queue immediately (start() enqueues all), or produce on demand (pull() — called by the engine only while controller.desiredSize > 0). The dial is highWaterMark (HWM). Underspecified fact — live-falsified on Chromium 152: the engine primes HWM + 1 pull calls, not HWM (measured: default strategy → 2 pulls; HWM 8 → 9 pulls). You get one chunk more of look-ahead than the number you wrote.

Live: default vs HWM = 8

Pull-source that counts its pull() invocations. Nobody reads — we just open a reader once.

ready

Why pull() exists

new ReadableStream({
  async pull(c){
    const chunk = await produceOne();
    c.enqueue(chunk);
  },
}, { highWaterMark: 8 }); // or new CountQueuingStrategy({highWaterMark:8})

desiredSize = HWM − queued. The engine calls pull() only while desiredSize > 0 → the consumer's speed throttles the producer through the queue depth. Byte-sized sources use ByteLengthQueuingStrategy so the dial is bytes, not chunks. Default HWM when no strategy is passed: 1 (one chunk of look-ahead — plus Chromium's one settling pull).

Queue-growth rule: enqueue when desiredSize ≤ 0 still succeeds — HWM is advice to producers that check, enforced for pull() cadence and pipeTo, never a hard wall for push sources.

4. WritableStream — sinks, writers, and write() as the valve

A WritableStream wraps a sink (start/write/close/abort) with a queue of its own. getWriter() gives a writer whose write(chunk) promise resolves only when the queue drains past HWM — awaiting write() IS backpressure. writer.desiredSize mirrors the writable queue; it goes null once closed/errored.

Live: slow sink (60ms/write), HWM 2

The sink contract

const sink = new WritableStream({
  write(chunk, ctl){ return networkSend(chunk); },
  close(){ /* flush */ },
  abort(reason){ /* tear down */ },
}, { highWaterMark: 2 });

const w = sink.getWriter();
for (const c of chunks) await w.write(c);
// write() pends when queue ≥ 2 → producer throttled
await w.close();   // calls sink.close()

Every OPFS createWritable(), MediaRecorder-adjacent sink and pipeTo destination in our other entries is exactly this shape.

5. pipeTo — the engine-written pump loop

readable.pipeTo(writable) is the manual while(read()) write() loop, written by the engine: error-aware, lock-managing, and — the part hand-rolled loops always forget — backpressure-correct in both directions (it reads again only after the sink's write promise settles).

ready
pipeTo locks BOTH streams for its duration — a second getReader() on either throws. The manual loop is for when you must interleave (progress, sampling, UI ticks); otherwise pipe.

6. TransformStream & pipeThrough — chunk boundaries are lies

A TransformStream is a writable glued to a readable with your transform(chunk, controller) in between. The number-one streaming bug is assuming producer chunk boundaries mean anything — network chunks split mid-line, mid-number, mid-token. A correct transform carries a residual buffer and only emits complete units.

Live: NDJSON line parser vs adversarial cuts

Input: 5 JSON records, pre-split at hostile offsets (mid-number, mid-brace, 1-byte chunk). Naive transform (parse each chunk) vs buffered parser.

ready

The buffered line transform

function lines(){
  let buf = '';
  return new TransformStream({
    transform(chunk, c){
      buf += chunk;
      let i;
      while ((i = buf.indexOf('\n')) >= 0){
        c.enqueue(buf.slice(0, i)); buf = buf.slice(i+1);
      }
    },
    flush(c){ if (buf) c.enqueue(buf); },
  });
}
src.pipeThrough(new TextDecoderStream())
   .pipeThrough(lines())
   .pipeTo(sink);

TextDecoderStream / TextEncoderStream are transforms too — UTF-8 with streaming multibyte sequences handled.

8. tee() — one wire, two consumers, two independent buffers

stream.tee() forks into two branch streams with independent queues: a fast reader doesn't wait on a slow one — instead the slow branch's queue grows. Cancellation is two-key: cancelling one branch keeps the source alive for the other; the source's cancel() fires only when both branches cancel.

The traps: tee() has no flow control between branches — branch B's unread queue buffers everything branch A consumes (tee a 4K video wire to a slow analytics lane and you've built a memory leak with a spec badge). And on Chromium 152, a branch reader's cancel() promise never settles while the sibling still holds data (live-falsified above) — the cancel still takes effect, but awaiting it hangs: fire-and-forget branch cancels or cancel via AbortSignal-wired pipeTo.

9. Locks & async iteration — for await, break-cancels, and from()

Streams are single-consumer. for await (const chunk of stream) (via values()/Symbol.asyncIterator) is sugar over a reader: it locks the stream, and — the falsified-in-the-lab part — break cancels the source. Also probed live: ReadableStream.from(), the static that wraps any async iterable — Firefox shipped it (117), Safari 27 will, Chrome has NOT shipped it (even in 152): a rare Firefox-first inverted holdout.

10. Errors & the three prevent* flags — the pipeTo wiring table

Defaults on pipeTo(dest, opts): source closes → dest closes (preventClose); source errors → dest aborts (preventAbort); dest errors → source cancels (preventCancel). Errors do not silently vanish — the pipe promise rejects and the paired stream is torn down. In a pipeThrough chain, a failing transform errors everything downstream.

11. Byte streams & BYOB — bring your own buffer, zero-copy

Construct with new ReadableStream({type:'bytes'}) (or get fetch().body, already a byte stream) and you may take a getReader({mode:'byob'}): you allocate the buffer, the engine fills it — no per-read allocation. Live-probed traps: the view you pass is detached/transferred (your old reference dies); the returned value is a fresh view on YOUR backing store; and tee()'d branches are not byte streams — BYOB readers throw on them.

Live: default reader vs BYOB on a byte stream

ready

BYOB loop

const res = await fetch(url);         // res.body.type === 'bytes'
const rd = res.body.getReader({ mode:'byob' });
let buf = new Uint8Array(4096);
while (true){
  const { value, done } = await rd.read(buf.subarray(0, 512));
  if (done) break;
  consume(value);      // view into YOUR buffer
  // ⚠ original view detached after each read (transferred)
}

Safari got byte streams/BYOB only in 26.4 (Mar 2026) — cross-engine BYOB is 5 months old. WebView-less sinks: OPFS writable.write() accepts the same views.

Gotcha wall (all live-probed on this page)

  • Default HWM is 1 — and Chromium primes HWM+1 pull calls (2 at default, 9 at HWM 8).
  • Push sources can enqueue past HWM — it's advice, not a wall.
  • pipeTo locks both streams; getReader() on either → TypeError.
  • for-await…break cancels the source (upstream cancel() fires).
  • tee() branches buffer independently — slow branch = memory leak.
  • Chromium: tee-branch reader.cancel() promise pends forever — never await it.
  • BYOB detaches your view per read; teed branches refuse BYOB.
  • desiredSize goes null on closed/errored — guard your gauges.
  • Chunk boundaries are meaningless — always carry a residual buffer.
  • CompressionStream accepts only gzip/deflate/deflate-raw (no zstd).

When NOT to pipe

  • Data fits in memory and isn't arriving incrementally → array + loop. Pipes cost locking ceremony for nothing.
  • You need random access / re-reads → streams are forward-once (tee before two passes, or buffer via OPFS).
  • Multiple live consumers with flow control → tee() is wrong; build a fan-out TransformStream with per-child HWM.
  • Safari 26.x + async iteration → gate values(), fall back to reader loop (the loop is the universal subset — every engine since 2015).
  • Streaming fetch upload bodies (duplex:'half') — Chromium-only; keep blob uploads for Safari/FF.
