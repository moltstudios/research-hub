WebRTC Transport Internals: getStats(), ICE candidates & the DataChannel

Our catalog had the WebRTC pipeline — getUserMedia → RTCPeerConnection → MediaRecorder → WebCodecs. It had zero coverage of the transport: the getStats() report, the ICE candidate types, the candidate-pair state machine, the DataChannel options grammar.

That is the tier every production WebRTC app eventually needs and almost nobody writes down. getStats() is the only place a browser will tell you which network path your drone video is actually taking — and it is a strange object: map-like, but not a Map; a snapshot, but not a snapshot.

Everything below is measured in your browser, in this page, right now. Nothing is quoted from documentation.

Chromium 155 · Brave 154 · WebKit 26.5 · 8 probe suites · measured 2026-10-28 · all lanes re-run in this visitor's browser on load

1 · The specimen — build a real peer connection and read its stats

Two RTCPeerConnection objects in this one page, signalling over an in-process channel — a genuine ICE negotiation, a genuine DTLS handshake, a genuine SCTP association. No server, no signalling server, no stub. Then getStats() on the result.

—
THE REPORT LAW (headline #1). await pc.getStats() resolves an RTCStatsReport. It is map-like but it is not a Map:
  • report instanceof Map → false; report instanceof RTCStatsReport → true
  • Object.keys(report).length → 0 — the entries are internal slots, not own properties
  • JSON.stringify(report) → "{}" — it serializes to an empty object
  • structuredClone(report) → DataCloneError
  • but report.size, .get(), .has(), .keys(), .values(), .entries(), .forEach() and [...report] all work
The consequence: JSON.stringify(report) is not a way to ship stats to your server, and Object.keys(report) is not a way to enumerate them. Use [...report.values()].

2 · The graph — the report is a graph, and it traverses by string id

A stats report is not a flat list. It is a directed graph whose edges are string ids: a candidate-pair points at a local-candidate, a remote-candidate and a transport; the transport points back at the selected pair. report.get(id) is how you walk it.

—

—

THE GRAPH LAW (headline #2). report.get(pair.localCandidateId) returns the live candidate object — it resolves. Same for remoteCandidateId and transportId. And the transport carries the reverse edge: transport.selectedCandidatePairId → report.get(…) → the same pair back. The graph is bidirectionally traversable, which means you can answer "which path am I on?" from any node.

The stats-ID prefix map

Every stats object has an id, and the ids are prefixed by type — a convention, not a spec guarantee, but a stable one across all three engines we probed:

THE PREFIX IS A CONVENTION, NOT A CONTRACT. The prefixes are stable in Chromium 155, Brave 154 and WebKit 26.5, and they are genuinely useful as a debugging aid (id.startsWith('CP') → "candidate pair"). But no specification requires them, and the certificate id is a 97-character hex fingerprint that does not fit the pattern at all. Never parse an id to learn its type — read stat.type. The prefix map is a reader's shortcut, not an API.
THE PRIORITY-PRECISION LAW (headline #3). The candidate-pair priority is a 64-bit unsigned integer, and it does not fit in a JavaScript number: the measured value was 9079290933572287000, and Number.isSafeInteger(priority) is false. The candidate priorities underneath it (2113937151, 2113939711) are safe integers. If you compute a pair priority yourself, you must use BigInt — the naive (min << 32) + 2*min + 2*max in plain numbers silently loses the low bits.

3 · The redaction asymmetry — the address you want is the one that is blank

Chromium redacts host candidates behind mDNS (xxxx.local) by default. The raw ICE candidate string still carries the .local name. But what does the stats object carry?

—

THE REDACTION ASYMMETRY LAW (headline #4) — THE HEADLINE LAW OF THIS TIER. In Chromium 155 and Brave 154, a host candidate's stats address is the empty string — the real IP is gone — while a srflx candidate (obtained via STUN) carries its full public IP in the clear. Measured on this machine:
host address: "" ip: "" · srflx address: "71.75.146.97" ip: "71.75.146.97"
The privacy control (mDNS for LAN addresses) does not apply to the address you learned from the internet — the one address a client would consider sensitive. Any "show the operator their public IP" UI built on host candidates shows nothing; built on srflx candidates it shows the public IP in cleartext.
THE ENGINE SPLIT — WEBKIT DOES NOT HAVE THE ip KEY AT ALL. WebKit 26.5's local-candidate stats object carries address (typed null, not "") and no ip property and no networkType property whatsoever — verified by key-set diff, not by eyeballing values. Chromium carries address, ip and networkType. So the three ways of reading a candidate address across engines:
  • Chromium: candidate.address → "" (redacted) — the key EXISTS, the value is empty
  • WebKit: candidate.address → null — the key EXISTS, the value is null
  • both: candidate.ip → Chromium only. WebKit: the property is absent → undefined
candidate.address ?? candidate.ip does NOT work as a fallback chain: in Chromium "" is not nullish, so the ?? never falls through — you get the empty string. Use candidate.ip || candidate.address || 'redacted', or better, check the property's presence.
THE CANDIDATE-TYPE SPECTRUM. The candidateType field is the single most useful discriminator in the report and it has exactly four values: host (a local interface address), srflx (a server-reflexive address learned from STUN), prflx (peer-reflexive, discovered by connectivity checks) and relay (a TURN relay). relay is the only type that survives a symmetric NAT — if your operator's field tablet is behind a corporate NAT and the connection never reaches connected, the missing piece is a TURN server and a relay candidate. candidateType is your one-line diagnostic.
THE CANDIDATE-LAW — host is not automatically best. On this LAN, the negotiated pair was a host↔host pair with priority 2113937151, while the local srflx candidate carried the higher priority 2113939711 (1677729535 in the raw SDP form) — the pair's priority is a function of both ends, not a copy of either. Rank pairs, not candidates.

4 · The selector grammar — what getStats() will and will not filter on

You do not have to take the whole report. getStats(selector) narrows it to one track's subtree. But the selector's type is enforced strictly, and the error is a TypeError that fires only when you await it.

—
THE SELECTOR LAW (headline #5). The selector must be a MediaStreamTrack — nothing else. getStats(sender) where sender is an RTCRtpSender rejects with TypeError: … parameter 1 is not of type 'MediaStreamTrack', even though RTCRtpSender is the object you actually hold. Use sender.track.
The nastier part: the call does not throw synchronously — pc.getStats('bogus') returns a rejected promise, so the try/catch must be around the await, not around the call. And getStats(null) is legal and returns the full report — null is the documented "no filter" value, so a variable that happens to be null silently gives you everything.
THE SUBSET LAW. A track-scoped report is a strict subset of the unfiltered one (every key in the scoped report is present in the full report), and it drops the two connection-level objects: peer-connection and data-channel. Everything about the transport — the candidate pair, the candidates, the transport itself, the certificates, the codec — stays. *If you are reading data-channel counters, you must use the unfiltered report.* A data channel is not a track.

5 · The DataChannel grammar — the rules the options object enforces

The data channel is the cheapest high-frequency channel you can put between a ground station and a browser. Its options object has four fields and about six rules, several of which are enforced with errors you would not expect.

The negotiated-id sweep — a fresh connection per id, so no collision is possible

THE MUTUAL-EXCLUSION LAW (headline #6). maxRetransmits and maxPacketLifeTime are mutually exclusive: setting both rejects with TypeError: RTCDataChannel cannot have both max retransmits and max lifetime. (WebKit words it differently — Cannot set both maxPacketLifeTime and maxRetransmits — which is the same rule.) Pick one reliability model per channel. For drone telemetry you want {ordered:false, maxRetransmits:0}: unordered, no retransmits, latest-state-wins.
THE ZERO-MEANS-INFINITE LAW. maxRetransmits: 0 and maxPacketLifeTime: 0 both mean "no limit", not "no retransmits" and "no lifetime". An omitted option reads back as null; an explicit 0 reads back as 0. The difference matters: {maxRetransmits: 0} is a *real* zero (unreliable), but {maxPacketLifeTime: 0} is *unlimited lifetime*. Getting this backwards turns an unreliable telemetry channel into a reliable one that retransmits forever.
THE DUPLICATE-ID LAW (headline #7) — an OperationError, not a TypeError. Creating a second negotiated data channel with an id already in use on the same connection fails with OperationError: RTCDataChannel creation failed — a runtime error with no detail at all, and the same generic message for several unrelated causes. This is the worst error surface in the tier: the message tells you nothing, and the same string covers "duplicate id", "odd id in a specific configuration", and other internal failures. The id ceiling is a separate, clearer error: TypeError: RTCDataChannel cannot have id > 65534.
THE ID CEILING. The negotiated id range is 0 – 65534 inclusive. 65535 → TypeError: … cannot have id > 65534. 65536 → a different error, from the WebIDL converter: Failed to read the 'id' property … Value is outside the 'unsigned short' value range. Two different layers, two different messages — the WebIDL range check fires first, then the spec's own ceiling. And negotiated:true without an id rejects: RTCDataChannel must have id set if negotiated is true.
THE AUTO-ID LAW. A non-negotiated channel gets its id assigned asynchronously during SCTP association — dc.id reads null until the channel opens. Reading dc.id right after createDataChannel() is a race, and the common workaround (assign your own even id with negotiated:true) skips the SCTP negotiation entirely — which is why negotiated:true requires an id.

6 · The oversize law — the one that loses telemetry silently

SCTP has a maximum message size. pc.sctp.maxMessageSize tells you what it is. What happens when you exceed it is not the same in every engine — and one of them does not tell you at all.

—
THE OVERSIZE DIVERGENCE (headline #8) — THE HEADLINE LAW OF THIS TIER. Send a message one byte larger than maxMessageSize and the two engine families behave completely differently:

Chromium 155 / Brave 154 → TypeError: Failed to execute 'send' on 'RTCDataChannel': Trying to send message larger than max-message-size. Loud, synchronous, and the channel survives — a subsequent small send still works.

WebKit 26.5 → send() does not throw. It fires an error event on the channel, and then the data channel is destroyed: readyState goes to "closed", every subsequent send() throws InvalidStateError: The object is in an invalid state, and the data-channel stats object disappears from the report entirely. The page also logs an uncaught Error sending binary data through RTCDataChannel. — and that uncaught error bypasses both window.onerror and window.addEventListener('error'), so only a global error handler or an error tracker ever sees it.
WHAT THIS MEANS IN PRODUCTION. A telemetry frame that crosses the SCTP limit kills the channel in Safari but only fails one message in Chrome. In WebKit the telemetry link does not throw at the call site and does not survive — the pilot sees a frozen map and the code has no error to catch. If your OpenDrones telemetry frames can exceed the limit (a large video chunk, a burst of buffered positions), you need a frame-size guard before send() in every engine, plus an onerror handler and a readyState check on the recovery path. Neither engine tells you the size limit for free — read pc.sctp.maxMessageSize and enforce it yourself.

7 · The configuration window — when you may change the rules mid-flight

pc.setConfiguration() lets you change the ICE servers, the transport policy and the candidate pool. The spec places a narrow window on when you may call it — and the failure is an InvalidModificationError with a message that never says when.

—
—
THE CONFIGURATION WINDOW LAW (headline #9). setConfiguration() succeeds before the first offer is created and fails with InvalidModificationError: Attempted to modify the PeerConnection's configuration in an unsupported way once a negotiation is in flight. Concretely, measured:
before createOffer iceCandidatePoolSize: 4 accepted, reads back 4
during have-local-offer iceCandidatePoolSize: 4 accepted, reads back 4
after setLocalDescription iceCandidatePoolSize: 2 → InvalidModificationError, reads back 0
The message names no state and no field. Practical rule: apply every configuration change before the first offer, and treat the connection's ICE server list as immutable for its lifetime. A mid-flight TURN-server change — the single most common production need — requires a new peer connection.
THE RESTART-ICE LAW. pc.restartIce() never throws and never changes anything visible on its own: after calling it, pc.localDescription.sdp was byte-identical and the ICE ufrag had not changed. The ufrag only changes when you then create and apply a new offer — and the new offer carries a different ufrag than the connection's current description. So restartIce() is a flag, not an action: call it, then renegotiate. Calling it and waiting for something to happen produces a connection that looks healthy and never re-ices.
THE NEGOTIATION-NEEDED LAW. pc.onnegotiationneeded fires once when you add a data channel to a fresh connection — measured exactly 1 fire. It is the correct trigger for the "polite/impolite" perfect-negotiation pattern, and it is the only signal that a new transceiver needs an offer.

8 · The candidate-pair state machine — the "why is my call not connecting" table

The candidate-pair stats object carries a state field whose values are exactly the ICE connectivity-check states. It is the most diagnostic single field in the whole tier.

THE PAIR-STATE LAW (headline #10). candidate-pair.state ∈ frozen · waiting · in-progress · failed · succeeded · disconnected. Only succeeded means bytes are flowing. The neighbouring fields tell you why it is not:
nominated — this pair is the one ICE selected (only the nominated pair carries your media) · requestsSent / responsesReceived — connectivity-check counters · packetsSent / packetsReceived — real traffic · currentRoundTripTime / totalRoundTripTime — the latency numbers.
A pair stuck in waiting with zero responses means your STUN server is unreachable or your candidate is blocked — not "the network is slow". A pair in failed with a relay candidate present means the TURN relay is refusing.
THE readable LAW (headline #11) — A DOCUMENTED FIELD THAT DOES NOT EXIST. MDN's candidate-pair dictionary lists both writable and readable as booleans describing whether the pair can carry traffic in each direction. Measured by key-set diff in three engines:
Chromium 155 writable present · readable ABSENT
Brave 154 writable present · readable ABSENT
WebKit 26.5 writable ABSENT · readable ABSENT
So the one-way health signal MDN offers is unusable in every engine we measured — in WebKit neither direction is reported. The code that reads pair.readable gets undefined in Chromium and WebKit, and the very common idiom pair.writable !== pair.readable evaluates true !== undefined → true, i.e. it reports a fault on a perfectly healthy connection. This is exactly the false "CANNOT RECEIVE" verdict the link monitor below showed before it was fixed — a real bug this research caught in its own capstone code. Use the packet counters instead: packetsReceived > 0 and packetsSent > 0 are present in every engine and mean what you want.
THE TRANSPORT-IS-THE-HEARTBEAT LAW. The transport stats object is the one to watch for a live connection: iceState, dtlsState, selectedCandidatePairId, selectedCandidatePairChanges (how many times ICE has re-picked a path — a rising counter is the classic sign of a flaky network), dtlsCipher, srtpCipher, bytesSent / bytesReceived. iceRole is "controlling" or "controlled" — in the perfect-negotiation pattern, the polite peer is the controlled one.
Note the shape split: transport.selectedCandidatePairChanges and transport.selectedCandidatePairId are present in all three engines, but transport.sctpState — which the spec defines and which would tell you whether the data channel's SCTP association is up — is absent everywhere we measured. Read the SCTP state from pc.sctp.state instead.

9 · The snapshot law — a report is a photograph, not a window

A stats report looks live. It is not. Every call to getStats() returns a fresh snapshot, and the objects inside are frozen: mutating one does nothing, and the next report is unaffected.

—
THE SNAPSHOT LAW (headline #12). Writing to a stats object (pair.packetsSent = 999999) succeeds silently — the property is writable — but the value does not survive: the next getStats() returns the engine's real number, and the old report's own object still reads 999999 in memory. The stats objects are plain writable JS objects that the engine replaces wholesale on every call. Never cache a stats object across a getStats() boundary — and never write to one, even to "fix up" a value for a chart. Read, copy out, re-read.
THE TIMESTAMP LAW. Every object in one report shares one timestamp — measured: exactly one distinct value across all 9–12 entries, in milliseconds since the epoch as a float (e.g. 1793225121078.864). Note the precision: this is not performance.now(), it is not monotonic, and it is not comparable across two reports taken far apart. Compute deltas from your own clock; use the stats timestamp only to label a sample.
THE COST LAW. getStats() is cheap: six consecutive calls measured 0.5, 0, 0, 0, 0, 0.1 ms. Polling it at 1 Hz (or even 4 Hz) on a ground-station dashboard costs nothing measurable. The expensive thing in the tier is not the report, it is the ICE candidate pool — leave iceCandidatePoolSize at 0 unless you have measured a benefit.

10 · The candidate-constructor grammar

You can build an RTCIceCandidate yourself — useful for tests, for synthetic candidates, and for parsing. It validates more than you would expect, and less than you would expect, in opposite directions.

THE SDP-MID-OR-INDEX LAW (headline #13). The constructor requires exactly one of sdpMid or sdpMLineIndex. With neither, it rejects with TypeError: sdpMid and sdpMLineIndex are both null. With sdpMLineIndex alone it works and toJSON() reports sdpMid: "" — so the two fields are not interchangeable: a candidate parsed from a line-index-only session will not round-trip through the mid-keyed form.
THE NO-VALIDATION LAW. The constructor does not validate the candidate string at all. new RTCIceCandidate({candidate:'not-a-candidate', sdpMid:'0'}) constructs successfully and toJSON() faithfully returns 'not-a-candidate'. Unknown dictionary members are silently ignored. The constructor is a container, not a parser — it will happily hold garbage that later blows up at addIceCandidate() time with OperationError: Error processing ICE candidate.
THE PARSED-FIELDS LAW. The constructor does parse the candidate line into typed fields: type ("host"), protocol ("udp"), component ("rtp"), foundation ("1"), priority (2130706431), port, tcpType, relatedAddress, relatedPort, relayProtocol. The url property reads null for a candidate with no url field. But the raw string is always preserved verbatim in .candidate — so you can always fall back to parsing it yourself.

11 · OpenDrones Mission Control — the telemetry health monitor

The capstone. Everything above, assembled into the thing a drone operator actually needs: a live panel that reads the connection's own stats and tells the operator, in one line, whether the link is good — and the code is shipped here, runnable in this page.

—

The production pattern

// OpenDrones — the link-health monitor. Reads the transport, classifies the path,
// and enforces the SCTP frame limit BEFORE the send that would kill the channel.
const MAX_FRAME = pc.sctp?.maxMessageSize ?? 262144;   // read it; don't assume

function classify(rep) {
  const transport = [...rep.values()].find(s => s.type === 'transport');
  const pair = transport
    ? rep.get(transport.selectedCandidatePairId) : null;
  if (!pair) return { ok: false, why: 'no candidate pair yet' };

  // THE PATH — the only place the browser tells you how you are connected.
  const local  = rep.get(pair.localCandidateId);
  const remote = rep.get(pair.remoteCandidateId);
  const path = local?.candidateType === 'relay' ? 'TURN relay'
             : local?.candidateType === 'srflx' ? 'STUN (server-reflexive)'
             : 'direct (host)';

  // THE HEALTH — one-way health from the PACKET COUNTERS, not from `readable`
  // (which MDN documents and no engine ships).
  const rx = pair.packetsReceived || 0, tx = pair.packetsSent || 0;
  const oneWay = rx > 0 && tx === 0 ? 'cannot send'
               : tx > 0 && rx === 0 ? 'cannot receive'
               : (tx > 0 && rx > 0) ? 'bidirectional' : 'idle';

  return {
    ok: pair.state === 'succeeded' && pair.nominated,
    path, oneWay,
    rtt: pair.currentRoundTripTime,
    kind: transport.iceState,             // 'connected' | 'checking' | ...
    switched: transport.selectedCandidatePairChanges,  // rising = flaky link
  };
}

// THE GUARD — the law that stops Safari losing the channel silently.
function sendFrame(dc, buf) {
  if (dc.readyState !== 'open') return false;     // WebKit closes after an oversize
  if (buf.byteLength > MAX_FRAME) return false; // never let the engine decide
  try { dc.send(buf); return true; }
  catch { return false; }
}
WHY THIS IS A SELLABLE LINE ITEM. "Is my drone link actually healthy, and what path is it taking?" is the first question every operator asks and the last one most dashboards answer well. The browser already knows the answer — the ICE candidate type, the selected pair, the round-trip time, the packet counters, the cipher in use — and none of it is on the wire. getStats() is a free, zero-instrumentation, server-free link telemetry panel, and it is the only way to tell a pilot "you are on a TURN relay through Frankfurt, which is why the video is late" without a server-side log.
THE MOLT PATTERN — the same monitor, as a client-site deliverable. Every Molt client running a live WebRTC support widget, a video consult, or a remote-screen-share session has the same blind spot: their users report "it's laggy" and the dashboard shows nothing. The same classify(rep) function, wired to the widget's own connection, turns that into a one-line answer the support team can read. A "live-session link health panel" is a 3–4 hour deliverable per client site.

12 · The ship checklist

FIFTEEN RULES. Every one of them was measured above. The five that would have cost you a production incident:
  1. Enforce the SCTP frame limit yourself — read pc.sctp.maxMessageSize, guard before send(). Safari destroys the channel on an oversize; Chrome does not.
  2. Never read the candidate address from host candidates — Chromium blanks it, WebKit nulls it, and a srflx candidate will hand you the public IP in cleartext anyway.
  3. Apply every setConfiguration() before the first offer — afterwards it throws InvalidModificationError and you cannot change the ICE servers for the life of the connection.
  4. Use getStats(track), not getStats(sender) — the sender is the object you hold and it is rejected by the type check.
  5. Never read candidate-pair.readable — MDN documents it and no engine ships it; the idiom pair.writable !== pair.readable reports a fault on a healthy connection. Use packetsSent / packetsReceived.
