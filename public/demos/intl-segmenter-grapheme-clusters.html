1 · Surface census — three prototype members, three granularities

Intl.Segmenter is a constructor taking (locales, {granularity, localeMatcher}). Its prototype carries exactly constructor · resolvedOptions · segment — three members. segment(str) does not return an array: it returns a Segments object (prototype: containing), which is iterable and lazy. Every item is a plain object with exactly three enumerable keys — segment · index · input — plus isWordLike at word granularity.

const g = new Intl.Segmenter(undefined, { granularity: 'grapheme' });
g.resolvedOptions()                       // { locale: 'en-US', granularity: 'grapheme' }
[...g.segment('👨‍👩‍👧‍👦')]                  // [{ segment:'👨‍👩‍👧‍👦', index:0, input:'👨‍👩‍👧‍👦' }]
g.segment('Drone 👨‍👩‍👧‍👦 ok').containing(9) // { segment:'👨‍👩‍👧‍👦', index:6, input:… }
THE LAZY-OBJECT LAW. Segments is not an array — no .map, no .length, no .filter. Spread it or use Array.from(). And because every item carries a reference to the entire original string in .input, holding one segment of a 5 MB log line pins all 5 MB until the item is collected.

2 · THE THREE COUNTS — paste anything below

Bars are proportional to the string length in each unit. The gap between the green bar (graphemes — what a human sees) and the grey bar (code units — what .length returns) is exactly the class of bug this tier exists to kill.

THE ORPHANING LAW. A JS string is UTF-16 code units. Every emoji above is wider than one unit, so s.slice(0,n) can cut a surrogate pair in half and render \ud83d as tofu. Spreading with [...s] is not a fix: it yields code points, and a ZWJ family, a flag, or a skin-tone sequence is several code points joined by invisible joiners. Only Intl.Segmenter gives you the boundary a human would draw.

4 · The truncation lab — three strategies, same sentence

THE TRUNCATION LAW. slice(0,N) cuts code units, [...s].slice(0,N) cuts code points — both are wrong, in different ways. Code-unit truncation on 🛩️🛩️🛩️ returns a literal lone surrogate (U+1F6ED + orphan). Code-point truncation on the same string returns 3 whole planes but still breaks a skin-tone or flag. Grapheme truncation is the only strategy that is correct for all three unit systems at once.
// ✅ correct at every layer
const seg = new Intl.Segmenter(undefined, { granularity: 'grapheme' });
const truncate = (s, n) => {
  const parts = Array.from(seg.segment(s));
  return parts.length <= n ? s : parts.slice(0, n).map(p => p.segment).join('') + '…';
};

5 · NO \X — why regex cannot replace this

Other regex engines (PCRE, Rust regex, .NET, Oniguruma) all expose an \X "extended grapheme cluster" escape. JavaScript does not — it raises SyntaxError: Invalid regular expression: /\X/gu: Invalid escape at parse time, so the usual workaround fails before it runs. The available Unicode property escapes are per-code point, which is the wrong axis:

AttemptResult on 👨‍👩‍👧‍👦Verdict

THE SINGLE-SOURCE LAW. In JavaScript there is exactly one built-in grapheme algorithm — Intl.Segmenter (UAX #29, Unicode 15.1+ data). Every hand-rolled emoji-regex workaround is a slower, less correct reimplementation of it. Reach for the API.

Japanese, Chinese and Thai do not delimit words with spaces, so .split(' '), indexOf()-based highlighting and word-count UI are all wrong there by construction. granularity:'word' gives locale-aware boundaries from CLDR data — and every item carries isWordLike so you can separate real words from punctuation without a regex.

[...new Intl.Segmenter('en', { granularity:'word' }).segment("drone's flight-path!")]
// The(true) ' (false) drone's(true) ' (false) flight(true) - (false) path(true) ! (false)
THE HIGHLIGHT LAW. Every segment item carries a code-unit index, so search-result highlighting is a first-class job: slice input.slice(index, index + segment.length) and you can never split a cluster. That single fact removes the entire class of "highlighting breaks Korean/Jamo" bugs.

7 · SENTENCE granularity + the pager

granularity:'sentence' uses CLDR sentence-break rules, so abbreviations survive: Dr. and No. do not end a sentence the way a .split(/[.!?]/) does. Pairs with isWordLike for "summarise this log entry" pipelines — the exact shape of an OpenDrones incident timeline.

8 · Segments.containing(index) — caret → grapheme

Click any character position in the bar below to ask the engine which grapheme owns that code-unit index. This is the primitive behind correct caret movement, arrow-key stepping and "delete the character" in a text editor — it is the Intl.Segmenter answer to Selection.modify() on mobile.

THE INDEX LAW. containing() takes a code-unit index (same space as .length and .slice), not a code-point or grapheme index. Mixing the three is the most common way to get an off-by-emoji caret. It never throws on an out-of-range index — it returns the last segment.

9 · Throughput + the line granularity probe

Segmentation is linear and fast enough for every keystroke — the object is lazy, so segmenting 200 KB of telemetry to render one truncated label costs microseconds. Cache the Segmenter instance: constructing one per call re-does locale resolution, which is the expensive part.

THE GRANULARITY TRAP. There is talk of a granularity:'line' for UAX #14 line breaking, but it is not universally available — live-probed here it throws RangeError: Value line out of range for Intl.Segmenter options property granularity, and it is absent from MDN's compat data. Wrap it in try/catch and fall back to word + your own line-break regex. Never ship code that assumes it exists.
