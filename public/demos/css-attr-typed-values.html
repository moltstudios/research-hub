CSS attr() Typed Values — the Markup Becomes the API

For two decades attr() could only whisper strings into content. The redesign (Chrome 133, Feb 2025) lets it parse attributes into numbers, lengths, angles, percentages, colors, custom-idents — in any property, inside calc(), with var()-style fallbacks. Structural data in, visual design out, zero JavaScript.

01

The two-decade wait, and why it ended

attr() with types was promised in old CSS3 drafts (~2003), deferred through css-values-3 → 4 → 5. The blocker was security: attributes can hold secrets (CSRF tokens, API keys), and a styling function that could flow them into url() would leak them into network requests. The spec resolved this with attr()-tainting — typed values are marked tainted at computed-value time, and any use as (or inside) a <url> invalidates the declaration. As WebKit put it in the Interop 2026 announcement: "Now that security concerns have been worked through in the specification, browser makers are united in our excitement to ship this long-awaited capability."

02

Anatomy — one function, three type forms

attr( <name> <type-or-unit>? , <fallback>? )

/* 1 — no type: classic string, exactly the old behavior */
content: attr(data-label)

/* 2 — typed: the type() wrapper, full syntax power incl. unions */
color:   attr(data-accent type(<color>), currentcolor)
scale:   attr(data-zoom type(<number>), 1)
width:   attr(data-w type(<length> | <percentage>), 0px)

/* 3 — unit shorthand: bare unit ident, numbers come from markup */
font-size:  attr(data-size px)
rotate:     attr(data-heading deg, 0deg)
transition-duration: attr(data-t s, .3s)
width:      attr(data-fill %, 0%)

Fallback semantics mirror var(): it fires when the attribute is missing or unparseable as the requested type. No type + no fallback → empty string. Typed + no fallback + unparseable → guaranteed-invalid → the declaration is invalid-at-computed-value-time (IACVT) and the property falls back to the cascade (usually its initial value — or the static line above it).

Rename note: the string keyword is now raw-string (Chromium originally shipped it as string; both work for a transition period). raw-string means no CSS parsing — even escapes and comments stay literal.

Lab — the custom-property trap (resolve where it lives)

attr() inside a custom property resolves on the element where the property is defined, then the resolved value inherits down. Badge B carries data-name="ARC-2". Its ::before reads the attribute directly — works. Its ::after reads var(--name), which its parent defined as attr(data-name raw-string, "ghost") — the parent has no such attribute, so the fallback resolves there and "ghost" is what inherits. Same attribute, same element, two different answers depending on where resolution happens.

B: resolving… 
#trap-wrap { --name: attr(data-name raw-string, "ghost"); }  /* resolves on PARENT: no attr here */
#trap-b::before { content: attr(data-name raw-string, "?"); } /* resolves on CHILD: finds ARC-2 */
#trap-b::after  { content: var(--name); }                      /* inherits resolved "ghost" */
Rule: never launder attr() through a custom property on an ancestor expecting it to re-resolve on descendants — it will not. Resolve on the element that owns the attribute, or pass the string down after resolving.

Production — Molt variant cards (markup is the API)

Same component, three configurations — zero variant classes. Padding, border, and background all read from attributes, which template engines and CMS fields emit natively. Compare with inline style="": attributes keep the values in markup but the rules in the stylesheet — CSP-friendly (no style-src-attr relaxation), themeable (swap the stylesheet, markup untouched), and diffable.

Adoption notes & gotcha recap

RuleWhy
Static line above the attr() lineNon-supporting engines drop the whole declaration — same discipline as if() and nested CSS
Gate with @supports (x: attr(x type(*)))Parses ≠ supports; probe the exact form you use
Always give typed attr() a fallbackUnparseable + no fallback → IACVT → property falls to the cascade (initial/unset) — silently
Never build URLs from attr()attr()-tainting → IACVT by design (secrets stay out of network requests)
Don't pass --x: attr() down expecting re-resolutionResolves on the defining element; children inherit the result
Empty value ≠ missing value (string form)Empty stays empty for raw-string; typed parses fail → fallback (live-proven §4)
Attributes are strings — validate at the sourcetype() won't save you from units already baked in ("12px" into px parse fails → fallback)

Where it lands in the stack: :has() styles by structure, @container style() by ancestor tokens, if() by conditions — typed attr() is the data plane: per-instance values from markup. Together they retire most of the "JS exists only to copy state into classes/styles" code in a component library.

Polyfill posture: none worth shipping. Attribute-driven components degrade to the static line — design fallbacks that look intentional (default sizing, default color), not broken.

Related catalog entries: CSS if() (logic plane), container style queries (token plane), :has() (structure plane), relative color syntax (derives ramps from an attr() seed — §6), Customizable Select (markup-driven styling's biggest sibling).
