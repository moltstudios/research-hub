HTML-in-Canvas — the drawElementImage tier

The WICG HTML-in-Canvas proposal is the DOM↔pixel bridge the platform never had: lay out real HTML — text, CSS, i18n line-breaking — and draw it into a 2D canvas or a WebGL texture. Canvas apps today fake this with fillText (no rich layout, no accessibility tree) or SVG-in-<img> (no live DOM). This page measures the shipped Chromium implementation live in your tab and holds it against the explainer — where they disagree, the engine wins and the chip says so. Reference measurements below were harness-probed on Chrome for Testing 155.0.0.0 behind --enable-features=CanvasDrawElement.

probing…

§1 · What it is, and why it matters

Five primitives: a canvas opts into laying out its descendants; descendants opt into being drawable; a paint event tells you when snapshots changed; drawElementImage / texElementSubImage2D raster those snapshots into 2D/WebGL; geometry APIs sync the DOM with where the pixels landed.

  • Accessibility: the drawable element stays in the DOM — screen readers see real elements with roles and names, not an opaque canvas. (Geometry exposure is the weak half — §7.)
  • i18n: real CSS line-breaking, shaping and font fallback — the chart-label / in-game-menu problem the explainer leads with.
  • The DOM↔pixel bridge: rich text in a WebGL hero, HUD labels drawn over telemetry, HTML exported as pixels — without duplicating layout in JS.

THE FLAG LAW. There is no gradual degradation: without --enable-features=CanvasDrawElement (chrome://flags/#canvas-draw-element) every member reads undefined and the layoutsubtree attribute in your markup reflects to nothing. Feature-detect typeof CanvasRenderingContext2D.prototype.drawElementImage === 'function' — one check gates the whole tier.

THE DRIFT LAW. The explainer's content attribute does not exist in the build that actually ships; the build gates on layoutsubtree instead. Meanwhile captureElementImage — often reported "not shipped" — is shipped as an HTMLCanvasElement method, and ElementImage is a real transferable. Code written against the explainer alone will call a nonexistent attribute and miss a working API. Trust probes, not prose.

§4 · LIVE — real HTML → 2D pixels

The canvas below carries a layoutsubtree attribute and a real DOM child (teal chip, top-left — that's live HTML, not canvas pixels). With the flag on, drawElementImage rasterizes the child into the buffer at three destinations: 5-arg, 3-arg natural size, and the 9-arg source-rect overload. Then we read pixels back. Measured (the distance law, §3 row 9): the draw silently no-ops — no exception, zero pixels — when the canvas sits far below the viewport, so this lane arms on proximity and fires as you scroll to it. §7 · The geometry lane — DOM↔canvas sync & the hit-test bridge

The explainer's answer to "my pixels moved, where is my DOM?": updateElementGeometry installs a canvas transform + hit-test order (2D contexts run it automatically on every draw), clearElementGeometry removes it, elementgeometryupdate notifies. We run the whole lane live against the §4 canvas.

idle
THE BRIDGE LAW (measured). On this build the geometry half is plumbing without water: updateElementGeometry returns undefined without complaint, drawElementImage's auto-geometry runs — yet document.elementFromPoint() over the drawn location still returns the canvas, and a pointer event there hits the canvas, never the child. getElementTransform throws on the very argument the IDL documents. Pixels land; hit-testing and geometry do not. Build your own hit-map (you know dx,dy,dw,dh) and keep the child in the a11y tree for reading, not pointing.

§8 · THE LAWS — sharpest measured edges

All rows harness-measured on CFT 155 + flag; error strings verbatim from the engine.

#lawmeasured evidence
1The family law — the element must be a DOM descendant of that very canvasdrawing an element that lives elsewhere: InvalidStateError: The element can only be drawn into its nearest ancestor <canvas>.
2The gate law — the canvas must carry layoutsubtreewithout it: InvalidStateError: DrawElementImage requires the canvas to have the layoutsubtree attribute. (same gate on texElementSubImage2D, its own message)
3The cache law — no snapshot, no drawa freshly-inserted child throws InvalidStateError: No cached paint record for element. — with any arity — until one rendering update has recorded it. Wait for the first paint (or use requestPaint() + one frame) before the first draw. display:none children never get a record.
4The arity law — 3 required, 2 optional, options-dict folklore wrong.length === 3; 1 arg → TypeError: 3 arguments required, but only 1 present. (el,dx,dy) draws at natural size ✓; (el,dx,dy,dw,dh) scales ✓; 9-arg source-rect ✓. A 4th-arg options dict is silently coerced to dwidth — it cannot be distinguished from a number.
5The visibility law — the child must stay in the canvas boxchild at position:absolute;left:-4000px gets a record and draws blank white; display:none has no record. Keep drawable children inside the canvas's box (the demo pattern: absolute, top/left 8px).
6The lenient-attr law — drawable is not enforcedexplainer: "exception thrown… without the drawable attribute". Measured: a child without it drew successfully (pixels 176,92,26,255 = its #b05c1a fill). Keep the attribute — it marks intent and nesting — but never rely on it as a validation gate.
7The pointer gap — drawn pixels are not hit-testableelementFromPoint at the drawn location → the canvas; pointerdown there → canvas handlers only. Even after the auto-geometry pass of drawElementImage.
8The handle law — ElementImage is real and closablecanvas.captureElementImage(el) → ElementImage (global ctor exists, flagged) → draws by handle ✓ → close() ✓ → drawing a closed handle: InvalidStateError: The ElementImage has been closed.
9The distance law — draws silently no-op far outside the raster windowmeasured at 375px (CFT 155, flag on): pixels land with the canvas 900px below the fold; all-zero with no exception at 6200px. Snapshot recording follows rendering, and rendering skips far-offscreen content. Arm on visibility (IntersectionObserver), draw when near, and verify by pixel readback — the call succeeding proves nothing.
9The viewport law — subtrees only raster near the viewporta canvas 6,000 px below the fold: requestPaint() fires a paint event, drawElementImage doesn't throw — and the pixels land blank (0,0,0,0), even 10 s later. Same canvas after one scrollIntoView(): 11,107,93,255. Scroll away + mutate + redraw → blank again: the snapshot does not survive leaving the viewport. Keep drawable canvases on screen (or draw on an IntersectionObserver) — verified live in §4.

§9 · Capstones — the OpenDrones HUD & the Molt WebGL hero

OpenDrones: a live telemetry HUD — the label is real DOM (screen-reader visible), re-snapshotted every half second and drawn into the canvas over the grid. Without the flag the same HUD degrades to fillText, visibly dumber typography, honestly labelled. Molt: §5 is the whole pitch — rich serif italic text landing in a WebGL texture is the hero-banner pattern without canvas-text hacks.

Watching for stabilizationchrome://flags/#canvas-draw-element · WICG html-in-canvas repo · the drift table above is your regression checklist when a flag flip lands
  1. One feature check gates the tier: drawElementImage on the 2D prototype.
  2. Markup contract: <canvas layoutsubtree> + child with drawable, child kept inside the canvas box.
  3. First draw only after the first paint; requestPaint() to pump the loop; mutations coalesce into one event per frame.
  4. changedElements tells you which children actually invalidated — redraw only those.
  5. Read back pixels to verify draws in tests (deterministic on this build: 11,107,93,255).
  6. WebGL: same gate, same family law, plus the WebGLCopyElementImageConfig dictionary (unknown keys silently ignored).
  7. The geometry half is shipped-but-dormant: probe again each milestone before building on it.
