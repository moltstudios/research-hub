Pointer Events — the Web's Unified Input Model

One event family for mouse, touch, and pen: pointerdown / move / up / cancel plus pointer capture, coalesced & predicted event streams, pressure/tilt/twist telemetry, and a click-target rule that surprises everyone once. This page live-probes every claim on the engine you're using right now.

Section 1

What & why — one API to replace three

Before Pointer Events, interactive surfaces juggled mousedown (desktop), touchstart (mobile, passive-by-default, no mouse-equivalents), and proprietary pen events. Pointer Events collapse all three into one pipeline: every contact point — mouse cursor, finger, stylus — is a pointer with a stable pointerId for its lifetime. You write the drag handler once.

🖱️ Mouse

One persistent pointer, constant id for the whole session. pressure = 0.5 while any button is held (no real hardware pressure).

👆 Touch

Each finger = its own pointerId. Implicit capture: the element that got pointerdown keeps all moves — exactly how native mobile scrolling feels.

🖊️ Pen

Full telemetry: pressure 0–1, tiltX/Y, twist, barrel button via buttons, plus getCoalescedEvents() for OS-rate input.

Support: core (events + capture) is Baseline ≈ 2020, ~99%+ — Chrome 55 / Firefox 59 / Safari 13 (incl. iOS 13). Ship ungated; the tiers above it (coalesced, predicted, raw-update) are capability-probed below.

The three properties everyone gets wrong
  • buttons is a bitmask: 1 left · 2 right · 4 middle · 8 back · 16 forward. Held left+right = 3, not 2.
  • button = the button that changed in this event (0 down, 2 right, …) and −1 for plain moves — not "which buttons are held". Chorded presses/releases arrive as pointermove — one pointerdown per gesture, period.
  • isPrimary: the first finger of a multi-touch gesture. Mouse is always primary. Two mice → two primaries (rare, but legal).

Pointer capture — the retargeting engine

el.setPointerCapture(id) in a pointerdown handler redirects all subsequent pointer events for that pointer to el — no hit-testing, no per-frame elementFromPoint, no listeners on window. Release the mouse over anywhere; your element still gets pointerup.

Section 4 · requires drive

The click trap — where does click land after a captured drag?

Pointer capture retargets pointer events… but click is a compatibility mouse event from a different spec generation. Press on A (which captures), drag to B, release over B. Which element receives the click? The pipeline drive answers it live below — and the answer is why sliders "commit" correctly instead of clicking random underlying UI.

Per spec (Pointer Events §click)

The click event fires at the element that would be the hit-test target or the capture target — engines had latitude for years; the live chip below records what this engine actually does.

Practical rule

Never listen for click on drag-capable UI to detect "real activation" — use pointerup + a movement threshold, or you'll get clicks that follow drags.

Section 7

High-frequency input — coalesced, raw & predicted events

Real devices emit pointer input far faster than 60 Hz. The browser batches intermediate samples into one pointermove — getCoalescedEvents() hands you every sample (pen drawing, gesture math). pointerrawupdate skips the rAF alignment entirely; getPredictedEvents() projects pen trajectory forward.

getCoalescedEvents()

Ch 58 · FF 59 · Safari 18.2 (Dec 2024 — six years last). Returns [] for synthetic and for OS-batched mouse on most platforms.

getPredictedEvents()

Ch 77 · FF 89 · SF 18.2. Pen-only tier — predictions for latency compensation (ink prediction).

pointerrawupdate

Chromium 58+ only (FF/Safari ✗ as of 2026 — runtime-probed in the badges). Fires per raw input, before batching; keep handlers < 1 ms.

Section 9

touch-action — the CSS contract that gates everything

touch-action is the negotiation: it tells the browser which gestures the page renounces, so it can promise not to hijack the pointer mid-gesture. Without it, a vertical finger-drag becomes a scroll and your drag dies with pointercancel — the single most common "my drag works on desktop, breaks on mobile" bug.

ValueMeaningUse for
autoBrowser may take any gesturedefault — drags get cancelled
nonePage handles everythingdrag surfaces, canvases, sliders
pan-x pan-yScroll/pan allowed, pinch-zoom renouncedmap surfaces (pan yes, zoom mine)
pinch-zoomOnly zoom survivesimage viewers

Support is ancient and universal: Ch 36 / FF 52 / SF 13 — but iOS shipped it in 9.3, three years before iOS got Pointer Events at all. Put touch-action:none on the draggable element, not body (you'd nuke scrolling).

Gotcha wall (each one live-probed on this page)

  1. Capture on pointerdown, never on move — later is a race you sometimes lose.
  2. Never compare pointerId === 1 — mouse ids are engine-chosen constants, not spec'd (this page's live id is recorded in §2).
  3. touch-action:none on drag surfaces or the browser cancels you (§9).
  4. Reset state on pointercancel, not just pointerup (§6).
  5. Synthetic PointerEvents default pointerType:'', not 'mouse' (§5 probe 4).
  6. dispatchEvent bypasses the capture pipeline — retargeting only happens for real input (that's why this page needs a driver for §3–§6).
  7. click follows capture, not hit-testing — live answer in §4.
  8. pointerenter/leave never bubble; over/out do; capture retargets boundary events too.
  9. getCoalescedEvents() is empty for synthetic + batched mouse — don't build on it existing (§7).
  10. buttons is a bitmask; button === −1 on plain moves (§8).
