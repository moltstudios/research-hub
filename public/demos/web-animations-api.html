Web Animations API — element.animate(), the Unified Animation Engine

Every animation on the page — CSS keyframes, CSS transitions, view transitions, scroll-driven effects, JS-built motion — is the same Animation object in the same engine, reachable via document.getAnimations(). CSS declares; WAAPI controls: play, pause, scrub, rate-change, persist, commit. The control surface the animation tier was missing: linear() is how motion feels, timelines are the clock, offset-path is the road — WAAPI is the transport bar.

01Why this matters

The catalog has the pieces: linear() easing, scroll-driven animations (11 entries!), motion path, view transitions. What it never established is the model underneath them all: the Web Animations API is the single engine every one of those features compiles down to. A CSS @keyframes rule becomes a CSSAnimation object; a transition becomes a CSSTransition object; element.animate() builds an Animation directly. All three expose the same transport: .play() .pause() .reverse() .finish() .cancel(), .currentTime scrubbing, .playbackRate, promises (.ready .finished), and lifecycle state.

The unlock: anything you can declare in CSS, you can control from JS — without re-authoring it. Pause every animation on the page in one line. Scrub a mission-replay flight authored as pure CSS. Change playback speed without a re-render. That is a class of capability none of the declarative entries could do alone — and it is why this entry unifies them.

Support: three waves

Core (Baseline ~2020): animate() Chrome 36/FF 48/Safari 13.1; the transport + promises (persist, commitStyles, finished, replaceState) Chrome 84/FF 75/Safari 13.1 — effectively universal.

2023 wave: animation-composition Chrome 112/FF 115/Safari 16 (Baseline Jul 2023) — additive transform stacking; JS ScrollTimeline/ViewTimeline constructors Chrome 115/Safari 26 (Firefox preview-only).

2025-26 wave: overallProgress — the timeline-agnostic progress readout — Chrome 133/FF 142/Safari 26.2; commitStyles endpoint fix same trio.

Who it is for

OpenDrones: mission replay scrubber (the Aug 22 offset-path demo, upgraded with a transport bar), telemetry gauges with pause-on-inspect, 2×/4× review speed on recorded flights.

Molt Studios: hero entrances with a replay button, pause-all on reduced-motion or tab-blur, additive hover effects that stack on an entrance animation without fighting it (composition: add).

// one surface for everything the page is animating
const all = document.getAnimations();          // document-wide
const mine = el.getAnimations();               // per-element (CSS anims + transitions + JS)
all.forEach(a => a.pause());             // pause the whole page — CSS included
// a.constructor.name -> "CSSAnimation" | "CSSTransition" | "Animation"

Gotcha baked into the model: getAnimations() only returns animations currently in effect (running, pending, or filling). A finished fill:none animation is gone — which is the memory-management design, section 09.

03Anatomy — animate() shorthand vs KeyframeEffect + Animation

el.animate() is sugar: it builds a KeyframeEffect (what happens: keyframes + target + timing) wrapped in an Animation (when it happens: playback state + timeline), then plays it. The long form separates those concerns — and makes the effect editable at runtime.

live — edit keyframes while it runs
🛩️
// shorthand — build + play in one call
const anim = el.animate(
  [{ transform: 'scale(1)' }, { transform: 'scale(1.3)' }],
  { duration: 800, iterations: Infinity,
    direction: 'alternate', easing: 'ease-in-out' }
);
// long form — separate WHAT from WHEN
const fx = new KeyframeEffect(el, keyframes, opts);
const anim = new Animation(fx, document.timeline);
anim.play();
// runtime edits — impossible with CSS alone:
fx.setKeyframes(newKeys);      // hot-swap, playback continues
fx.getKeyframes();             // normalized + computedOffset
anim.effect.getComputedTiming(); // live progress, iterations…

05updatePlaybackRate() vs the playbackRate setter — the drift race

Compositor-accelerated animations (transform/opacity) keep advancing even while the main thread is blocked — the LoAF lesson in miniature. If the main thread wakes up and sets playbackRate directly, it preserves its stale view of currentTime and the animation visibly jumps. updatePlaybackRate() is asynchronous on purpose: it synchronizes with the real current position first, then changes the rate.

lane A — playbackRate = 3 (setter, immediate)

lane B — updatePlaybackRate(3) (synced, async)

Run the race — it measures currentTime continuity across the rate change for both methods.
Honest lab: whether the setter jump manifests depends on compositor drift at that instant — this measures it live and reports both deltas. The rule stands regardless: in production use updatePlaybackRate() for any user-facing speed control; the direct setter is fine for stopped/scrubbed animations where you own currentTime.

06animation-composition — replace / add / accumulate

The classic WAAPI limitation was "last animation wins": two animations on the same property fought, and the winner erased the loser. animation-composition (Baseline Jul 2023) changes that: add stacks effects, accumulate adds iteration-aware, replace is the old behavior. Each lane below runs a base drift (translateX 0→120px) plus a second pulse animation (translateX 0→60px) that differs only in composite mode.

replace — pulse wins, base erased

add — drift + pulse stack

accumulate — iteration-aware add

The composite-stack trap (live-falsified on this engine): a finished, filling animation that sits underneath a newer animation is auto-removed the moment it finishes — its fill contribution vanishes and the stack silently collapses to the newest layer. Uncheck the box and run to watch it happen: all three lanes end at the pulse value instead of the stack value. persist() the foundation animations of any composite stack — auto-removal (section 08) does not know your base layer was load-bearing.
// the pattern: ambient base motion + interactive overlay that STACKS instead of fighting
const base = el.animate({ transform: ['translateX(0)', 'translateX(120px)'] },
                        { duration: 3000, fill: 'forwards' });
base.persist();  // ← load-bearing: without it, auto-removal reaps the base at finish (see callout)
const pulse = el.animate({ transform: ['translateX(0)', 'translateX(60px)'] },
                         { duration: 1500, composite: 'add' });
// also a CSS property:  animation-composition: add;  (same engine, declarative form)

For transforms, add concatenates the per-function lists (drift then pulse); for plain numbers/colors it sums/blends underlying values. accumulate differs from add once iterations repeat — its per-iteration delta accumulates. Molt pattern: entrance animation (translateY + fade) stays alive while a hover-lift adds on top — no re-authoring, no fighting, see section 12.

The unit trap (probed live below): on a document timeline, anim.currentTime is milliseconds. On a progress-based timeline it is a percentage (a CSSNumericValue, e.g. 42.7%) — code that assumes ms breaks silently. The timeline-agnostic readout is anim.overallProgress (0→1, Chrome 133/FF 142/Safari 26.2), with the universal fallback anim.effect.getComputedTiming().progress.

Support: constructors are Chrome 115+ / Safari 26+; Firefox is preview-only — gate with 'ScrollTimeline' in window and fall back to the CSS animation-timeline form (Baseline, all engines) or rAF. The demo panels degrade to a note in that case.

08Auto-removal, replaceState & persist() — the leak-proof design

The #1 historical WAAPI complaint was memory leaks: infinite piles of finished fill: 'forwards' animations. The engine's answer: a finished, filling animation becomes replaceable, and the moment a newer animation overrides it, the browser auto-removes it — firing the remove event and flipping replaceState to 'removed'. persist() opts an animation out forever.

stack — newest wins, losers auto-removed
remove events log here
const a = el.animate(keyframes, { duration: 500, fill: 'forwards' });
a.addEventListener('remove', () => { /* superseded — engine freed it */ });
a.persist();               // keep it alive despite being overridden
a.replaceState;             // 'active' | 'persisted' | 'removed'
document.getAnimations().length;  // stays flat — this is the leak fix, working

Production rules: (1) an animation you still need a handle on (scrub-later, resume) → persist() it; (2) everything else → let auto-removal clean up, or cancel() explicitly; (3) never rely on a finished transient's fill — it can vanish the moment a sibling animation overrides it.

09commitStyles() — bake the end state, free the animation

The partnership with auto-removal: when an entrance finishes and you want its look to stay, you have three options — keep a filling animation alive (costly, fragile), hand-write the end style, or commitStyles(): write the animation's final keyframe values into the element's inline style, then cancel() the animation with zero visual change.

M
await anim.finish();            // commitStyles requires the finished state
anim.commitStyles();          // end keyframes → el.style (inline)
anim.cancel();                // effect freed, fill gone — look identical
// requirements: playState 'finished' + fill forwards/both, real element target
// (Chrome 144 / FF 142 / Safari 26.2 fixed commitStyles to include the endpoint)

The readout shows el.getAttribute('style') before and after — you can watch the transform + opacity appear as inline style while the animation count drops to zero. This is the correct "one-shot entrance" production pattern: nothing filling, nothing persisted, nothing to leak.

The gotcha wall (all engine-verified patterns)

1. play()/pause() are async — state goes through pending; await anim.ready before asserting playState in tests.

2. cancel() rejects finished with an AbortError DOMException — always .catch() finished promises you race against user actions, or you get unhandled rejections.

3. fill:'forwards' leaks by design — every finished+filling animation you keep alive holds an effect in the "current animations" list. Auto-removal helps (supersession), but the clean patterns are commitStyles+cancel (one-shot) or cancel on teardown. Corollary proven live in section 07: the same auto-removal reaps un-persisted composite-stack foundations the instant they finish under a newer animation — persist() anything load-bearing.

4. progress timelines change currentTime units — ms on DocumentTimeline, percent CSSNumericValue on Scroll/ViewTimeline. Timeline-agnostic: overallProgress, or effect.getComputedTiming().progress. And overallProgress is 0 for infinite-iteration animations — live-probed: the infinite flight read overallProgress 0 while its per-iteration progress was 0.62 (∞ iterations → ∞ division → 0, not null — a null check will not save you). The universal per-iteration readout is getComputedTiming().progress; .currentIteration gives the lap number.

5. Reverse carefully: reverse() on a finished fill:forwards animation replays it backward; setting playbackRate = -1 on a finished animation does nothing until currentTime is rewound. Use reverse().

6. Compositor caveat: only transform/opacity animations ride the compositor — animating layout properties (width, top) via WAAPI still runs on the main thread and will stutter under load (see the LoAF entry). Author transform-only keyframes.

7. GroupEffect/sequence effects never shipped — sequencing is offsets/delays within one effect, or manual finished-chaining (a.finished.then(() => b.play())).

8. CSS animations are read-write: grabbing el.getAnimations() and mutating currentTime/playState of a CSSAnimation works — but if you cancel() it, the CSS rule re-creates it on next style invalidation. The declarative layer stays the source of truth.

Adoption posture: core transport + composition are ship-today everywhere. JS timeline constructors get a feature gate ('ScrollTimeline' in window) with the Baseline CSS form as fallback. Nothing here needs a library — this entry retires the GSAP timeline-shaped dependency for scrub/rate/pause UIs.
