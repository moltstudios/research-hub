01Surface discovery — always a function, but is it a useful one?

Is queryLocalFonts exposed? What does 'in', typeof, and the property descriptor look like?

// (await gate)
The shape: Unlike EyeDropper / Geolocation / Camera — which are object-absent on insecure origins or pre-permission — queryLocalFonts is ALWAYS exposed on window in a secure origin. The gate is at call time, not at surface time. descriptor.writable is true, enumerable true, configurable true — it's a regular global, not a getter or symbol-keyed slot.

02The empty-array permission wall — the most insidious gate in the catalog

What does queryLocalFonts() actually return when permission is prompt vs granted vs denied?

// (await gate)
THE HEADLINE FALSIFICATION. Every other gated browser API in the catalog has a discoverable rejection pattern: EyeDropper.open() without a gesture pends forever; navigator.wakeLock.request() rejects with NotAllowedError; navigator.usb.requestDevice() rejects with SecurityError or NotFoundError; EyeDropper, Camera, Geolocation, Bluetooth are object-absent on insecure origins.

Local Font Access is the SILENT NOTHING. await window.queryLocalFonts() with no permission grant resolves to an empty array — length: 0. Not a rejection, not a NotAllowedError, not a pend. The promise RESOLVES with []. The only way to detect the gate failure is to check result.length === 0. If you assume "I got fonts, the user must have granted" — you'll ship a tool that silently fails on every fresh visitor.

Bonus falsification: navigator.permissions.query({ name: 'local-fonts' }) returns 'prompt' even when the browser-level permission has been granted (via dev-tools policy or page context). The Permissions API reflects the user's interactive state, not the actual API access state. Test the call, not the query. 
// Three patterns, three APIs, three gates
await new EyeDropper().open();              // → PENDShow or hang (no silent fail)
await navigator.wakeLock.request('screen'); // → NotAllowedError OR succeeds
await window.queryLocalFonts();             // → [] OR real array (silent fail)

// The only safe check
const fonts = await window.queryLocalFonts();
if (fonts.length === 0) {
  // Not 'user denied' — could be: never prompted / dismissed prompt / policy-blocked.
  // Show a manual opt-in UI, never assume.
}

03Permissions API — only the hyphenated name works

What does navigator.permissions.query({name: '...'}) accept for this feature?

// (await gate)
The only valid name is 'local-fonts'. 'local_fonts' (underscore), 'font-access', and 'fonts' ALL throw TypeError: Failed to execute 'query' on 'Permissions'. Internally the engine stores it as local_fonts (the permission property of the returned PermissionStatus reads 'local_fonts' with underscore), but the input to query() MUST be the hyphenated form. Same shape as EyeDropper's permission-name duality.

04Worker jail — main-thread only (like Camera, Web Bluetooth)

Can queryLocalFonts be called from a dedicated worker?

// (await gate)
Workers: navigator exists, navigator.permissions works, but queryLocalFonts is undefined. The function lives on window only. Dedicated workers inherit the permission grant (verified via permissions.query('local-fonts') returning 'granted'), but the enumeration surface doesn't follow. Same main-thread-only pattern as Camera / Web Bluetooth / EyeDropper. Pass font data INTO a worker via postMessage + transfer, do not try to query from inside.

05Same-origin iframe — full inheritance

Can an iframe enumerate the same fonts as its parent?

// (await gate)
Same-origin iframe: full inheritance — same 526 fonts, same surface. No Permissions-Policy gate by default. Cross-origin iframes default-deny per the new permissions model (same as Camera/BLE). This is the embed-friendly ladder — Molt's portfolio embeds, OpenDrones' third-party telemetry widgets all work inside the parent's permission grant.

06The options flag that does nothing on macOS

Does postscriptNamesByUniqueFamily actually compact the list?

// (await gate)
On macOS CfT 154: default === true === false — all three return the same 526 fonts. The postscriptNamesByUniqueFamily: true flag is meant to compact the enumeration to one representative per family (the spec's "compact" mode). On macOS the underlying CoreText enumeration already returns every variant — the flag is a no-op. Only on Windows/Linux does the option matter. Don't write production code that depends on the flag's compact-mode behavior without testing on your target OS.

07FontData shape — getters, not values

What does a FontData instance actually expose?

// (await gate)
The properties are GETTERS, not values. Object.entries(fontData) === {} — every property (family, fullName, postscriptName, style) is a getter on the prototype with no underlying slot. blob is the only non-accessor (it's a function value). Mutation is silently ignored: fontData.family = 'X' reads back the original. You MUST read via the getters; you CANNOT spread, clone, or JSON.stringify a FontData. Use the dedicated postMessage serialization that preserves getters, or build your own plain-object DTO.

08Blob round-trip — the raw font bytes with the wrong MIME type

What does await fontData.blob() actually return?

// (await gate)
blob.type === 'application/octet-stream' — always. The browser does not discriminate by format. The font data could be TTF, OTF, dfont, TTC, WOFF, WOFF2 — the engine returns the same MIME type for every font. Production code MUST sniff the magic bytes: 00 01 00 00 = TTF, 4F 54 54 4F ("OTTO") = OpenType/CFF, 74 74 63 66 ("ttcf") = TrueType Collection, 74 72 75 65 ("true") = Mac dfont (resource fork). Never trust blob.type.

Idempotence: calling blob() twice returns DIFFERENT Blob instances (each call creates a fresh one) but identical bytes. Size and content are deterministic; identity is not.
Use URL.createObjectURL(blob) + new FontFace(family, url).load() to actually USE the font in your page. This is the integration pattern: enumerate → blob → object URL → FontFace API → document.fonts.add() → render with the user's real installed fonts.

09Style field non-normalization — the engine reports whatever the font says

Is style a fixed enum like CSS font-weight?

// (await gate)
macOS CfT 154 returned 74 unique style strings across 526 fonts — "Plain", "Bold", "Regular", "Condensed", "Outline 6 Dot", "Pinpoint 6 Dot", "W0"..W9, "HouseScript", "Bold Inclined", "Demi", "Wide", "Ornaments", "Black Condensed"… there is NO canonical normalization. The engine mirrors whatever the font's internal name table says. Some fonts report "Plain" (Apple system fonts) while others report "Regular" (cross-platform). Apple's "Apple Braille" family uses "Outline 6 Dot", "Pinpoint 8 Dot", etc. as styles. There is no mapping table.

Production rule: if you need normalized weights, parse style yourself into a known bucket (Regular/Bold/Italic/etc.) via your own regex — never assume "Regular" means weight 400.

10Multi-style families — the audit data

How many styles per family does a typical Mac install report?

// (await gate)
180 unique families × 526 fonts = ~2.9 fonts per family on average. Some families balloon: Apple SD Gothic Neo has 8 weights (Thin/UltraLight/Light/Regular/Medium/SemiBold/Bold/Heavy). American Typewriter has 7. Apple-supplied families are well-organized; third-party fonts often have "Regular" + "Bold" and nothing else. The split between family (grouping key) and style (variant key) is the cleanest enumeration surface — use it as the dedup primitive.
