1 · The quartet — one transition is three events, and transitionrun fires at schedule time

A transition with a delay fires run the moment it is scheduled, start when the delay expires, end at delay+duration. With no delay, run+start co-fire in the same tick. elapsedTime at end is the duration only — never including the delay.

THE CANCELLABLE SPLIT — Chromium reports cancelable:true on every transition event; Firefox + WebKit report false (preventing them is meaningless either way — but the flag your code asserts differs per engine).
THE SURFACE SPLIT — WebKit's TransitionEvent.animation getter returns the live CSSTransition object from inside the handler; Chromium ships pseudoTarget instead; Firefox ships neither.

2 · The no-event traps — five ways a transitionend listener never fires

Each button performs a "transition" that produces zero events on every engine. This is the #1 animation bug class: code that waits for an end that never comes.

Trap lab — press each, watch the ledger stay empty

The five traps

THE NO-OP TRAP — setting a property to its current value creates no transition at all (measured: 0 events, 3/3). Conditional code like if (open) el.style.width='300px' silently never animates when the value is already 300.
THE ZERO-DURATION LAW — transition: width 0s fires no events whatsoever — not even transitionrun (3/3). A bare transition: width defaults to 0s: instant jump, silent forever.
THE AUTO WALL — height: 40px → auto never transitions (discrete pair, no events) — the reason interpolate-size / calc-size() exist.
THE BOGUS-PROPERTY SILENCE — transition: bogus-prop 300ms is kept in gCS (unlike a bad easing, which kills the whole declaration) but never matches anything: no events, forever.
THE SPECIFICITY SHADOW — if a higher-specificity rule wins, the property never changes and nothing fires (this page's own probe fixture hit it: #p1{opacity:1} beat .hidden{opacity:0} → the transition was never born).

3 · The fan-out — one style change under transition: all is N × 3 events

Change three properties at once → nine events. The end events arrive in alphabetical order on Chromium/Firefox — WebKit fires them in a different (reverse-of-set) order. A keyed listener runs three times; an unkeyed one commits three times.

Live fan-out — transition: all 250ms, three properties change

The order split

THE FAN-OUT LAW — with transition: all, one style change emits a run/start/end trio per changed property. Guard with e.propertyName or you will run your commit three times. Measured: identical alphabetical order (background-color → opacity → width) on CfT + Firefox; WebKit fired reverse-of-set.

4 · The kill matrix — how a running transition dies, and what fires

A 900ms transition is launched, then killed at ~300ms by four different causes. Only one of them fires anything.

Kill lab

— launch a transition, then kill it —
THE DISPLAY-NONE CANCEL — hiding the element fires transitioncancel with elapsedTime = progress so far (measured 0.167 at the kill point). Re-showing does not resume: the transition is gone (3/3).
THE REMOVAL SILENCE — detaching the element mid-flight fires nothing at all — no cancel, no end. Reattaching jumps to the target with no events. Cleanup wired to transitionend never runs (3/3).
THE RETARGET PAIR — changing the value mid-flight fires transitioncancel + a fresh transitionrun + transitionstart in the same tick — the new flight starts from the current interpolated value, never the old start.

5 · The retarget math — reversal shortening is alive, and the delay is never credited

The famous "browsers shortened reversal transitions" behavior was declared folklore-adjacent for years. Measured on all three engines: retarget to the original start → the return flight is scaled by the remaining-fraction (~250ms below). Retarget to a new value → full duration (~500ms). Retarget during the delay → the delay restarts from zero.

Live trajectory — 0→400px (500ms), retarget at ~50%

THE REVERSAL SHORTENING LAW — 400→0 (500ms) interrupted at ~200px heading back to 400: the return completed in ~250ms on all three engines — duration × |target − current| ÷ |target − old start|. Flip a hover state mid-flight and the exit is visibly snappier than the entry — by design.
THE FULL-DURATION LAW — retarget to a new endpoint (not the original start): full duration from the current value (end event measured +501ms after retarget, 3/3).
THE DELAY RESET LAW — retarget while still inside the delay: cancel + fresh run, and the entire delay runs again — no credit for time already waited (start measured at retarget+400ms, 3/3).

6 · The discrete tier — allow-discrete, the exit flip, and the Firefox void

transition-behavior: allow-discrete lets display itself transition: on exit the box survives until the end of the duration, then flips to none — the zero-JS exit animation. On entry (with @starting-style) it flips at the start.

Exit lab — opacity 400ms, display 400ms allow-discrete

Telemetry pane — press exit; the flip-to-none is timed live.

Your engine's verdict

THE FIREFOX VOID — Firefox 151 parses transition-behavior: allow-discrete, returns it from getComputedStyle, answers CSS.supports() true — and never animates display: the transition is simply not created (0 events, flip is instant). CfT + WebKit run the full quartet with the flip at ~end. Exit animations on Firefox need the visibility pattern or JS.
THE VISIBILITY PATTERN STILL WORKS — opacity .3s, visibility 0s .3s: visibility flips at delay expiry ≈ exactly when opacity hits 0 — measured 300/307/326ms, 3/3. The pre-2024 fade-out idiom remains the cross-engine fallback.

7 · @starting-style — the entry door, and the display:none self-sabotage

Entry transitions from display:none need a before-change style. Put opacity:0 in @starting-style → works (interpolated 0.10 → 1, events fire, 3/3). Put display:none inside it → every entry transition dies: zero events, element appears instantly at final values.

Twin lanes — correct vs self-sabotaged

nested, opacity only → animates
@starting-style { opacity: 0 }
nested + display:none → dead
@starting-style { opacity: 0; display: none }
top-level form + inline flip → STILL animates
same display:none sabotage — top-level @starting-style, display flipped via inline style
THE STARTING-STYLE KILLER — CONFIGURATION-DEPENDENT (2×2×2 matrix measured) — display:none inside @starting-style kills all entry transitions in the standard class-driven pattern when display is in the transition list (nested form: 0 events, instant appearance — 3/3). The kill is narrow and real: a nested form without display in the transition list still animates; a top-level form killed the class-driven lane too (3/3); only the top-level form with an inline-style display flip escaped with its opacity entry intact (3/3). The de-confound battery ran both orientations after the first reading contradicted itself — the third lane above is the stable escape configuration. The display flip is handled by allow-discrete automatically; writing display:none into the starting style is cargo cult that can kill its own animation.
THE ENTRY-ONLY RULE — @starting-style affects only the first style resolution of a newly-rendered element (display:none→block, popover open, dialog show). It is not a keyframe alternative.

8 · Animation events — the n−1 iteration law, the infinite wall, the frozen clock

The animation face of the tier: animationstart (after delay), animationiteration (exactly n−1 times), animationend (elapsed = duration × iterations), animationcancel (elapsed = progress). Pausing freezes the animation clock — elapsedTime reports animation time, not wall time.

Animation waterfall — iterations: 3 × 240ms

— animation events land here —
THE N−1 LAW — 3 iterations → exactly 2 animationiteration events (at elapsed 0.24 · 0.48) then animationend at elapsed 0.72 — duration × iterations, 3/3 exact.
THE INFINITE WALL — infinite: animationend never fires (measured 1.2s of a 100ms loop: start + iterations only, 0 ends). Any await animationend on a looping spinner hangs forever.
THE FROZEN CLOCK — paused for 500ms mid-run: end fires at wall-time +500ms but reports the same elapsedTime — the pause doesn't bill the animation (3/3).
THE MASK LAW — a running @keyframes animation on a property suppresses transition creation for that property entirely (measured: transition events = zero while the animation runs) — and two animations on one property: the later in the list wins, both report events.

12 · Method, engine ledger, falsifications

Method

5 probe batteries (~40 lanes × 3 engines = 120 lane-runs) over a plain-HTTP loopback origin, one fresh single-purpose document per lane (running transitions and leftover listeners leak — the no-op trap's own law). Event capture via document-level recorders with performance.now() timestamps; value truth via per-frame getComputedStyle samplers to settle. Discrete flips timed by 20–33ms polling loops. Reduced-motion lanes via emulated media.

Engine ledger

FALSIFIED ON THE BENCH (3): "reversal shortening was removed — all retargets take full duration" (alive: shortened exactly toward the original start, 3/3) · "engines reduce/disable CSS transitions & animations under prefers-reduced-motion: reduce" (none do — both ran and fired ends under emulated reduce, 3/3) · "a running transition beats a running animation / they fight" (no fight — the animation masks transition creation; zero transition events ever fire).
Lane limits: background-tab throttling of transition clocks not measurable headless (documented, un-probed) · the fan-out ordering beyond simultaneous three-property changes not exhaustively enumerated · Firefox tested at 151 (void may close in later builds — the verdict is version-pinned).
