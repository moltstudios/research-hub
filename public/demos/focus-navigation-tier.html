Focus Events & Tab Navigation — the tier every modal, menu and cockpit HUD rides on

The focus system is the platform's navigation state machine: four events in a fixed ladder, an order grammar for the Tab key, an interaction-keyed :focus-visible heuristic, and a set of walls (shadow, iframe, inert, removal) that each decide what the rest of the page is allowed to see. Measured live in four engines — three hard engine splits, one focus() no-op that manufactures phantom laws, and one piece of modern folklore (async focus events) falsified on the bench.

§1 The four-step ladder universal · 4/4 engines

Moving focus from A to B fires exactly four events, in a fixed order — and it is not the order most diagrams draw. The two old-target events fire first, blur before focusout; then the two new-target events, focus before focusin. focus/blur do not bubble but are composed:true; focusin/focusout bubble. A non-capture listener on document sees only focusin/focusout — attach with capture to see all four.

THE LADDER. blur(A, related=B) → focusout(A, related=B) → focus(B, related=A) → focusin(B, related=A). The relatedTarget points at the other side on all four — never null during an in-document move. Measured identical for .focus() calls, real Tab presses and programmatic moves, in every engine.

THE BUBBLING SPLIT. document.addEventListener('focus', h) (bubble phase) fires never — only the capture phase or the target sees focus/blur. If your global focus tracker hears nothing, this is why: listen for focusin/focusout at document level, or add {capture:true}.

§2 The synchronous ladder & the no-op trap universal · 4/4 engines · folklore falsified

A focus move fires all four ladder events synchronously, inside the focus() call — blur and focusout on the old element, focus and focusin on the new one — in every engine measured, from a script context or a real click handler. The "focus events are now asynchronous" folklore (a real spec proposal, briefly shipped in some builds) does not describe any 2026 engine on this bench. But the call has a silent no-op mode that fakes async perfectly.

THE SYNC LAW. y.focus() while x is focused: by the time the call returns, all four listeners have already run — blur@x, focusout@x, focus@y, focusin@y, each measurable synchronously. Identical from evaluate (no gesture) and from inside real click/keydown handlers. State and events arrive together.
THE NO-OP TRAP (and how it fakes async). y.focus() when y already has focus fires nothing — no events, no scroll, silent return. Our own first probe measured "async events, 4/4 engines" this way: a prior lane had already focused the target, the flag never flipped inside the call, and the no-op read as "events fire later." A focus test that doesn't rotate its targets is measuring the no-op, not the timing. One falsified law, caught by this demo's own §2 chip disagreeing with the probe.

§3 The click-focus census — Safari's button split engine split · measured 4/4

What does a real click focus? Not what you think, and not the same thing in every engine. Click each row's element — the census reads document.activeElement after the real click.

THE WEBKIT BUTTON SPLIT. In Safari, clicking a native <button> does not focus it — activeElement stays body. Text-entry surfaces (input, select, textarea), links, <summary>, contenteditable and any tabindex element are click-focused in Safari. The Chromium family click-focuses all of them. Consequences: :focus styles never apply to Safari buttons; “is this control active?” checks return body; a dialog opened by clicking a button restores focus to body on close in Safari (§10).

§4 :focus-visible — the interaction heuristic universal · 4/4 engines

The heuristic every focus ring now rides on, measured with real Tab presses and real clicks. And the new focusVisible option — shipped everywhere, including WebKit.

THE HEURISTIC TABLE. Tab → :focus-visible matches. Mouse click on a button or tabindex div → no match. Mouse click on a text input → match (text-entry surfaces always match — the caret is the ring). Script focus() → depends on the page's interaction state: on a virgin page it matches, after any pointer interaction it doesn't. No stickiness: Tab once, then click — the click's focus shows no ring. Identical in all four engines.

THE focusVisible OPTION — UNIVERSAL. el.focus({focusVisible:true}) forces the ring on, {focusVisible:false} forces it off — honored in Chrome-for-Testing 148 + 149, Brave 156 and WebKit 26.5. The proof for “off”: on a virgin page the script-focus heuristic says match, and the option flips it to no-match. The escape hatch for menu/roving-tabindex widgets that script-focus real targets is now Baseline.

§5 The tabindex grammar universal · 4/4 engines

The Tab key walks a strict grammar: positive tabindex values first, ascending, ties in DOM order — then tabindex=0 and natively-focusable elements in DOM order. tabindex="-1" (and any negative value) means programmatically focusable but never Tab-reached. And an invalid value is not a zero — it is invisibility.

THE INVALID-TABINDEX LAW. tabindex="abc" does not fall back to 0 — the element is not focusable at all, not by Tab and not by .focus(), in any engine. A templated tabindex (:tabindex="null" rendering the string “null”) silently removes the element from focus reality. Any negative value behaves exactly like −1.

§6 The click-anchor law universal · 4/4 engines

Click anywhere non-focusable, then press Tab. Focus does not start at the first element — it continues from your click. The spec's “sequential focus navigation starting point” is real, in every engine, and it is set by pointer.

click zone — not focusable
click the striped zone, then press Tab (then Shift+Tab)…
THE ANCHOR. After the click, Tab lands on the first tabbable after the click point (mid), and Shift+Tab on the last one before it (first). On a virgin page the first Tab follows the §5 grammar — on this demo's first Tab it enters §1's targets, because the page order is document order for tabindex=0. Support engineers: “Tab skips my login form” is usually this law plus a stray earlier focusable, not a bug.

§7 The removal split · hidden · inert engine split · measured 4/4

Three ways a focused element stops being focusable — three different answers about who gets told.

THE REMOVAL SPLIT. Remove the focused element from the DOM: the Chromium family fires blur + focusout (relatedTarget null) and focus falls to body. WebKit fires nothing at all — activeElement silently becomes body. A cleanup path wired to the element's own blur listener (unsubscribe, save state, release a lock) runs in Chrome and never in Safari. The React unmount-with-focus-inside class of bug is engine-split four ways to Sunday.
THE HIDDEN GRAMMAR. focus() on a display:none element is a silent no-op (no events). Hiding a focused element via display:none or visibility:hidden fires blur+focusout in all four engines and focus falls to body.
THE INERT LAW. Setting inert on an ancestor of the focused element fires blur+focusout immediately (all four engines) and focus falls to body; focus() on an inert element is a silent no-op. Loading overlays: add inert, don't just stack a veil.

§8 The shadow tier — retarget, relatedTarget, delegatesFocus universal + 1 split

Focus crosses an open shadow boundary, but the outside world sees a retold story: the host.

THE RETARGET TRIPLE. Focus the inner element of an open shadow root: outside listeners see focus/focusin with target = the host; document.activeElement === host; and the inner truth is only at host.shadowRoot.activeElement. The relatedTarget of the blur on the old outer element retargets to the host too — never null, never the inner node.
THE DELEGATESFOCUS SPLIT. With {delegatesFocus:true}, host.focus() lands on the first focusable inside the tree — in all four engines (outer activeElement = host, shadowRoot.activeElement = inner). But for clicks: the Chromium family delegates any click within the host — even on a non-focusable shadow pad — to the inner focusable. WebKit delegates nothing on click: clicking inside stays on body (Safari's button-click law, §3, pierces even delegatesFocus).

§9 The iframe wall — window blur & the nullified relatedTarget universal · 4/4 engines

Focus moves between documents at an iframe boundary — the parent document learns less than you think, from more places than you think.

THE IFRAME LAW. Focusing an element inside an iframe: the parent's blur on the old element carries relatedTarget = null (it never crosses the document boundary — same-origin or not), the parent window itself fires blur (focus now belongs to the child browsing context), and the parent's activeElement becomes the <iframe> element. Returning focus fires window focus first, then the element's focus. Global “is the app focused” trackers must treat window blur from an embedded pane as a context move, not a page-deactivation.

§10 Dialog trap + restore · the autofocus race universal + 1 split

The platform's native focus machine, and the one attribute whose winner depends on your engine.

THE TRAP+RESTORE. showModal() moves focus to the first focusable inside (a tabindex=-1 dialog with no focusables takes the focus itself); close() returns focus to the previously-focused element — in all four engines. The WebKit footnote: if the dialog was opened by a click on a native button, §3 means nothing was focused — restore lands on body. Focus the opener programmatically and Safari restores it too.

THE AUTOFOCUS RACE SPLIT. Page with <input autofocus> and a script focus on another element: Chromium family — the script wins, autofocus never fires a single event. WebKit — the autofocus attribute wins, blur/focus pair fired after load. Dynamically-inserted autofocus elements focus nothing, anywhere. An SSR page that focuses a search box on load behaves differently in Safari than Chrome when markup carries autofocus elsewhere.

§11 The focus-scroll split engine split · measured 4/4

focus() scrolls the element into view — but when, and by how much, differs per engine.

MINIMUM ALIGNMENT. The default scroll brings the element just barely into view — measured: an element 2200px below lands at rect.top 868 in a 900px viewport (bottom edge inside, zero centering). Not scrollIntoView({block:'center'}) — the minimum.
THE TIMING SPLIT. In the Chromium family the scroll is settled synchronously — scrollY reads its final value the instant focus() returns. In WebKit the scroll happens asynchronously — a synchronous scrollY read after focus() still shows the old position; it settles a frame or two later. E2E scroll-after-focus assertions must wait-for-settle on Safari. And {preventScroll:true} is honored by all four — the fix for dropdown/flyout focus that yanks the page.
