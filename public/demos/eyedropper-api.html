EyeDropper API — the Color-Picker Tier

The browser's native eyedropper: one constructor, one method (open({signal?})), one result type ({sRGBHex}). Behind that API sit four walls — transient activation, double-open, AbortSignal lifecycle, secure-context — each with its own rejection class. Live-probed on Chromium 154 (headless): two spec-text assumptions are falsified — the gesture wall doesn't reject (it pends silently), and the abort reason flows through as a raw string, not a DOMException.

1. Capability & Prototype

EyeDropper ships in Chromium 95+ but is gated by secure-context and a tiny surface area: one constructor, one method. The prototype is barren — no static helpers, no inspector.







  
2. Anatomy — the surface area

  
Two interfaces in the spec: EyeDropper (the ctor) and ColorSelectionResult (the resolve shape). One option: {signal: AbortSignal} for cancel-via-code.

  






  
3. The Transient-Activation Wall

  
Every open() call must land within ~5s of a real user gesture. The spec text says "without transient activation, return a new promise rejected with NotAllowedError". CfT 154 LIVE FALSIFIES the rejection shape: without a gesture, the Promise does NOT reject — it pends forever, with the eyedropper mode silently engaged and waiting for a user click. Headless confirms: no timeout, no rejection. (In headed Chrome with a UI, the engine still throws — see the gotcha wall for the production distinction.) Same wall shape as requestFullscreen() and requestPointerLock(), but with a different outcome.

Production impact: the §3 falsification is the #1 integration trap. Every demo that says "EyeDropper rejects without gesture" is wrong on this engine. Always gate behind a real onclick handler — the engine simply PENDShow silently otherwise.






  
4. The Double-Open Wall

  
The spec is explicit: If another eyedropper is already open then return a new promise rejected with an "InvalidStateError" DOMException. This is an ENGINE singleton, not a per-instance singleton — one user gesture opens one modal eyedropper at a time, regardless of how many EyeDropper instances you've made. Live-verified on CfT 154: second open() from a DIFFERENT EyeDropper() instance rejects with "Failed to execute 'open' on 'EyeDropper': EyeDropper is already open."

5. SecureContext Gate

  
EyeDropper is marked Exposed=Window, SecureContext in the IDL. On plain HTTP (non-localhost) the whole class is absent — same object-absent law as Geolocation / Camera / WebUSB. Even 'EyeDropper' in window returns false.

  






  
6. AbortSignal Lifecycle

  
Pass new AbortController().signal; abort(reason) dismisses the eyedropper UI and rejects the promise with the supplied reason. Pre-aborted signal → rejects immediately with the raw reason value (CfT 154 LIVE: the reason arrives as a STRING, not a DOMException — same contract as fetch's abort). Cancelling mid-flight → promise rejects with your reason.

7. The Promise Resolves Once & Forever

  
ColorSelectionResult is a single dictionary with one field: sRGBHex: string. Always a valid simple color per CSS. The hex is in the form #rrggbb — never #rgb, never rgba, never oklch. Convert in JS for other spaces.

  






  
8. The Re-entry Cost

  
EyeDropper is no-stateful: the constructor is free, the prototype is empty, and you can construct thousands. But the user pays: every open() pulls focus from the page, hides the cursor, shows the magnifier, and waits for the next click. Don't open it in a rAF loop; cache the picked color in your own state.
