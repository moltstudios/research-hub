01 The whole grammar — two rule types, one JSON blob


A speculation rule is a JSON script tag. The engine parses it eagerly (including rules injected after load — that's how every lab on this page works), silently ignores invalid rules with only a console warning, and never throws into your page.


{
  "prefetch": [{
    "urls": ["/checkout"],              // list form: exact URLs
    "eagerness": "immediate",           // default for list rules
    "requires": ["anonymous-client-ip-when-cross-origin"],  // privacy-proxy prefetch
    "referrer_policy": "strict-origin-when-cross-origin"
  }],
  "prerender": [{
    "where": {                           // document form: pick URLs from the DOM
      "and": [
        { "href_matches": "/*" },
        { "not": { "href_matches": "/logout" } },
        { "not": { "selector_matches": ".no-spec" } }
      ]
    },
    "eagerness": "moderate"              // default for document rules (prerender)
  }]
}




✓urls and where are mutually exclusive per rule — mixing them invalidates the rule (console warning, no exception)


✓Injection after load works: document.createElement('script') + type="speculationrules" + head.append() — the engine re-scans on insertion


!Invalid JSON in the tag = silent no-op + one console warning. Your bundler's JSON minifier can break these tags


iSame rules can arrive via HTTP header Speculation-Rules: /rules.json (file must be served application/speculationrules+json) — CDN-friendly, zero HTML edits









02 Eagerness — corrected semantics


The four levels describe when the browser is allowed to speculate, not when it promises to. The 2026-05 entry garbled these ("50ms after viewport" for eager); the engine truth:




LevelFires onBest for


immediateRule observation — page load or injectionShort static URL lists (hero product, next wizard step)


eagerLink enters the viewport (dwelling briefly)Document rules on link-heavy pages


moderateHover / touch dwell on a matched linkThe default for document-rule prerender; the workhorse


conservativePointerdown / touchstartCheckout, heavy pages — maximum confidence, minimum head start




Budgets (Chromium, enforced per 30s window, FIFO eviction): immediate ≈ 50 prefetches / 10 prerenders; eager|moderate|conservative ≈ 2 prefetches / 2 prerenders each. Consequence: never write {"where":{"href_matches":"/*"},"eagerness":"immediate"} — you'll burn the budget on the first 10 links in DOM order, not the ones users want.




✓List-rule defaults: immediate. Document-rule defaults: moderate for prerender, moderate for prefetch (Chromium 121+)


!Budget is a ceiling on initiation, not a queue you control — eviction is FIFO and merciless


iHover-to-pointerdown is ~100–300ms of saved latency even when prerender doesn't fire; conservative still beats a cold nav

04 Live prerender lab — the arrival receipt


Prerender runs the full page — JS, layout, fetches — in a hidden frame and activates on click. This lab injects a prerender rule for ?stage=arrival&pre=1 (eagerness immediate) and hands you the link. If your engine honors it, the arrival banner reports activationStart > 0; if it doesn't (see §06 for how often that happens), you get an honest 0 with type: "navigate".





idle

Navigate → check activationStart

While prerendering, the target page sees document.prerendering === true; the moment you click, prerenderingchange fires and activationStart freezes the head start into the timing record.






✓Canonical proof chain: activationStart > 0 + document.prerendering at parse + prerenderingchange at activation — all three, or it didn't happen


✓Prerendered navigations can hit sub-50ms LCP — the render happened before the click


!Prerender executes your JS before the user commits — analytics, session heartbeats, and "page viewed" beacons all fire on speculate+activate, double-counting if unguarded


✗Prerenders are cancelled silently on: 30s timeout, memory pressure, eviction by budget, target cache-control changes — no DOM event tells the initiator









05 Activation-time JavaScript — the only correct patterns


// In the page that might be prerendered — run at top of bundle:
if (document.prerendering) {
  // Cold spec: page is rendering speculatively. NO analytics, no side effects.
  document.addEventListener('prerenderingchange', () => {
    // Activated by a real user navigation — NOW fire analytics.
    const nav = performance.getEntriesByType('navigation')[0];
    sendView({ activationStart: nav.activationStart });   // subtract from all timings
  }, { once: true });
} else {
  sendView({ activationStart: 0 });  // normal navigation
}

// Adjusting any user-timing by the head start:
const nav = performance.getEntriesByType('navigation')[0];
const tSinceClick = metric.startTime - nav.activationStart; // if > 0, prerendered




✓performance.now() keeps ticking during prerender — always subtract activationStart before comparing to user-perceived latency


✓prerenderingchange fires exactly once, only on activation. Cancellation fires nothing — design for "maybe it never activates"


!Chrome reserves prerender usage ~30s (configurable via ?...&__second_wait= internal) — a prerender that ages out is discarded and the nav goes cold

Across 20+ runs the prerender initiation path never once produced a server-side fetch, while prefetch fired reliably in identical environments. Whether the gate is environment detection, memory heuristics, or localhost/automation policy — the actionable truth is that you cannot assume prerender initiated. In production, verify with DevTools → Application → Speculative Loads (per-page status including exact "not used because…" reasons) or the NT2 proof chain from §04.




✗Honest fail: proactive prerender never initiated under automation/localhost on this host — treat any "prerender works" claim from a headless CI screenshot with suspicion


!DevTools' own Speculative Loads panel is the only surface that reports why an attempt was abandoned; CDP page sessions expose nothing (the Preloading domain is not attached to ordinary page targets)


iObserved on production: in an environment where prerender won't initiate (CDP-driven browser, this site), the prerender lab's navigation still returned deliveryType: "navigational-prefetch"', activationStart: 0 — the engine silently downgraded prerender to prefetch. You still win the fetch, you just don't win the render


✓Prefetch is the dependable half of this API — every environment, every rule form, every time. Ship prefetch first, treat prerender as upside









07 The supporting cast — headers that change the deal




Header / directiveWhat it does


Speculation-Rules: /rules.jsonLoads rules from an external file — must be same-origin, application/speculationrules+json


No-Vary-Search: params=("q") Lets a prefetched/prerendered URL survive query-string changes on listed params (search pages!)


Supports-Loading-Mode: credentialed-prerenderOpt-in on the target: allows cross-origin same-site prerender to send cookies


Content-Security-Policy: script-src 'inline-speculation-rules'Required when CSP restricts script-src — else inline rule tags are stripped






✓requires: ["anonymous-client-ip-when-cross-origin"] routes cross-site prefetch through a privacy proxy — required for cross-site prefetch, and prerender cannot use it (no cross-site prerender)


!No-Vary-Search works for speculation and back/forward cache — one header, two wins — but only in Chromium


✗CSP without 'inline-speculation-rules' (or a hash of the rule JSON) silently kills inline rules — a classic "works locally, dies behind the corporate CSP" trap









08 Safety list — what must never be speculated


Prerender is a real page load with no user. Everything that was true about "don't do this on load" is now true about "don't do this on a load the user may never commit to":




✗State-changing endpoints: logout, delete, add-to-cart POSTs, email sends — exclude with {"not":{"href_matches":"/logout"}} always


✗Analytics that double-fires on speculate+activate — guard with document.prerendering (§05)


!Cookie-dependent cross-origin pages need Supports-Loading-Mode opt-in or they prerender signed-out


!Heavy media pages — prerender budget is 2; a 40MB hero video will eat it and get evicted


✓Auth walls: prerendering them means you burned a slot on a redirect to /login; exclude by pattern


iServer load multiplies by speculation rate — watch your origin's cache-hit ratio before scaling document rules site-wide









09 Framework integration — Next.js patterns that survive


// app/layout.tsx — inline rules (remember CSP 'inline-speculation-rules')
export default function RootLayout({ children }) {
  return (<html><body>{children}
    <script type="speculationrules" dangerouslySetInnerHTML={{ __html: JSON.stringify({
      prefetch: [{ where: { href_matches: "/*" }, eagerness: "moderate" }]
    }) }} />
  </body></html>);
}

// middleware.ts — header-delivered rules (zero HTML coupling)
export function middleware(res) {
  res.headers.set("Speculation-Rules", "/rules.json");
  return res;
}




✓Start with moderate prefetch on all internal links — cheapest, safest, universally supported in Chromium, invisible if unused


✓Prerender the one or two money paths (product → cart for OpenDrones; case study → contact for Molt) with explicit URL lists


!Client-side routers (SPA-ish Next layouts) speculate URLs the router then re-renders — activation still works, but hydration cost lands at click-time; measure activationStart in RUM, not lab Lighthouse


i<link rel="prefetch"> and friends are the legacy tier; speculation rules supersede them in Chromium — don't double-speculate the same URL

11 Recap & why this stays P2



✓ 16 verified · ! 11 warnings · ✗ 8 falsified · 7 informational — 42 chips above


The one-paragraph truth: Speculation Rules is two APIs wearing one tag. Prefetch is a dependable, boring, universally-firing performance win — ship it on internal links today with moderate eagerness and prove hits via deliveryType. Prerender is a powerful but fragile contract: initiation is gated by budgets, memory, origin policy, and (as this entry's battery shows) entire environment classes where it silently never starts — so gate side effects on document.prerendering, verify activation via the NT2 chain, and treat every "prerender will fix our LCP" estimate as conditional until RUM shows real activationStart > 0 traffic.


Why P2, not P1: Chromium-only, zero effect in Firefox/Safari, and the wins are latency polish — transformative for e-commerce funnels (OpenDrones checkout), nice-to-have for a portfolio. The falsification findings (§06) raise its documentation value but not its urgency.
