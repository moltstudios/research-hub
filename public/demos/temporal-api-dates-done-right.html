Temporal — JavaScript dates, finally done right

After 9 years of design work, the Temporal API replaced the 1995-vintage Date object with immutable types, first-class time zones, explicit calendars, and arithmetic that survives daylight-saving transitions. It shipped in Chrome 144, Firefox 139, and Node 26 — here's what it fixes and how to adopt it before Safari catches up.

Checking Temporal support…
SECTION 01

Date's five original sins — reproduced live in your browser

The Date object was ported from Java 1.0 in 1995 and frozen into ECMAScript 1. Every defect became permanent, because the web never breaks backwards compatibility. These five bugs are why Moment, Luxon, and date-fns exist.

Sin #1 — Months are zero-indexed 
new Date(2026, 0, 1)  // month 0 = January 🤦

Thirty years of off-by-one bugs. Temporal: Temporal.PlainDate.from('2026-01-01') — what you write is what you get.

Sin #2 — Dates are mutable 
const d = new Date('2026-08-15T12:00:00Z');
addDayHack(d); // mutates d in place!

Pass a Date to any function and it can silently rewrite your value. Every Temporal method returns a new object.

Sin #3 — String parsing is ambiguous 
new Date('2/3/2026')
// Feb 3 or Mar 2? Depends where it runs.

Locale-dependent parsing produces values that differ between your laptop, your build server, and your user in Berlin. Temporal parses ISO 8601 only — one answer, everywhere.

Sin #4 — Date knows exactly two zones 
// UTC, and whatever the host machine is set to.
// "What time is it in Dublin?" = library territory.

Your server's ambient zone leaks into every value it touches. Temporal attaches the zone to the value: '2026-10-25T01:30:00[Europe/Dublin]'.

Sin #5 — Arithmetic drifts across DST (the expensive one)

Add "one day" to a timestamp the classic way — getTime() + 24*3600*1000 — and you get 25 or 23 wall-clock hours whenever daylight saving flips in between. Double bookings, renewal periods that don't line up, "why is the invoice date wrong" tickets. Section 6 shows Temporal's answer live.

The business case isn't developer comfort — it's eliminating a recurring class of production defect (billing periods, renewals, bookings, reporting windows) that Date is structurally incapable of preventing.
SECTION 02

The mental model: Plain · Instant · ZonedDateTime

Most date bugs in real codebases are category errors — a value that is conceptually a calendar date, stored and compared as an exact moment, picking up a spurious conversion on every hop. Temporal gives each concept its own type. Get the type right and half your timezone bugs become unrepresentable.

Temporal.PlainDate / PlainDateTime / PlainTime

A date on a calendar — no zone, no time

Invoice dates, dates of birth, sale dates, hotel check-in day. "August 15, 2026" means the same thing to every human who reads it. No conversions, no drift.

Temporal.PlainDate.from('2026-08-15')
Temporal.Instant

An exact point on the world timeline

Flight-log timestamps, event ordering, SLA clocks, "when did the server receive it." Two Instants compare unambiguously anywhere on Earth. UTC-natured, zone-free.

Temporal.Instant.from('2026-08-15T22:00:00Z')
Temporal.ZonedDateTime

A wall-clock time, in a specific place

"The appointment is at 9:00 in Dublin" — the meeting that must stay at 9:00 local even when DST rules change. Carries date + time + offset + zone + calendar.

Temporal.ZonedDateTime.from(
  '2026-10-25T01:30[Europe/Dublin]')

SECTION 04
Anatomy of a Temporal string — the zone is part of the value

  
A fully-resolved ZonedDateTime.toString() is a complete, self-describing record. No ambient state, no "it depends on the server."

  

    
2026-10-25T01:30:00+01:00[Europe/Dublin][u-ca=iso8601]

    

      ISO calendar date
      wall-clock time
      UTC offset (computed)
      named zone (the identity)
      calendar system
    

    
The named zone is the identity; the offset is derived from it. That's what lets .add() do the right thing across a DST transition — the value knows where it lives.

    

    

  







  
SECTION 05
Immutable by default — every operation returns a new value

  
No setters anywhere in the API. Data flows through your app without defensive copies.

  

    
const launch = Temporal.PlainDate.from('2026-08-15');
const scrub   = launch.add({ days: 7 });   // new value
launch.toString(); // still 2026-08-15 — unchanged
launch.with({ month: 9 });            // 2026-09-15 — also a new value

    

  







  
SECTION 06
The killer demo: arithmetic across a DST transition

  
US clocks spring forward on Sun March 8, 2026 (02:00→03:00). Starting from Saturday noon in New York, "add one day" and "add 24 hours" disagree — and only Temporal lets you say which one you mean.

  

    

      
      
    

    

      
Start (noon Saturday)
—

      
→

      
add({ days: 1 }) — calendar day
—

      
→

      
add({ hours: 24 }) — exact duration
—

    

    
// With Date, the classic hack silently picks ONE of these for you:
start.getTime() + 24*3600*1000  // = exact 24h. Wall clock shifts to 13:00. Was that intended?

    
Neither answer is "wrong" — they mean different things. Temporal's superpower is that the difference becomes explicit in your code instead of implicit in your bugs. Bookings want days: 1; SLA clocks want hours: 24.

  







  
SECTION 07
Ambiguous & nonexistent times — refuse to guess

  
Twice a year, some local times don't exist (spring forward) or happen twice (fall back). Date picks an answer silently. Temporal lets you choose the policy — including throwing at the system boundary, where a loud exception at write time is enormously cheaper than a wrong invoice in month three.

  

    

      
      
      
    

    

    

    
Result meaning: an epoch timestamp for each disambiguation shows the two candidate instants are genuinely different points in time (3600s apart). For billing and audit systems, reject at the input boundary + explicit resolution downstream is the pattern that pays for itself.

  







  
SECTION 08
Duration — flight-time math for Mission Control

  
Temporal.Duration handles both exact durations (90 minutes) and calendar durations ("2 months, 3 days"). Differences come from since() / until(), rounded to the units you ask for.

  

    
🚁 OpenDrones flight log — exact flight duration

    

      
      
      
      
      
      
    

    

    
const flight = launch.toInstant().until(land.toInstant());
flight.round({ largestUnit: 'hour', smallestUnit: 'minute' });
flight.total({ unit: 'minutes' }); // billable minutes

    
The launch/land Instants give exact airborne time (what the FAA log wants); the ZonedDateTimes preserve the local wall-clock story for the pilot's report. One value each, no conversion soup.

  







  
SECTION 09
Distributed fleet ops — live world clock, DST-aware

  
Four operating regions, ticking once per second. Each clock is a real Temporal.Now.zonedDateTimeISO(zone) — the UTC offset is computed from the current DST state of the zone, not a fixed offset table. This is the Mission Control sidebar, done in one line per city.

  

  

    
const now = Temporal.Now.zonedDateTimeISO('Asia/Tokyo');
now.hour;            // local wall-clock hour — DST-correct right now
now.offset;          // '+09:00' — derived, always in sync with the zone
now.timeZoneId;      // 'Asia/Tokyo'

  







  
SECTION 10
Calendars, YearMonth & MonthDay — the types Date never had

  
Temporal is calendar-aware via Intl's full calendar inventory, and ships the two "partial" types every billing and scheduling system eventually reinvents badly.

  

    

      Calendar systems
      
Temporal.PlainDate.from('2026-08-15[u-ca=hebrew]')
  .toLocaleString('en-u-ca-hebrew',
    { dateStyle: 'full' })

      

      
Hebrew, Islamic, Japanese, Chinese, Persian, Buddhist, Indian — first-class, not a plugin. Operations stay calendar-correct (adding a month in the Hebrew calendar is a Hebrew-calendar month).

    

    

      PlainYearMonth & PlainMonthDay
      
Temporal.PlainYearMonth.from('2026-08')
Temporal.PlainMonthDay.from('--08-15')
// recurring date with no year: birthdays, anniversaries

      

      
Billing periods, lease months, fiscal quarters, "same time next month" — modeled directly instead of Date + convention.

    

  







  
SECTION 11
Adoption strategy for August 2026 — asymmetric, on purpose

  
Support is uneven: backend done, browsers two-thirds done, iOS the holdout. Treat server and client as separate decisions.

  

    

      
✅ Do now

      
    
        
  • Node 26 backends: Temporal is unflagged (V8 14.6) — no new scheduling, billing, or reporting logic should start on Date.
    • 
        
  • Audit before migrating: grep new Date(, getMonth, setHours, date-lib imports; classify each site as Plain / Instant / Zoned. The audit alone finds bugs.
    • 
        
  • Fix storage semantics first: exact moments → timestamptz; calendar dates → date. Wrong at the DB = guesswork above it.
    • 
        
  • CI in a non-UTC zone: run one job in an aggressive-DST zone — most date bugs are invisible in UTC, which is exactly how they reach production.
    • 
      

    

    

      
🧩 Frontend, deliberately

      
if (!('Temporal' in globalThis)) {
  await import('temporal-polyfill');
}

      
    
        
  • Polyfill economics are unusually good: the FullCalendar temporal-polyfill is <20 kB min+gzip, tree-shakeable per-function — smaller than the date library it usually replaces, with a known removal date.
    • 
        
  • Boundary rule: parse external input with disambiguation: 'reject'; fail loudly at entry, not plausibly in the ledger.
    • 
        
  • Measure hot loops: Chrome's Temporal date arithmetic is currently slower than Date (parsing is faster); Firefox is near-parity. Don't migrate a hot loop on faith.
    •
