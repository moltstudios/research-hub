MediaRecorder API — In-Browser DVR: Record Canvas, Mic & Screen to Video Files

new MediaRecorder(stream) turns any MediaStream — canvas, webcam, mic, screen share, a Web Audio graph — into an encoded video/audio Blob entirely client-side. The missing RECORD button of the media tier: WebRTC streams it live, WebCodecs gives frame-level control, MediaRecorder is the one-liner DVR.

01Why this matters

Every project we ship already generates the raw material for video: animated heroes, canvas telemetry, live feeds. Today that material dies in the tab. MediaRecorder closes the loop with zero server, zero encoding pipeline, zero npm packages — the browser's own hardware encoder writes the file.

ConsumerUse case
Molt StudiosExport interactive case studies / hero animations as shareable MP4/WebM reels for socials & proposals; client testimonial capture (mic + slides canvas); "record your configuration" on 3D configurators.
OpenDronesMission DVR: a rolling buffer that keeps only the last N seconds, so an INCIDENT button saves pre-roll evidence after the event — without recording (and storing) entire flights. Pairs with WebRTC feeds (8c498f00) and the WAAPI mission replay (93ff8f41).
The tier story: getUserMedia/getDisplayMedia acquire → WebRTC transports live → MediaRecorder captures to file → WebCodecs (§11) is the escape hatch when you need frame-accurate control or faster-than-realtime export.

02Anatomy — five methods, six events, one Blob

const stream = canvas.captureStream(30);            // or getUserMedia / getDisplayMedia / audio graph
const rec = new MediaRecorder(stream, {
  mimeType: pickMime(),                             // MUST be probed — see §4
  videoBitsPerSecond: 2_500_000, audioBitsPerSecond: 128_000
});
rec.ondataavailable = e => chunks.push(e.data);       // BlobEvent — collect EVERY chunk
rec.onstop = () => {
  const blob = new Blob(chunks, { type: rec.mimeType });
  video.src = URL.createObjectURL(blob);                // play / download / upload
};
rec.start(1000);                                      // timeslice ms → chunk per second
rec.pause(); rec.resume(); rec.requestData(); rec.stop();

State machine: inactive → recording ⇄ paused → inactive. requestData() force-emits a chunk without stopping. videoBitsPerSecond/audioBitsPerSecond are requests — read back the actual values after construction (they differ per engine; §5 prints them live).

Three sources of MediaStreams: ① device — getUserMedia/getDisplayMedia; ② any <canvas> — canvas.captureStream(fps) (2D, WebGL, WebGPU — the animation itself becomes the video track); ③ Web Audio — AudioContext.createMediaStreamDestination() lets you mix mic + synthesized sound into one track (§7).

04The codec matrix — ask the browser, not the blog post

MediaRecorder.isTypeSupported(mime) is the ONLY reliable feature test. The landscape (probed live below on your engine):

  • Chromium & Firefox: WebM containers — VP8/VP9/AV1 video + Opus audio (FF also records Ogg/Opus audio).
  • Safari 14.1 → 18.3: MP4 / H.264 + AAC only. WebM requests returned false, full stop.
  • Safari 18.4 (Mar 2025)+: the dam broke — WebM (VP8/VP9 + Opus), Ogg, fragmented MP4, PCM/ALAC lossless, HEVC and AV1 recording. Safari flipped from the most restrictive recorder to arguably the most permissive.
MIMESupported hereNote
Production picker — order candidates best-first, take the first hit, let the tail be the universal fallback: 
const CANDIDATES = [
  'video/mp4;codecs="avc1.42E01E,mp4a.40.2"',  // H.264+AAC — plays everywhere incl. Safari<18.4, editors
  'video/webm;codecs="vp9,opus"',                // Chromium/FF, best quality-per-bit
  'video/webm;codecs="vp8,opus"',                // universal WebM floor
  'video/webm'                                   // last resort
];
const mimeType = CANDIDATES.find(m => MediaRecorder.isTypeSupported(m)) ?? '';
Why MP4 first when Chrome can also record MP4 (H.264): one file format across the whole client base — socials, iMessage, and Premiere all accept it, and MP4 carries real duration metadata (§10).

06Rolling buffer — "save the last 8 seconds" AFTER it happened

The OpenDrones killer pattern: with start(1000) you get a chunk per second. Keep a ring of the last N chunks, throw the rest away, and an INCIDENT button freezes evidence with pre-roll — recording 24/7 costs nothing because nothing is retained.

const KEEP = 8, ring = [];
rec.ondataavailable = e => {
  ring.push(e.data);
  if (ring.length > KEEP + 1) ring.splice(1, 1);   // evict from index 1 — NEVER index 0!
};
saveBtn.onclick = () => new Blob(ring, { type: rec.mimeType }); // init segment + recent clusters

Live falsification target: the WebM init segment (EBML header + track info) lives in chunk #0. Evict it like any other chunk and the saved file is garbage. That's why the eviction above starts at index 1 — and the ☠ button proves it by replaying a header-less blob.

09The hidden-tab freeze — and pause/resume

Canvas animation runs on rAF; rAF suspends in background tabs. Record, switch tabs for ~5s, come back: the WebM shows a frozen frame while wall-clock (and audio, if any) runs on. The recorder never stops — your source just stops painting.

Fix for mission-critical recording: paint from a Worker via transferControlToOffscreen() — worker rAF keeps running in background tabs, so the stream never freezes. That's the OffscreenCanvas entry (d73ebc12) doing DVR duty. Pause/resume, by contrast, is clean: a paused recorder emits NOTHING (no gap encoded), timestamps stay continuous.

10The duration: Infinity file — live falsification

Chromium's WebM muxer streams clusters without a final Duration element. The recorded FILE has no duration metadata — scrub bars break, editors complain, <video>.duration reports Infinity. Still true in 2026 (three repair libraries are actively maintained: ts-ebml, fix-webm-duration, webm-duration-fix). Probe it:

const v = document.querySelector('video');
v.src = URL.createObjectURL(webmBlob);
v.onloadedmetadata = () => {
  if (v.duration === Infinity) {
    v.currentTime = 1e101;                    // force seek past EOF — engine computes real length
    v.ontimeupdate = v.ontimeupdate || (() => {
      v.ontimeupdate = null; v.currentTime = 0;   // now v.duration is the REAL number
    });
  }
};
Honest limits: the 1e101 trick repairs the element, not the file — the downloaded WebM still lacks metadata. For file-level repair append the duration element with fix-webm-duration (pure JS, ~2KB), or sidestep the whole class of bugs by recording MP4 when the engine allows (§4 picker puts H.264 MP4 first for exactly this reason).

11MediaRecorder vs WebCodecs — when to reach higher

MediaRecorderWebCodecs + muxerffmpeg.wasm
ModelRealtime black box: stream in → encoded Blob outFrame-accurate: you feed VideoFrames, get EncodedVideoChunks, mux yourself (mediabunny, formerly mp4-muxer)Transcode anything, ~25MB wasm
Speed1× (wall clock)Faster than realtime — render 1000 frames, encode, doneSlow (wasm single-thread unless COOP/COEP)
Controlmime, bitrates, timeslice — that's itPer-frame keyframes, GOP, size changes, HDR, precise seekingEverything ffmpeg does
Effort~10 lines~150 lines + muxer libPipeline glue + memory
Use whenRecording live/interactive sessions (DVR, testimonials, screen capture)Exporting rendered content (reels, GIF-ish clips, offline render)Transcoding existing files client-side

Real-world datapoint: apps that shipped MediaRecorder→WebM→ffmpeg.wasm transcode pipelines have publicly replaced the ffmpeg leg with WebCodecs+MP4 muxing for 5-20× faster exports. Rule of thumb: if a human watches it happen live, MediaRecorder; if a machine renders it, WebCodecs.
