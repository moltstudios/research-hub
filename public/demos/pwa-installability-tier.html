PWA Installability — the install tier

"Installable" is not a vibe: it is a checklist the browser runs (manifest + icons + start_url + display + HTTPS + a service worker with a fetch handler), a one-shot event that hands you the ask (beforeinstallprompt), and a surface the app lands on once installed (display-mode, launchQueue, getInstalledRelatedApps). This page measures every criterion live from real values, registers a real service worker and watches clients.claim() flip the controller, and is honest about the one thing that cannot be forced: the prompt event itself.

§1 · Why installability — and what is measured vs claimed

THE RETENTION LAW. An installed PWA is a home-screen icon with zero install friction — no store, no download, no review queue. The retention numbers quoted around PWAs (installed apps opened ~2–3× more often, fewer checkout drop-offs) are industry claims, not measurements on this page — they are labelled [claim] below and must be re-measured on OpenDrones' own analytics. What is measured here: this very session runs in a plain browser tab (display-mode: browser), on a secure context, with the install-event surface present — the exact before-state an OpenDrones operator starts from.

The OpenDrones pitch in one line: Mission Control is a re-ordered-ten-times-a-day tool; an operator who installs it gets an icon, a standalone window and an offline shell instead of a bookmark they never open. The install flow is the cheapest retention lever in the whole stack — it costs one manifest, one service worker, and one well-timed button.

THE MISSING-MEMBER LAW. Chrome's hard failures are few: no name/short_name, no start_url, no icon ≥144px, display: browser, no service worker with a fetch handler, insecure origin. Everything else — theme_color, background_color, shortcuts, screenshots, file_handlers — is richness: the app still installs without them, it just gets a plainer install sheet, no jump-list, no file association. Budget your effort accordingly: the six hard rows first, richness second.

§4 · THE SERVICE-WORKER LANE — real registration, real claim, live controller flip

SW scripts cannot be Blob/data URLs — they must be same-origin http(s) files (measured constraint; a blob: registration rejects with a security error). So this page registers /pwa-install-sw.js when the gate server (or a deployment that ships it, source below) serves it — and reports the constraint honestly when it isn't there.

THE CLAIM LAW. A page load is not controlled by a service worker it registers itself — navigator.serviceWorker.controller reads null until the next navigation… unless the SW calls clients.claim(), which adopts existing tabs and flips controller to a live ServiceWorker mid-session. That flip is measured live above — it is the single most misunderstood line in PWA onboarding code.
// pwa-install-sw.js — ship this file next to the page to make §4 pass everywhere.
// Chrome's criterion: a fetch handler, registered synchronously at eval time.
self.addEventListener('install',  function () {});                       // no precache in the demo
self.addEventListener('activate', function (e) { e.waitUntil(clients.claim()); });
self.addEventListener('fetch',    function () {});                       // pass-through observer:
                                                                          // seen, never answered — network proceeds

Note the pass-through fetch handler: Chrome's installability check only requires that the handler exist — the offline behaviour is your product decision (§9's offline order-status capstone is where it starts earning). The demo unregisters the worker after measuring, and this page keeps its controller until reload — also measured, above.

§5 · THE INSTALL-PROMPT LANE — the event, honestly

THE ONE-SHOT LAW. beforeinstallprompt is a deferred, single-use capability: call e.preventDefault() to suppress the mini-infobar, stash the event, and later — inside a user gesture, ideally after a conversion — call e.prompt(). The userChoice promise resolves once with {outcome:'accepted'|'dismissed', platform}; the event object is dead afterwards. There is no second prompt from a stashed event. And the event itself only ever fires when the browser's promotability + engagement heuristics pass — headless Chromium does not run them, so the event does not fire there (measured twice on real probes, and again on this page: see the wait chip).
// The full production flow — this is the lane the chips above measure the presence of.
let deferred = null;                                  // the one-shot handle
addEventListener('beforeinstallprompt', (e) => {      // heuristics passed (NOT in headless)
  e.preventDefault();                                 // suppress the mini-infobar
  deferred = e;                                       // stash for your own button
});
installBtn.addEventListener('click', async () => {    // MUST be inside a user gesture
  if (!deferred) return showPlatformInstructions();   // iOS/Firefox never get the event
  deferred.prompt();                                  // the native install sheet
  const { outcome } = await deferred.userChoice;      // 'accepted' | 'dismissed'
  deferred = null;                                    // spent — never reuse
  if (outcome === 'accepted') hideInstallUI();
});
addEventListener('appinstalled', () => hideInstallUI());  // fires after real install

§6 · THE INSTALLED SURFACE — display-mode, overlay geometry, related apps

The install moment is detectable after the fact by media query: an installed standalone PWA matches (display-mode: standalone) — that's the signal to hide your custom install button ("already installed") and to switch analytics to "app session". On desktop Chromium, display_override can request window-controls-overlay, whose titlebar geometry is readable in CSS via env(titlebar-area-*) and in JS via navigator.windowControlsOverlay — both measured below.

THE RELATED-APPS LAW. navigator.getInstalledRelatedApps() exists and resolves — but it only ever reports apps listed in the manifest's related_applications AND installed natively on the machine. With an empty list it resolves [] (measured below). It is a native-app bridge (Play/Store packages), not a "am I installed?" check — use display-mode for that.

§7 · THE LAUNCH QUEUE — file handling for an installed PWA

THE FILE-HANDLING CHAIN. For a PWA to receive a file the OS hands it, three links must all hold: the manifest declares file_handlers (action in scope + accept MIME map — validated in §3), the app is actually installed (no handler surface for a tab), and the page arms launchQueue.setConsumer() — the callback then receives LaunchParams with files (real FileSystemFileHandles) and targetURL. Miss any link and the queue exists but never speaks. OpenDrones angle: "open flight log .csv in Mission Control" is a two-line manifest entry once installed.

§9 · CAPSTONE — the conversion-timed install button (live)

The recommended product pattern, running right here: the install button starts disabled. Fire the conversion first ("order confirmed" in OpenDrones' real flow — the button below stands in for checkout success), watch the user-activation flags flip, and then offer the install. Never on load. Never a mini-infobar you don't own.

THE TIMING LAW. The prompt converts best at a peak of gratitude: right after checkout succeeds, right after the first flight log renders. At page load the user has no reason to accept — you'd burn the one-shot event on a stranger. Gate the button on: conversion event → deferredPrompt stashed → matchMedia('(display-mode: browser)').matches (not already installed) → click → prompt(). No deferred event (iOS, Firefox, headless)? Show the §8 instructions card — measured live by the button above.

Offline order-status capstone: the §4 service worker plus the Cache API is enough to ship "your last known order + flight status" offline — the page opens with a home-screen icon in a field with one bar of signal and still shows the operator something true (labelled with sync time). That, not a splash screen, is the reason the SW lane exists. Molt client angle: the §2 checklist plus the §9 button pattern is a productizable "installability audit + install flow" deliverable for every e-commerce client — half a day of work, permanently compounding retention.

  1. Installability is a checklist, not luck — §2 is the whole contract, computed from real values.
  2. The prompt event is one-shot, gesture-bound and heuristic-gated; treat "it didn't fire" as an environment fact.
  3. preventDefault() the infobar, own the button, time it after conversion.
  4. SW registration does not control the registrant — clients.claim() does; measure it, don't assume it.
  5. Manifest hard criteria: name, start_url, ≥144px icon, display, SW, HTTPS. Everything else is richness.
  6. getInstalledRelatedApps bridges to native apps only — [] without related_applications.
  7. File handling = manifest file_handlers + real install + launchQueue.setConsumer — all three or nothing.
  8. iOS Safari and Firefox never fire the event; ship the instructions card as the primary path.
  9. Headless can develop everything except the prompt — gate the prompt in headful.
  10. Label what you didn't measure: [claim] for industry numbers, [doc] for cross-platform facts.
