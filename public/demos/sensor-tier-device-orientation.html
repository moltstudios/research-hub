§01 The model — one IMU, three Euler angles, two doors

Every phone IMU answers one question — "which way is the device pointing?" — and the platform exposes it through two APIs built a decade apart: the legacy deviceorientation/devicemotion events (universal, 2011-era), and the Generic Sensor family (AbsoluteOrientationSensor, Accelerometer…, Chromium-only). Same silicon, different contracts.

The spec's rotation is intrinsic Z-X-Y: R = Rz(α)·Rx(β)·Ry(γ) — device frame → earth frame. α is a compass-like heading (0 = north-ish, depends on the source), β tilts around the long axis, γ rolls around the screen-perpendicular... no — γ rolls around the axis parallel to the top edge. Get this wrong and your horizon flies backwards (§09).

§02 The null-wall — trusted events, worthless values

The single most important engine truth for this tier, and it never appears in tutorials: on a machine with no IMU, Chromium still fires deviceorientation, deviceorientationabsolute and devicemotion — isTrusted: true — with every value null. Listeners run; math feeds on null; NaN propagates into your transforms.

Live — 2.5s listen on this host (auto-ran on load)

// The guard every tilt feature needs — before the first null reaches Math.cos()
addEventListener('deviceorientation', e => {
  if (e.alpha === null || e.beta === null || e.gamma === null) return;  // no sensor — stay in fallback mode
  render(e.alpha, e.beta, e.gamma);
});
Production meaning: "the event fired" is NOT "the feature works". Feature-detect the values, not the listeners — ship the pointer/scroll fallback until a non-null reading arrives.

§04 The twin pipelines — relative vs absolute, and the override that only feeds one

deviceorientation (relative: may drift, magnetometer-free on some engines) and deviceorientationabsolute (fixed earth frame: needs a magnetometer/fusion source) are separate provider pipelines that happen to share an event shape. The absolute twin sets e.absolute = true and fires in addition — never instead.

§05 The permission ladder — the iOS gesture wall & the query-name lies

iOS 13+ gates both event families behind DeviceOrientationEvent.requestPermission(), which must be called inside a user gesture — call it on load and it rejects. Desktop Chromium ships the same method as a no-op that resolves 'granted' with no prompt and no gesture. Your ladder has to handle both.

async function enableTilt(btn) {
  const D = typeof DeviceOrientationEvent !== 'undefined' ? DeviceOrientationEvent : null;
  if (D && typeof D.requestPermission === 'function') {
    try { const v = await D.requestPermission(); if (v !== 'granted') return fallbackMode(); }  // iOS: inside the tap handler, only
    catch { return fallbackMode(); }
  }
  startListening();  // desktop/Android: events flow without asking
}

§07 The quaternion bridge — one rotation source behind both doors

The headline cross-check of this study: inject Euler angles through the legacy door (CDP → deviceorientation) and read them through the modern door (RelativeOrientationSensor.quaternion) — then verify the spec's own Euler→quaternion math (intrinsic Z-X-Y) against the live quaternion. If they agree, both doors read the same rotation provider.

Driven — inject (100°, 20°, 30°), read the sensor quaternion, compare

// W3C DeviceOrientation § — Euler (Z-X-Y intrinsic) → quaternion, the reference conversion
function eulerToQuaternion(a, b, g) {           // degrees in, [x,y,z,w] out
  const d = Math.PI / 180, A = a*d, B = b*d, G = g*d;
  const R = mul(rotZ(A), mul(rotX(B), rotY(G))); // R = Rz·Rx·Ry
  return matrixToQuaternion(R);                // Shepperd's method — see demo source
}
// quaternions double-cover: q and −q are the SAME rotation — compare via |dot| ≈ 1
Gimbal lock: at β = ±90° (phone vertical), α and γ rotate around the SAME axis — Euler degenerates. The quaternion path has no such singularity: it's the reason aviation HUDs and AR engines convert immediately and never transport Euler across module boundaries.

§08 Screen compensation — the compass that spins when you rotate the phone

α/β/γ are in the device frame — they do not change when the OS rotates your UI. A portrait-designed heading tape held in landscape reads off by the screen angle. Compensate with screen.orientation.angle (§ sibling study 76eb1c6f):

const ang = (screen.orientation && screen.orientation.angle) || window.orientation || 0;
headingEl.style.transform = `rotate(${(alpha - ang + 360) % 360}deg)`;  // heading-only fix — full fix rotates the whole frame
