Prerendered pagereveal — the activation tier

The queue question: does pagereveal fire on prerender activation, and does the activated page get a cross-document View Transition? What the probe found first was a wall — and the wall is itself the headline law. Below it: everything that IS measurable about speculation × navigation today, live in your browser.

Under a CDP-driven browser (Playwright/Puppeteer), prerender initiation never fires. 02The prefetch × morph compatibility law — live lab

Can a prefetched navigation still run a cross-document View Transition? Yes — fully. Measured: prefetched arrival fires pagereveal with viewTransition set and all 10 UA animations run, identical to a cold navigation. The both-pages opt-in (@view-transition) still governs — a prefetched page without it gets the stamp but no morph. The zero-JS instant-nav recipe ships today: speculation prefetch + the VT opt-in on both pages.

07Capstone: OpenDrones instant mission-nav

The fleet console pattern: every drone card's detail page gets a prefetch rule with eagerness:"moderate" (hover-dwell) plus the @view-transition opt-in on index + detail. Result on Chromium-class engines: hover → prefetch, click → morph from the prefetched response, zero JS in the transition path. WK users: HTTP cache still serves deliveryType:"cache" arrivals (fast, no stamp). FF users: plain cache, plain navigation — the honest degradation.

<script type="speculationrules">
{ "prefetch": [{ "source": "document", "where": { "href_matches": "/drones/*" },
                 "eagerness": "moderate" }] }
</script>
<style>@view-transition { navigation: auto; }</style>
<!-- + one view-transition-name per card. Done. -->
✓Telemetry recipe: log deliveryType on arrival — "navigational-prefetch" = your speculation won the fetch; "cache" = the disk cache did; "" = cold. Three users, three receipts, one line of JS.

09Method, falsifications, limits

Open the method block

Method: 3 probe generations + 12 isolation configs ×3 engines over plain-HTTP loopback and production HTTPS; truth from the server request log (the receipt — Sec-Purpose headers), NavigationTiming arrival fields, in-document event logs, timed getAnimations() censuses, CDP Target.setDiscoverTargets for prerender-target materialization, and a self-signed-HTTPS lane for the secure-context hypothesis.

Falsified this session (2, mine): (1) "self-signed HTTPS / secure context unlocks prerender under automation" — it doesn't; the wall is CDP-shaped, not scheme-shaped (prod HTTPS replication seals it). (2) "static inline rules initiate where injected ones don't" — both fire prefetch, neither fires prerender. Plus one harness bug caught in-session: gen-1's bare /b.html href dropped the destination's query (the both-pages law ate the control lane — my own instrument, the href-equivalent of the stale-selector strike).

Instrument lessons (2): (1) setContent = opaque origin — speculation (even prefetch) never fires on setContent pages; goto only. (2) THE UNIQUE-URL LAW — max-age cross-lane cache contamination: a prefetch lane reusing the control lane's URL reads a disk-cache hit (no server request) as a "successful prefetch"; every speculation lane gets a unique URL + explicit cache-control.

Lane limits: prerender activation, activationStart > 0, pagereveal-at-activation, and the prerender budget are human-hand lanes (the wall); WK prerender/prefetch measured on the installed 26.5 build only; no Windows/Android; Chromium Prerender2 holdback population share unknown.
