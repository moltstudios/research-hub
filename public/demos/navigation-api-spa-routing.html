Section 2

History API vs Navigation API — Side by Side

The History API was never designed for SPAs. Navigation API fixes its core shortcomings.

🔇 History API (Old)

  • Three separate mechanisms: pushState, popstate, click handlers
  • popstate doesn't fire on pushState/replaceState
  • Can't read the full history stack
  • Can't edit non-current entries
  • No built-in focus management
  • No async scroll restoration
  • No form submission handling
  • Inconsistent cross-browser behavior

🔊 Navigation API (New)

  • One navigate event for ALL navigation types
  • Link clicks, back/forward, programmatic — all caught
  • Full history stack access via navigation.entries()
  • Per-entry state via getState()
  • Automatic focus restoration on back/forward
  • scroll: 'manual' + event.scroll() for async
  • Form submissions via event.formData
  • intercept() with committed + finished promises

The old way — 3 separate APIs wired together manually

// 1. Click handler — intercept link clicks globally
document.addEventListener('click', (e) => {
  const link = e.target.closest('a[data-route]');
  if (!link) return;
  e.preventDefault();
  history.pushState(null, '', link.href);
  renderRoute(new URL(link.href).pathname);
});

// 2. popstate — handle back/forward SEPARATELY
window.addEventListener('popstate', (e) => {
  renderRoute(location.pathname);
});

// 3. Initial render — doesn't fire any event
renderRoute(location.pathname);

// Problems:
// - popstate doesn't fire on pushState/replaceState
// - No form submission handling
// - No scroll restoration for async content
// - Can't inspect the full history stack
// - Edge cases galore (cross-origin iframes, etc.)

The new way — one centralized event

// ONE listener catches: link clicks, back/forward,
// programmatic navigate(), form submissions, reloads — everything
navigation.addEventListener('navigate', (event) => {
  if (!event.canIntercept) return;  // cross-origin, downloads

  const url = new URL(event.destination.url);

  event.intercept({
    async handler() {
      const content = await fetchContent(url.pathname);
      document.getElementById('app').innerHTML = content;
    }
  });
});

// That's it. URL updates, history stack, focus management —
// all handled automatically by the browser.

Section 5

intercept() + View Transitions — App-Like Route Morphs

The Navigation API and View Transitions API are designed to work together. Wrap DOM updates inside document.startViewTransition() during intercept for seamless animated route changes.

The 10-line recipe for animated route transitions

navigation.addEventListener('navigate', (event) => {
  if (!event.canIntercept || event.hashChange) return;

  const url = new URL(event.destination.url);

  event.intercept({
    async handler() {
      const content = await fetchRouteContent(url.pathname);

      // Wrap DOM update in a view transition
      document.startViewTransition(() => {
        document.getElementById('app').innerHTML = content;
      });
    }
  });
});

With named view-transition-name for targeted animations

/* CSS — name the element you want to morph */
#spa-view {
  view-transition-name: spa-root;
}

/* Old snapshot slides left, new slides in from right */
::view-transition-old(spa-root) {
  animation: slide-out-left 0.3s ease-in forwards;
}
::view-transition-new(spa-root) {
  animation: slide-in-right 0.3s ease-out forwards;
}

@keyframes slide-out-left {
  to { transform: translateX(-30px); opacity: 0; }
}
@keyframes slide-in-right {
  from { transform: translateX(30px); opacity: 0; }
}

The SPA demo above (Section 3) uses this exact pattern. If your browser supports View Transitions, route changes animate smoothly. The browser snapshots the old DOM, runs your handler, snapshots the new DOM, and morphs between them — all off the main thread.

The composability story: Navigation API + View Transitions + Scroll Restoration = the full SPA toolkit, all native. No React Router, no Framer Motion page transitions, no manual scroll position caching. The platform handles it.
Section 6

History Stack Explorer — navigation.entries()

The Navigation API exposes the full history stack — a massive improvement over the History API, which only gives you history.length and history.state.

Click "Refresh Stack" to see the live history entries.

What each entry gives you

const entries = navigation.entries();

entries.forEach((entry, i) => {
  console.log({
    index: i,
    url: entry.url,            // full URL of this entry
    key: entry.key,            // stable ID — use with traverseTo()
    id: entry.id,              // unique per entry
    state: entry.getState(),   // developer-defined state object
    sameDocument: entry.sameDocument,  // true if same-origin SPA route
  });
});

// Current entry
console.log(navigation.currentEntry.url);

// Jump to any entry by key
navigation.traverseTo(someEntryKey);

// Go back / forward
navigation.back();
navigation.forward();
Why this matters: With the History API, history.length tells you how many entries exist but not WHAT they are. You can't inspect the stack, can't jump to a specific entry by identity, and can't detect when entries are disposed (e.g., when the user navigates back then forward to a new location). The Navigation API gives you full visibility.
Section 7

Per-Entry State Management

Each history entry has its own state object — perfect for restoring scroll position, form data, or UI state when the user navigates back.

The three ways to set state

// 1. Set state during navigate()
navigation.navigate('/?route=dashboard', {
  state: { scrollY: 420, filter: 'active' }
});

// 2. Set state during reload()
navigation.reload({
  state: { visitCount: (navigation.currentEntry.getState()?.visitCount || 0) + 1 }
});

// 3. Update state without navigation — for ephemeral UI state
// (e.g., expand/collapse state, scroll position)
navigation.updateCurrentEntry({
  state: { ...navigation.currentEntry.getState(), detailsOpen: true }
});

// Read state
const state = navigation.currentEntry.getState();
// { scrollY: 420, filter: 'active', detailsOpen: true }

Listen for state changes

navigation.addEventListener('currententrychange', (event) => {
  console.log('Navigation type:', event.navigationType);
  console.log('Previous entry:', event.from);
  console.log('New entry:', navigation.currentEntry);

  // Restore UI state from the new entry
  const state = navigation.currentEntry.getState();
  if (state?.scrollY) window.scrollTo(0, state.scrollY);
  if (state?.filter) setFilter(state.filter);
});
Key difference from History API state: history.state is serialized to JSON on every pushState, losing references and prototypes. Navigation API state is structured-clone compatible (preserves Dates, Blobs, etc.) and updates atomically via updateCurrentEntry().

Form Submissions — No onsubmit Needed

The navigate event automatically catches same-document form submissions. Access the data via event.formData — no preventDefault(), no fetch() boilerplate.

OpenDrones Arc Pre-Order Form

✓ Order submitted! Check the event log below.

How the form is handled — zero form-specific JS

// The SAME navigate event handler catches form submissions
navigation.addEventListener('navigate', (event) => {
  if (event.formData && event.canIntercept) {
    // Standard HTML form → automatically caught here
    const data = event.formData;

    event.intercept({
      async handler() {
        const customer = data.get('customer');
        const model = data.get('model');
        const qty = data.get('quantity');

        await submitOrder({ customer, model, qty });
        renderOrderConfirmation(customer, model, qty);
      }
    });
  }
});

Baseline 2026 Newly Available — ~93% global traffic. Chrome/Edge had it since 2022 (4 years head start). Firefox 147 and Safari 26.2 closed the gap in early 2026, making it Baseline.

Caveat: Safari 26.2 is missing precommitHandler support, which limits some advanced redirect-during-navigation patterns. The core navigate + intercept surface is fully supported.

Does this kill React Router / TanStack Router?

No — but it changes what you reach for. React Router and TanStack Router have open discussions about adopting the Navigation API as their backend. They sit on top of it rather than reimplement the History API workarounds. The frameworks still add value: nested routes, data loaders, error boundaries, code splitting.

What the Navigation API kills: the need to install a router just to avoid full-page reloads on a content site. If your routing needs are modest — a blog, a docs site, a dashboard with a handful of views — the platform now has you covered.
