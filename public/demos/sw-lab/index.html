01What actually registers, and where

A service worker is an event-driven script the browser runs off the main thread. It has no DOM access, no localStorage, and it stays asleep between events — the browser may terminate it after ~30 s idle and restart it later, resetting all its globals. It exists for exactly three interception jobs: fetch, push/sync, and offline serving.

Registration anatomy — the only two facts that determine everything else:

// script URL + scope, both resolved against the PAGE that registers
const reg = await navigator.serviceWorker.register('./sw.js');
// default scope = the directory containing sw.js → /demos/sw-lab/
// the worker intercepts fetches ONLY from pages inside its scope

02Scope rules — enforced live

Scope is a path prefix. You may never register a scope broader than the worker script's own directory unless the server sends Service-Worker-Allowed. And a scope can only be owned by one registration at a time.

The noclaim companion directory /demos/sw-lab-noclaim/ registers its own worker — two workers, two scopes, zero interference. That is the deployment pattern you want.

Why event.waitUntil() matters: install and activate can outlive their event handler's synchronous code. waitUntil(promise) tells the browser "keep this worker alive and this state open until the promise settles." Without it, an async precache can be killed mid-flight — the worker gets terminated and the install fails. Same pattern for fetch: respondWith(promise) holds the response channel open.

04Control & claim() — the most misunderstood fact

A page only becomes controlled when it loads after a worker in its scope is active — or when the worker calls clients.claim() from activate. The lab below loads a page before its worker activates (the worker deliberately skips claim) — watch it stay uncontrolled until reload.

// the two control-adoption patterns
self.addEventListener('activate', e => {
  e.waitUntil(self.clients.claim());   // adopt already-open pages, no reload needed
});
// WITHOUT claim: pages opened before activation stay uncontrolled until
// they are reloaded — "works on the second visit" is literally this rule

05Updates, registration identity & unregister

The browser byte-compares the worker script: same bytes → same worker, no update event; changed bytes → new worker installs and (with skipWaiting) activates. Updates are checked on navigation and every ~24 h while open — and by default the main script fetch bypasses the HTTP cache (updateViaCache: 'imports'), so you can't wedge yourself with a stale worker file.

// the production update dance (versioned caches + skipWaiting + refresh)
const V = 'shell-v7';
self.addEventListener('install', e => e.waitUntil(
  caches.open(V).then(c => c.addAll(SHELL)).then(() => self.skipWaiting())
));
self.addEventListener('activate', e => e.waitUntil((async () => {
  for (const name of await caches.keys())      // delete everything that isn't this version
    if (name !== V && name.startsWith('shell-')) await caches.delete(name);
  await self.clients.claim();
})()));

06CacheStorage anatomy — no service worker required

caches is available to any secure context: window, dedicated worker, even with zero registrations. It is a named-bucket store of Request→Response pairs, completely independent from the HTTP cache, with no built-in expiry — you are the garbage collector.

07Cache matching — URL keys, query strings, methods

Keys are full URLs including query strings. Matching is exact by default; three request-matching options bend the rules.

cache.match(request, { ignoreSearch, ignoreMethod, ignoreVary })

08Single-read bodies & atomicity traps

A Response body can be read once. cache.put() reads the body — so a response you already consumed cannot be cached, and a response you cache can still be cloned first. add()/addAll() add a status check that put() deliberately lacks.

The add-vs-put asymmetry, in one line each: cache.add(url) = fetch + reject unless status 200 + put. cache.put(req, res) = store whatever you hand it — including 404s and 500s, which is how a naive cache-first strategy can permanently serve an error page offline. Real apps validate res.ok before putting.

09Opaque responses — cached but metered

A no-cors cross-origin fetch resolves, but the browser hides everything: status: 0, type: 'opaque'. These can be cached — yet browsers pad their storage cost (~7×) against quota because real size can't be inspected.

11Navigation preload & Static Routing API

Two latency-repair tools. Navigation preload starts the network request for navigations while the worker boots, killing the "first load after idle is slow" penalty. The Static Routing API (InstallEvent.addRoutes, Chrome 123+, Safari 27, not yet in Firefox) routes matching requests straight to cache/network without waking the worker at all — routes can only be registered inside install.

12Production capstones

OpenDrones Mission Control: the offline pattern is precache-the-shell + runtime-cache-the-telemetry + versioned cleanup. The capstone run flips the worker offline and proves every shell asset still serves.

Molt Studios — static-site worker in ~25 lines (versioned precache, runtime fill, cleanup, copy-paste ready):

const V = 'molt-v1';
const SHELL = ['./', './index.html', './styles.css', './app.js'];
self.addEventListener('install', e => e.waitUntil(
  caches.open(V).then(c => c.addAll(SHELL)).then(() => self.skipWaiting())
));
self.addEventListener('activate', e => e.waitUntil((async () => {
  for (const name of await caches.keys())
    if (name !== V && name.startsWith('molt-')) await caches.delete(name);
  await self.clients.claim();
})()));
self.addEventListener('fetch', e => {
  if (e.request.method !== 'GET') return;                 // never touch mutations
  e.respondWith(caches.open(V).then(async cache => {
    const hit = await cache.match(e.request);
    if (hit) return hit;                                  // cache-first
    const res = await fetch(e.request);
    if (res.ok && new URL(e.request.url).origin === location.origin)
      cache.put(e.request, res.clone());                  // runtime fill, same-origin only
    return res;
  }));
});

Gotcha wall — the traps that bite in production:

  • 24-hour update ceiling: open pages check for worker updates on navigation and at most every 24 h — stale workers persist by design.
  • No dynamic import() in workers; importScripts() works but URLs are resolved statically at first evaluation.
  • Forbidden APIs: localStorage, synchronous XHR, alert — the worker is not a page.
  • Idle termination (~30 s): all worker globals are volatile; re-derive state on every event.
  • Caches never expire: no TTL, no header awareness — unversioned caches grow forever; your activate cleanup is the GC.
  • unregister() keeps caches and storage: it removes the worker, not the data — clean up explicitly.
  • Secure contexts only (HTTPS or localhost) — service workers silently don't exist otherwise.
  • A fetch-less worker still controls pages — but addRoutes with source:'fetch-event' then throws.
