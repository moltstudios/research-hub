Payment Request API — the checkout tier

The native browser sheet for credit cards, Apple Pay/Google Pay, and URL-based payment handlers. Live-probed engine truths: the strict ISO 4217 currency validation, the "after the first show() needs gesture" wall, the secure-payment-confirmation statics, modifier data must be an object, and the no-method-manifest = silent console error.

Reach: Chrome 67+ (Apr 2018) · Safari 12.1+ (Mar 2019) · Edge 79+ · Firefox removed 2018, behind flag since 2024 (~70% unflagged, ~85% with flag)
Surface: 12 prototype members, 2 statics · main-thread only · secure-context only
OpenDrones fit: Arc pre-order checkout + Battery store + Compliance report purchase

1 Live capability detection probe

Three checks for support. The PaymentRequest constructor is THE gate — if absent, fall back to a hosted-checkout redirect (Stripe Checkout, Braintree, etc.).

if ('PaymentRequest' in window) {
  const req = new PaymentRequest(
    [{ supportedMethods: 'basic-card' }],
    { total: { label: 'T', amount: { currency: 'USD', value: '10.00' } } }
  );
  if (await req.canMakePayment()) { /* show the sheet */ }
}

2 Prototype surface (12 members) + 2 statics probe

The shipped API is one constructor + 3 lifecycle methods (show / abort / retry) + 5 readonly state properties + 2 event handler attrs + canMakePayment / hasEnrolledInstrument. Plus 2 statics on the constructor: securePaymentConfirmationAvailability and getSecurePaymentConfirmationCapabilities (the SPA/SPC tier). MDN's PaymentRequest.supports() proposal did NOT ship — the static is undefined on CfT 148 / Brave 154.

3 Method identifiers: the format wall probe

Three legal identifier shapes: the legacy short names (basic-card), the URL methods (https://merchant.example/pay), and secure-payment-confirmation (the EMV 3-D Secure / FIDO-based WebAuthn payment auth). The format is strict — empty strings, whitespace, and bare scheme prefixes all throw. The engine ALSO fetches the URL's payment method manifest at constructor time (the Link: rel=payment-method-manifest HTTP header convention) — a silent console error if 404.

4 PaymentCurrencyAmount — strict ISO 4217 probe

Currency codes must be exactly 3 ASCII letters. 'us' (2-letter), 'USD ' (trailing space), and '012' (numeric) all throw RangeError. The amount value must be a valid decimal string — '1e2' (scientific) throws. '0.00' is legal (zero-cost orders). Total amount must be non-negative (displayItems can be negative for discounts/refunds).

5 Options: shippingType + requestPayer* probe

Four request* booleans (requestShipping / requestPayerEmail / requestPayerName / requestPayerPhone) and a shippingType enum of 'shipping' / 'pickup' / 'delivery'. Bogus values throw — the engine is strict. The trio of on* setters + addEventListener('paymentmethodchange' / 'shippingaddresschange' / 'shippingoptionchange') gives you the full update lifecycle.

6 Modifiers, displayItems, shippingOptions probe

Three display tiers: displayItems (line items, can be pending: true until a calculation settles), modifiers (per-method total/display swaps, e.g. "5% off with Visa"), and shippingOptions (one must be selected: true if present — engine doesn't auto-pick the first). Modifier data must be an object/null, not a string/number.

7 canMakePayment vs hasEnrolledInstrument probe

canMakePayment() is the public capability check (does the browser support this method at all?), hasEnrolledInstrument() is the stronger user-state check (does this user have a saved card for this method?). Both return false in headless Chromium — the spec mandates a positive return requires the browser to have evidence. In production: use canMakePayment as the gate, hasEnrolledInstrument as a softer "likely saved" hint for the UI label.

8 The transient-activation wall: "after the first show() needs gesture again" probe

The most-cited engine truth NOT in MDN: the first show() per page load needs transient user activation. Every subsequent show() in the SAME PAGE also needs fresh activation — even if the prior one resolved/rejected. The exact console error: "PaymentRequest.show() calls after the first (per page load) require either transient user activation or delegated payment request capability." This kills the naive "user clicks Pay, sheet closes, sheet re-opens with different method" pattern. Fix: every Pay button is its own show() in its own click handler.

button.addEventListener('click', () => {
  const req = new PaymentRequest(methods, details, options);
  req.show().then(respond).catch(err); // single show per click
});

9 Abort, complete() enum, retry() flow probe

Three lifecycle completion values: complete('success') (the user paid and the merchant confirmed), complete('fail') (transaction declined at the processor), complete('unknown') (state unclear — e.g. user closed the tab). The retry({payer, shippingAddress, shippingOption, error}) flow on PaymentResponse re-shows the sheet with the user's corrections highlighted (or an error message). abort() during a show resolves the show promise with AbortError: 'The website has aborted the payment' — pre-show abort() throws InvalidStateError.

10 Secure Payment Confirmation (EMV 3-D Secure / WebAuthn-based) probe

The new W3C standard for strong-customer-authentication (SCA) — combines EMV 3DS with WebAuthn. Two statics on the PaymentRequest class probe availability: securePaymentConfirmationAvailability() returns one of 'available' / 'unavailable-no-transient-user-activation' / 'unavailable-no-user-verifying-platform-authenticator', and getSecurePaymentConfirmationCapabilities() returns {browserBoundKeyHardware: bool}. On this headless Mac mini: unavailable-no-user-verifying-platform-authenticator (no Touch ID / Windows Hello).

11 Workers + secure-context + iframe policy probe

PaymentRequest is a main-thread-only API — DedicatedWorkerGlobalScope does NOT have it (probe-verified: typeof PaymentRequest === 'undefined' in a real Worker). The ctor requires a secure context (HTTPS or http://localhost / http://127.0.0.1 / file://); plain HTTP LAN origins reject at ctor. iframes are n/a — the surface doesn't exist in workers, so the cross-origin policy question is moot.

12 OpenDrones Arc pre-order checkout capstone

The production integration. requestShipping: true + a verified-shipping region selector drives the shipping options. requestPayerEmail + requestPayerName + requestPayerPhone autofill the receipt. Modifier applies a 10% pre-order discount to basic-card. On shippingaddresschange, the handler fetches live rates from the OpenDrones /api/ship-rates and calls event.updateWith(...) with refreshed options — the user sees the price change in the sheet without ever leaving it.

const arcReq = new PaymentRequest(
  [
    { supportedMethods: 'basic-card', data: { supportedNetworks: ['visa','mastercard','amex'], supportedTypes: ['credit','debit'] } },
    { supportedMethods: 'https://opendrones.app/pay' }
  ],
  {
    id: 'arc-' + orderId,
    total: { label: 'Arc pre-order', amount: { currency: 'USD', value: '1299.00' } },
    displayItems: [
      { label: 'Arc base unit'.replace('base unit','Arc base unit'), amount: { currency: 'USD', value: '1499.00' } },
      { label: 'Pre-order discount', amount: { currency: 'USD', value: '-200.00' } }
    ],
    modifiers: [{
      supportedMethods: 'basic-card',
      additionalDisplayItems: [{ label: '10% off via card', amount: { currency: 'USD', value: '-129.90' } }],
      total: { label: 'Arc + card discount', amount: { currency: 'USD', value: '1169.10' } }
    }],
    shippingOptions: [
      { id: 'std', label: 'Standard (5-7 days, free)', amount: { currency: 'USD', value: '0.00' }, selected: true },
      { id: 'exp', label: 'Express (1-2 days)', amount: { currency: 'USD', value: '49.00' } }
    ]
  },
  { requestShipping: true, requestPayerEmail: true, requestPayerName: true, requestPayerPhone: true, shippingType: 'shipping' }
);

arcReq.addEventListener('shippingaddresschange', async e => {
  const addr = e.target.shippingAddress;
  const rates = await fetch(\`/api/ship-rates?country=\${addr.country}&zip=\${addr.postalCode}\`).then(r => r.json());
  e.updateWith(Promise.resolve({ shippingOptions: rates, total: / total w/ shipping */ }));
});
Click the button to attempt the OpenDrones Arc sheet. In headless Chromium with no enrolled cards, expect NotSupportedError or AbortError — the gesture wall is what we're proving.

Decision rules (the production playbook):

  • Most US/global SaaS: list basic-card + https://google.com/pay + Apple Pay (via Apple's JS, not URL method) — covers ~95% of paying visitors.
  • EU regulated (PSD2 SCA): add a 3DS challenge via the payment method modifier + secure-payment-confirmation if your PSP supports it (Stripe + Adyen do).
  • B2B high-ACH-volume (US): PaymentRequest doesn't support ACH directly — fall back to a hosted ACH flow for Plaid/Manual entry.
  • Subscription rebills: PaymentRequest is for the FIRST capture only. Tokenize via your PSP, then use their hosted charge for rebills.
  • All sites: never call show() outside a user gesture handler. Never assume canMakePayment() === true means enrolled — treat the false branch as a normal hosted-checkout redirect.
