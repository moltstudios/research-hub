§01Surface census — the door and its two satellite interfaces

What the engine exposes on a secure origin, before any capture is attempted.

Three surfaces ship together: getDisplayMedia itself (cross-browser since 2019–2020: Chrome 74, Firefox 33, Safari 13.1), the Element / Region Capture family (CropTarget.fromElement() + BrowserCaptureMediaStreamTrack.cropTo() — Chromium-only), and the Capture Handle family (setCaptureHandleConfig for the captured page, video.getCaptureHandle() for the capturer — §06). Note the asymmetry already: on CfT 154 the interface BrowserCaptureMediaStreamTrack exists with cropTo and restrictTo on its prototype — but MediaStreamTrack.prototype.cropTo is undefined. Which class your track actually is decides whether Element Capture is reachable at all (§11).

§02The constraint menu — getSupportedConstraints under-reports the display tier

The 36-key menu is the getUserMedia menu; only 3 display keys are declared.

MDN documents a rich display-constraint surface: cursor, displaySurface, logicalSurface, selfBrowserSurface, surfaceSwitching, monitorTypeSurfaces, preferCurrentTab, systemAudio, suppressLocalAudioPlayback, restrictOwnAudio. Live on CfT 154, getSupportedConstraints() declares only three of them — yet the granted-path track's getSettings() reads back cursor and logicalSurface anyway (§08). The menu is not the capability surface; it's an under-report. Capability-detect by reading a granted track's settings, never by this menu.

§03The walls — a third rejection shape (not the gesture SecurityError, not the pend)

Live no-gesture calls, 3.5s timeout-wrapped, verbatim outcomes.

The catalog's other gated APIs reject in two familiar shapes: SecurityError "Must be handling a user gesture" (BLE, WebUSB, Wake Lock) or a silent pend (EyeDropper, the BLE/WebUSB choosers). getDisplayMedia headless on CfT 154 chooses a third shape: instant InvalidStateError: Invalid state — even inside a real trusted click (7ms, userActivation.isActive === true). This is a state wall, not an activation wall: headless Chromium has no capture factory, and the API reports that, gesture or no gesture. The documented activation requirement belongs to the picker path — §07 proves it: with a capture factory installed via launch flag, the call resolves with zero gesture. Also note the validation order: {video:false, audio:false} throws TypeError before the state wall — unlike Web Bluetooth, where the activation gate masks validation errors, here dictionary validation runs upstream. And the empty-call divergence: getUserMedia() no-arg throws TypeError; getDisplayMedia() no-arg hits the state wall instead.

§04Permissions — the queryable door with the underscored readback

One of the few gated APIs whose permission IS queryable.

navigator.permissions.query({name:'display-capture'}) works on Chromium and returns 'prompt' on a fresh profile — but the PermissionStatus.name readback is 'display_capture' (underscore), while the query input must be hyphenated. Same input/output duality as local-fonts and the EyeDropper family. And the deeper truth from §07: capture availability and permission state are fully decoupled — with the automation door installed and captures resolving, the state still reads 'prompt'. A granted capture doesn't flip this permission; the picker is the consent, not the permission store.

§05The worker jail — mediaDevices vanishes entirely

Blob-worker probe, postMessage-fired (not just registered).

Same law as the camera tier: in a dedicated worker navigator exists, navigator.permissions works, but navigator.mediaDevices is undefined — the whole media-device island is main-thread-only. Ship capture orchestration on the main thread; workers only post-process frames you ship them.

§06Capture Handle — the write-only black hole

The config door accepts everything; the read door doesn't exist.

The spec story: a captured page calls setCaptureHandleConfig({handle, exposeOrigin}), and the capturer's <video> element reads it via getCaptureHandle() — letting OpenDrones' DVR know it's recording the mission tab itself, not some other tab. Live on CfT 154 the story collapses: setCaptureHandleConfig exists and resolves undefined for every input — a valid handle, an empty string, a 300-character handle (spec caps at 32), unknown keys, even null. No validation, no rejection, no observable effect. Meanwhile video.getCaptureHandle is undefined on every video element — the read side never shipped flag-clean. You can configure a handle that nobody can read.

Documented from the probe battery (a page cannot relaunch its own browser).

Chromium has a real automation door for display capture: --auto-select-desktop-capture-source=Entire screen. Measured truths from the battery, each one a falsification of an assumption:

§09applyConstraints lab — the settings dictionary that echoes impossible values

Runs against the live capture from §08 (documented from the battery otherwise).

Three battery-measured truths: (1) scaling works — applyConstraints({width:320, height:240}) re-negotiated the track to 320×240 and flipped resizeMode from crop-and-scale to none. (2) cursor constraints are a silent no-op on monitor surfaces — cursor:'never' resolved and settings.cursor stayed 'always'. (3) the echo lie — applyConstraints({width:{exact:9999}}) resolved, and getSettings() then reported width: 9999, height: 6249 while getCapabilities() capped width at 1280. The settings dictionary partially parrots your request back at you; it is not a frame-level truth-teller. Cross-check against capabilities, and against video.videoWidth for ground truth.

§10Stop semantics — the ended event that never fires

Self-stop silence, measured (3s watch, live when a §08 stream exists).

Identical law to the camera tier: track.stop() flips readyState to 'ended' and stream.active to false, but the ended event does not fire on your own stop — a 3-second listener registered before the stop saw nothing. The ended event is for external death only (the user clicking the browser's own "Stop sharing" bar, the source window closing). A second stop() is a silent no-op, not a throw. Build stop-button UX on your own state, not on ended.

§11Element Capture — the door this engine can't reach

CropTarget.fromElement works; cropTo exists — on a class your track isn't.

The Region/Element Capture contract: CropTarget.fromElement(el) mint a token, then track.cropTo(target) re-scopes the live capture to that element — the "record only this panel" feature. Live census on CfT 154: CropTarget.fromElement works on any element, detached from any capture (resolves fine below). BrowserCaptureMediaStreamTrack.prototype has both cropTo and the older restrictTo. But the monitor-capture track the automation door returned walked a prototype chain of MediaStreamTrack → EventTarget → Object — a plain MediaStreamTrack — so track.cropTo(target) threw TypeError: track.cropTo is not a function. The interface exists; the instance doesn't implement it on this path. Capability-detect with typeof track.cropTo === 'function' at runtime, per track — never by interface census.

The crop target: a plain element. CropTarget.fromElement() accepts it without any capture in flight.

§12MediaRecorder composition — the capture → evidence pipeline

Captured stream → WebM, 800ms, live when a §08 stream exists.

The battery's composition proof: a granted monitor capture recorded for 800ms through MediaRecorder (default mimeType) produced a video/webm;codecs=vp8 blob of 96,241 bytes — the entire screen-recording pipeline runs client-side with zero added permissions. When no display grant exists, the permission-free lane still records: a canvas.captureStream() of content you already own (§14's DVR runs exactly that, gate-verified headless).

§13The iframe policy wall — object present, call gated

Same-origin srcdoc child + two cross-origin children (no-allow vs allow="display-capture").

With the automation door installed (so the state wall of §03 can't mask policy outcomes), the battery measured a clean three-way split: a same-origin child resolved a monitor capture; a cross-origin child without delegation rejected NotAllowedError: Access to the feature "display-capture" is disallowed… — note this is the policy wall, a different name and message than the state wall, and it fires first; the same cross-origin child with allow="display-capture" resolved. The cross-origin object itself is fully present (typeof getDisplayMedia === 'function') — the object-absent law of insecure origins does not apply here; this is object-present, call-gated, like Web Bluetooth's iframe tier.

Cross-origin child default: the GitHub Pages mirror of this repo; add ?crossbase=http://127.0.0.1:PORT to probe against a local second origin (that's how the offline gate does it).

§14Capstone A — OpenDrones mission DVR (permission-free lane)

canvas.captureStream + MediaRecorder. No picker, no grant — runs anywhere, gate-verified.

The mission wall renders a synthetic HUD (attitude ladder, battery, telemetry ticker) to an offscreen-composited canvas at 30fps; the record button pipes canvas.captureStream(30) straight into MediaRecorder and hands the pilot a WebM. This is the production lane that needs zero user permissions — everything the DVR needs is already yours. getDisplayMedia is only for capturing surfaces you don't own (the GCS app itself, a video window, the whole screen for debriefs).
