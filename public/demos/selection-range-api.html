Selection API + Range — The Text Tier's Model Layer

The machinery under every text interaction this catalog has shipped — the P1 Custom Highlight API paints ranges, Clipboard copies them — but the model itself (getSelection(), Range, caretPositionFromPoint) never got its own entry. Every claim below is an executable chip, live-probed on this engine.

§01 · The Selection object — identity, anchor/focus & direction

window.getSelection() and document.getSelection() return the same per-document Selection object. A selection is modeled as an anchor (where it started) and a focus (where it ended) — not "start/end". When the user shift-drags leftward the anchor stays put and the focus lands before it: a backward selection. Selection.direction (Ch 137 / FF 126) finally exposes this directly.

Identity & the live model

const sel = getSelection();
sel.anchorNode; sel.anchorOffset;   // start
sel.focusNode;  sel.focusOffset;    // end
sel.isCollapsed; sel.type;          // Caret|Range|None
sel.direction;                      // forward|backward|none

Backward selections & direction readout

// anchor AFTER focus in the same node
sel.setBaseAndExtent(t, 9, t, 2);
sel.anchorOffset > sel.focusOffset; // true
sel.direction;                       // 'backward'

rangeCount is 0 (no selection), 1 (normal), or n — multiple ranges are a Firefox-only Ctrl-select capability; Chromium/Safari cap at 1. Probed live in §09 where shadow DOM drives it to 0.

§02 · Range anatomy — offset semantics & DOM surgery

A Range is two boundary points, each a (node, offset) pair — and offset means different things by node type: in a text node it counts characters; in an element node it counts child nodes. This one dual meaning explains most Range bugs.

The offset dual meaning

<p id=demo>AB<b>CD</b>EF</p>
r.setStart(demo, 1);      // before <b>
r.setStart(demo.firstChild, 1); // inside 'AB'

Surgery: clone / extract / insert

r.extractContents(); // CUTS nodes out
r.cloneContents();   // copies (fragment)
r.insertNode(el);    // inserts at start
r.compareBoundaryPoints(
  Range.START_TO_START, other) // <0 / 0 / >0

intersectsNode() is boolean-only (no overlap geometry) — use compareBoundaryPoints for ordering, comparePoint() to ask "is this point inside" (it throws WrongDocumentError for nodes from another document).

§03 · selectionchange — the event contract & the form-control separate world

The event fires on the Document (it does not bubble), carries no payload — read getSelection() inside the listener — and when you change the selection programmatically it is queued as a task: listeners run after your script finishes, unlike focus/click. And the big one: input/textarea selections live in a separate world — selectionStart/End/Direction on the element, invisible to window.getSelection().

Queued-as-task proof + target truth

let fired = false;
document.addEventListener(
  'selectionchange', () => fired = true);
sel.setBaseAndExtent(t, 0, t, 3);
fired; // false — still this task
// …after a timeout: true

The input parallel universe

inp.setSelectionRange(2, 7, 'backward');
inp.selectionStart;        // 2
inp.selectionDirection;    // 'backward'
getSelection().isCollapsed; // STILL true!

Legacy note: old WebKit/Blink fired selectionchange on the Selection object itself; the spec moved it to Document. Probed live — on this engine the Selection-object listener is ….

§04 · caretPositionFromPoint vs caretRangeFromPoint — the two-name trap

Click-to-caret has two APIs: the standard document.caretPositionFromPoint(x, y) → CaretPosition {offsetNode, offset} (Firefox first; Chromium since 128) and the legacy document.caretRangeFromPoint(x, y) → Range (Chromium/Safari, non-standard but universal in practice). Coordinates are viewport-relative (clientX/clientY space).

Both names, same caret

const r = span.getBoundingClientRect();
const p = document.caretPositionFromPoint(
  r.left + 2, r.top + r.height/2);
p.offsetNode;  // the text node
p.offset;      // 0..1 at the left edge

Probe span: FLIGHTPATH-NOMINAL

Out-of-bounds & the portable ladder

const pos =
  document.caretPositionFromPoint?.(x, y) ??
  (r => r && { offsetNode: r.startContainer,
                 offset: r.startOffset })(
    document.caretRangeFromPoint?.(x, y));

§05 · Range geometry — getClientRects() & the caret box

Ranges are paintable geometry: getClientRects() returns one rect per line fragment a selection covers (a wrapped selection spans several), and getBoundingClientRect() is their union. A collapsed range's rect is the caret's line box — width 0, full line height — the primitive for caret overlays and @-mention popups.

Wrapped selection = multiple rects

telemetry downlink stabilized over the ridge crossing

The collapsed caret box

r.collapse(true);
const rect = r.getClientRects()[0];
rect.width;   // 0 — a caret has no width
rect.height;  // the line height

§06 · Mutation methods — setBaseAndExtent, extend(), deleteFromDocument(), modify()

setBaseAndExtent(anchorNode, anchorOff, focusNode, focusOff) is the full-control setter. extend() moves only the focus — the programmatic shift-select, and the way to flip direction without touching the anchor. deleteFromDocument() performs a live edit through the selection. modify() (non-standard but in every engine's muscle memory) moves/extends by word/line — the keyboard-selection semantics.

extend() flips direction

sel.setBaseAndExtent(t, 8, t, 8); // caret
sel.extend(t, 2);                 // focus back
sel.direction;                    // 'backward'

deleteFromDocument + modify

sel.setBaseAndExtent(t, 3, t, 6);
sel.deleteFromDocument(); // removes 3 chars
sel.modify('extend','forward','word');

Cross-document addRange(): the spec is silent, engines decide — probed live against a range built in document.implementation.createHTMLDocument(). removeAllRanges() empties the selection (type:'None', rangeCount:0, toString():'').

§07 · user-select, selectstart & ::selection

user-select: none gates the user, not the API — programmatic selection of shielded text still works (probed). selectstart fires for user-initiated selection attempts only (cancelable — preventDefault() blocks the drag from selecting). ::selection styles the paint with a small property set (color, background-color, text-decoration, text-shadow, …).

sel.toString(); // includes shielded text

§08 · toString() semantics — the visibility filter divergence

What text does a selection give you? Selection.toString() and Range.toString() are not guaranteed to agree: the Selection API spec historically defines its string via the text a user would copy (rendering-aware), while Range.toString() concatenates text nodes (pure DOM). Probed live against display:none, visibility:hidden, and user-select:none content.

probe paragraph — AA ZZ-display-none YY QQ-visibility-hidden BB

AAZZ-display-noneYYQQ-visibility-hiddenBB

The extraction trio

sel.toString();                  // copy-model
r.toString();                    // DOM-model
r.cloneContents().textContent;   // always everything

What this means for copy features

A "copy selected telemetry" button that reads getSelection().toString() silently drops hidden spans; a diff/export tool that reads the Range keeps them. Neither is wrong — pick the model that matches the feature, and know you are picking.

§09 · Shadow DOM — getComposedRanges() & the blind classic

The old API is shadow-blind: a selection that lives entirely inside a shadow root reports rangeCount: 0 from window.getSelection() — the page sees nothing. getComposedRanges() (Baseline Aug 2025) returns StaticRanges in the composed tree; pass the ShadowRoots to see nodes inside them, or get the range re-scoped to the host element.

The blind classic, live

// selection entirely inside shadow text
getSelection().rangeCount;   // 0 — blind
getSelection().getComposedRanges()
  // StaticRange w/ real nodes

Re-scoping: with vs without the root

getComposedRanges()                         // → host
getComposedRanges({shadowRoots:[root]})     // → nodes

Probe host: (text inside is in an open shadow root). StaticRanges are snapshots — re-read after DOM mutations, don't cache across edits.

§10 · surroundContents() & the partial-node wall

range.surroundContents(el) wraps the selection in one call — and throws InvalidStateError when the range starts or ends inside a non-text node (the "I selected from mid-word through a <b>" case). The recipe that never throws: extractContents() → wrap → insertNode().

The throw, live

one two three four

r.setStart(p.firstChild, 2);   // mid 'one '
r.setEnd(p.lastChild, 2);      // mid 'four'
r.surroundContents(mark);      // InvalidStateError

The recipe that works

const frag = r.extractContents();
mark.appendChild(frag);
r.insertNode(mark);

§11 · Capstone — OpenDrones: click-to-annotate mission log & selection time spans

The production pattern: click anywhere in the log → caretPositionFromPoint finds the line → a Range over that line's text → getClientRects() positions an annotation flag with zero DOM mutation of the log itself (the evidence stays pristine — pairs with the Custom Highlight tier). Select lines and read the span: the selection string is regexed for the first/last T+mm:ss stamps and the mission-time delta computed.
