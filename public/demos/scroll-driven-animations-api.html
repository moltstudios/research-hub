1 · The Problem: JavaScript Scroll Listeners

For 15 years, scroll-triggered animations required JavaScript — IntersectionObserver, scroll event listeners, GSAP ScrollTrigger, or libraries like AOS and Framer Motion. These approaches share the same fundamental problems: they run on the main thread, compete with your app code for CPU time, and cause jank on low-end devices.

❌ Old Way — JavaScript

// Scroll listener + state management
window.addEventListener('scroll', () => {
  const scrolled = window.scrollY;
  const height = document.body
    .scrollHeight - window.innerHeight;
  const progress = scrolled / height;
  bar.style.transform = `scaleX(${progress})`;
  // ⚠️ Runs on main thread
  // ⚠ Fires ~60x/sec during scroll
  // ⚠ Competes with React/render
  // ⚠ Jank on mid-range phones
});

// OR: IntersectionObserver + class toggle
const obs = new IntersectionObserver(
  (entries) => {
    entries.forEach(e => {
      e.target.classList.toggle('visible',
        e.isIntersecting);
    });
  },
  { threshold: 0.2 }
);
cards.forEach(c => obs.observe(c));
// ⚠ Still toggles classes on main thread
// ⚠ Can't scrub forward/backward
// ⚠ No off-thread option

✅ New Way — Pure CSS

/* Reading progress bar — 4 lines */
.progress {
  animation: grow auto linear;
  animation-timeline: scroll(root);
}
@keyframes grow {
  to { transform: scaleX(1); }
}

/* Reveal on scroll — 3 lines */
.card {
  animation: fade-up linear both;
  animation-timeline: view();
  animation-range: entry 0% entry 40%;
}
// ✅ Runs on compositor thread
// ✅ Zero JS bundle weight
// ✅ Scrubs forward/backward
// ✅ 60fps even under load

2 · scroll() — Scroll Progress Timeline

The scroll() function creates a ScrollTimeline that tracks the scroll position of a container. The animation is at 0% when the container is scrolled to the top, 100% when scrolled to the bottom. As you scroll, the animation scrubs forward. Stop scrolling → the animation freezes at that exact point. Scroll back → it reverses.

/* scroll() syntax */
animation-timeline: scroll();          /* nearest scrollable ancestor, block axis */
animation-timeline: scroll(root);       /* track page (documentElement) scroll */
animation-timeline: scroll(self);       /* track this element's own scroll */
animation-timeline: scroll(nearest);    /* same as default */
animation-timeline: scroll(root block); /* explicit axis */
animation-timeline: scroll(root inline);/* horizontal scroll */

The scroller values:

  • nearest — nearest ancestor scroll container (default)
  • root — the document viewport (most common for page-level effects)
  • self — the element's own scroll position (for scrollable widgets)

The axis values:

  • block — progress along the block axis (vertical in most writing modes, default)
  • inline — progress along the inline axis (horizontal)
  • y / x — explicit physical axes

The CSS scroll-driven animations module allows you to animate property values along a scroll-based timeline rather than the default time-based document timeline. This means you can animate an element by scrolling the element, its scroll container, or its root element, rather than just by the passing of time.

Before this feature, creating scroll-driven animations required JavaScript scroll event listeners and IntersectionObserver objects on the main thread. Any time you rely on the main thread to render effects with JavaScript, you run the risk of blocking the main thread, which can lead to an unresponsive page and a bad user experience.

With native CSS scroll-driven animations, the browser moves the scroll-tracking to the compositor thread — the same thread that handles GPU-accelerated transforms and opacity. This means your scroll animations run at 60fps even when the main thread is busy with React renders, data processing, or other heavy work.

Scroll-driven animations are inherently interactive. Unlike time-based animations that play through to completion, scroll-driven animations respond in real time to the user's scroll position. Stop scrolling and the animation pauses. Scroll back up and the animation reverses. This creates a direct-manipulation feel that time-based animations cannot match.

The feature is built on top of the existing CSS Animations and Web Animations API infrastructure. This means scroll-driven animations inherit all the advantages of regular CSS animations — keyframe control, easing functions, animation-fill-mode, the ability to run off the main thread — with one new property: animation-timeline.

Two timeline types are available: Scroll Progress Timelines (created with the scroll() function or scroll-timeline-name property) and View Progress Timelines (created with the view() function or view-timeline-name property). Scroll Progress tracks the scroll position of a container. View Progress tracks the visibility of a specific element within the scrollport.

The page-level progress bar at the very top of this page also uses scroll(root) — scroll the main page to see it fill.

3 · view() — View Progress Timeline

The view() function creates a ViewTimeline that tracks the visibility of the animated element itself in the scrollport. Timeline progress starts at 0% when the element begins entering the viewport and reaches 100% when it finishes leaving. This is the modern replacement for IntersectionObserver + class-toggle fade-in patterns.

/* view() syntax */
animation-timeline: view();             /* track on block axis (default) */
animation-timeline: view(block);         /* explicit block axis */
animation-timeline: view(inline);         /* horizontal visibility tracking */
animation-timeline: view(block 100px); /* with inset — shrink tracked area */

4 · animation-range — Controlling When Animations Fire

The animation-range property controls which part of the scroll timeline triggers the animation. Without it, animations run from timeline start to end. With it, you specify a precise window using range names for view() timelines, or percentages/lengths for scroll() timelines.

The four view() range names

RangeStartsEndsUse Case
entryElement begins entering viewportElement fully in viewportReveal animations (fade-in, slide-up)
exitElement begins leaving viewportElement fully out of viewportFade-out, shrink-away
coverElement starts intersectingElement stops intersectingParallax (entire time visible)
containElement fully visibleElement starts to leavePin animations (active while centered)
 
/* Complete during entry phase only */
animation-range: entry 0% entry 100%;

/* Fast reveal — first 40% of entry */
animation-range: entry 0% entry 40%;

/* Entire time element is in view (parallax) */
animation-range: cover 0% cover 100%;

/* Only when fully contained (centered) */
animation-range: contain 0% contain 100%;

/* For scroll() — use percentages or lengths */
animation-range: 0% 100%;    /* full scroll */
animation-range: 0px 120px;     /* first 120px of scroll */
animation-range: 20% 80%;      /* middle section */

5 · Named Timelines — scroll-timeline-name & view-timeline-name

Anonymous timelines (scroll() / view()) work when the animated element is inside the scroller. For more complex setups — like animating a fixed-position element based on a different element's scroll — use named timelines.

/* Named scroll progress timeline */
.scroll-container {
  scroll-timeline-name: --my-scroller;
  scroll-timeline-axis: inline; /* optional */
}
.animated-child {
  animation: slide auto linear;
  animation-timeline: --my-scroller;
}

/* Shorthand */
.scroll-container {
  scroll-timeline: --my-scroller inline;
}

/* Named view progress timeline */
.hero-image {
  view-timeline-name: --hero-vt;
}
.overlay-text {
  animation: fade-text auto linear;
  animation-timeline: --hero-vt;
}

/* timeline-scope — extend a named timeline to descendants */
body {
  timeline-scope: --page-scroller;
}
When to use named
Fixed-position elements, cross-component animations, decoupled trigger/target
When to use anonymous
Simple cases — element animates based on its own or nearest ancestor's scroll
timeline-scope
Extends a named timeline declared in one subtree to be visible in another

The CSS scroll-driven animations module provides functionality that builds on the CSS animations module and Web Animations API.

It allows you to animate property values along a scroll-based timeline rather than the default time-based document timeline.

This means you can animate an element by scrolling the element, its scroll container, or its root element, rather than just by the passing of time.

Animations can be set to progress along a scroll-based timeline instead of the default time-based document timeline, without needing JavaScript.

Scroll-driven animations are performant. JavaScript scroll-driven animations require scroll event listeners on the main thread. CSS scroll-driven animations run off the main thread.

The animation-range property controls which part of the timeline triggers the animation. Without it, the animation runs from start to end of the timeline.

With animation-range, you can specify a precise window. For view() timelines, range keywords like entry, exit, cover, and contain are available.

For scroll() timelines, you use percentages directly: animation-range: 0% 100% or pixel values: animation-range: 0px 120px.

Named timelines use scroll-timeline-name and view-timeline-name to create reusable timeline identifiers that can be referenced by descendant elements.

The timeline-scope property extends a named timeline to be visible across different parts of the DOM tree.

.nav {
  position: sticky;
  top: 0;
  animation: shrink linear forwards;
  animation-timeline: scroll(root);
  animation-range: 0px 120px; /* completes in first 120px */
}
@keyframes shrink {
  from { padding: 24px; background: rgba(0,0,0,.5); }
  to   { padding: 8px;  background: rgba(0,0,0,.95); }
}

7 · Parallax Without JavaScript

The most-requested scroll effect — elements scrolling at different speeds — is now 6 lines of CSS. The background translates slower than the content, creating depth. Uses view() with cover range so the parallax runs the entire time the section is visible.

Parallax Section

Background moves slower than foreground — pure CSS

Keep scrolling to see the parallax effect end as the section exits.

The background element is oversized (inset: -30%) so movement doesn't reveal edges.

.parallax-bg {
  position: absolute;
  inset: -20%; /* oversize to hide edges during movement */
  background: url('/hero.jpg') center/cover;
  animation: parallax linear;
  animation-timeline: view();
  animation-range: cover 0% cover 100%;
}
@keyframes parallax {
  from { transform: translateY(-15%); }
  to   { transform: translateY(15%); }
}

11 · Combining Time-Based + Scroll-Driven Animations

An element can run multiple animations simultaneously — some time-based, some scroll-driven. Map them positionally with comma-separated values. This enables patterns like "fade in on load, then float with scroll."

.element {
  animation:
    fade-in 0.3s ease both,     /* 1st: time-based, fires on load */
    float-up linear both;        /* 2nd: scroll-driven */
  animation-timeline:
    auto,                        /* auto = document timeline (1st) */
    view();                      /* view timeline (2nd) */
}

/* Same @keyframes work for both */
@keyframes fade-in { from {opacity:0} to {opacity:1} }
@keyframes float-up { from {transform:translateY(40px)} to {transform:translateY(0)} }
⚠️ Firefox quirk
Firefox requires a non-zero animation-duration for scroll-driven animations to apply. Set animation-duration: 1ms — it has no effect on scroll-driven animations (scroll position controls timing, not duration), but satisfies the Firefox requirement.
/* Firefox-safe pattern */
.reveal {
  animation: fade-up 1ms linear both;  /* 1ms satisfies Firefox */
  animation-timeline: view();
  animation-range: entry 0% entry 50%;
}

13 · Reduced Motion & Accessibility

Every scroll-driven animation MUST respect prefers-reduced-motion. For some users, motion causes physical discomfort (vestibular disorders, motion sickness). The CSS contract is simple — and it's not optional.

/* The universal reduced-motion reset */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

Accessibility considerations specific to scroll-driven animations

ConcernGuidance
Vestibular disordersLarge parallax movements can trigger nausea. Keep translation under 15% and always respect prefers-reduced-motion.
Screen reader usersScroll-driven animations are purely visual — they don't affect DOM order or semantics. No ARIA changes needed.
Keyboard navigationIf content is hidden by default (opacity: 0) and only revealed on scroll, keyboard users navigating past it may see a flash. Use animation-fill-mode: both to prevent the flash.
Cognitive loadDon't apply scroll animations to everything. One or two deliberate moments per page. A page where every section fades in reads as a template, not a design.

14 · Performance: Compositor vs Main Thread

The single biggest advantage of CSS scroll-driven animations over JavaScript: they run on the compositor thread, not the main thread. This means scroll animations stay smooth at 60fps even when your main thread is completely blocked by React renders, JSON parsing, or image decoding.

✅ When you still need a JavaScript library
Gesture-based animations (drag-to-dismiss, swipeable cards) · Physics-based motion (spring, momentum) · Complex orchestrated sequences with branching state · Dynamic data-driven animations. For these, reach for Motion One (~5KB) or @react-spring/web.
