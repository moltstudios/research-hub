Idle Detection API — The Presence Tier

The browser native answer to "is the pilot still at the screen?" — IdleDetector reports userState (active/idle) and screenState (locked/unlocked) without any input-event heuristics. Live-probed on Chrome for Testing 154 headless (macOS arm64): the sticky-latch law that bricks a denied detector, the gesture wall on requestPermission(), the undocumented 'prompt' resolution, a four-door CDP grant no-op, and the worker anti-jail.

Chrome 94+ (Jul 2021) Edge 114+ Firefox — never (privacy position) Safari — never Secure context only Not Baseline · Experimental Ships in dedicated workers

§01 · The tier in one screen

Idle Detection completes the attention tier alongside Page Visibility (document.visibilityState — is the tab shown?), Wake Lock (e55980b5 — keep it shown), and Notification (3e3acdd3 — interrupt when hidden). Idle Detection is the missing half: shown but unattended. A Mission Control dashboard can be the visible tab while the pilot stepped away — only this API knows.

The engine truth in four lines: (1) a start() that fails the permission check still latches the detector as started — it can never be restarted; (2) requestPermission() without a user gesture rejects NotAllowedError — and with a gesture in a prompt-less environment it resolves the undocumented value 'prompt'; (3) no CDP/automation door can grant the permission — all four doors accepted, none took effect; (4) the object ships in dedicated workers — the rare anti-jail, your idle watcher can live off the main thread.

§02 · Surface census

The whole interface is one constructor, one static, one method, two getter properties, one event — the smallest gated API in this catalog after EyeDropper.

// the entire surface
new IdleDetector()                    // ctor: permissive — numbers and bogus dicts accepted
IdleDetector.requestPermission()      // static — THE ONLY permission door (no navigator.idle)
detector.start({ threshold, signal }) // the one method
detector.userState   // "active" | "idle" | null (null until a successful start)
detector.screenState // "locked" | "unlocked" | null
detector.onchange    // event-handler attribute — ships on the prototype
// prototype members: [userState, screenState, onchange, start, constructor]

There is no PermissionStatus on the constructor (no static permission field), no stop() — stopping is abort-signal only, no peek APIs, no idle-time readback. Object.keys(detector) is always [] — the enumerable-lie family (all members are prototype getters).

§03 · The four-wall ladder — argument validation before permission, always

Every start() call climbs four walls in a fixed order. The first two fire synchronously as TypeError in every permission state — validation is state-independent (the same layering law first proven on Notification).

WallTriggerOutcome (live-probed)
1 · WebIDL conversionthreshold: -5000, 'bogus', start(60000)TypeError — "outside the unsigned long value range" / "not of type IdleOptions". Note '60000' (numeric string) coerces and passes.
2 · Started latchsecond start() on a latched detectorInvalidStateError — "Idle detector is already started." Fires even before the threshold check.
3 · Semantic thresholdthreshold: 100, 59999, 0TypeError — "Minimum threshold is 1 minute." 60000 ms is the hard floor; no clamping, no rounding up.
4 · Permission (async)ungranted originNotAllowedError — "Idle detection permission denied." The only async wall.

Calling start() with no options at all defaults the threshold to 60000 — it passes walls 1-3 and lands on wall 4 like any valid call.

§04 · The sticky-latch law — a denied start bricks the detector

Headline falsification. MDN and the Chrome docs teach one flow: request permission, then start. The engine adds a trap they never mention: the moment a start() call passes argument validation, the detector latches "started" — even if the permission check then rejects. Every later start() on that instance throws InvalidStateError forever. A detector that was denied delivers null states and never fires change. The only recovery is a new constructor.
// the trap — every tutorial flow is wrong on this engine
const d = new IdleDetector();
await d.start({ threshold: 60000 });  // → NotAllowedError (not granted yet)
await d.start({ threshold: 60000 });  // → InvalidStateError: already started
d.userState                            // → null, forever
// the fix — one detector per attempt
async function watchIdle(opts){
  const d = new IdleDetector();       // fresh instance per attempt
  await d.start(opts);                // throws if still ungranted — caller decides
  return d;
}

Validation failures (walls 1-3) do not latch — only a call that reaches wall 4 latches. Probed by replaying the ladder on one instance: threshold:100 → TypeError, retry → still NotAllowedError path; once a valid call lands on the permission wall, retry → InvalidStateError.

§05 · The gesture wall + the undocumented 'prompt' resolution

IdleDetector.requestPermission() is the only permission door, and it carries its own wall shape: called without a user gesture it rejects NotAllowedError: "Must be handling a user gesture to show a permission request." — a third distinct NotAllowedError message in this one API (gesture wall ≠ permission-denied wall ≠ policy wall below).

Docs drift, live: MDN documents the resolution vocabulary as "granted" / "denied". CfT 154 adds a third value — in a prompt-less environment (headless) a trusted-click call resolves 'prompt': it neither shows a prompt, nor pends, nor denies. Your state machine must handle a value the docs do not list.

In your headed browser this button may show the real permission bubble (grant/denied). In headless/CI it resolves 'prompt' — the honest no-prompt truth.

§06 · The CDP four-door no-op — the granted path is CI-unreachable

Chromium automation exposes four permission-grant doors. For idle detection (probe: Browser.grantPermissions scoped + unscoped with enum idleDetection, Browser.setPermission scoped + unscoped with descriptor idle-detection): all four accepted — and none took effect. After every grant: permissions.query still 'prompt', start() still NotAllowedError. A bogus name ('idle-detection-hyphen') is correctly rejected with "Unknown permission type", so enum validation is live — the doors work, the grant just never lands.

Second cataloged case after Window Management (08a147ad) — contrast notifications (3e3acdd3), which IS grantable per-origin in CI. Production consequence: your tests can never green-test the granted lifecycle; gate on the honest ungranted states (this page does exactly that). The granted-path behaviors documented below are spec-anchored and labeled as such.

§07 · Permission vocabulary duality — hyphen in, underscore out

The local-fonts family again: permissions.query accepts only the hyphenated 'idle-detection' (underscore and camelCase both TypeError — "not a valid enum value"), while the returned PermissionStatus.name reads back 'idle_detection' — underscore. Never string-compare the readback against your input.

Nuance vs local-fonts: there the query stayed 'prompt' even when API access existed. Here the query does carry policy truth — a cross-origin frame without allow reads 'denied' (§09) — while the grant state remains CDP-invisible from every door (§06).

§08 · The worker anti-jail — the idle watcher ships off-thread

The rarest shape in this catalog: a permission-gated API whose interface ships in dedicated workers. BLE, Local Fonts, and Camera are main-thread-only; IdleDetector constructs and start()s inside a worker (it lands on the same permission wall — but as a real call, not an object-absent stub). The whole presence watcher can live off the main thread and post state transitions upward.

// worker-side idle watcher (start() still needs the origin grant)
self.onmessage = async () => {
  const d = new IdleDetector();
  d.onchange = () => postMessage({ user: d.userState, screen: d.screenState });
  await d.start({ threshold: 60000 }); // throws here until granted — retry with fresh ctor
};

The permission query also works inside the worker ('prompt' / idle_detection observed). Probed on a dedicated worker; navigator.userActivation does not exist there — so a worker cannot run requestPermission() usefully; request from the page, watch from the worker.

§09 · Iframes — the SecurityError policy wall, and query reflects it

Default Permissions-Policy allowlist is self: same-origin frames inherit; cross-origin frames without allow="idle-detection" get a different exception family — SecurityError: "Access to the feature 'idle-detection' is disallowed by permissions policy" plus a console Permissions policy violation — and their permissions.query reads 'denied'. With allow= the frame passes the policy wall and lands on the ordinary permission wall (NotAllowedError). Policy precedes permission — and precedes the latch too: the denied frame retries into SecurityError again, never InvalidStateError.

The child below runs the full battery in-frame: surface check, query, start(), and the latched retry. Same-origin child on this host; cross-origin child from the mirror host. If the mirror is unreachable the chip degrades to an honest info, never a hang.

§10 · The abort contract — your reason, verbatim

The EyeDropper/fetch family: a pre-aborted signal rejects start() with the raw abort reason — a string reason rejects as that string, an Error reason rejects as that exact error. No DOMException, no AbortError wrapping. e.name is undefined on the string shape — do not branch on it.

const c = new AbortController(); c.abort('user navigated away');
try { await detector.start({ threshold: 60000, signal: c.signal }); }
catch (reason) {
  // reason === 'user navigated away' (typeof 'string', NOT an Error)
}

Mid-run abort (spec-anchored, granted path): the detector stops, states stop updating. There is no restart — abort is terminal for the instance (the latch from §04 has no unlatch).

§14 · The ship checklist

Nine rules

  1. One detector per attempt. A denied or aborted start latches the instance dead (§04).
  2. Ask inside a click. requestPermission() outside a gesture rejects (§05).
  3. Handle three values from requestPermission: granted / denied / prompt (§05).
  4. Never branch on e.name for aborts — the reason is your raw value (§10).
  5. 60 000 ms is a hard floor — sub-minute thresholds throw TypeError, they do not clamp (§03).
  6. Detect, do not assume: typeof IdleDetector !== 'undefined' first — the object is deleted on insecure origins while permissions.query still answers.
  7. Feature-detect the policy too: a frame can have the object and still be policy-denied — catch SecurityError separately (§09).
  8. Gate CI on ungranted truths — no automation door grants this API (§06).
  9. Announce the privacy trade to users — this API answers "is anyone watching," so say why you ask.
