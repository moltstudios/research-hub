01 · The problem

One long task = one frozen page

The main thread runs exactly one task at a time. Any task over 50ms is a "long task" — and during it, clicks queue, keys buffer, nothing paints. The classic advice — "break up your tasks" — had no dedicated API for a decade, so we yielding-ed with setTimeout(fn, 0). That has three real problems:

The three sins of setTimeout yielding

SinWhat happens
1 · Punished for yieldingYour continuation goes to the back of the queue. If a third-party script queued work before you yielded, their entire job runs before your part 2. You did the right thing and got demoted for it.
2 · No prioritiesTimer tasks are all equal. Analytics beacons, image decoding, and the handler responding to a pilot's stick input wait in one undifferentiated line.
3 · Nested-timeout clampAfter 5 levels of nested timers, the browser imposes a minimum ~4ms delay per setTimeout — a throughput tax on fine-grained chunking (MDN: nested timeouts).
Also retired: navigator.scheduling.isInputPending() — Chrome's own team no longer recommends it: it can return false while the user has interacted, and input isn't the only thing worth yielding for (animations, rAF, paint). Yield unconditionally instead.

Feel it: freeze vs yield (click, then try typing in the box)

Press a button, then immediately type into the input and watch the echo. Naive crunches 700ms in one gulp. Yielded crunches the same 700ms but await scheduler.yield() every ~40ms.

02 · Anatomy

Two methods, one mental model

scheduler.postTask(cb, options?)

Queue a one-shot function with explicit control. Returns a Promise with the callback's value (or rejection on error/abort).

OptionEffect
priorityImmutable priority: 'user-blocking' | 'user-visible' (default) | 'background'
signalA TaskSignal (abort + mutable priority) or plain AbortSignal (abort only)
delayms before the task enters the queue (a prioritized setTimeout)

await scheduler.yield()

Pause any async function mid-task, let the browser run pending work (input, paint, other tasks), then continue. Takes no arguments.

The killer property: the continuation is scheduled ahead of other similar tasks already queued — you yield without losing your place. Inside a postTask callback, it inherits that task's priority (§08).

Where it lives: globalThis.scheduler — on window and workers (WorkerGlobalScope.scheduler), so heavy crunching in a dedicated worker can be prioritized too. Feature-detect with 'scheduler' in globalThis.
// The two-line version of "don't freeze the page":
async function saveSettings() {
  validateForm(); showSpinner(); updateUI();   // user-visible part
  await scheduler.yield();                    // ← browser can paint + take input HERE
  saveToDatabase(); sendAnalytics();           // continuation: still YOUR task, prioritized
}

06 · Lab C

Mutable priority: TaskController.setPriority() mid-flight

Immutable priorities are fine for most work. The carousel case is the spec's own motivation: images prefetch at background, then the user scrolls one into view — that prefetch must jump the queue. Post tasks with a TaskSignal (no priority option!) and change the controller's priority while chunks are still pending. The prioritychange event fires on the signal.

—
Mutability rule: a task's priority is changeable only if you pass a TaskSignal and don't set options.priority. Setting both makes the priority immutable. Already-running tasks are unaffected — re-sorting applies to pending ones.
Gotchas found the hard way (live-verified in Chrome 148): (1) The TaskController constructor takes a TaskControllerInit dictionary — new TaskController({ priority: 'background' }); a bare priority string throws TypeError. setPriority() and postTask(…, { priority }) take the string — only the constructor wants the object. (2) TaskPriorityChangeEvent.newPriority is undefined in Chrome 148 (prototype exposes previousPriority only) — read signal.priority inside the handler instead.
const tc = new TaskController({ priority: 'background' }); // ⚠ TaskControllerInit DICT — a bare string THROWS in Chrome
tc.signal.addEventListener('prioritychange', e =>
  log(`${e.previousPriority} → ${e.newPriority ?? tc.signal.priority}`)); // ⚠ Chrome 148: e.newPriority is undefined — read signal.priority
for (chunk of chunks) scheduler.postTask(chunk, { signal: tc.signal }); // mutable ⬇ no priority option
tc.setPriority('user-blocking');                        // pending chunks jump the queue
07 · Lab D

Abort: cancel the pipeline you no longer need

Every postTask promise wired to a signal rejects with AbortError the instant the controller aborts. OpenDrones case: a background crunch for mission A is 4 chunks in when the pilot switches to mission B — kill the remaining work, don't waste another cycle, then start the new batch.

—
Why it matters: setTimeout can be cleared only by keeping every timer id yourself. TaskController extends AbortController — one call aborts any number of tasks, and (per MDN) pending tasks reject with a DOMException named AbortError.
08 · Lab E

Priority inheritance: a yield inside a background task stays background

scheduler.yield() alone gets user-visible. But awaited inside a postTask callback, the continuation inherits the surrounding task's priority: a background job that yields doesn't suddenly get to cut in front of user-visible work — it just keeps its place among other background tasks. Exactly what "yield ≠ surrender" means at the bottom of the stack.

—

Expected: P1 (bg) runs and, while holding the thread, queues a user-visible job (amber) and a plain new background task; P1 then yields. The continuation P2 does NOT cut ahead of the user-visible work (inheritance keeps it background), but DOES run before the new background task BG2 — “yield ≠ surrender” at the bottom of the stack. With plain yield() outside a low-priority postTask, continuations run before other similar tasks (§04).

09 · Cross-browser

The production wrapper (and the honest one-liner)

Safari hasn't shipped the Scheduler API (as of Aug 2026), so production code needs a fallback ladder. The nuance most posts skip: await globalThis.scheduler?.yield?.() on Safari awaits undefined — a microtask — which never returns to the event loop and never lets paint happen. That's acceptable only when "yield if prioritized, else keep going" is the policy you actually want.

yieldToMain() — the version to ship

function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();        // Chrome/Edge 129+, FF 142+
  return new Promise(r => setTimeout(r, 0));                  // Safari: real task boundary,
}                                                                  // …but continuation goes to back of queue

// The "yield only if prioritized" one-liner (microtask on Safari — NO event-loop yield):
await globalThis.scheduler?.yield?.();
Polyfill: scheduler-polyfill (npm) emulates postTask + yield on top of MessageChannel/timeouts — behavior parity for ordering, but no true priority inheritance for continuations. Types for TS: @types/wicg-task-scheduling.
10 · Lab F

Deadline batching: don't pay yield overhead per job

yield() is cheap but not free — yielding after every 1ms job wastes more time in scheduling than in work. The web.dev pattern: keep working until 50ms since the last yield, then yield once. Run 140 jobs × ~7ms (~1s of work) and drag the deadline — watch task count, yield count, and worst task length trade off.

—
async function runJobs(jobs, deadline = 50) {
  let lastYield = performance.now();
  for (const job of jobs) {
    job();
    if (performance.now() - lastYield > deadline) {   // only yield when we've earned it
      await yieldToMain();
      lastYield = performance.now();
    }
  }
}
