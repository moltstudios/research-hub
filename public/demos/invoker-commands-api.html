The Problem

The Boilerplate We Wrote a Thousand Times

Open a dialog. Close a popover. Toggle a menu. Every single one required the same JavaScript ceremony: find the button, find the target, add a listener. Repeat for every interactive pair on the page.

// The old way — 1,000 repetitions across every codebase const btn = document.querySelector('#open-btn'); const dlg = document.querySelector('#my-dialog'); btn.addEventListener('click', () => { dlg.showModal(); });

The problem isn't just verbosity — it's the loading gap. Buttons relying on JS listeners are inert until the script downloads, parses, and executes. Users click nothing-happens buttons during that window.

The Solution

Two HTML Attributes. Zero JavaScript.

commandfor points to the element to control (like popovertarget). command says what to do. The browser handles the wiring.

<!-- Before: 4 lines of JS --> <button id="open-btn">Open</button> <script> document.querySelector('#open-btn').addEventListener('click', ...) </script> <!-- After: 2 HTML attributes --> <button type="button" commandfor="my-dialog" command="show-modal"> Open Settings </button> <dialog id="my-dialog"> <button type="button" commandfor="my-dialog" command="close">Done</button> </dialog>

Custom Commands

Extend with --dashed-ident Commands

Custom commands start with -- (same convention as CSS custom properties). The target element receives a CommandEvent that you handle with a single listener.

🚁
OpenDrones Mission Control
// Custom commands — the -- prefix is the namespace <button commandfor="my-img" command="--rotate-left">Rotate</button> const img = document.getElementById('my-img'); img.addEventListener('command', (e) => { if (e.command === '--rotate-left') img.style.rotate = '-90deg'; if (e.command === '--rotate-right') img.style.rotate = '90deg'; // e.source → the button that triggered it // e.command → the dashed-ident string }); // Key detail: handler is on the TARGET, not the button. // Multiple buttons can trigger the same target without coordination.

Progressive Enhancement

The Best Part: HTML Works Either Way

Browsers that don't understand commandfor simply ignore it. The <dialog> and popover elements still work normally. Your fallback JS only runs in browsers without support.

// The HTML is the same for ALL browsers: <button id="open" commandfor="dlg" command="show-modal">Open</button> <dialog id="dlg">...</dialog> // Fallback — ONLY runs if Invoker Commands is unsupported: if (!HTMLButtonElement.prototype.hasOwnProperty('commandForElement')) { document.getElementById('open').addEventListener('click', () => { document.getElementById('dlg').showModal(); }); } // Benefits of the declarative approach: // 1. Interactive BEFORE JS downloads/parses — zero loading gap // 2. Accessible relationship: browser knows button↔target semantically // 3. Works without JS entirely (with graceful degradation) // 4. Less code to ship, parse, execute, and maintain

Recap

Why Invoker Commands Matters

🎯 The Core Wins

  • Zero loading gap — buttons work before JS downloads. The browser handles the wiring.
  • Less JavaScript — every addEventListener('click', () => dialog.showModal()) is deleted.
  • Accessibility built-in — browser knows the button↔target relationship, manages aria-expanded and focus.
  • Progressive enhancement — unsupported browsers fall through to normal JS listeners. HTML is valid either way.
  • Extensible — --dashed-ident custom commands give component libraries a consistent API surface.
  • Composable — pairs with Popover API, Anchor Positioning, :state(), View Transitions, Web Components.
  • Built-in command="close" sets returnValue — the dialog's return value is the button's value attribute. Zero-JS confirm/cancel flows.
✅ Use Invoker Commands when
Opening/closing popovers or dialogs, building menus, tooltips, settings panels, filter UIs, or any button-triggered show/hide interaction.
⚠️ Keep JS when
You need complex state machines, conditional logic before showing, animation orchestration, or the target element isn't a popover/dialog.
